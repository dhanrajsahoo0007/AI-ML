Agent interviews test whether you can build systems where a model takes actions, safely and reliably. Expect to explain the agent loop, design tools and permissions, handle memory and failures, and above all show how you would evaluate an agent.

Related deep-dives: [Harness Engineering](/ai-system-design/genai-system-design/harness-engineering) · [Agentic AI Evaluation](/ai-system-design/genai-system-design/agentic-ai-evaluation) · [Prompt Engineering (ReAct)](/ai-system-design/genai-system-design/prompt-engineering-types)

<InterviewQuestions>
  <InterviewQuestion question="What is an AI agent, and how is it different from a chatbot?" category="Fundamentals" level="Junior">
    An agent is an LLM-driven system that pursues a goal over multiple steps by deciding which actions to take, calling tools, observing results and adjusting. A chatbot mostly responds to messages. The defining features of an agent are autonomy over the sequence of steps and the ability to act on external systems.
  </InterviewQuestion>
  <InterviewQuestion question="Describe the basic agent loop." category="Fundamentals" level="Junior">
    The model receives the goal and context, reasons about the next step, either calls a tool or produces a final answer, and if it called a tool, the result is added to the context and the loop repeats. The harness enforces stopping rules such as a step limit, a budget or a success condition.
  </InterviewQuestion>
  <InterviewQuestion question="Workflow vs agent: when should you not use an agent?" category="Design" level="Mid">
    If the steps are known in advance, a fixed workflow of LLM calls and code is cheaper, faster, more predictable and easier to test. Agents are worth their cost and risk when the path depends on intermediate results and cannot be scripted, such as open-ended research or debugging. Many good systems are mostly workflows with an agentic step where needed.
  </InterviewQuestion>
  <InterviewQuestion question="Explain ReAct and plan-and-execute patterns." category="Design" level="Mid">
    ReAct interleaves reasoning, an action and an observation at every step, adapting continuously. Plan-and-execute first produces a full plan, then executes the steps, possibly with a cheaper model, and re-plans when something fails. ReAct is flexible for exploratory tasks; plan-and-execute is more efficient and easier to monitor for longer structured tasks.
  </InterviewQuestion>
  <InterviewQuestion question="How do you prevent the context from growing without bound in long agent runs?" category="Memory" level="Senior">
    Summarize or compress older steps, keep only essential tool outputs, store large artifacts outside the context and pass references, and retrieve details when needed. Sub-agents can handle subtasks in their own context and return short results. Track tokens per step to catch growth early.
  </InterviewQuestion>
  <InterviewQuestion question="When would you use a multi-agent system?" category="Design" level="Senior">
    When a task splits naturally into parts that benefit from separate contexts, tools or instructions, such as parallel research on several sub-questions, or a writer and reviewer pair. Multi-agent systems add coordination overhead, cost and new failure modes, so a single well-tooled agent should be the default until evaluation shows a clear benefit.
  </InterviewQuestion>
  <InterviewQuestion question="How do you make agents reliable?" category="Reliability" level="Mid">
    Give them focused context and good tools, validate every tool call, verify results with tests or checks and feed errors back, set step and cost budgets, add human approval for risky actions, and keep detailed traces. Then measure success on an evaluation suite and iterate on the failures.
  </InterviewQuestion>
  <InterviewQuestion question="What are the main failure modes of agents?" category="Reliability" level="Mid">
    Looping or repeating actions, choosing the wrong tool or arguments, losing track of the goal in long contexts, stopping too early or never stopping, hallucinating tool results, being hijacked by injected instructions in tool outputs, and taking harmful actions. Each maps to a harness control: budgets, validation, summaries, stop criteria, sandboxing and permissions.
  </InterviewQuestion>
  <InterviewQuestion question="How do you secure an agent that can take actions?" category="Safety" level="Senior">
    Apply least privilege with scoped, short-lived credentials, allow-list actions, sandbox code execution, require human confirmation for irreversible or external actions, treat all tool outputs and retrieved content as untrusted, filter for data exfiltration, and log every action for audit. Test with prompt-injection and abuse scenarios.
  </InterviewQuestion>
  <InterviewQuestion question="What is indirect prompt injection, and why is it dangerous for agents?" category="Safety" level="Senior">
    It is when instructions are hidden in content the agent reads, such as a web page, email or document, rather than typed by the user. Because agents can act, a successful injection can cause data leaks or unwanted actions on the user's behalf. Defenses include isolating untrusted content, restricting what actions can follow from it, and requiring confirmation.
  </InterviewQuestion>
  <InterviewQuestion question="How do you evaluate an agent?" category="Evaluation" level="Mid">
    Use a versioned set of realistic tasks run in a sandbox, graded mainly by checking the final state or outcome, plus trajectory checks for tool use and policy, and calibrated LLM judges for open-ended parts. Run each task several times, report success and consistency, and track cost, latency and safety. Production failures become new test cases.
  </InterviewQuestion>
  <InterviewQuestion question="What metrics would you track for an agent in production?" category="Evaluation" level="Mid">
    Task completion rate, escalation to humans, user feedback, tool error rates, steps and tokens per task, cost per successful task, latency, guardrail triggers and sampled human review scores, broken down by task type and version.
  </InterviewQuestion>
  <InterviewQuestion question="How would you design a research agent that writes reports from web sources?" category="Design" level="Senior">
    Plan sub-questions, search and fetch sources in parallel, extract relevant passages with citations, deduplicate and check source quality, then synthesize a report where every claim cites a source, followed by a verification pass for unsupported claims. Bound the run with time and cost budgets, and evaluate on questions with known answers and human ratings of report quality.
  </InterviewQuestion>
  <InterviewQuestion question="How do coding agents use feedback to improve their output?" category="Design" level="Mid">
    They run code, tests, linters and type checkers in a sandbox after making changes and feed the errors back into the next step. Tests act as an objective signal, so the agent can iterate until they pass. This feedback loop is the main reason coding agents are more reliable than single-shot code generation.
  </InterviewQuestion>
  <InterviewQuestion question="What is the difference between agent memory and RAG?" category="Memory" level="Mid">
    RAG retrieves from a curated, mostly static knowledge base to answer questions. Agent memory is written by the agent itself from its interactions, such as user preferences or results of past tasks, and must handle updates, conflicts and forgetting. Both use retrieval, but memory adds a write path and correctness concerns.
  </InterviewQuestion>
  <InterviewQuestion question="How do you control the cost of agents?" category="Reliability" level="Senior">
    Set per-task budgets for steps, tokens and time, use smaller models for routine steps and larger ones for planning or hard reasoning, keep contexts compact, cache tool results, avoid unnecessary multi-agent overhead, and stop early when success criteria are met. Track cost per successful task, since failed runs also cost money.
  </InterviewQuestion>
  <InterviewQuestion question="Which agent frameworks do you know, and when would you avoid one?" category="Tools" level="Mid">
    Common options include LangGraph for graph-based stateful workflows, provider agent SDKs, and multi-agent frameworks such as CrewAI or AutoGen. Frameworks speed up prototyping, tracing and state handling. Avoid heavy abstractions when they hide prompts and control flow you need to debug or when a simple loop in your own code is enough.
  </InterviewQuestion>
  <InterviewQuestion question="What are agentic benchmarks like SWE-bench and tau-bench used for?" category="Evaluation" level="Senior">
    SWE-bench measures whether coding agents can resolve real GitHub issues, graded by the repository's tests. tau-bench measures tool-using customer-service agents against a simulated user, checking final database state and consistency over repeated trials. They help compare models and approaches, but your own task-specific evaluation should decide launches.
  </InterviewQuestion>
  <InterviewQuestion question="How do you decide how much autonomy to give an agent?" category="Design" level="Mid">
    Match autonomy to the cost of mistakes and how verifiable the outcome is. Start with read-only tools and human approval, measure success and error types, then automate the action classes that prove reliable. Irreversible, external or expensive actions should keep a checkpoint.
  </InterviewQuestion>
  <InterviewQuestion question="What is a planner-executor split and why use different models for each?" category="Design" level="Senior">
    A capable model writes the plan and handles re-planning, while cheaper, faster models execute routine steps such as extraction or simple tool calls. This cuts cost and latency while keeping quality on the hard decisions. The interface between them must be explicit, such as a structured list of steps with success criteria.
  </InterviewQuestion>
  <InterviewQuestion question="How do you test an agent's tools in isolation?" category="Evaluation" level="Junior">
    Write unit tests for each tool's behavior and error handling like any other code, then test the model's use of each tool with a set of prompts and expected calls, measuring tool-selection and argument accuracy. Problems found here are cheaper to fix than in end-to-end runs.
  </InterviewQuestion>
  <InterviewQuestion question="What is reflection or self-critique in agents, and does it help?" category="Reliability" level="Mid">
    The agent reviews its own output or trajectory, identifies mistakes and revises. It helps most when there is an external signal to reflect on, such as test failures or tool errors; pure self-critique without new information gives smaller and less reliable gains and costs extra calls.
  </InterviewQuestion>
  <InterviewQuestion question="How would you give an agent access to a company database safely?" category="Safety" level="Senior">
    Expose a narrow tool rather than raw SQL where possible, such as parameterized queries or views for specific questions. If text-to-SQL is needed, use a read-only role limited to approved tables, validate and limit generated queries, mask sensitive columns, and log every query. Writes should go through specific, permission-checked API actions.
  </InterviewQuestion>
  <InterviewQuestion question="How do you observe and debug agents in production?" category="Reliability" level="Mid">
    Trace every run end to end: prompts, model outputs, tool calls with arguments and results, latency and cost per step, and the final outcome. Group traces by task type and failure category, replay failing traces against new versions, and alert on spikes in errors, loops or cost.
  </InterviewQuestion>
