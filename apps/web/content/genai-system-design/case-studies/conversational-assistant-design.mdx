Design an assistant every Brightpost employee can ask, from a support lead checking a refund rule to a warehouse shift lead raising a ticket for a broken scanner.
The company's data sits in about 10 million documents across nine systems, each with its own permissions and rate limits, changing all day.
The hard parts are never showing a document to someone who cannot open it and keeping that true as permissions change.
It must also act as the person who asked without anything leaving the company, and keep 106 tools from drowning the model.

- Interviewers use this question to see whether you put the permission check before the model reads anything, can give the staleness of a permission as a number per source, and keep writes behind code and the user's own rights.

## Overview

- **Permissions travel with the data, keyed on immutable ids.** Connectors map every source account to its Entra object id through SCIM or single sign-on, never by email; chunks carry principal ids, and the asker's principals are resolved per request and filtered **inside** both the keyword and vector searches.
- **Never looser than the source's own search, and stale by a number per path.** Org-wide links count only for redeemers and label-encrypted files are not indexed; events apply a revocation in ≈ 35 s (illustrative), polls bound it at 10 or 60 min while they succeed, and a path that cannot prove its bound leaves the results after 30 or 150 min.
- **A router picks the path:** cited answer (65%), lookup (15%), internal write (8%), agent (5%), other (7%). Lookups and writes load one tool bundle (10,553 tokens instead of 67,086 for all 106 tools); only the agent uses tool search; Slack and mail are searched live, never copied (≈ 735 ms).
- **Everything runs as the user; writes stay inside; memory is explicit.** Delegated tokens for reads and writes, a code-rendered card before every write, no tool whose effect can reach an outsider, and memory made only of what the user chose to save.

## API design

| Call | Who calls it | When |
| --- | --- | --- |
| `POST /v1/conversations/{id}/turns` | Web app, Slack app, Teams app, warehouse handhelds | Every message; identity from the session only; the response is a Server-Sent Events (SSE) stream |
| SSE events `status`, `sources`, `token`, `card`, `done`, `error` | Gateway → client | `status` at ≈ 320 ms; `sources` at ≈ 510 ms; `card` for a write |
| `POST /v1/cards/{card_id}/confirm` and `/cancel` | Client | Card states `pending → executing → done / unknown / failed`; one execution per card; `POST /v1/actions/{action_id}/withdraw` removes a T1 item within 10 min (notifications already sent stay) |
| `GET /v1/memory`, `PATCH` and `DELETE /v1/memory/{id}`, `POST /v1/memory/{candidate_id}/save` | Client | Memory is saved only by the user |
| `POST /v1/connections/{connector}/authorize` | Client | First use of a non-Microsoft source or a write scope: the source's consent page; tokens land in the broker, never in the client or the model |
| `POST /v1/turns/{id}/feedback` | Client | Thumbs, "wrong source", "I can't open this source" (a mapping or staleness signal) |
| Admin: connectors, exclusions and holds, audit | Admins and security (audited, need-to-know) | Budget used, last reconcile, bound and drop-out state per connector; "which grant admitted this document for this user at this time" |
| Internal `retrieve(principal_set_id, query)`, `check_live(doc_ids, user)`, `tool_call(user, tool, args)` | Orchestrator, agent | The only paths to the index and the systems |

The turn endpoint streams a status, the permitted sources, then the answer.

```http
POST /v1/conversations/c_2b7/turns
Authorization: Bearer <Entra session>
Idempotency-Key: t_91d4
Accept: text/event-stream
{ "text": "Can I refund order 4471? The kettle arrived cracked and it was £42.", "client": "teams" }

200 OK
event: status   data: {"text": "Searching your sources…"}
event: sources  data: {"sources": [{"n": 1, "title": "Damaged on arrival", "system": "confluence", "label": "General"}, …]}
event: token    data: {"text": "Yes, but it needs an approver: refunds over £30 "}
event: done     data: {"turn_id": "t_91d4", "unsupported_sentences": 0, "omitted_sources": []}
```

Every tool declares its tier, audience, scopes and how a retry is deduplicated; this is one of 106.

```json
{ "name": "jira_create_issue",
  "description": "Create an issue in an internal Jira project the user can create issues in.",
  "input_schema": { "type": "object", "required": ["project", "summary"],
    "properties": { "project": {"type": "string"}, "summary": {"type": "string", "maxLength": 200},
      "description": {"type": "string", "maxLength": 4000}, "priority": {"enum": ["Low", "Medium", "High"]} } },
  "x-tier": "T1",
  "x-audience": "project members; refused if the project has portal customers, contractors or anonymous access",
  "x-scopes": ["read:jira-work", "write:jira-work"],
  "x-dedupe": "entity property card_id; after a timeout wait 10 s, then read the user's recent issues by REST before any retry" }
```

| Code | Meaning | What happens |
| --- | --- | --- |
| 401 `consent_needed` | No token for this source | A card: "Connect your helpdesk to include cases"; the answer goes on without that source and says so |
| 403 `insufficient_scope` | First write | Step-up consent for the write scope only |
| 403 `not_entitled` | The source refused | Shown as is; never retried with another identity |
| 409 `card_expired` / `card_executed` | Stale or double confirm | No second execution |
| 422 `audience_blocked` | The target can reach an outsider (guest, shared channel, portal, external address) | The card explains; no override |
| 429 `source_throttled` | Source budget hit | Lookups wait once (`Retry-After`); answers omit that source and say so |
| 503 `connector_unavailable` | Connector past its drop-out age | Its results are excluded: "Jira results are temporarily unavailable" |

- **Identity from the session only:** the gateway checks account status in the principal store on every turn; the request body never names a user.
- **Rendering, cards and egress:** plain text with citation chips, writes only through code-rendered cards (payload, audience, highest label, provenance), and audiences resolved at execution; the rules are in Safety and guardrails.

Each chunk carries principal ids, not users; the ACL store keeps the truth that patches it.

```text
chunk:  { chunk_id: "sp_88a1:c4", doc_id, source: "sharepoint", text (≈ 400 tokens), vec_int8: int8[1024],
          bm25_en | bm25_pl | bm25_ro, principals: ["g:entra:hr-partners", "s:sp:site-412:members"],
          deny: [], acl_version: 37, label_id: "confidential", modified, author_id }

principal_set:{hash} -> { user_id, principals: [140 ids], valid_from, valid_to }
user:{id}:set        -> current principal_set hash (Redis; invalidated on membership events)
```

```sql
CREATE TABLE doc_acl (
  doc_id text PRIMARY KEY, grants jsonb, deny text[],   -- grants: [{"principal": "g:entra:hr-partners", "kind": "read"}, …]
  inherits_from text,                                   -- the site, space or folder this ACL derives from
  acl_version bigint,                                   -- raised on every change; every retrieval records it
  dirty_since timestamptz, live_check boolean,          -- dirty 1 s after a notification; helpdesk, Confidential, restricted
  deleted_at timestamptz                                -- deny-all at once; out of the index within the revocation bound
);
```

### Identity mapping across the nine systems

- **The rule:** every grant and every user is joined on an immutable id issued or provisioned by Entra, never on an email string, because emails change, are user-set in GitHub and are reused when a leaver's address goes to a new hire.
- **Fail closed:** an unmapped grant is dropped; an unmapped user gets no principals from that source.

| Source | Join key to Entra | Source-local principals the connector expands | Guests and public grants |
| --- | --- | --- | --- |
| SharePoint and OneDrive | Entra object id (native) | Site groups (members reconciled with the site poll: P1 every 10 min, others hourly); sharing-link groups (each link's redeemers) | Guests are not askers; "Everyone except external users" maps to all mapped employees only where the site is in search; org-wide links → redeemers only |
| Confluence and Jira | Atlassian account linked by SCIM (externalId = object id) | SCIM-synced groups ride the Entra path; Confluence-local groups and Jira project roles reconciled hourly; page restrictions and issue-security levels live-checked | "Anyone logged in" → mapped employees with an account; portal customers ignored |

| GitHub | Enterprise Managed Users provisioned from Entra | Teams, repository collaborators | Outside collaborators ignored |
| Slack (writes only; reads are live) | SCIM user, externalId = object id, checked at consent | Channels, for egress checks | Guests and shared-channel members make a channel external |
| ERP, HR, WMS | HR employee id, which Entra carries as `employeeId` | Cost centres, HR roles, warehouse roles and sites | Contractors without an HR record get no tools |

- **Shared handhelds:** Entra shared-device mode, a sign-in per shift, sign-out at shift end and a 15-minute idle lock, so a session never outlives the person.
- **Non-user identities:** the SharePoint crawler holds `Sites.Selected`, granted site by site from an allow list (payroll and legal never), on ingestion workers in a separate segment and never on the request path; other crawlers are read-only installs. There is no decryption identity at all.
- **The two exceptions:** the WMS service account (read and ticket-create only) runs behind our check of the user's warehouse role and site; the token broker mints short-lived tokens only for the session's own user, sender-constrained where the source supports it, and revokes them on deprovisioning.
- **Access patterns:** principal set by user (Redis, then PostgreSQL); filtered top-100 per shard per query; ACL re-check by `doc_id` for the ≈ 160 candidates; patches by `doc_id`; audit by principal set id and validity interval.
- **The source's audit shows the user and our app's client id;** we have not verified that any of the nine accepts a token-exchange `act` claim, so our audit is the record that the assistant acted.

The baseline: an employee signs in, types, and one model streams a reply.

### Step 2: Answer from an index of company documents (F1, N1, N5)

<AnimatedDiagram spec="animated/enterprise-assistant/architecture" step={2} caption="Step 2: connectors fill a 32.1M-chunk index from five sources and rankers cut 160 candidates to 8. The search is marked unfiltered: the crawler read everything." />

- **Adds:** connectors, the search index, the retrieval service, the rankers.
- **Flow:**
  1. Connectors read SharePoint, Confluence, Jira, the helpdesk and GitHub: 6.0M documents → 32.1M chunks of 400 tokens.
  2. A question runs a keyword search (BM25) and a vector search; the lists merge by reciprocal rank fusion (RRF: each chunk scores the sum of 1 ÷ (k + rank) across lists) into 160 unique chunks.
  3. A gradient-boosted personal ranker keeps 50 (team-level views, recency, author in the asker's team); a cross-encoder keeps 8, at most 3 a document.
  4. The model answers from the 8 with `[n]` citations, or says "not found in your sources".
- **Why this and not that:** ground answers in documents (P2), and run cheap rankers before the expensive one (P4). Keyword search stays because SKUs, PO numbers and error codes defeat vectors.
- **The gap:** the crawler reads with application rights, so the index holds everything and anyone can retrieve the pay bands.

### Step 3: Map identities; filter inside the search; never looser than the source (F2, N2)

<AnimatedDiagram spec="animated/enterprise-assistant/architecture" step={3} caption="Step 3: connectors map every account to its Entra id and write grants to the ACL store; the asker’s principal set now runs inside the search, and Slack and mail are searched live as the user." />

- **Adds:** the ACL and principal store, identity mapping in the connectors, live search for Slack and mail.
- **Flow:**
  1. Connectors join every source account to its Entra object id (SCIM or SSO) and write each document's grants as principal ids on its chunks.
  2. The gateway resolves the session's principal set: ≈ 120 ids on average (groups, sites, projects), cached in Redis. Unlike the concept page's single identity provider, memberships here come from nine systems and are synced, so they have a lag of their own (N4).
  3. The set runs as a filter **inside** both searches, so only permitted chunks are ever candidates; the ACL store re-checks the survivors in 5 ms.
  4. Org-wide links count only for their redeemers, as in SharePoint's own search (Microsoft's sharing documentation, as quoted by Office365ITPros in 2024; unredeemed-link canaries test it); sites hidden from the source's search and label-encrypted files are excluded at crawl time.
  5. Slack and mail are searched live with the user's own token, so the source applies its permissions (for Slack implied by the user-token scopes; private-channel canaries test it).
- **Why this and not that:** run as the user (P11) and enforce rules in code, not in the prompt (P10). An instruction such as "do not reveal confidential files" is not access control.
- **The gap:** permissions and deletes change all day, faster than a crawl.

### Step 4: Keep permissions fresh within each source's budget (F2, N4, N10)

<AnimatedDiagram spec="animated/enterprise-assistant/architecture" step={4} caption="Step 4: a permission-sync pipeline applies events in about 35 s and budgeted polls bound the rest; the ACL store patches the index in place." />

- **Adds:** permission sync (events, budgeted polls, reconciles, drop-out).
- **Flow:**
  1. A source notification (a revoked share, a delete, a raised label) marks the document dirty 1 s after it lands, so every answer live-checks it until the patch does.
  2. The connector fetches the effective ACL, writes the ACL store and patches `principals`, `deny` and `acl_version` in place: ≈ 35 s at p50, almost all of it the source's notification delay (30 s, illustrative).
  3. If an event is lost, polls sized to each source's rate limit find it: 300 sensitive (P1) SharePoint sites every 10 min, everything else hourly, using 35% of the SharePoint day.
  4. A site change is derived in the ACL store from one source call, not 50,000; deletes and DLP tombstones ride the same priority topic.
  5. Helpdesk cases, Confidential files, restricted pages and dirty documents are checked live as the user; a connector past its drop-out age leaves the results.
- **Why this and not that:** evaluate continuously and degrade gracefully (P16): canaries measure the lag and drop-out enforces the bound. The revocation takes effect once the ACL store is written, since every retrieval re-checks it; the index patch restores full result pages.
- **The gap:** it can read documents but not records, and it cannot act.

### Step 5: Route; look up and act as the user, inside the company (F3, F4, N7)

<AnimatedDiagram spec="animated/enterprise-assistant/architecture" step={5} caption="Step 5: a router picks the path and one tool bundle; the tool gateway checks audience, turns writes into cards and calls each system with the user’s own delegated token." />

- **Adds:** the router, the tool gateway, the token broker, connector tools (106 tools on MCP servers).
- **Flow:**
  1. A small router labels the turn (answer, lookup, write, agent, other), picks one connector's bundle for the user's entitlement class, and rewrites follow-ups, in ≈ 300 ms.
  2. The model calls a tool; the gateway checks the schema, the user's entitlement, the tier and the **audience** (who can see the effect).
  3. The token broker mints a short-lived delegated token for this user only; the source applies its own permissions.
  4. T1 and T2 writes become a card rendered by code; on confirm they execute once, deduplicated by the card id.
- **Why this and not that:** route by difficulty (P3), bound the blast radius (P12), one cached prefix per bundle (P7); the tiers are drawn in the deep dive.
- **The gap:** some tasks need several systems in an order nobody wrote down.

### Step 6: An agent for multi-step tasks, with tool search (F5)

<AnimatedDiagram spec="animated/enterprise-assistant/architecture" step={6} caption="Step 6: an agent loop, capped at 10 calls and 60 s, reaches tools only through the tool gateway, which also runs tool search over the user’s entitled tools." />

- **Adds:** the agent loop, tool search.
- **Flow:**
  1. The agent starts from a 3,986-token prefix: the stable 3,486 plus a 500-token `tool_search` tool.
  2. `tool_search` returns definitions only from the user's entitled tools (≈ 1,800 tokens a search).
  3. Read tools run as the user; any write is proposed as a card, as in Step 5.
  4. Caps: 10 calls, 60,000 tokens of context, 0.15 USD and 60 s; a `status` event each step.
- **Why this and not that:** manage context deliberately (P8) and cap in tokens (P6). Only 5% of turns need it, so the router keeps the other 95% on fixed workflows.
- **The gap:** it forgets that Tom works nights at Leeds, and he says so every time.

### Step 7: Memory the user can see and correct (F6, N9)

<AnimatedDiagram spec="animated/enterprise-assistant/architecture" step={7} caption="Step 7: a memory store gives at most 5 user-saved items to a prompt; the model can only propose a memory." />

- **Adds:** the memory store.
- **Flow:**
  1. Once a conversation, a small model proposes candidates from the user's own messages.
  2. Code accepts a candidate only if its text is a span of the user's own typing (pasted and quoted blocks are marked by the client and excluded), then shows it as a chip.
  3. The user saves it; at most 5 relevant items (200 tokens) go into a prompt.
  4. Edit, delete and "forget that" (confirmed in the UI) take effect next turn and are audited.
- **Why this and not that:** keep sensitive data inside a boundary (P17): memory holds only what the user said and saved, never text from documents another person could lose access to.
- **The gap:** documents and emails carry instructions, and nobody yet knows whether answers or permissions hold.

### Step 8: Guard, control egress and evaluate (F7, N2, N7)

<AnimatedDiagram spec="animated/enterprise-assistant/architecture" step={8} caption="Step 8: guards screen injected instructions and egress; every turn is audited with its acl_version, and evaluation runs the permission suite and canaries before each release." />

- **Adds:** guards (injection screen, rendering and egress rules), evaluation, audit and traces.
- **Flow:**
  1. Provenance labels mark all email and customer-written text as external, whatever the sender's domain.
  2. External spans are datamarked (spotlighting) and a multilingual injection screen reads every chunk and live result on use (25 ms).
  3. Rendering strips links and images; egress rules resolve each write's audience at execution.
  4. The audit keeps the principal set, the chunk ids with `acl_version`, live-check results, tool calls and card states for every turn.
  5. The permission suite, canaries, drift audit, gold sets, injection families and the action simulator gate each release.
- **Why this and not that:** treat retrieved content as untrusted (P13), carry provenance (P14), and keep a human escape hatch (P15): "I can't open this source" reports become suite cases.
- **The gap:** none; the gate decides each release (Evaluation and release gates).

## Component choices and why

### Binding: permissions in the index for indexed sources, live search for Slack and mail, live checks for the sensitive few

- **Choice:** early binding (ACLs copied onto chunks) for the five indexed sources; federated live search as the user for Slack and mail; a live check as the user for helpdesk cases, Confidential files, restricted Confluence pages, Jira issues with security levels and dirty documents.
- **Why:** a filter inside the search returns a full page of permitted results with no source calls (G3). Live search for Slack and mail means no lag, no backfill or reconcile, no copy of DMs and mailboxes to keep in sync, and the main injection channels screened on use (G2, G9); Slack also recommends its Real-time Search API for AI apps (as of November 2026).
- **Why not late binding everywhere:** ≈ 50 checks a turn × 0.49 answers a second at peak ≈ 25 source calls a second against throttled APIs, and short result pages whenever checks fail (G5).
- **Why not early binding alone:** the window would be the source's notification delay, which Graph states can reach 6 hours (as of November 2026) (N4).
- **Why not post-filtering the top results:** a warehouse user who sees ≈ 6% of chunks would get too few results, and no over-fetch size is safe (G1).

### ACL shape: principal ids on chunks, memberships per request, versioned principal sets

- **Choice:** chunks hold group, site and project ids; memberships live in the principal store and are resolved per request into a content-addressed principal set with a validity interval.
- **Why:** a joiner is one row, not 1.07M chunk rewrites (G5); the set id in each audit row answers "which grant admitted this at 10:03" (G8).
- **Why not a join at query time:** a round trip per candidate, 160 a turn, inside a 40 ms search.
- **Why not decrypt label-encrypted files with a super-user identity:** one credential that reads every protected file, and the source's log does not show who used it; they are excluded instead (G9).

### Permission sync: events first, polls sized to each budget, drop-out

- **Choice:** webhooks on all 8,000 drives; a priority topic for revocations, membership changes, deletes, label changes and widenings; P1 polls every 10 min and P2 hourly; source-local groups reconciled on the same cadence; a connector that cannot prove its bound leaves the results.
- **Why:** ≈ 843,900 RU a day is 35% of the SharePoint budget, leaving 650,000 (27%) for a 410 re-enumeration of every drive (624,000 RU ≈ 7 h); Atlassian's reconcile uses 32% of its quota (G5, G6, N4).
- **Why not a 10-minute poll of everything:** at 1 RU a delta call, 8,000 drives × 144 = 1.15M RU a day (48%), 74% with the other lines; that leaves ≈ 632,000 RU, barely the 624,000 a re-enumeration needs, and ≈ 1,228 RU a minute on average plus a 1,500-RU-a-minute re-enumeration breaks the 2,500 cap.
- **A deliberate departure:** Microsoft's scanning guidance runs a safety-net delta at most daily (as of November 2026); this design polls P2 drives 24× and P1 drives 144× a day on purpose, stays inside the RU budget, and treats a 429 as a missed cycle (the bound doubles, then drop-out).
- **Why not require every group to be Entra-synced:** SharePoint site groups and Jira roles cannot be, so the reconcile is needed anyway.
- **Why not nightly crawls:** a day of leaks after every revocation.

### Search engine: one hybrid engine with filterable HNSW and in-place updates

- **Choice:** one engine for keyword and vector search, with the ACL field indexed before the HNSW graph is built, an exact scan below 50,000 permitted chunks, and attribute updates that do not touch the vector.
- **Why:** both searches take the same filter (G2); 450,000 patches in 90 s need ≥ 5,000 in-place updates a second (G5), which a load test must confirm. The rate buys freshness and full result pages: a revocation is already enforced by the ACL-store re-check.
- **Why not float32 vectors in memory:** 131.5 GB a replica instead of 32.9; float32 stays on SSD for rescoring.

### Ranking: RRF, a personal ranker, a cross-encoder on 50

- **Choice:** RRF → gradient-boosted personal ranker (160 → 50 in 10 ms) → multilingual cross-encoder (50 → 8 in 120 ms), ≤ 3 chunks a document.
- **Why:** signals from the people-and-activity store (recency, team views, author in the asker's team, department affinity) lift the right procedure for each team (G1); hand-tuned weights until ≈ 50,000 labelled citation clicks exist, then trained with position-bias correction.
- **Why not dense only:** SKUs, PO numbers and error codes need keyword matching.
- **Why not an LLM reranker:** a mid-size call on every turn, ≈ 400 ms (illustrative), against 120 ms.

### Router and workflows: a small model with a JSON schema, fixed workflows for known shapes

- **Choice:** one small-model call labels the path, picks the bundle and any live search, and rewrites follow-ups (≈ 300 ms, 0.000058 USD); first turns start retrieval on the raw message in parallel.
- **Why:** 95% of turns have a known shape (G4, P3); the sensitive path has ≈ 215 ms of headroom, and a 600 ms router would put it at ≈ 1,585 ms, over the 1,500 target (G3).
- **Why not one agent for everything:** six model calls where one suffices; a typed write plus a card reaches the card in ≈ 2.45 s and is testable on the simulator, while an agent's path is chosen at run time and harder to bound (G10, N7).
- **Later, Agent2Agent (A2A):** calling a system's own agent is accepted for read questions where it applies rules we would otherwise copy (HR leave); its output counts as external content and any write it proposes returns as our card.

### Tools: entitlement-class bundles for lookups and writes, tool search in the agent

- **Choice:** 31 cached bundle prefixes (entitlement classes × connectors); tool search over entitled tools only in the agent; definitions pinned by hash and re-tested on change.
- **Why:** choice degrades past 30–50 tools (vendor guidance, as of November 2026), a warehouse picker never sees an ERP tool, and shared prefixes keep caches warm (G7); within a class the gateway refuses what the user's own rights do not allow.
- **Why not all 106 tools:** cached they cost only 0.0067 USD a call, so cost is not the reason; tool choice past 30–50 tools, attention spread over a 67,086-token prefix, and per-user tool lists that break the shared cache are.
- **Why not tool search everywhere:** an extra model step on every lookup, ≈ 600 ms (G3); lookups and writes are 23% of turns and have a known shape.
- **Why not code execution over MCP:** a sandbox holding private data with an outbound channel is the "lethal trifecta" (private data, untrusted content, a way out).

The figure puts the three prefixes on one scale.

<AnimatedDiagram spec="animated/enterprise-assistant/tool-loading" stepper caption="Cached, loading every tool is cheap; the reason not to is choosing among 106 tools, so routed turns get one bundle and only the agent searches." />

- **How to read it:** bar 1 is all 106 tools (3,486 stable + 63,600 of definitions), bar 2 one bundle for lookups and writes, bar 3 the agent's search prefix plus two searches.
- **The numbers:** all 3,486 + 106 × 600 = 67,086; bundle 3,486 + 7,067 = 10,553 (84% fewer); search 3,486 + 500 + 2 × 1,800 = 7,586 (89% fewer). The vendors' own savings (85% for tool search, 98.7% for code execution) each come from one example setup, not a benchmark.

### Run as the user: delegated tokens through a broker

- **Choice:** on-behalf-of tokens for Microsoft Graph; per-user OAuth with admin pre-consent where the source allows; write scopes on the first write; Enterprise-Managed Authorization (ID-JAG) once the sources support it.
- **Why:** a delegated token cannot read beyond the user (G2, P11); tokens are audience-bound and never passed through.
- **Why not ID-JAG now:** it would remove standing refresh tokens and per-user consent, but it is an IETF draft as of November 2026.
- **The exception:** the WMS has no per-user OAuth, so it runs through a service account behind our check of the user's warehouse role and site, with its own persona suite.

### Tiers by audience, egress at execution, dedupe per tool

- **Choice:** T0 reads, T1 the user's own item, T2 named colleagues or internal channels, T3 anything that can reach an outsider (not a tool); every write resolves its audience and the target's configured automations when it runs.
- **Why:** a tool is dangerous by who can see its effect: a public case reply emails a customer, a case set to "solved" emails the requester through the helpdesk's own trigger, a message to a channel with guests leaves the company (G10, N7).
- **Why not tiers by tool name:** `post_message` is safe to a team channel and a leak to a shared one.
- **Dedupe:** a Jira entity property `card_id` read back by REST after 10 s (illustrative; Jira's search is eventually consistent per its docs, as of November 2026); mail as draft-then-send; no automatic retry where no dedupe exists.

### Models, grounding and caching

- **Choice:** one mid-size model for answers and tools; small models for routing, grounding checks and memory extraction; self-hosted embedder and cross-encoder (2 GPUs); grounding checked after streaming; no shared answer cache.
- **Why:** model cost is 1.5% of build all-in, so citation quality wins (G1, G4); permitted text stays inside our boundary for embedding and reranking (G9); the first token stays at ≈ 1.15 s and unsupported sentences are marked (G3).
- **Why not a self-hosted LLM:** at ≈ 0.76 turns a second a GPU fleet idles.
- **Why not hold each sentence until checked:** ≈ 370 ms more to the first token (illustrative: the first sentence's decode plus a check).
- **Why not a shared answer cache:** the key must include the principal set, so hits are rare and a wrong key is a leak.

### Platform pieces

- **Choice:** our own thin gateway; a request-scoped orchestrator with the card state machine in PostgreSQL; a PostgreSQL outbox (≈ 0.9 events a second); Redis for principal sets; ClickHouse for per-stage traces; our own web, Slack and Teams clients, so rendering and unfurls are ours (G8, G12).
- **Why:** the gateway's account check reads the principal store on every turn; agent runs are ≤ 60 s and writes are single steps; permissions and identity need our own code, while a connector framework handles content and paging.
- **Why not an API-management product or a durable workflow engine:** the first cannot read the principal store on every turn, and nothing runs long enough to need the second.

<AnimatedDiagram spec="animated/enterprise-assistant/context-window" stepper caption="Instructions and tool definitions come first and are identical for everyone in a class, so they are read from the cache; only the turn and the sources change." />

- **How to read it:** the top bar is the answer call (stable 3,486, turn state 870, sources 3,520); the bottom bar a lookup or write call, the same 3,486 plus one connector's 7,067 tokens of tools, then the turn.
- **No per-user value sits in the cached prefix:** the user's site, language and the date live in the changing block, so one prefix serves everyone in a class.

**The numbers:**

- Answer call: 3,486 × 0.10 + 4,390 × 2.00 + 250 × 10.00, per million = 0.0116 USD, against 0.0183 uncached: the cache saves 36%.
- The 4,390 changing tokens are plain input, since nothing reads them back; a lookup writes its 870-token turn to the 5-minute cache because its second call re-reads it. The 31 bundle prefixes sit on the 1-hour cache (≤ 964 USD a month of writes).

## Latency and cost budget

The waterfall puts the indexed answer, the live-check overlap, the live search, a lookup, a write and the agent side by side.

<AnimatedDiagram spec="animated/enterprise-assistant/latency" stepper caption="The live check runs alongside the cross-encoder, so a sensitive answer costs about 140 ms, not 260; a live Slack or mail search costs about 735 ms, which is why it has its own target." />

**The numbers:** p50 in ms; a 600 ms first token and 80 tokens a second are illustrative for a mid-size model behind an API.

- **p95 by root-sum-square of stage spreads** (edge 150, router 200, search 60, cross-encoder 40, live wait 221, first token 600, decode 781, live search 700, mail bodies 198; the rest ≤ 10): answer first token ≈ 1,799 ms (N3 ≤ 2,500), with a live check ≈ 1,975, with a live search ≈ 2,856 (≤ 3,500), both ≈ 3,020; complete ≈ 5,289 ms p95 indexed, 5,452 with a live check (N3 ≤ 7,000); ≈ 6,255 and 6,414 with a live search (≤ 7,500).
- **Stage-sum bounds** are 2,230, 2,591, 3,802 and 4,163 ms, so the live-search paths meet p95 only if tails are independent. With the router, first token and decode added linearly (one provider) every path still meets N3 except live search plus a live check (≈ 3,595 ms first token against 3,500, ≈ 7,502 complete against 7,500), which is gated on the 5,000-turn replay.
- **Live checks:** at most 4 a sensitive answer, deadline 500 ms; 1.3% of checks miss it, so 3.8% of sensitive answers lose one of their ≈ 3 chosen sensitive documents (N1 ≤ 5%); 5.0% while a drive re-enumerates. The normal fit understates right-skewed APIs, so the measured p99 replaces it after launch.
- **Lookup:** edge 20 + router 300 + first token 600 + 60-token call 750 + broker 5 + tool 300 + second first token 500 = **2,475 ms** (p95 ≈ 3,707, N3 ≤ 5,000). Write: 20 + 300 + 600 + 120 tokens 1,500 + schema, entitlement, audience and policy 30 = **2,450 ms** to the card (p95 ≈ 3,201); the confirm is a new request: 20 + 5 + write 400 + template 10 = **435 ms** (p95 ≈ 1,545).
- **Agent:** 20 + 300 + 6 × 600 + 560 tokens 7,000 + 3 tools × 300 + 2 tool searches × 30 = **11,880 ms** p50 and ≈ 14,658 p95 (N3: 15 s p50, 30 s p95); hard stop at 60 s.

<Callout tone="red" title="What breaks">
  Put a 600 ms router in front of retrieval and the live-check path reaches ≈ 1,585 ms at p50, over its 1,500 target. First turns need no rewrite, so they start retrieval on the raw message in parallel with the router; follow-ups wait for the rewrite.
</Callout>

- **Personas:** picker, shift lead, support agent, support lead, AP clerk, controller, HR partner, engineer, contractor, new joiner, leaver mid-day, mover from support to warehouse, "email reused by a new hire", "Atlassian or Slack account not linked". One failing check blocks the release, however well the others pass.

<AnimatedDiagram spec="animated/enterprise-assistant/release-gate" caption="One leak in 5,600 probes blocks the release, however good the other seven checks are: the permission suite gates at zero." />

- **How to read it:** a release candidate (a new prompt and ranker) fans out to eight checks; seven pass, and the permission suite fails on one org-linked file the persona never redeemed, so the result is Block: fix the org-link grant. The measured values drawn are illustrative.

**The numbers:**

- Zero leaks in n probes bounds the leak rate at 3 ÷ n at 95%: 3 ÷ 5,600 = 0.054% per probe **for these personas and canaries**, not a production leak rate.
- Drift: there are 6.0M × 5,000 = 30B (document, user) pairs, so a uniform sample sees almost nothing structural: a 40-member group mapped wrongly on 2,000 documents (80,000 pairs) shows up in a week of 70,000 uniform draws with probability 1 − e^(−70,000 × 80,000 ÷ 30B) ≈ 17%.
- So the sample is stratified, and a bug touching 1 in 10,000 retrieved pairs is seen within a week of 35,000 retrieval-stratum draws with probability 1 − e^(−3.5) ≈ 97% (illustrative); structural mapping bugs are caught first by the persona suite and canaries, and the drift rate bounds only aggregate drift.
- Injections: 0 of 700 bounds following at 0.43% overall but only at 3% for any one 100-case family, which is the number that matters for a new channel.
- The gold set at 85% on 1,200 questions has a ± 2.0-point interval, so the gate is a paired comparison with the last release, not a raw threshold; p95 per path is gated on a 5,000-turn replay and cost a turn within 10%.

- **Online:** thumbs; "wrong source"; "I can't open this source"; not-found rate per department and language; card confirm, cancel and withdraw rates; tool 403s; live-check drops; budget used and staleness per connector.
- **Rollout:** an oversharing scan first; then read-only answers on two sources, all sources, lookups, T1 writes, T2 writes, the agent, each behind its gate; impact is measured by a stepped-wedge rollout by site (each warehouse site and office team joins in a random order), comparing tickets to IT and HR, time to answer and the not-found rate with sites not yet on.

## Safety and guardrails

- **Oversharing, continuously:** a widening share on a Confidential or pattern-matched file holds it at once until the owner reviews; every source's widest principals ("Everyone except external users", open spaces, "anyone logged in" projects) are scanned weekly.
- **Org-wide links in numbers:** 6% of SharePoint files carry one (144,000); each counts only for its redeemers, and 3% of those (4,320) are Confidential or pattern-matched and held even for redeemers until reviewed (illustrative).
- **The rule:** the assistant may be stricter than the source, never looser than the source's own search.

## Deep dives

### Permission propagation end to end

- **Two kinds of change:** a document's ACL lives on its chunks, so it needs a patch; a membership lives in the principal store, so it needs no chunk rewrite.
- **Three clocks per path:** the typical lag (events), the bound while polls succeed (10 or 60 min, doubled by one throttled cycle), and the drop-out age, the only hard bound (30 min on P1 sites, 150 elsewhere).
- **The budget decides the bound:** SharePoint allows 2.4M RU a day per app, so the poll cadence is a budget line, not a preference.

The figure follows one revocation down four paths and then spends the SharePoint day.

<AnimatedDiagram spec="animated/enterprise-assistant/permission-propagation" stepper caption="Events make a revocation effective in about 35 seconds; budgeted polls bound it at 10 or 60 minutes while they succeed, and a site that cannot prove its bound drops out of the results." />

- **How to read it:** lane 1 is the event path, lane 2 a lost event caught by the P1 poll, lane 3 a throttled poll and the drop-out, lane 4 a site-group removal caught by the next reconcile; the bar below spends the SharePoint day.

**The numbers:**

- Event path: notify 30 (illustrative; Graph states an average under 1 min and a maximum of 6 h) + queue 1 + fetch 2 + map 0.1 + patch 1 + refresh 1 ≈ 35 s; dirty 1 s after the notification lands. The revocation is enforced once the ACL store is written, about a second before the index refresh, because every retrieval re-checks it.
- Budget: 139,200 (events, fetches, downloads) + 228,000 (polls) + 432,000 (site groups, at an illustrative 4 RU a call: the line to measure first) + 44,700 (live checks and drift) = 843,900 RU, 35%; reserve 650,000 (27%) covers a 624,000-RU re-enumeration in ≈ 7 h.
- Atlassian: ≈ 69,700 of 219,000 Tier 2 points an hour (32%); without Tier 2 the shared 65,000-point Tier 1 pool cannot carry the hourly reconcile. Entra group membership ≈ 2.5 min p50, ≤ 5 min.

<Callout tone="red" title="What breaks">
  A delta token can come back 410, and then the drive's changes are unknown until it is re-enumerated. That drive's chunks switch to live checks (at most 4 a turn, 5.0% of those answers lose a document) for up to ≈ 7 h, paid from the reserve.
</Callout>

### Worked example: the pay-band file

1. 09:12: an HR partner shares "FY27 pay bands" with an org-wide link; three HR partners redeem it. The site is P1 (Confidential) and the share widens access, so the file is held at once: even the redeemers do not see it in the assistant until the owner reviews.
2. Without the hold (an unlabelled file), only the three redeemers could retrieve it; Tom, who never opened the link, cannot, which matches the source's own search.
3. 10:00:00: the owner removes the link. The notification arrives ≈ 10:00:30 → dirty at 10:00:31 → effective ACL fetched at 10:00:33 (5 RU) → 9 chunks patched at 10:00:34 → visible to the index at 10:00:35.
4. If the notification is lost, the P1 poll (1 RU a call) sees it by ≈ 10:10:05; if that cycle is throttled, ≈ 10:20; after 30 min without a successful reconcile the site drops out of results.
5. Audit: "who retrieved it between 09:12 and 10:00:35" is a query over chunk ids with `acl_version`, joined to principal sets by validity interval, which also names the grant that admitted each retrieval.

### Acting as the user, inside the company

- **Tiers by audience:** T0 reads seen only by the user (no card); T1 the user's own item (card, withdrawable within 10 min); T2 named colleagues or internal channels (card with exact payload, audience and label); T3 anything an outsider can see or that cannot be undone (not a tool, only a link to the system's own screen).
- **Automations count as audience:** case statuses are limited to internal-only ones, and Jira transitions run only in allow-listed projects verified to have no outbound automation.

The figure draws the tiers, then Tom's ticket from the router to Jira.

<AnimatedDiagram spec="animated/enterprise-assistant/action-tiers" stepper caption="A tool’s tier comes from who can see its effect, checked when it runs; Tom’s ticket is created once, as Tom, after he confirms the card." />

- **How to read it:** the top is T0–T3 by audience; then Tom's ticket for WH-LEEDS: router, Jira bundle, gateway checks (schema, entitlement, audience), step-up consent on his first write, the card, his confirm, his delegated token, and WH-1182 created once with `card_id = c_51e`.

**The numbers:**

- 8% of turns are writes: ≈ 1,150 cards a weekday, each 0.00400 USD of model cost; card at ≈ 2,450 ms p50 (p95 ≈ 3,201), done ≈ 435 ms after confirm (p95 ≈ 1,545).

### In practice: when buying a seat product is the better call

- **Build and run this design:** 9 engineers (300,000) + infrastructure 15,135 + model 4,777 ≈ 320,000 USD a month ≈ 64 a seat; the team is 94%.
- **A mixed purchase:** 2,000 knowledge-worker seats at 25.5 (a 30 USD list price as of November 2026, less an illustrative 15%) + warehouse staff on the free chat with metered agents (2–30 credits a turn: 2 for a grounded answer at 2025 launch prices, the upper end illustrative), assuming their licences include the free chat, + 5 engineers for Brightpost's own tools, identity and vendor tests + their infrastructure ≈ 238,000 a month (223,000–254,000) ≈ 48 a seat. The 21 USD business tier is capped at 300 seats (partner pages, as of November 2026), so it is not an option.
- **Data residency decides neither:** both send prompts to a model provider, so name its region in the contract.

| A customer-facing support assistant | Retrieval, tiers, cards | The customer is the principal; money behind a policy service: [Customer Support Agent](/genai-system-design/case-studies/customer-support-agent) |
| 100,000 employees, 100M documents | Binding, sync design, tiers | ≈ 10× the index at today's mix (17× if everything is indexed); per-app source budgets grow far less, so more sources move to live checks or live search; per-region deployments |
| Search only, no chat | Index, filter, ranking, sync | No answer model, router or tools |
| A regulated bank or hospital | All controls | More sources late-bound; in-region models; full answer text kept under the records regime |

## How real systems do it

- **2024–2026, Glean:** mirrors each source's ACLs and identities and evaluates them before returning results, runs agents as the triggering user, and ranks with popularity, people connections and department affinity; its documented defaults run from 2 minutes (Salesforce cases) to days for full crawls, which Glean calls defaults, not guarantees.
- **2025–2026, Microsoft 365 Copilot:** surfaces only content the user can at least view; an org-wide link does not put a file in search until it is redeemed (Microsoft's sharing documentation, as quoted by Office365ITPros in 2024; the suite's unredeemed-link canaries test it); Microsoft's deployment guidance starts with fixing oversharing. A 2024 Gartner survey (reported by Computerworld) found 40% of 132 IT leaders delayed rollouts by 3 months or more over oversharing.
- **2026, Atlassian Rovo:** drops a connector's results when it cannot confirm permissions are current, and searches Outlook, Gmail and Slack live rather than indexing them; Atlassian moved apps to points-based rate limits in March 2026.
- **2025–2026, Slack:** cut commercially distributed non-Marketplace apps' history and replies calls to 1 a minute in May 2025 (internal apps keep 50+) and pointed AI apps at its Real-time Search API, renamed in February 2026.
- **2024–2025, injection in shipped assistants:** PromptArmor showed Slack AI leaking a private-channel secret through an injected link (2024); EchoLeak (CVE-2025-32711, CVSS 9.3) did it to Microsoft 365 Copilot with one email, through link and image rendering (2025).
- **2025, Anthropic:** tool search and code execution with MCP report 85% and 98.7% token savings, each from one example setup rather than a benchmark.
- **Where this design differs:** Glean and Copilot index most sources; here Slack and mail are live only and the poll cadence is a budget line, because a single-tenant build must fit each source's published per-app limits; raising them is a request, not a design input.

## Failure modes & pitfalls

- **Webhooks stop or subscriptions expire:** noticed by the per-drive "last event" age; the P1 or P2 poll still bounds the lag, and past drop-out the connector leaves results with a banner.
- **A delta token returns 410:** that drive's chunks switch to live checks (at most 4 a turn; 5.0% of those answers lose a document) and a re-enumeration runs from the 650,000-RU reserve (≈ 7 h for every drive at once).
- **SharePoint throttles (429 with `Retry-After`):** seen in the budget dashboard; polls pause, live checks continue, and a missed P1 cycle stretches its bound to 20 min. A Slack 429 sends the answer without Slack, which says so: ≈ 5.5% of peak minutes overflow with the per-conversation cache (≈ 13% without); fix by asking Slack for the larger-team tier.
- **A site is re-shared (450,000 patches):** noticed by patch-queue depth; 90 s of in-place updates, with its documents dirty and live-checked meanwhile.
- **Redis fails:** principal sets are read from PostgreSQL (+ ≈ 150 ms, illustrative: the sensitive path at ≈ 1,435 ms, still under 1,500); if PostgreSQL fails too the turn is refused, never answered unfiltered.
- **Atlassian does not grant Tier 2:** the hourly reconcile cannot run on the shared 65,000-point pool, so Atlassian paths move to their 150-min drop-out or to live checks until it is granted.
- **The model provider throttles (≈ 730,000 tokens a minute at peak):** pause the agent, then lookups, then move answers to a second model family that passed the gold set; actions only on a model that passed the simulator.

## Interview framework

1. **Minutes 0 to 5:** users by department, sources, permissions, staleness per source, actions and their audience, one tenant or many, the constraint order.
2. **Minutes 5 to 10:** numbers: 14,430 turns a weekday, 32.1M chunks, 55.6 GB a replica, 3.32M ACL patches a day, the SharePoint budget, 0.011 USD a turn.
3. **Minutes 10 to 20:** Steps 1 to 4: baseline, index, identity and the filter, staleness within budgets.
4. **Minutes 20 to 30:** Steps 5 and 6: router and bundles, run as the user, audience tiers and cards, the agent.
5. **Minutes 30 to 36:** Steps 7 and 8: memory; injection, egress, evaluation.
6. **Minutes 36 to 45:** one deep dive: propagation with the pay-band file, acting inside the company, or build or buy; tool loading if the interviewer asks.

**What interviewers listen for:**

- **Mid:** hybrid search, ACLs on chunks, a filter inside the search, citations, a card before writes.
- **Senior:** binding per source with numbers, rate-limit budgets, identity joins, delegated tokens, egress by audience, bundles against tool search.
- **Staff:** never looser than the source's search, drop-out, derived-text redaction, build or buy with a real team and a mixed purchase, multi-tenancy.

- **Red flags:** "tell the model not to reveal confidential data"; an org-wide link as "everyone"; a 10-minute poll of everything; matching users by email; "internal recipients only" checked by tool name; loading every tool; memory that learns silently.
