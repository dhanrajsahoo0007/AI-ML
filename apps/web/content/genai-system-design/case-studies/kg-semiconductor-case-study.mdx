A yield engineer sees ten lots of product PX7 leave wafer sort with an edge-ring failure pattern and asks, "Why did yield drop on lots PX7-1022 to PX7-1031?"
The answer needs every wafer's history across 800 steps, what changed on those chambers, what the sensors saw, whether the test floor is the cause, and what the fab learned before.
The hard parts are one chamber as one node across six systems that name it differently, 10¹¹ sensor samples a day kept out of the graph, and queries the model can write but not abuse.
Statistics must separate a chamber from a coincidence in time, and process IP must never leave the site.

- Interviewers use this question to see whether you design the ontology and identity before the model, keep statistics in code and get them right, show hypotheses with effect sizes rather than verdicts, and can price keeping models on site.
- **Research honesty:** no primary engineering write-up of a production LLM and knowledge-graph root-cause system in a fab exists. This page leans on SEMI standards (from summary pages), papers, vendor documents and vendor marketing, each labelled.
- Every fab volume, data rate, latency, salary, licence fee and unit cost is an estimate for one illustrative 300 mm fab at a mature node, and the worked investigation (PX7, ETCH04, WO-55120) is invented.
- In the terms of the concept pages, this is a [knowledge graph](/ai-system-design/genai-system-design/knowledge-graph-systems) read by templates and guarded queries, not [GraphRAG](/ai-system-design/genai-system-design/graphrag) community summaries: the questions are exact joins over a schema the fab already knows.

## Overview

- **Ontology and identity first.** Types follow SEMI E120 and E10 (equipment and states), E90 (wafer locations) and E164 (common EDA metadata; most sensor names stay vendor-specific and go through the identity map); one master id per tool, chamber, part, recipe body, probe card and reticle, and every literal in a question is linked to one before any query runs.
- **Three stores, one key set, one guarded path.** The graph holds relations (≈ 62.7M nodes, ≈ 237.6M edges, ≈ 41.1 GB); the columnar store holds wafer-level rows (1.92B over 5 years); the FDC store keeps the samples (≈ 1.77 × 10¹¹ a day). The model reaches both queryable stores only through 40 templates or guarded queries under read-only scoped roles.
- **Statistics in code that hold up.** Time-matched cohorts, within-lot comparisons, max-T over 7,040 candidates in two ordered families (wafer labels permuted within lots, then lot labels within process days), and the top 3 replicated on 50 held-out lots. Engineers see effect sizes with lot-cluster intervals, never a raw p-value.
- **Hypotheses, not verdicts.** A ranker in code scores effect size, timing, mechanism path, sensor evidence and past cases, calibrated on replay; a "checked and not supported" list says what was ruled out and why. The model writes the explanation; the engineer records the verdict.
- **Everything on site, reasoning tokens counted.** An open-weight reasoning model (gpt-oss-120b class, Apache 2.0) on two hosts at low effort, with 80 hidden tokens a call budgeted; encoders fill template slots so 56% of lookups need no model call before the table.
- **Fresh, and honest about completeness.** MES track-outs reach the graph in ≈ 5 s p50; E10 state changes within 2 minutes; a downtime with no maintenance record yet is a named gap, and a late, backdated record flags the answers it would have changed.

<KeyIdea>The graph remembers how every wafer travelled; code decides which differences are real, with effect sizes, inside the same lots and the same days; the model plans the search and explains the evidence. It proposes hypotheses for an engineer to confirm, never a root cause.</KeyIdea>

- **Fab terms:** a lot is 25 wafers in a FOUP (the sealed carrier); the route is the ordered list of steps; a tool has chambers; a recipe is the MES logical recipe, mapped to a tool’s PPID (the SECS/GEM process program id), and the body actually on the tool; an excursion is a yield drop beyond control limits; PM is preventive maintenance.
- **Fab systems:** MES (execution), FDC (sensor fault detection), SPC (statistical process control), YMS (yield management), CMMS (maintenance), RMS (recipes); wafer sort is the electrical test that gives each die a bin and each wafer a map, whose spatial pattern is a signature.
- **Analysis terms:** commonality analysis asks what bad wafers shared that good ones did not; FMEA rows and 8D reports are the fab's written failure knowledge; Cypher is the graph query language; effect size is the difference in rates; family-wise error is the chance of any false hit among many tests.

## API design

| Call | Who calls it | When |
| --- | --- | --- |
| `POST /v1/questions` (SSE response) | Engineer's web app (fab SSO) or the YMS "ask" button with the selected lots | Every question; scope comes from the SSO token's groups, never from the request body |
| SSE events `plan`, `result`, `hypotheses`, `evidence`, `sentence`, `gap`, `flag`, `done`, `error` | Gateway → app | `plan` echoes lots, metric, cohort rule and watermarks; `result` is a lookup table with its query; `hypotheses` is the ranked table rendered by code; `gap` names a missing or untestable input; `flag` marks an earlier answer a late event changed |
| `POST /v1/hypotheses/{id}/verdict` | 8D owner (others comment) | `confirmed`, `rejected` or `inconclusive`, with evidence ids and `ranking_seen`; upsert on (hypothesis, engineer) so a retry writes once |
| `POST /v1/answers/{id}/flags` | Engineer | A wrong number, mapping, link or query; to the knowledge-engineering queue |
| `GET /v1/answers/{id}/provenance` | Engineer, audit | Template id or query text, linked ids, watermarks per store, ontology version, model, reasoning effort and ranker versions |
| Typed columnar operations: `wafers_through`, `yield_by`, `metrology`, `etest`, `apc`, `wip_through` | Templates, the orchestrator | Each takes master ids and a window; a wafer or id set above 100,000 is refused with "narrow the window" |
| Internal `graph.template`, `graph.query`, `columnar.query`, `stats.investigate`, `traces.summary`, `recipe.diff`, `docs.search` | Orchestrator | `graph.query` and `columnar.query` are the only paths for generated queries and run the full guard chain; `recipe.diff` returns parameter values only to the owner module |

- **Scope before data:** SSO groups map to one role per scope group on every store: graph label grants (ingest adds a product-family label such as `:PF_PX7`), ClickHouse row policies, and the same filter on the trace API and document index. A nightly sync from YMS and MES groups is tested by the leakage set: "aligned and tested nightly", not "identical".
- **Read-only:** no write privilege on fab data in any store; verdicts, flags and audit go through the API into a separate database.
- **Literals are linked before execution:** every chamber, tool, step, recipe, lot, probe card and reticle name resolves against the identity map (exact, alias, then fuzzy with a chip to confirm). An unresolved literal stops the query ("unknown chamber 'ETCH4-B'; did you mean ETCH04-B?"); zero rows for a resolved id say "no rows for ETCH04-B in this window, data as of 10:42".
- **The hypotheses table is rendered by code:** the explanation cannot add, drop or re-rank a hypothesis; any number in a sentence must match a cited evidence item; no p-value in prose and no "the root cause is".
- **Transport:** SSE, because the plan, table, gaps and sentences must arrive in order on one connection, the table before any prose.
- **Idempotency:** `Idempotency-Key` returns the same stream on retry; ingest upserts on source ids; verdicts upsert on (hypothesis, engineer).

## Data model

- **Bitemporal and versioned:** every event and edge carries `valid_from` and `valid_to` (when it was true in the fab) and `recorded_at` and `superseded_at` (when we knew it). A correction writes a new version, so "what the system knew at 10:42 that day" is the versions with recorded_at at or before T and superseded_at after it.
- **Retention follows the 5-year replay:** events, genealogy, recipe bodies and material lots stay 5 years in the graph; execution (`Run` nodes, sort insertions, inspections) 2 years in the graph and 5 years in the columnar store, whose typed views older replays read.

<AnimatedDiagram spec="animated/kg-semi/ontology" caption="The run is the hub: it ties a lot to a step, a tool, the chambers it visited and the recipe body version the RMS verified for the job; approved knowledge links a signature back to the events that can cause it." />

**How to read it:**

- Step 1 is execution and equipment: `Run` (lot × step × tool) points to its lot, step, tool and, through `VISITED`, the chambers (2.5 a run: a cluster tool passes etch then strip); chambers are E120 modules qualified for ≈ 8 steps.
- Step 2 adds what changes: the recipe body version the RMS verified for the job (upload-and-compare at job start, or the last golden compare; "unverified" when stale), material lots, part installs, E10 state changes, PMs, holds and SPC events, and the test side (sort insertion, probe card, tester, program).
- Step 3 adds approved knowledge (`FailureMechanism` with its FMEA row, approver and date; `ExcursionCase`) and the FDC trace as a reference matched by context, never as samples.

**The numbers:**

- 62.7M nodes × 200 B + 237.6M edges × 120 B (four time fields each) ≈ 41.1 GB, in memory on one 128 GB server.
- Which wafer took which chamber is a columnar row: 736,438 a day × 730 days would be 537.6M edges, 2.3× every other edge.

<Callout tone="red" title="What breaks">
  Key runs on the MES logical recipe and a tool-local edit becomes invisible: the body changed with no RMS version. Runs point to the body version the RMS verified, golden-compare mismatches are events, and APC adjustments are columnar indicators, so drift is not read as a recipe change.
</Callout>

One graph template and one typed columnar call show the two query shapes; both take master ids from the linker, never free text.

```cypher
// Template T07 "changes on a chamber in a window"
MATCH (c:Chamber {id: $chamber})<-[:ON]-(e)
WHERE e.valid_from >= datetime($from) AND e.valid_from < datetime($to)
  AND (e:Maintenance OR e:PartInstall OR e:FdcHold OR e:StateChange OR e:GoldenMismatch OR e:Qualification)
RETURN labels(e)[0] AS kind, e.id AS id, e.valid_from AS at, e.summary AS summary
ORDER BY at
LIMIT 200
```

```sql
-- Typed operation wafers_through(chamber, step, window) on the readonly=1 profile (row policy: product family)
SELECT wafer_id, run_id, slot, track_out
FROM wafer_step
WHERE chamber = {chamber_id} AND step_seq = {step} AND track_out >= {from} AND track_out < {to}
LIMIT 100000;
-- max_execution_time 5 s and max_rows_to_read 200M live in the readonly=1 profile; settings constraints stop a query raising them
```

- **Why `Run` stays in the graph:** templates traverse lot → run → chamber → event → mechanism in one pattern, and generated queries need typed relations; relational-only would leave the model writing recursive SQL for genealogy.
- **The cost of duplication:** one ordered ingest log feeds both stores, a nightly reconciliation compares counts per day and chamber, and "data as of" on every answer is the minimum watermark over the stores it used.
- **Chamber-first reads:** without the (chamber, step, time) projection, PX7's 5-year share (8 of 52.6 lots a day × 1.92B ≈ 292M rows) exceeds the 200M read cap.

### Step 1: A model on site, behind a scope check (F2, N6)

The baseline: the engineer's question goes through the site gateway to one on-site model that writes SQL against MES reporting tables from a schema dump.

<AnimatedDiagram spec="animated/kg-semi/architecture" step={1} caption="Step 1: the engineer app asks through a gateway that maps SSO groups to scope roles and audits; the orchestrator prompts an on-site model on two hosts." />

- **Adds:** the engineer app, the gateway, the orchestrator, the on-site model.
- **Flow:**
  1. The app sends the question with the fab SSO token.
  2. The gateway validates it, maps the groups to scope roles and writes an audit record.
  3. The orchestrator gives the model the question and a schema dump; the model writes SQL against MES reporting tables.
  4. The answer streams back.
- **Why this and not that:** scope before any data read (P11); IP on site from the first step (P17); the simplest thing that answers (P1).
- **The gap:** each system names a chamber differently, a query that runs can still be wrong, and the model guesses causes from its memory of etch physics.

### Step 2: One graph, one id per thing (F4, F5, N4, N7)

<AnimatedDiagram spec="animated/kg-semi/architecture" step={2} caption="Step 2: fab systems send events in order through one ingest log with identity resolution into a bitemporal knowledge graph; the model’s free queries to it are dashed." />

- **Adds:** the fab systems, the ingest log and identity resolution, the knowledge graph.
- **Flow:**
  1. MES, E90 locations, E10 state changes, FDC holds, SPC, CMMS, RMS body verifications, YMS and the test floor publish to one ordered ingest log keyed by source id.
  2. Each name resolves through the identity map; an unresolved one waits 10 minutes, then goes to quarantine, never into the graph.
  3. Upserts are bitemporal: a correction is a new version with its own `recorded_at`.
- **Why this and not that:** ground before generating (P2), and provenance on every edge (P14). Deep dive 1 shows what one missing mapping does to a hypothesis.
- **The gap:** the model still writes free queries that may join wrongly, use a misspelled name, scan everything or try to write, and wafer-level questions have no store.

### Step 3: Linked literals, templates first, one guard chain for both stores (F2, N2, N10)

<AnimatedDiagram spec="animated/kg-semi/architecture" step={3} caption="Step 3: a query guard with the linker and caps replaces the free queries; its read-only reads reach the graph and a new columnar store, and encoders join the models." />

- **Adds:** the linker, templates and query guard; the encoders; the columnar store.
- **Flow:**
  1. An encoder routes the question and matches one of 40 templates; it fills the slots, or the model does when it cannot.
  2. Otherwise the model generates Cypher or SQL from a 2,500-token schema subset.
  3. Every literal is linked to a master id; the query is parsed and allow-listed, checked against the schema, bounded and `EXPLAIN`ed.
  4. It runs under a read-only scoped role on an assistant-only replica (5 s, 512 MB, row caps); code renders the table with the query shown.
- **Why this and not that:** rules in code, not in the prompt (P10); bound the blast radius (P12); a cheap encoder before the model (P4). Deep dive 2 draws the chain.
- **The gap:** lookups work, but "why" needs valid statistics over millions of wafer-steps, which neither the graph nor the model should do.

### Step 4: Statistics in code: time-matched, within lot, max-T, held-out (F1, N1)

<AnimatedDiagram spec="animated/kg-semi/architecture" step={4} caption="Step 4: a statistics engine reads cohort counts from the columnar store and asks a trace read API, which reads samples by reference from the existing FDC store." />

- **Adds:** the statistics engine, the trace read API, the existing FDC trace store.
- **Flow:**
  1. The metric comes from the semantic layer; the cohort is every product wafer that passed each candidate step in the same process days.
  2. The test side is checked first (probe card, tester, retest recovery).
  3. 5,360 within-lot candidates get 10,000 within-lot permutations stratified by slot class; then 1,680 lot-level candidates are tested on residual wafers with lot labels permuted within process days; max-T in each family.
  4. Inseparable candidates are clustered.
  5. FDC indicators for the top cells, then trace summaries by reference; the top 3 are replicated on 50 held-out lots.
- **Why this and not that:** cascade from cheap to expensive (P4): counts first, indicators next, traces only for the top candidates. Deep dive 3 draws the statistics.
- **The gap:** effect sizes and a cluster are not an answer: nothing says what changed, why it would cause this signature, or how sure we are.

### Step 5: Ranked hypotheses with evidence (F1, N3)

<AnimatedDiagram spec="animated/kg-semi/architecture" step={5} caption="Step 5: an evidence and ranker card reads through the guard’s templates and ranks in code; a checks card verifies every number and word the model writes." />

- **Adds:** the evidence assembler and ranker, the checks.
- **Flow:**
  1. Per cluster: change-point, a "what else changed" table, mechanism paths, post-PM qualification, past cases and WIP at risk, in parallel.
  2. A logistic ranker in code scores each hypothesis; isotonic calibration maps it to high, medium or low.
  3. Code renders the `hypotheses` table and the "checked and not supported" list.
  4. The model writes explanations and checks; every number is matched against the evidence.
- **Why this and not that:** constrain the output (P9); budget latency per stage (P5), so the table arrives at ≈ 6.0 s before the model writes; manage context (P8).
- **The gap:** mechanism paths exist only for what someone typed into the graph; the FMEA sheets and 8D reports are not in it.

### Step 6: Written knowledge becomes approved edges and citable passages (F3, F6)

<AnimatedDiagram spec="animated/kg-semi/architecture" step={6} caption="Step 6: document extraction writes approved edges to the graph and chunks to a document index, from which the evidence card reads passages." />

- **Adds:** document extraction and review, the document index.
- **Flow:**
  1. Nightly, the model extracts triples from FMEA rows, 8D reports and SOPs with the ontology as the schema.
  2. Each proposed triple carries its source span; an engineer approves it, and the approval date is stored.
  3. Approved triples become `FailureMechanism` edges; chunks are indexed for citation.
- **Why this and not that:** treat retrieved content as untrusted (P13), so an instruction planted in a report never becomes an edge; provenance (P14). Extraction precision must reach ≥ 0.9 on 1,000 labelled triples before a mechanism type is offered.
- **The gap:** nobody records whether a hypothesis was right.

### Step 7: The 8D owner confirms; verdicts close the loop (F6, F7)

<AnimatedDiagram spec="animated/kg-semi/architecture" step={7} caption="Step 7: verdicts, with ranking_seen, and audit records flow along the bottom into a verdicts and audit store." />

- **Adds:** the verdicts and audit store.
- **Flow:**
  1. The engineer runs the confirmation checks: the part record, post-PM qualification, inline edge metrology, a split lot.
  2. The 8D owner records confirmed, rejected or inconclusive with evidence ids and `ranking_seen`.
  3. A confirmed cause becomes an `ExcursionCase`, used by past-case search and the evaluation set.
- **Why this and not that:** keep a human escape hatch and close the loop (P15). `ranking_seen` marks labels the ranking may have influenced, so evaluation can separate them.
- **The gap:** is it better than the YMS screen, and does a new ranker, prompt or ontology version break it?

### Step 8: Evaluate on as-of replays and seeded faults (N1, N2, N3)

<AnimatedDiagram spec="animated/kg-semi/architecture" step={8} caption="Step 8: a replay and release gate reads the confirmed cases from the verdicts store and decides every release." />

- **Adds:** the replay and release gate.
- **Flow:**
  1. 270 confirmed excursions are replayed on bitemporal as-of state, with knowledge filtered to approval dates.
  2. The same cases run through the YMS screen for a paired comparison.
  3. 2,000 seeded faults (500 with a benign co-occurring change) and 1,000 nulls test the statistics; the query set and calibration follow.
- **Why this and not that:** evaluate continuously and degrade gracefully (P16); 300 labels are few, so seeded faults test the statistics where labels are free.
- **The gap:** none; the gate decides each release.

## Component choices and why

- Every box in the final diagram: what we picked, why, and why the usual alternatives lose. Driver ids (G) refer to the drivers table; F and N to the requirements.

### Build or buy: build the joining and guarding layer, buy the parts

- **Choice:** build the identity map, the guard chain, the statistics and the evaluation set; buy the graph database, the columnar store, the model weights and the YMS with its wafer-map signatures.
- **Why:** the cross-system identity map and the statistics are the fab's own and must be audited by the fab; a vendor assistant sees only what its product ingests (G1, G8, G9).
- **Why not the YMS vendor's assistant:** PDF Solutions markets a semantic layer with an air-gapped LLM option (vendor claim, 2026), but there is no evidence of its accuracy on this fab's excursions and the fab cannot gate its releases. Revisit when it exposes its semantic layer to the fab's own replay set.

### Ontology: expert-built from SEMI standards, versioned

- **Choice:** a knowledge engineer with yield, process, equipment and test owners writes the types before ingest, from E120, E10, E90, E164 and ISA-95 levels; semantic versions, migrations as scripts, and the 500-question query set run in CI against a migrated snapshot.
- **Why:** templates, schema subsets, prompt examples and extraction prompts carry the ontology version they were tested on, and the audit stores it per answer (G1, G8).
- **Why not an LLM-induced schema (GraphRAG-style):** not anchored, not validated, not traced, as MFG-AgentGraph (workshop paper, 2026) argues for manufacturing.
- **Why not a public ontology whole:** Infineon's Digital Reference (≈ 800 classes) covers supply chains, not chamber-level execution; reuse its terms where they fit.

### Identity: an owned map, and question literals linked before any query

- **Choice:** an identity map per source owned by equipment engineering; hold-and-retry for 10 minutes, then quarantine; a daily coverage report; every literal in a question linked to a master id, with a chip on a fuzzy match.
- **Why:** a split chamber keeps its effect size but loses its timing and sensor evidence (N4), and an invented `ETCH4-B` returns zero rows that read as "nothing happened" (N2).
- **Why not fuzzy or model matching at ingest:** a wrong merge joins two chambers' histories silently. The KG concept page allows fuzzy matching; a fab deliberately chooses stricter, and the model may only propose mappings into review.

### Where data lives: graph for relations, columnar for wafers, FDC store for samples

- **Choice:** three stores fed by one ordered ingest log, reconciled nightly; `Run` nodes stay in the graph as the model's typed query target.
- **Why:** samples are ≈ 744× the graph's edge count a day; wafer-level visits would add 537.6M edges; the statistics read 2,000-wafer cohorts in one columnar pass (G3, G6).
- **Why not everything in the graph:** size and scan cost.
- **Why not everything relational:** each hop is fine, but the model's query target loses typed relations and genealogy becomes recursive SQL.

### Graph database: an on-site property graph with role-based access

- **Choice:** Neo4j Enterprise class, 1 primary and 2 assistant-only read replicas, ≈ 41.1 GB in memory.
- **Why:** Cypher is what Text2Cypher work targets and ISO/IEC 39075 GQL (2024) converges with it; roles without WRITE and label grants exist in the enterprise edition (G9).
- **Why not Amazon Neptune:** cloud-only. **Why not Kùzu:** its repository was archived in October 2025 after its acquisition (news reports).
- **Why not RDF + SPARQL + SHACL:** right if formal alignment dominates. **Why not PostgreSQL + Apache AGE:** workable at this size; chosen against for access control and tooling (judgement).

### Queries: templates first, guarded generation second, for both stores

- **Choice:** 40 templates (28 graph, 12 cross-store) cover 70% of lookups and the encoder fills 80% of their slots; the rest is generated from a schema subset and four verified examples and runs through one guard chain.
- **Why:** on CypherBench (2024) the best zero-shot execution accuracy was 61.58% and models under 10B scored below 20%, while on Neo4j's dataset (2024) the best model, fine-tuned or not, reached ≈ 30% strict match; the metrics differ, and the chosen model's score is unknown until measured on the fab's 500 questions (N2, G3).
- **Why not free generation everywhere:** "wrong but valid" queries return plausible answers.
- **Why not templates only:** the long tail goes back to hand-written SQL.

### Statistics: time-matched, within lot, max-T, held-out replication

- **Choice:** compare a chamber's wafers with other-chamber wafers of the same lots in the same process days; 10,000 within-lot permutations stratified by slot class, with the maximum of standardised statistics (Westfall–Young); lot-level candidates tested on residual wafers with lot labels permuted within process days; top 3 replicated on held-out lots.
- **Why:** lot-level factors (time, upstream tools, resist lot, wet-bench batch) cancel inside a lot, but upstream chambers and slot order do not, so chambers at other steps compete in the same max-T. Max-T accounts for the dependence between candidates, assuming wafers are exchangeable within a lot and slot class (G2, G8, N1).
- **Why not Benjamini–Hochberg on wafer-level p-values:** it assumes independence or positive dependence, these candidates are heavily dependent, Benjamini–Yekutieli would cost ≈ 9.4×, and wafer-level tests ignore lot clustering. BH also controls a weaker target (false discoveries); family-wise control costs power, which the held-out step recovers.
- **Why not replicate on the data that selected the candidates:** selective inference controls nothing. **Why not a black-box yield model:** unexplainable, and 300 labels overfit.

### Model: an on-site open-weight reasoning model at low effort, encoders where they suffice

- **Choice:** gpt-oss-120b class (Apache 2.0, ≈ 117B total and 5.1B active parameters, one 80 GB GPU; as of November 2026) on two hosts, harmony format applied by the server, low effort, constrained JSON decoding.
- **Why:** process IP stays on site (G9); like for like a hosted API would cost ≈ 132.5 USD a day against 240, a GPU premium of 107.5 USD (1.1%).
- **Why not medium effort for the writer:** + 220 reasoning tokens puts the explanation at ≈ 15.0 s p50 mixed, at the target, and ≈ 16.1 s typed, over it; the grader and measured token counts decide.
- **Why not a hosted frontier model under contract:** who may see process technology and where it is processed is the fab's legal call; this design assumes "on site" and prices it.
- **Why not a domain fine-tune first (SemiKong-style):** no published numbers to beat; fine-tune a small text-to-Cypher model from validated logs if the generated slice stays under 80%.

### Orchestration and ranking: a fixed workflow and a ranker in code

- **Choice:** plan → cohort → tests → evidence → confirm → rank → write as a fixed workflow; a logistic ranker over five features, cross-fitted by time, with isotonic calibration into high, medium and low.
- **Why:** the procedure is known, and the same window must give the same table (G3, G8, N3).
- **Why not an agent choosing tools:** variance and latency with no gain on a known procedure; SemiFA (paper, 2026) is a four-agent pipeline on 930 images, not evidence of production accuracy.
- **Why not let the model rank:** fluent, uncalibrated and unstable between runs.

### Smaller parts

- **Choice:** the site's existing API gateway and message bus; OpenSearch-class BM25 + vectors for documents; the YMS's own signature classes, our classifier only where it lacks one; a sub-1B cross-encoder reranker; an append-only audit store.
- **Why:** each reuses what the fab already certifies or keeps one definition of a signature (G8, G12).
- **Why not vectors only for documents:** part numbers and recipe names need exact match. **Why not the model as reranker:** 60 ms against seconds.

| Passage reranker | Sub-1B cross-encoder | Host A | 60 ms for 40 candidates |
| Document extraction (FMEA, 8D) | Same model, batch, low effort | Host B, nightly | Proposals for review |
| Independent grader (eval only) | A second open-weight family | Host B | Grades explanations between engineer rounds; never a gate alone |

- **Reasoning channel:** never shown to users and kept only in the audit store; the model card says it is not intended for end users.

- **Breakpoints:** the 80 reasoning tokens are a budget, not a measurement; the typed plan misses 2.0 s at ≈ 95 tokens a call, the document first sentence at ≈ 103, the typed explanation at ≈ 135, a generated lookup at ≈ 163.

  Budget a reasoning model without its reasoning tokens and the planner looks like 900 ms when it is 1,700. </Callout>

- **Cost:** GPUs 240 USD a day (2.4%); ≈ 9,950 USD a day all-in; 9.21 USD a question, 0.22 of it GPU, and a marginal question costs ≈ 0 on fixed GPUs.

## Evaluation and release gates

| Offline set | Size | Source | What it checks |
| --- | --- | --- | --- |
| Rolling-origin replay | 300 confirmed excursions from 5 years; first 30 only train, 270 scored | 8D reports, replayed on as-of state | hit@3 ≥ 70% (± 5.4), hit@1 ≥ 45% (± 5.9), coverage ≥ 90% |
| Paired baseline | The same 270 | The YMS commonality screen | McNemar on paired hit@3; detectable difference ≈ 7.6 points at 20% discordant pairs |
| Seeded faults and nulls | 2,000 seeded (500 with a benign co-occurring change); 1,000 nulls | Injected into historical data | In the top 3 ≥ 90% (± 1.3), also gated per effect-size bin (10, 20, 40 points); "high" on nulls ≤ 5% (± 1.4) |
| Query set | 500: 300 template (100 cross-store), 150 generated, 50 misspelled names | Engineer questions with gold queries on a frozen snapshot | ≥ 95% (± 2.5 if questions were independent; also gated per template); ≥ 80% (± 6.4); never "no rows" |
| Bypass and leakage | 300 bypass attempts; 200 leakage prompts | Writes, `LOAD CSV`, dynamic Cypher, planted instructions | 0 executed (≤ 1.0% on this constructed set); 0 leaks (≤ 1.5%) |
| Calibration | ≈ 100 in the "high" bin | Replay, cross-fitted | Confirmed ≥ 60% with the Wilson lower bound ≥ 50% (50.2–69.1%) |
| Extraction | 1,000 expert-labelled triples | FMEA and 8D | Precision ≥ 0.9 (± 1.9) before a mechanism type is offered |

- **No leakage in replay:** each case runs on the versions recorded before its detection time, with a ranker fitted only on cases closed before it and knowledge approved before it, so a case never sees its own 8D report.
- **Replay fidelity:** ≈ 120 cases from the last 2 years replay exactly (hit@3 ± 8.1 on that class alone); the older 150 use columnar execution and daily sensor aggregates. A gap over 10 points between the classes is investigated before release.
- **Metric sensitivity:** every investigation re-ranks with the signature threshold at 0.7 and 0.9; a top hypothesis that moves is shown as "sensitive to the metric definition".
- **Exposure bias:** verdicts carry `ranking_seen`; the 8-week shadow (results computed, not shown) yields only ≈ 9 confirmed cases (60 a year × 8 ÷ 52), too few to gate but enough to check that exposed verdicts agree with unexposed ones.
- **Verification bias:** the 270 are the excursions someone solved, often with the YMS screen, so the paired test is tilted toward it and silent on unsolved ones; time from detection to confirmed cause and the share of excursions closed are the online outcome.
- **Online and rollout:** time from detection to confirmed cause, verdict rates per confidence label, flags per 1,000 answers, quarantine size, source lag. Etch first, then all front-end modules, then the fab; a "high" rejected over 40% of the time in a month rolls the ranker back.

The release gate runs every check on a candidate ranker, prompt set and ontology version.

<AnimatedDiagram spec="animated/kg-semi/release-gate" caption="The candidate passes the headline replay but fails the slice where a benign change shares the window, so it does not ship: time confounding is the failure this gate exists to catch." />

- **How to read it:** the candidate fans out to nine checks; lime passes and red fails; one failure feeds the Block box and nothing ships. The measured values in the figure are illustrative.

**The numbers:**

- hit@3 at 73% on 270 cases has a Wilson interval of about ± 5.4 points, so a 70% gate cannot tell 70% from 73%; it can tell 70% from 60%.
- The failing slice is 84% against 90% on the 500 time-confounded seeded faults, while the 2,000-fault headline passes at 92%: the average hides the one failure that matters most here.

## Safety and guardrails

| Threat | Where it enters | Control | Code or prompt |
| --- | --- | --- | --- |
| Generated query writes or deletes | Generation | No WRITE in any role; the parser rejects write clauses; ClickHouse `readonly=1` | Code |
| Query scans everything or exhausts memory | Generation | ≤ 4 hops, LIMIT 1,000, time filter on event labels, `EXPLAIN` heuristic, 5 s, 512 MB, 200M rows read, 100,000 ids across stores, 2 in-flight per engineer | Code |
| Dynamic Cypher, procedures, files | Generation | `CALL` allow-list excludes `apoc.cypher.*`, `apoc.load.*`, `apoc.periodic.*`, `dbms.*`; `LOAD CSV` blocked; no network from database hosts | Code |
| Hallucinated or misspelled names | Planner, slots, generation | Every literal linked to a master id; unresolved stops the query | Code |
| Read outside scope | Any store | Label grants, row policies, filtered trace and document APIs; "n hidden by scope"; nightly ACL sync | Code |
| Instructions planted in reports, FMEA cells or node properties | Documents, graph text | Quoted as data with ids; extraction schema-checked and approved; the writer may only restate evidence | Code + prompt |
| Wrong but valid query | Generation | Templates first; query and paraphrase shown; the query-set gate | Code + product |
| Correlation from time, chance hits, dependence | Statistics | Time-matched within-lot comparison; change-point; max-T; held-out replication; no raw p-value | Code |
| Test-floor artefact read as a process cause | Statistics | Probe card, tester and retest check first | Code |
| Trace on the wrong wafer; recipe confusion | Ingest | Context match with a rate per tool type; recipe body per run; golden-mismatch events | Code |
| Stale graph after maintenance | CMMS lag | E10 state events; "CMMS record pending" gap; flags on answers changed by late events | Code |
| IP exfiltration; tampered weights | Model, logs, intake | On-site models, no egress, reasoning only in the audit store; hash-checked, scanned, pinned weights | Code + network + process |
| Automation bias | Engineer | Calibrated confidence with intervals; checks before action; `ranking_seen`; the assistant never acts | Product |

- **Why roles, not driver modes:** a driver's READ access mode mainly controls routing (Neo4j community answers); a role without WRITE is enforcement. LangChain's Cypher chain asks for narrowly scoped credentials after CVE-2024-8309, a prompt-to-Cypher injection.
- **Why label grants, not property rules:** property-based rules test one property each, and a DENY fails open when it cannot be evaluated (Neo4j manual, read November 2026).
- **Export control and trade secrets (framing, not legal advice):** EAR deemed exports, the December 2024 SME technology ECCNs, the January 2025 foundry rule (logic at 16/14 nm and below) and Taiwan's core-technology list (14 nm and below) bite at advanced nodes. At this mature node, trade-secret law and customer agreements carry the boundary.
- **AI diffusion rule:** BIS announced in May 2025 that it would rescind the January 2025 rule and not enforce it; it did not cover open weights.

## Deep dives

### Ontology and identity: one chamber, one node

- **Standards fix names:** E120 gives the equipment hierarchy, E90 the wafer locations, E164 common EDA metadata (most sensor names stay vendor-specific) and E10 the six states; MES time is the clock.
- **Genealogy:** splits, merges, rework, scrap, sorter moves and re-ID, with the scribe id as the wafer's identity and old ids kept as aliases.
- **Batch and cluster tools:** a batch tool records wafer and slot positions per batch; a cluster tool records ordered chamber visits, which is why `VISITED` has a sequence.

### Read-only, validated queries over two stores

- **The benchmarks are not comparable:** 61.58% execution accuracy on CypherBench (Wikidata views, 2024), ≈ 30% strict match on Neo4j's Text2Cypher dataset (2024); models under 10B scored below 20% on CypherBench.
- **Server-level caps:** `db.transaction.timeout` and `db.memory.transaction.max` apply to the whole server, which is acceptable because the replicas serve only the assistant; `EXPLAIN` row estimates are a heuristic for variable-length patterns, so the caps are the bound.

</Callout>

### From candidates to ranked hypotheses, and how engineers confirm them

- **Sort-date populations confound time:** wafers sorted together passed a given step weeks apart (holds, rework, hot lots), so at that step bad wafers are post-change and many good ones pre-change; the cohort is defined by process time at each step instead.
- **Candidate kinds:** chamber at a step or at any step (re-entrant), recipe body and golden mismatches, APC drift, material lots, maintenance and state windows, reticles, tool at a step and batch-tool runs such as WET07 (both lot-level), probe card, tester, program. Slot and batch position are strata, not candidates; a kind below 80% coverage is "not testable".
- **The assumption under the permutation:** wafers in a lot must be exchangeable, and a cluster tool that assigns chambers by slot breaks that, aliasing chamber B with a slot class (Jaccard 0.31, illustrative). Permutations are stratified by slot class, and a full alias is reported as a cluster.
- **Tool-wide causes:** a cause on the whole tool (transfer robot, gas box) raises every chamber, so it shows no within-lot difference; tool at a step and batch runs are lot-level candidates, tested on residual wafers.
- **Combinations:** pairs are not candidates (16,000² cells); a cause that exists only in a combination (B at 412 after chamber 3 at 300) is a known blind spot, shown as "no single-factor hypothesis", never as "nothing found".
- **Timing is weak alone:** a chamber logs ≈ 0.21 maintenance, qualification or part events a day (illustrative), so one falls within a day of a random change-point ≈ 34% of the time (1 − e^−0.42). The ranker scores alignment against that base rate and against sister chambers' events.
- **Held-out lots share the window:** they guard against selection on noise, not against a time confounder; the change-point and the sister chambers do that. "Replicated" is the statistic's word; "confirmed" is the 8D owner's verdict.

- 10,000 permutations × 7,040 candidates × 12 words (a 750-wafer discovery set as a bitmap) is ≈ 845M 64-bit AND-popcounts, ≈ 0.6 s on a few cores (estimate); each statistic is standardised against its permutation mean and spread before the maximum.

### The site boundary and on-site models

- **Why on site:** recipes and yields are trade secrets at any node, and the leak path is real (Samsung, 2023, under How real systems do it). Taiwan's 2022 law (5 to 12 years in prison) and US controls add to that only at advanced nodes.
- **What you lose:** frontier quality and managed upgrades. The design needs little of it: encoders fill slots, code tests and ranks, and the model plans, writes queries and explains.

<AnimatedDiagram spec="animated/kg-semi/site-boundary" caption="Fab data comes in, weights come in through intake, and nothing goes out; the GPUs cost about 107.5 USD a day more than a hosted API (1.1%), and the people to run them about 411 more, about 5% of the system in all." />

- **How to read it:** the fab network is read only; the site data centre has no internet route; intake brings weights in hash-checked, with SEMI E187 (2022) cited as the fab's own precedent for software near equipment; the hosted API is drawn with no route.

**The numbers:**

- On site, 4 GPUs × 24 h × 2.5 USD = 240 USD a day; hosted like for like, 12.5 USD of tokens + 120 for the two encoder GPUs a hosted design still runs = 132.5. The premium is ≈ 107.5 USD a day, 1.1% of ≈ 9,950.
- The people premium is larger: if serving, intake and upgrades take half an ML engineer (illustrative), that is ≈ 411 USD a day, and with the GPUs still ≈ 5% of the total.
- A fab may also exclude models by origin as policy; the two-host fleet serves ≈ 0.65 streams at burst on either host alone.

### Worked example: the wet bench that ran most of the bad lots

1. Chamber B of ETCH04 fails 80% of its held-out wafers (100 of 125) against 4.0% (15 of 375) on sister chambers A, C and D in the same 20 lots: a risk difference of 76 points [≈ 65–84, lot-cluster, illustrative], and B is above its sisters in 20 of 20 lots.
2. WET07, a batch wet bench at step 414, ran 28 of the 40 bad ETCH04 lots against 12 of the 40 clean ones; tested alone by lot, it would be flagged strongly, because it shares the lots, not the cause.
3. The ordered procedure tests lot-level candidates only on residual wafers, the non-B ones: WET07's lots show 33 of 825 (4.0%) against 37 of 925 (4.0%) elsewhere (shown over the 80 cohort lots for illustration; the procedure tests on the 30 discovery lots), so it goes to "checked and not supported".
4. Lot-cluster intervals use a design effect of 1 + (wafers a lot − 1) × 0.1 (illustrative intra-lot correlation): 6.25 B wafers a lot gives 1.525, 18.75 sister wafers gives 2.775, widening 72–86% to 70–87% and 2.4–6.5% to 1.8–8.8%.
5. Early in an excursion one lot can be enough for a large effect (5 of 6 B wafers against 1 of 19 sister wafers), but a 10-point effect (14% against 4%) needs about 34 tool lots, so the card says "unconfirmed, k more lots expected by day d".

| [Stream Processing and Windowed Aggregation](/system-design/patterns/stream-processing-and-windowing) | Hold-and-retry for early events; flags for late, backdated ones | An E90 location can precede the MES split |
| [Materialized Views and Read Projections](/system-design/patterns/materialized-views) | The (chamber, step, time) projection of wafer-step rows | Chamber-first reads under the 200M-row cap |
| [Bulkheads, Shuffle Sharding and Cell Architecture](/system-design/patterns/bulkheads-and-cell-architecture) | Assistant-only graph replicas with server-level caps | A runaway query cannot slow ingest or other users |
| [Tail-Latency Hedging, Deadlines and Degradation](/system-design/patterns/tail-latency-and-degradation) | Max-of-n budgets; 6 s trace deadline; statistics-only fallback | Six parallel evidence draws set the 2,745 ms stage |
| [Distributed Time, Clocks and Ordering](/system-design/patterns/distributed-time-and-clocks) | MES time as the clock; bitemporal edges | "What did we know then" needs two times per fact |

## Same design, other systems

| If the interviewer asks for… | What stays the same | What changes |
| --- | --- | --- |
| A second fab with a different MES | Ontology, guards, statistics, ranker, model | A connector and identity map per MES; ontology versions per site; per-site scopes, since one site's process may be controlled for the other's staff |
| A foundry with many customers | Ontology, guards, statistics | Product yield is the customer's: cross-customer statistics only as aggregates above a minimum count, which costs power; past cases and documents filtered by customer |
| Assembly and test (back end) | Graph, guards, statistics | Units and strips instead of wafers; test programs as the recipe analogue |
| Predictive maintenance | Ontology, CMMS and E10 events, traces by reference | "Which chamber needs a PM?" is a model over indicators; the graph supplies part history |
| The [clinical knowledge-graph assistant](/genai-system-design/case-studies/kg-healthcare-case-study) | Rules and statistics in code, provenance, abstention, a boundary | Standard vocabularies instead of SEMI names; PHI under a BAA instead of on-site IP; alerts instead of hypotheses |

## How real systems do it

- **No production write-up exists:** papers, standards and vendor documents describe parts of this system, but none gives latency, volume or accuracy in use.
- **2012, Hsu, Chen and Fan (paper, WSC):** greedy tool commonality misses tool combinations, and in industry practice the root cause usually does not rank first.
- **2021, Infineon with Know-Center and TU Graz (paper):** a root-cause knowledge-management concept combining graph embeddings and language models; no experimental numbers.
- **2023, Samsung:** banned generative AI tools for staff after sensitive code was pasted into ChatGPT (Bloomberg report).
- **2024–2025, papers:** FabGPT (multimodal defect Q&A on in-house data), SemiKong (a semiconductor LLM, etching first) and OGPAL (ontology-guided FMEA extraction, nDCG@20 0.719 against 0.450 for RAG on automotive assembly lines); gpt-oss released under Apache 2.0 in 2025.
- **2026, papers and a vendor:** SemiFA (four agents, a report in 48 s on one A100, telemetry the most useful modality); MFG-AgentGraph argues for SHACL-validated, provenance-traced, local KG-LLM agents; PDF Solutions markets a semantic layer with an air-gapped LLM option (vendor claim).
- **Where this design differs:** the papers let models or agents reason over the graph; here code tests and ranks, because an engineer may inhibit a chamber on the answer and needs the same table every time.

## Failure modes & pitfalls

- **Both model hosts down:** no plans, generated queries or explanations; templates from a form, the statistics and the hypotheses table still work, and the app says so. One host down leaves a replica for the ≈ 0.65 streams at burst.
- **Trace API slow:** the 6 s deadline passes; hypotheses show with "sensor evidence pending" and confidence drops a bin.
- **A renamed tool:** its events vanish into quarantine; the coverage alert fires the same day, equipment engineering fixes the mapping, and affected answers get a `gap`.
- **Stale graph after maintenance:** an E10 downtime with no work order becomes "CMMS record pending"; when the record lands, answers whose window it changes are flagged.
- **A whole-graph scan:** refused by `EXPLAIN` or stopped by the 5 s timeout and 512 MB cap on an assistant-only replica; the engineer sees "narrow the window".
- **Ranker drift on a new module:** the replay gate and online rejection of "high" above 40% catch it; a module with fewer than 20 confirmed cases (illustrative) gets "medium" at most.
- **A wrong approved knowledge edge:** an engineer flags it; edges carry approver and date, so the answers that used it are found by edge id.

## Interview framework

1. **Minutes 0 to 5:** users, question types, what exists (MES, FDC, the YMS screen), and the constraint order: IP and scope, no false certainty, correct numbers, latency, cost.
2. **Minutes 5 to 10:** numbers: 1,315 wafers and 42,082 runs a day, 1.77 × 10¹¹ samples; a graph of ≈ 62.7M nodes and ≈ 237.6M edges (≈ 41.1 GB); 1,080 questions a day; 7,040 candidates.
3. **Minutes 10 to 20:** steps 1 to 3: the on-site baseline and why it fails; ontology and identity; linked literals, templates and one guard chain for both stores.
4. **Minutes 20 to 30:** steps 4 and 5: time-matched within-lot statistics with max-T and held-out replication; ranked hypotheses with effect sizes; the waterfall with reasoning tokens.
5. **Minutes 30 to 36:** steps 6 to 8: approved knowledge, verdicts, rolling-origin replay and seeded faults.
6. **Minutes 36 to 45:** one deep dive: identity, query guards, correlation versus cause in time, or the site boundary.

**What interviewers listen for:**

- **Mid:** why a graph, the ontology, read-only queries, statistics in code, an on-site model.
- **Senior:** the identity map and literal linking, the guard chain over two stores, time confounding and within-lot comparisons, max-T versus BH, calibration, reasoning tokens in the latency budget.
- **Staff:** leakage-free evaluation with 300 labels, bitemporal replay, the foundry customer boundary, export-control framing, buy versus build, a cost that is mostly people.

**Red flags:**

- "The LLM finds the root cause"; sensor samples in the graph; free text-to-Cypher with a write-capable user; "we told the model not to write".
- Lot-level commonality on a multi-chamber tool; p below 0.05 on 7,040 tests; a tiny p-value shown as proof; sort-date populations.
- Budgeting a reasoning model without its reasoning tokens.

  <InterviewQuestion question="What role should the LLM play, and what should it not do?" category="Trade-offs" level="Senior" followUps={[{ question: "Why not let an agent choose its own tools for the investigation?", level: "Senior", answer: "The procedure is known (plan, cohort, tests, evidence, replicate, rank, write), so an agent adds variance and latency with no gain, and the same window must give the same table for replay.   - It plans typed investigations, fills template slots the encoder cannot, writes guarded queries for the long tail, explains the evidence, suggests checks and proposes FMEA triples for approval. Its one consequential choice is the plan (lots and metric), so the plan is echoed before any test runs and the metric id comes from the semantic layer, never from model-written SQL.
  - It never computes statistics, ranks, shows p-values, records verdicts or writes to a store; code renders the hypotheses table at ≈ 6.0 s before any model text, and the explanation cannot add, drop or re-rank a row.
  - That keeps the model small in the bill (GPUs are 2.4% of ≈ 9,950 USD a day) and off the path for 56% of lookups, which get their table with no model call before it.
  - The trade-off is less open-ended exploration. The failure to watch is a fluent "the root cause is" or a number the evidence lacks: code blocks the phrase and drops any sentence whose number is not in a cited item, the independent grader samples explanations, and the N3 gate checks that "high" is confirmed ≥ 60% with a lower bound ≥ 50%.
