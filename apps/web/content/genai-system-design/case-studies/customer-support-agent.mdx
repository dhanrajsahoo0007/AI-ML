Design an agent that answers Brightpost's customers, follows its support procedures and moves money on their behalf.
The hard parts are the refunds it must not make, knowing when to hand over to a person, and proving that tickets are resolved rather than abandoned.

- Interviewers use this question to see whether you keep money and policy decisions out of the model, and whether you can define and measure "resolved".

## Overview

- A small model **routes** each message to a **procedure**, to a grounded **answer**, or to a person; a procedure is a tested script for one intent (its steps, tools and articles).
- Answers get **evidence fetched before the model runs**: hybrid (keyword plus vector) search for 40 candidates, a **cross-encoder** reranker that reads question and chunk together, a 2,000-token budget.
- The model **reads** orders as the verified customer and **asks** for refunds by naming items and a reason; a **policy service in code** computes the amount, checks it and pays once through a ledger.
- Write tools wait for a **bad-actor check**; a **supervisor check** (rules, then a small model) reviews every reply; aggregate **circuit breakers** cap automatic refunds per hour.
- Every case can reach a **person with a summary**; resolution is reported in three buckets (by the agent, with an approval, handed off) by a 7-day, any-channel rule.
- Releases pass a **simulator** run four times per scenario (**pass^4**: all four runs must pass) and a **canary** on 5% of traffic with same-day leading metrics.

## API design

| Call | Who calls it | When |
| --- | --- | --- |
| `POST /v1/conversations` | Chat widget | Customer opens chat; returns `conversation_id` |
| `POST /v1/conversations/{id}/messages` | Chat widget | Each customer message; the response is a Server-Sent Events (SSE) stream |
| `POST /v1/inbound/email` | Email provider webhook | An email; joins a case only on a verified customer match |
| `POST /v1/verify` | Chat widget, email link | A one-time code binds an email or a guest to a customer |
| `POST /v1/conversations/{id}/feedback` | Chat widget | "Did this solve it?" |
| `POST /internal/refund-requests` | Orchestrator (tool call) | The model asks for a refund |
| `POST /internal/approvals/{id}/decision` | Support staff | Approve or reject a refund over £30 |
| `POST /internal/handoffs` | Orchestrator | Open a helpdesk ticket with a summary |
| `POST /v1/webhooks/payments` | Payment provider | A refund settled, failed, or was made outside the agent |
| `POST /v1/webhooks/helpdesk` | Helpdesk | A person replied, or the case closed or reopened |

The message endpoint streams progress events; the reply arrives whole, after its check.

```http
POST /v1/conversations/c_81f2/messages
Authorization: Bearer <customer session>
Idempotency-Key: msg_5b19
Accept: text/event-stream
{ "text": "My kettle arrived cracked. It's order 4471. Can I get my money back?", "attachments": ["img_77"] }

200 OK
event: typing    data: {}
event: status    data: {"text": "Checking your order…"}
event: action    data: {"type": "refund", "order_id": "4471", "amount": "42.00", "status": "pending_approval"}
event: message   data: {"text": "I've asked a colleague to approve your £42.00 refund…", "citations": ["kb/damaged-on-arrival"]}
```

The refund tool names items and a reason; it never names an amount or a customer.

```json
{ "name": "request_refund",
  "description": "Ask for a refund of items on the verified customer's order. The policy service computes the amount and decides.",
  "input_schema": { "type": "object", "required": ["order_id", "items", "reason"],
    "properties": { "order_id": {"type": "string"},
      "items": {"type": "array", "items": {"type": "object", "properties": {"line_item_id": {"type": "string"}, "quantity": {"type": "integer"}}}},
      "reason": {"enum": ["damaged", "not_arrived", "wrong_item", "return_received"]},
      "evidence_ids": {"type": "array", "items": {"type": "string"}} } } }
```

- **Tools per procedure:** `get_order`, `list_orders`, `get_tracking`, `request_refund`, `request_reship`, `cancel_order`, `escalate`, and a read-only `search_help` for side questions.
- **Two retrieval paths:** a procedure prefetches its own articles by id, with no search. When no procedure is active (about half of messages), a knowledge search runs on the raw message in parallel with the router: wasted if the router then picks a procedure, but it costs 0.0005 USD (illustrative) and keeps a question inside 2.5 s.
- **Retries:** every attempt carries an attempt id (the tool-call id). The same attempt id returns the same result; a reused attempt id with a different payload is `409 idempotency_mismatch`.
- **Paying twice:** any `pending_approval`, `submitted` or `refunded` request on the same items blocks a new attempt. A retryable refusal (`needs_evidence`, `breaker_open`), a `failed` payment or a `withdrawn` request allows one. A `pending_approval` request can be withdrawn when the customer changes their mind; a `submitted` one cannot.
- **One order at a time:** the policy service locks the order's ledger row while it decides. Requested, submitted, pending and refunded amounts all count against the order's paid total.
- **Refunds made elsewhere:** staff refunds in the payment console arrive by webhook and by hourly reconciliation, so they count too. The ledger row id is the payment provider's idempotency key; provider keys expire, so after a long outage reconciliation looks the payment up by ledger id before any new attempt.
- **Amount and destination:** computed from item prices, quantities and the shipping rule, paid only to the original payment method. Store credit is a separate, lower tier.
- **Evidence:** a `damaged` or `wrong_item` claim needs evidence for each item. An automatic damaged refund covers one item per claim; more goes to a person.
- **Errors:** `200 refunded` · `202 pending_approval` · `422 refused` (`not_owner`, `already_refunded`, `outside_window`, `needs_evidence`, `breaker_open`) · `409 idempotency_mismatch` · `503 payments_unavailable`.
- **`503` and `422`:** a `503` waits in the workflow and the agent says an email will follow. `needs_evidence` asks for the photo; `breaker_open` holds the request in the workflow with a stated reply time. A final refusal (`not_owner`, `outside_window`, `already_refunded`) never ends the conversation: it hands over to a person, because a refusal can touch statutory rights.
- **The agent never says "refunded" before `200 refunded`.**

## Data model

| Data | Store type | Why (driver ids) | Partition key | Consistency | Rejected alternative and its cost |
| --- | --- | --- | --- | --- | --- |
| Cases, messages, case state | Relational database (<TechIcon id="oss/postgresql" /> PostgreSQL) | One case across channels; read-your-writes; a version column for the per-case lease (F6, G5, G7) | None needed (≈ 18 M cases a year); index on `customer_id` | Strong per case | A document store: hand-offs and reports join customers and actions |
| Refund ledger, order snapshots, audit snapshots | Relational database (<TechIcon id="oss/postgresql" /> PostgreSQL), owned by the policy service | Row lock per order, unique attempt id, sums against the paid total in one transaction (F4, G2, G8) | `order_id` | Strong | Calling the payment API directly: no record, no lock, no sum |
| Help-centre index | Search engine with keyword and vector fields (<TechIcon id="oss/elasticsearch" /> Elasticsearch or OpenSearch) | Product codes need keywords, phrasing needs vectors; 22 MB (F1, G6) | Single shard | Eventual, ≤ 10 minutes | A dedicated vector database: a second system for 3,600 chunks |
| Message throttles, hot case cache, case leases | In-memory store (<TechIcon id="oss/redis" /> Redis) | Per-message limits and the hot case on every turn; money limits never live here (G5) | `customer_id` | Best effort, rebuilt from the database | Money limits in Redis: a lost counter resets a refund limit |
| Traces and outcomes | Columnar store (<TechIcon id="oss/clickhouse" /> ClickHouse) | 1.6 GB a day scanned for evals and dashboards (F7) | Day | Eventual | Traces in the case database: scans compete with live traffic |
| Evidence (photos) | Object storage | Shown to approvers, kept with the audit snapshot (G11) | Case id | Write once | Photos inline in messages: no retention rules |
| Procedures, prompts, eval sets | A versioned registry | Every release names exact versions (G8) | n/a | Versioned | Prompts edited live: no rollback, no audit |

- **The registry's owners:** support operations author procedures, the simulator gates them, and engineers review any new tool.

The case store keeps the case state that code writes from tool results.

```sql
CREATE TABLE cases (
  case_id      uuid PRIMARY KEY,
  customer_id  bigint,                -- null until verified; then from the session, never from the model
  channel      text,                  -- 'chat' | 'email'
  intent       text,                  -- 'damaged_item', set by the router
  procedure    text,                  -- 'damaged_item@v7'
  state        jsonb,                 -- verified facts, steps done, pending action
  status       text,                  -- 'open' | 'handed_off' | 'closed'
  version      int NOT NULL,          -- the lease: an update must carry the version it read
  updated_at   timestamptz
);
CREATE INDEX ON cases (customer_id, updated_at);
```

The policy service owns the ledger; one row per attempt, one lock per order.

```sql
CREATE TABLE refund_requests (                 -- the policy service's ledger
  request_id    uuid PRIMARY KEY,              -- one row per attempt; the provider's idempotency key
  attempt_id    text UNIQUE NOT NULL,          -- the tool-call id: a retry of the same attempt replays its result
  payload_hash  text NOT NULL,                 -- a reused attempt id with another payload: 409
  order_id      text NOT NULL,                 -- the order row is locked while deciding
  customer_id   bigint NOT NULL,
  items         jsonb NOT NULL,                -- [{line_item_id, quantity}]
  amount_minor  int NOT NULL,                  -- computed by the policy service: 4200 = £42.00
  destination   text NOT NULL,                 -- 'original_payment_method'
  status        text NOT NULL,                 -- requested | pending_approval | submitted | refunded | failed | refused | withdrawn
  reason_code   text,
  provider_refund_id text,
  approved_by   text, approved_at timestamptz,
  audit         jsonb,                         -- prompt version, evidence ids, tool results, model's stated reason
  created_at    timestamptz
);
CREATE TABLE order_snapshots (order_id text PRIMARY KEY, paid_minor int, items jsonb, refunded_minor int);
```

The help index holds one document per chunk; Redis holds only what can be rebuilt; ClickHouse holds one row per span.

```text
help index:  { chunk_id, article_id, version, audience: "customer", title, text, embedding[1536], updated_at }

lease:case:{case_id}      -> orchestrator id, with a TTL renewed at each step
throttle:msg:{customer}   -> messages in the last minute
case:hot:{case_id}        -> cached copy of the case row, invalidated on write

CREATE TABLE spans (day Date, case_id UUID, turn UInt16, stage LowCardinality(String),
  model String, tokens_in UInt32, tokens_cached UInt32, tokens_out UInt32, ms UInt32,
  verdict String, payload String CODEC(ZSTD)) ENGINE = MergeTree ORDER BY (day, case_id, turn)
```

- **Lease:** one orchestrator at a time owns a case; it renews a Redis key while it works and writes only if the case's version is unchanged.
- **Case state:** written by code from tool results; fields the model proposes are checked against tool results before they are stored.
- **Access patterns:** load the case each turn under its lease; lock one order row per refund decision; sum a customer's refunds over 7 and 30 days from the ledger.
- **More access patterns:** chunks filtered to `audience = customer`; traces scanned by day; evidence fetched by case id for the approval card.

## Building the architecture, step by step

- We start from one model call and add a part only when a requirement or a driver forces it.
- Each figure shows the design after that step; the step's new parts are outlined and the moving dots show its flow.

### Step 1: One model call (F1)

The baseline: the customer's message goes to one model, and its reply comes back.

<AnimatedDiagram spec="animated/support-agent/architecture" step={1} caption="Step 1: a chat gateway, an orchestrator and one model behind the platform’s LLM gateway. It answers, but from memory." />

- **Adds:** the chat gateway (sessions, limits, SSE), the orchestrator, the platform's LLM gateway, the agent model.
- **Flow:**
  1. The customer's message reaches the chat gateway.
  2. The orchestrator builds a prompt and calls the model through the LLM gateway.
  3. The reply goes back over the stream.
- **Why this and not that:** start with the simplest design that can pass the evals (P1). The LLM gateway is the platform's: it holds the keys, token limits and the fallback model.
- **The gap:** the model invents Brightpost's policy from what it learned in training.

<PremiumBreak />

### Step 2: Ground answers in the help centre (F1)

<AnimatedDiagram spec="animated/support-agent/architecture" step={2} caption="Step 2: a retriever and reranker over the help index; the sync job re-indexes an edited article in minutes." />

- **Adds:** the retriever and reranker, the help index, the help-centre sync.
- **Flow:**
  1. Hybrid search (keywords and vectors) returns the top 40 chunks.
  2. A cross-encoder reranker scores each chunk against the question; the best that fit 2,000 tokens go into the prompt.
  3. The model answers and cites the articles it used.
  4. When an article is edited, the sync job re-chunks and re-embeds it, inside N7's 10 minutes.
- **Why this and not that:** retrieval, not fine-tuning, because articles change weekly (P2, G6). A **cross-encoder** reads the question and the chunk together, so it ranks better than vector distance alone.
- **The gap:** 80% of intents (order status, damage, returns, account) need a tool or an action, and search cannot answer them.

The retrieval funnel shows where the 40 candidates come from and what the reranker costs.

<AnimatedDiagram spec="animated/support-agent/retrieval-funnel" caption="3,600 chunks narrow to 40 candidates, then to the 5 that fit the 2,000-token budget. The reranker costs about 150 ms and 0.0005 USD (illustrative)." />

**How to read it:**

- Each band is one stage; its width is the number of chunks still in play.
- The label on the reranker band is its cost; the gate under the last band is the recall target that keeps it.

**The numbers:**

- 1,200 articles × 3 chunks = 3,600 chunks; 2,000 tokens ÷ 400 tokens a chunk = 5 passages kept.
- The reranker adds about 150 ms (illustrative), but it runs alongside the 250 ms router, so the question turn does not wait for it.
- Gate: recall@5 (the share of queries whose right article is in the top 5) ≥ 90% on 300 labelled queries (illustrative); if vector search alone matches it, drop the reranker.

### Step 3: Route each message to a procedure (F2)

<AnimatedDiagram spec="animated/support-agent/architecture" step={3} caption="Step 3: a small-model intent router picks a procedure, with its own tools and articles, or asks the customer to clarify." />

- **Adds:** the intent router.
- **Flow:**
  1. A small model returns the intent and a search query as structured output.
  2. A threshold fitted on 2,000 labelled messages turns its score into a calibrated confidence.
  3. Confident: start the procedure with its tools and its articles; unsure: ask; off-topic: decline politely.
- **Why this and not that:** a procedure makes each intent testable on its own and gives it its own autonomy level (P1). The router itself is the cheap path (P3); order status, 40% of intents, can move to the small model once its procedure passes the simulator there (a lever, not in the 0.036 USD).
- **The gap:** procedures need the customer's orders, and the customer must be who they say.

### Step 4: Verify, then read orders as the customer (F3)

<AnimatedDiagram spec="animated/support-agent/architecture" step={4} caption="Step 4: order tools call the orders and payments API with the verified customer id that the platform adds, never one the model wrote." />

- **Adds:** the order tools; the orders and payments API (external).
- **Flow:**
  1. A signed-in session, or a one-time code for email and guests, gives the case a `customer_id`.
  2. The model calls `get_order(4471)`; the platform adds the `customer_id` to the call.
  3. The API answers only for that customer's orders; code writes the result into the case state.
- **Why this and not that:** identity comes from verification, never from the model, so persuasion cannot widen what it reads (P11, G9).
- **The gap:** reading is not refunding.

### Step 5: Refunds through a policy service (F4)

<AnimatedDiagram spec="animated/support-agent/architecture" step={5} caption="Step 5: the model asks; the policy service locks the order, computes the amount, checks every rule and pays once through its ledger." />

- **Adds:** the policy service, the refund ledger, the refund workflow and reconciliation, risk signals.
- **Flow:**
  1. The model calls `request_refund` with items and a reason.
  2. The policy service locks the order and computes the amount from item prices.
  3. It checks the owner, the 30-day window, the evidence, the customer's 7- and 30-day totals and the breaker.
  4. Up to £30, the workflow pays once; above £30, the request is `pending_approval` and a person decides.
- **Why this and not that:** money rules and amounts live in code (P10, G2). Tiers, per-customer caps and an hourly breaker bound the blast radius (P12, G10).
- **The gap:** the words can still be wrong, and a write could fire on a conversation already flagged as abuse.

### Step 6: Check actions and words (F1, F4)

<AnimatedDiagram spec="animated/support-agent/architecture" step={6} caption="Step 6: write tools wait for the bad-actor verdict; every reply passes rules, then a small-model judge, before it is sent." />

- **Adds:** the checks: a bad-actor gate and a supervisor.
- **Flow:**
  1. A bad-actor classifier runs in parallel with the model; write tools wait for its verdict and for a rule check on the proposed call.
  2. Each reply passes rules first, then a small-model judge for grounding, policy and tone.
  3. Pass: send; fail: revise once; fail again: hand over.
- **Why this and not that:** a cascade from cheap to expensive: rules, a small model, then a person (P4, G3). Actions are checked before they happen; words before they are sent.
- **The gap:** some cases need a person, and an email follow-up starts from nothing.

### Step 7: Hand over with a summary; one case across channels (F5, F6)

<AnimatedDiagram spec="animated/support-agent/architecture" step={7} caption="Step 7: the case store keeps one case across chat and email; hand-offs and approvals reach staff in the helpdesk with a summary." />

- **Adds:** the helpdesk, support staff, the case store.
- **Flow:**
  1. A trigger fires; a mid-size model writes a summary from this customer's tool results.
  2. The summary keeps verified facts apart from customer claims, and goes to the helpdesk.
  3. Approvals over £30 arrive in the same queue with the photo and the history.
- **Triggers:** the customer asks (that turn) · a legal or chargeback threat · signs of vulnerability · negative sentiment twice · two failed attempts · low router confidence twice · a final refusal · an action above the limit.
- **Why this and not that:** an escape hatch the customer can always reach (P15); a case-state block instead of raw logs keeps the context flat (P8, G7). Out of hours, the ticket states a reply time.
- **The gap:** nobody can say whether "closed" meant solved.

### Step 8: Measure resolution and learn (F7)

<AnimatedDiagram spec="animated/support-agent/architecture" step={8} caption="Step 8: traces and outcome events feed three-bucket resolution, the simulator and a weekly content-gap report." />

- **Adds:** outcomes and content gaps, the simulator and evals, the trace store.
- **Flow:**
  1. Every turn is traced; outcome events (a settled refund, a repeat contact) join the case.
  2. Resolution is counted in three buckets by the 7-day rule; a small-model judge reads every conversation.
  3. Failures become simulator scenarios; a weekly content-gap report goes to article owners.
- **Why this and not that:** evaluate continuously (P16) and close the loop (P15), so autonomy per intent grows only on evidence.
- **The gap:** none; this loop decides each intent's autonomy level.

## Component choices and why

- Every box in the final diagram: what we picked, why, and why the usual alternatives lose. Driver ids (G) refer to the drivers table; F and N to the requirements.

### Orchestration: an intent router and procedures

- **Choice:** a small-model router picks one of a handful of procedures; each procedure has its own steps, tools, articles and autonomy level.
- **Why:** each intent gets its own write tools, limits, rollout and tests (G8, G10, F2, P1).
- **Why not one agent with every tool:** rollout and limits cannot be set per intent, and every change re-tests every intent.
- **Why not multi-agent hand-offs (triage, then specialists):** more model calls a message and context lost at each hand-off. Revisit when one procedure outgrows one agent.

### Agent model: a mid-size frontier model

- **Choice:** a mid-size frontier model (for example Claude Sonnet 5.5, as of November 2026) behind the platform's LLM gateway.
- **Why:** multi-step tool use and policy reading at 0.0076 USD a message on average (G4, N4).
- **Why not the largest model:** higher price and first-token time; choose it only if it beats the mid-size model on the refund simulator by a set margin.
- **Why not a small model everywhere:** keep it for routing and checks until it passes the refund simulator (G2).
- **Why not our own fine-tuned model:** volume is not the problem (200,000 messages a day); labelled outcomes and a training team are. The traces collected now are the start of that set.

### Router: a small model with a calibrated threshold

- **Choice:** a small model with structured output (intent, search query), and a threshold fitted on 2,000 labelled messages.
- **Why:** about 0.0001 USD and 250 ms (G3, G4, P3); confidence comes from the calibration, not from the model's self-report.
- **Why not keywords:** they miss "it came in pieces".
- **Why not nearest neighbour on embeddings:** workable, but the small model also writes the search query and splits two intents in one message, handled in order.

### Retrieval: hybrid search, top 40, a cross-encoder, a 2,000-token budget

- **Choice:** keyword and vector search together for 40 candidates, a cross-encoder reranker, the best chunks that fit 2,000 tokens; a procedure prefetches its articles by id.
- **Why:** 98% groundedness needs the right article in the window (G1, N2, G6); the knowledge-heavy τ-knowledge benchmark (How real systems do it) shows agents fail at both retrieval and reasoning over documents.
- **Why not the top 5 by vector only:** measure recall@5 with and without the reranker on 300 labelled queries; that is the gate.
- **Why not an LLM as reranker:** a model call per query on the latency path, about a second (illustrative), against 150 ms.
- **Why not our own reranker now:** a trained reranker needs a large labelled set (Fin's used 400,000 queries labelled by a model; How real systems do it); the traces collected now are the start of that set.

### Help index: a search engine with keyword and vector fields

- **Choice:** <TechIcon id="oss/elasticsearch" /> Elasticsearch or OpenSearch, one index, one shard, with an `audience` field.
- **Why:** hybrid search in one query; product codes need exact keywords; 22 MB fits one node (F1, G6, N7).
- **Why not a dedicated vector database:** a second system to run for 3,600 chunks.
- **Why not PostgreSQL with a vector extension:** workable; weaker keyword ranking.

### Policy service: code, its own ledger, a durable workflow

- **Choice:** a service the model cannot bypass: it computes amounts, checks rules and limits, owns the refund ledger in <TechIcon id="oss/postgresql" /> PostgreSQL, and starts the payment workflow.
- **Why:** the amount and every limit are code (G2, G8, N5, P10).
- **Why not rules in the prompt:** injection and persuasion change what the model asks for.
- **Why not letting the model call the payment API:** no amount rule, no lock, no record.

### Workflow engine: approvals and payment retries

- **Choice:** a durable workflow engine (Temporal-style) for each refund: wait for approval, call the provider, retry, settle.
- **Why:** a refund waits hours for approval and retries a failed provider call without losing state (F4, G8, G12).
- **Why not a table plus a cron job:** workable at 3,000 a day; the engine gives timers, retries and history without writing them.

### Checks: a bad-actor gate on writes, then a supervisor cascade

- **Choice:** a bad-actor classifier in parallel with the model that write tools wait for; on every reply, rules, then a small-model judge.
- **Why:** actions are checked before they happen, words before they are sent, for 0.0004 USD a message (G1, G2, G3, P4).
- **Why not a mid-size judge on every reply:** about 20 × the cost (0.006 against 0.0003 USD for the same 2,800-token check) and about a second of latency (illustrative).
- **Why not checking the reply only:** by then a £30 refund is paid.

### Conversation store: PostgreSQL with a per-case lease

- **Choice:** <TechIcon id="oss/postgresql" /> PostgreSQL for cases and case state; a lease (version column plus a <TechIcon id="oss/redis" /> Redis key) per case.
- **Why:** two quick messages, or a chat and an email, must not run the case twice (F6, G5, G7).
- **Why not state only in the prompt history:** lost on hand-off, and it grows without bound.

### Trace store: ClickHouse

- **Choice:** <TechIcon id="oss/clickhouse" /> ClickHouse, one row per span, partitioned by day, 90 days kept.
- **Why:** 1.6 GB a day scanned for evals, dashboards and resolution (F7, G1, G8).
- **Why not the case database:** scans compete with live traffic.

### Hand-off: the existing helpdesk

- **Choice:** hand-offs and approvals become helpdesk tickets with the summary and the evidence.
- **Why:** staff already work there; one queue with the evidence on the card (F5, N6).
- **Why not a new console:** two queues to watch.

### Transport: POST plus Server-Sent Events

- **Choice:** each message is a POST whose response is an SSE stream of `typing`, `status`, `action` and `message` events.
- **Why:** events flow one way, server to client, and progress shows within 1 s (N3, G3).
- **Why not WebSockets:** a two-way socket for what is a request and a reply.
- **Why not polling:** progress events arrive late.

## Evaluation and release gates

| Offline set | Size | Source | What it checks |
| --- | --- | --- | --- |
| Golden set | 200 tickets | Real tickets, labelled; includes article and procedure collisions | Expected tool calls and end states |
| Refund scenarios | 150 × 4 runs | Simulator with personas and mocked APIs | pass^4: ledger and reply agree on all 4 runs |
| Other scenarios | 500 | Simulator | Each procedure end to end |
| Retrieval queries | 300 | Labelled from search logs | recall@5 |
| Injection and social engineering | 300 | Red team, in 5 languages and encodings | Zero tool calls on another target |
| Seeded unsupported claims | 200 | Edited replies | The judge's recall |

- **pass^k** means a scenario passes only if all k runs pass; one run per test hides an agent that succeeds 3 times in 4.
- **Gates:** pass^4 ≥ 90% on refund scenarios (± 5 points at 150); groundedness ≥ 98% on 753 statements; judge recall ≥ 0.95 on seeded claims; recall@5 ≥ 90% (illustrative).
- **Injection gate:** 0 failures in 300 cases; by the rule of three, the true failure rate is then at most 1% (3 ÷ 300) at 95% confidence.
- **Judge calibration:** 200 replies graded by staff; agreement (Cohen's kappa) ≥ 0.7 before the judge gates anything.
- **Online:** three-bucket resolution, repeat contact, CSAT (customer satisfaction score) against people's tickets, hand-off rate and reason per intent, approver override rate by band, seeded approvals caught, automatic refunds per hour, cost per conversation.
- **Judging live traffic:** a small-model judge on 100% of conversations (50,000 × 0.0008 = 40 USD a day); human review of 10% at launch, stepping down to 2% (illustrative).

Each intent climbs the same three rungs, and every release canaries before it reaches everyone.

<AnimatedDiagram spec="animated/support-agent/rollout" caption="Shadow, then assist, then autonomous, per intent; each rung opens only when its gate passes, and a canary can stop any release the same day." />

**How to read it:**

- Left to right are the rungs: shadow (drafts never sent), assist (staff approve drafts), autonomous; the gate under each arrow is what opens it.
- The canary strip below is every release: 5% of traffic with leading metrics and early-stop thresholds.

**The numbers:**

- Shadow runs 2 weeks and logs the refunds the agent would have made against what staff did; assist opens autonomy when 90% of drafts are sent unedited (both illustrative).
- The canary is 5% of 50,000 = 2,500 conversations a day; leading metrics (hand-off rate, judge scores, refunds per conversation) read the same day.
- A 2-point resolution drop needs about 4,700 canary conversations to detect: (1.96 + 0.84)² × 0.6 × 0.4 ÷ 0.02² ≈ 4,700 (5% two-sided, 80% power, the 95% control arm treated as known); ≈ 2 days, then 7 more days for the 7-day rule to confirm it.

<Callout tone="red" title="What breaks">
  Raise the £30 limit because approvers say yes to almost everything, and you may be measuring rubber-stamping. Seeded canary approvals that should be rejected prove the approvals are real decisions.
</Callout>

- **The gate that blocks a release:** any refund scenario below pass^4 90%, any injection failure, or groundedness below 98%.
- **Raising the £30 limit:** one band at a time (£30 to £50) behind a canary, only when the override rate in that band is under 2% (illustrative) on at least 150 approvals (0 overrides in 150 puts the true rate under 2% by the rule of three) and sampled audits are clean.
- **Also required:** fraud loss and chargebacks per £ refunded flat, and seeded canary approvals caught. Above £150 needs two people (illustrative).

## Deep dives

### Never pay twice: the refund path end to end

- **Ledger states:** `requested → pending_approval → submitted → refunded | failed`, plus `refused` and `withdrawn` (only from `pending_approval`); every open state counts against the order's paid total.
- **The order lock:** the policy service takes a row lock on the order snapshot, sums every open and settled request, and decides inside one transaction.
- **Two jobs, two mechanisms:** the attempt id makes a retry replay its first result; the lock and the sum stop a second attempt on the same items.
- **Reconciliation:** an hourly job compares `submitted` rows with the provider and repairs them, looking each payment up by ledger id before any new attempt because provider keys expire; refunds made outside the agent arrive by webhook and are inserted as rows.
- **Two messages in a row:** messages that arrive within a short window are coalesced before the model call; a later message sees any pending request in the case state and can withdraw it.

The sequence follows four refunds through the customer, the agent, the policy service and the payment provider.

**The numbers:**

- 3,000 refunds a day; 25% above £30 = 750 approvals at 2.5 minutes = 31 staff hours.
- Breakers: the per-conversation ratio stays flat on an honest sale day, and the absolute £ per hour is checked against that day's forecast; an exploit that brings its own traffic can keep the ratio near baseline, which is why the absolute cap exists.
- Worst case: one call is at most £30, refunds go only to the original payment method and never above the paid total, and a wave is bounded by the absolute hourly cap.

<Callout tone="red" title="What breaks">
  An idempotency key built from the order, the items and the reason looks safe, but it blocks the honest retry after `needs_evidence` forever. Use the attempt id for retries and the order lock with the sum for duplicates.
</Callout>

### What counts as resolved

- **Closed is not resolved:** a customer who gives up also closes the chat.
- **The rule:** no hand-off, no repeat contact about the same order or issue on any channel within 7 days, and the end state confirmed (refund settled, order found).
- **Three buckets:** resolved by the agent alone, resolved with an approval, handed off. The middle bucket keeps staff work out of the agent's headline.
- **Proactive updates:** "where's my refund?" contacts inside the stated settlement window are answered proactively and not counted as repeats.

The funnel takes one day's conversations from "ended without a person" down to "resolved".

<AnimatedDiagram spec="animated/support-agent/resolution-funnel" caption="68% of conversations end without a hand-off, but only 60% are resolved once repeat contact and the end state are checked." />

**How to read it:**

- Each band removes one way a conversation can look solved without being solved; the side branch is the 16,000 hand-offs.
- The last band splits into the two resolved buckets: by the agent alone and with an approval.

**The numbers:**

- Illustrative: 50,000 conversations → 34,000 ended without a hand-off (68%) → 31,500 with no repeat contact in 7 days → 30,000 with the end state confirmed: 60%.
- Of the 30,000: 29,300 by the agent alone and 700 with an approval; 16,000 handed off.
- A "closed" metric would report 68%: 8 points, or 4,000 conversations a day, of customers who were not helped.
- A vendor's billed resolution may count assumed resolutions; the definition is the number to audit (How real systems do it).

<Callout tone="red" title="What breaks">
  Count only one channel and a customer who emails after a chat looks resolved twice. The repeat-contact check joins on the verified customer and the order, across chat and email.
</Callout>

### Worked example: the cracked kettle

1. Message in at 0 ms; "typing" at 30 ms; router `damaged_item` and the article prefetched by id (no search) by 280 ms.
2. First tool call `get_order` at 1,075 ms, when "Checking your order…" appears; second tool call `request_refund` at 2,050 ms.
3. The policy service returns `pending_approval` at 2,250 ms; the reply is checked and sent at 4,450 ms.
4. Tokens: 3 agent calls with 3,300 + 300 + 300 uncached tokens (the article is in the first call): 0.00717 + 0.0015 + 0.00243 + cache writes 0.0018 ≈ 0.0129 USD; with router, gate and supervisor (0.0005), ≈ 0.013 USD.
5. Staff spend 2.5 minutes and approve at 10:20; the provider settles R-2291.
6. Day 7 with no repeat contact: resolved, in the "with an approval" bucket.

## Design decisions and why

| Decision | Options considered | Choice | Decided by | What we give up | Revisit when |
| --- | --- | --- | --- | --- | --- |
| Agent shape | One agent with every tool; router + procedures; multi-agent | Router + procedures | G8, G10, F2, P1 | Flexibility on odd requests | "Other" passes 20% of traffic |
| Who sets the refund amount | The model; the model checked against a total; policy computes it | Policy computes it from items | G2, N5, P10 | Goodwill gestures need a separate tier | Never, for money |
| Automatic limit | £0; £30; £100 | £30, raised a band at a time on evidence | G2, G10 | 750 approvals (31 staff hours) a day | Override rate under 2% and audits clean in the next band |
| Aggregate breaker | None; per customer only; per-intent hourly £ cap | Per-intent hourly cap + kill switch | N5, G10, P12 | Honest refunds wait for approval during a spike | Baseline variance too high for 3 × |
| Checks before acting and sending | Reply only; actions and reply | Gate writes on the bad-actor verdict; check every reply | G1, G2, G3 | 300 ms on every reply | Voice, or replies over 500 tokens |
| Retrieval | Top 5 by vector; top 40 + rerank, fetched by the procedure | Top 40 + rerank, prefetched | G1, N2 | 210 ms (in parallel with the router) | recall@5 without the reranker matches |
| Resolution definition | Closed; no person; 7-day any-channel + end state, three buckets | Three buckets, 7-day + end state | G1, N1 | A lower headline number and a week's delay | Never: it is what customers feel |
| Model per stage | One model; small + mid-size | Small for routing and checks; mid-size for the agent | G4, G3, P3 | Two models to evaluate | A small model passes the refund simulator |
| Build or buy | A vendor at 0.99 USD per outcome; build | Build the core, keep the helpdesk | G4, G8 | Owning QA and simulation tooling | Under about 3,770 conversations a day |

## How real systems do it

- **2025, Fin (Intercom):** its reranker, a ModernBERT-large cross-encoder trained on 400,000 queries × 40 candidates, lifted the ranking metrics MAP from 0.521 to 0.612 and NDCG@10 from 0.570 to 0.665 over Cohere Rerank v3.5. Latency held at P50 ≈ 150 ms, reranking cost fell 80%, and an A/B test over 1.5 million conversations raised resolution (p below 0.01; effect size not disclosed).
- **2026, Fin:** a resolution counts when the customer confirms it or leaves without asking for more, and assumed ones are billed; in August 2026 it dropped "Fin Constrained" conversations from the denominator and restated history. It bills 0.99 USD per outcome (resolutions, procedure hand-offs, disqualifications, self-serve routings), so the billed metric is the one to audit.
- **2025 → 2026, checks and simulation:** Decagon's supervisor model reviews every generated message before it is sent, with a bad-actor model running in parallel (2025). DoorDash's LLM-simulated customer with mocked order and refund APIs runs hundreds of conversations in minutes, and raw tool events that misled its chatbot led to a "case state layer" (2026).
- **2024 → 2025, containment:** Klarna's assistant handled 2.3 million conversations, two-thirds of chats, in its first month; in May 2025 its CEO said it would hire people again, yet in November 2025 it still reported the work of 853 agents. Salesforce's help site raised its hand-off rate from about 1% to about 5% on purpose in 2025 and got better results.
- **2024, Air Canada:** a tribunal held the airline liable for its chatbot's invented bereavement refund policy and rejected the argument that the bot was a separate legal entity (812 Canadian dollars in damages and fees).
- **2024 → 2026, benchmarks:** τ-bench (2024) found the best agent under 50% pass^1 across retail and airline, and retail pass^8 under 25%. τ²-bench's leaderboard top is 87.9% pass^1 (read 2026; versions not comparable), while τ-knowledge (2026), a knowledge-heavy banking set, tops out at 37.4% pass^1 and 20.6% pass^4.
- **Where this design differs:** vendors post-train their own answer and reranking models on millions of conversations. At Brightpost's volume an off-the-shelf model and cross-encoder pass the evals, and today's traces are what a later fine-tune needs.

## Failure modes & pitfalls

- **Policy answered from memory:** a wrong promise can make the company liable; groundedness drops in judged replies; articles fetched by the procedure, commitments only from tool results.
- **"Resolved" because the customer gave up:** resolution rises while CSAT falls and repeat contact rises; the 7-day any-channel rule with an end-state check.
- **A trap loop with no way to a person:** hand-off rate low, CSAT low; hand off on the turn the customer asks.
- **A viral refund phrasing:** automatic £ per hour or per conversation spikes; the breaker holds new automatic refunds and pages on-call, the kill switch stops the intent, and the phrasing joins the suite.
- **Stale or duplicate articles:** two answers to one question; re-index on edit, dedupe, and send a content-gap report to article owners.
- **Raw tool logs flood the context:** the agent refers to the wrong order; case state written by code from tool results.
- **Two runs on one case:** duplicate replies or tool calls; a per-case lease and message coalescing.

## Interview framework

1. **Minutes 0 to 5:** clarify volume, channels, actions, the refund limit, and what "resolved" means.
2. **Minutes 5 to 10:** numbers: 50,000 conversations, 5,000 tokens a call, 0.036 USD a conversation, the 2.5 s and 4.5 s targets.
3. **Minutes 10 to 15:** API and stores: the message stream, the refund tool without an amount, the ledger.
4. **Minutes 15 to 30:** Steps 1 to 5: baseline, retrieval, router, verification and read tools, the policy service.
5. **Minutes 30 to 38:** Steps 6 to 8: checks, hand-off, resolution and evals.
6. **Minutes 38 to 45:** one deep dive: paying twice, or what "resolved" means.

**What interviewers listen for:**

- **Mid:** retrieval with citations, tools, a refund limit outside the prompt, a hand-off.
- **Senior:** the amount computed in code, a ledger with an order lock and attempt ids, three-bucket resolution, pass^k, rollout per intent, aggregate breakers.
- **Staff:** build or buy against per-outcome pricing and who defines "resolved"; autonomy that grows on evidence (override rates, seeded approvals); the content and QA loop as an operating model.

**Red flags:** limits in the prompt; the model choosing the amount; success measured as tickets closed; one agent with every tool and no evals; no way to a person.

  - Rollout is per intent (order status can be autonomous while refunds are still in assist), and a change to returns re-tests returns, not everything.
  - The router is cheap: a small model at about 0.0001 USD and 250 ms, with a confidence threshold calibrated on 2,000 labelled messages; the cost is flexibility, since odd requests fall to "other" or a person.
  - It fails at the router: a misroute runs the wrong procedure, and an intent can change mid-case; verify with a per-intent confusion matrix on the 2,000 labelled messages and with collision and two-intent tickets in the 200-ticket golden set.

  - Provider token limits break first: 20 calls a second at 5,000 tokens is 6 M input tokens a minute at a normal peak and about 18 M on a sale day; reserve quota through the LLM gateway, and check whether the provider counts the cached reads (only about 1,500 tokens a call are uncached).
  - Approvals come next: 750 a day becomes 2,250, about 94 staff hours, and the 2-hour approval target slips; the breaker is built not to trip on an honest sale, so the fix is staffing planned from the sale forecast.
  - Cost scales with conversations at about 0.036 USD each, so 150,000 conversations cost about 5,400 USD that day.
  - The trade-off on a provider outage: the fallback model gives answers but no refunds, so refund intents hand off and the staff queue grows. Verify with a load test at 36 messages a second against the gateway's token quota before the sale.
