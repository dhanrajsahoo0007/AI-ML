A code assistant is one product with two clocks: inline completion must appear before the next keystroke, and an agent works for minutes on a task.
Completion is budgeted in milliseconds on a small model we serve ourselves; the agent is budgeted in tokens, steps, US dollars and what it may touch.
The hard parts are triggering and cancellation as capacity, keeping a changing repository searchable without shipping it to a server, and making an agent's commands safe by construction.

- Interviewers use this question to see whether you split the paths by budget, treat cancellation as capacity, keep search fresh, fence an agent's commands, network and packages, and pick a metric that cannot be gamed.
- **Running example:** an illustrative IDE assistant sold per seat to companies. The running customer is Brightpost's engineering team (400 developers), whose repo `brightpost-orders` and CSV bug come from the [Coding Agents](/ai-system-design/genai-system-design/coding-agents) page.
- **Labels:** model prices are list prices as of November 2026: a mid-size hosted model 2.00 USD per million input tokens, 0.10 cached, 2.50 to write the 5-minute cache, 10.00 output; a small one 0.10, 0.01, 0.125 and 0.50. Every volume, rate, throughput, latency, model speed, GPU price and salary is illustrative.
- **Terms:** *FIM* (fill in the middle) is a completion that sees the code before and after the cursor; *ghost text* is the grey suggestion Tab accepts; a *next-edit suggestion* proposes an edit elsewhere in the file.
- **More terms:** *typed-through* means the developer types the characters the ghost text already shows; *retained characters* are accepted characters still in the file 10 minutes later.

## Overview

- **Two paths with different clocks.** Completion runs on a small open-weight FIM model we fine-tune and serve in three regions: 225 ms at p50 and ≈ 308 at p95 for every suggestion (265 and ≈ 367 behind a corporate proxy). Chat and the agent use hosted mid-size and small models with prompt caching.
- **Triggering is capacity.** One 75 ms debounce on every key, a client-side pre-request gate, a typed-through cache and cancellation turn 12,000 key events a developer-day into 5,355 requests, 65% of them cancelled.
- **Search on the developer's machine first.** A local grep index and a symbol index serve every path, with an `explore` subagent for open questions; a server embeddings index is an A/B arm on large repositories, not a default. A Merkle tree of file hashes syncs only changed files.
- **Edits applied by the harness, the agent fenced by the OS.** Exact search-and-replace first, then a fast-apply model on the enclosing region. Commands run in an OS sandbox with no network, packages come only through the company's read-only registry mirror, and the agent cannot write its own configuration.
- **Seat economics on the mean seat.** ≈ 31.4 USD a seat a month at list prices, 71% of it the agent, with a heavy decile at ≈ 145. An illustrative 39 USD seat with a 20 USD pooled allowance and overage at list price × 1.25 gives ≈ 32% gross margin, never below 20%.
- **Measured by what is kept.** Retained characters and agent lines still present after 7 days lead; acceptance and a survey are guardrails; public SWE-bench scores only shortlist models.

## API design

| Call | Who calls it | When |
| --- | --- | --- |
| `POST /v1/completions` (HTTP/2, kept alive, pre-warmed on file focus) | IDE plugin | After the trigger rule; carries a `request_id` and the `supersedes` id it replaces |
| Stream reset on `request_id` | IDE plugin | A key that does not match the pending suggestion; the server aborts decode at once |
| `POST /v1/completions/events` (batched) | IDE plugin | `shown`, `accepted`, `partial_accept`, `jump_accepted`, `dismissed`, `retained` (counts at 30 s, 2 and 10 minutes) |
| `POST /v1/index/{workspace}/sync` | Plugin sync worker | 30 s after the last save, on a branch switch, before a cloud task: the root hash, then differing subtrees |
| `POST /v1/index/{workspace}/chunks` | Plugin sync worker | Embeddings arm only: changed chunks, secret-scanned, with HMAC-keyed paths; the server embeds and discards the text |
| `POST /v1/chat` (SSE) | IDE plugin | A chat turn; the client attaches its local grep and symbol candidates |
| `POST /v1/agent/sessions`, `POST /v1/agent/sessions/{id}/steps` | Plugin (local) or task runner (cloud) | Start a task; each model step returns tool calls that the client's policy engine checks before running |
| `POST /v1/apply` (stream) | Plugin | Apply a sketch edit to a region; returns the rewritten region |
| `POST /v1/cloud-tasks` | Plugin, or the issue tracker for organisation members only | A background task in a microVM, ending in a pull request on `agent/<task_id>` in the same repository; a private repository's task never pushes to a public one |
| `GET /v1/orgs/{org}/policy`, `GET /v1/orgs/{org}/audit` | Plugin; admins | Load the managed policy (never from the workspace); export the audit log |

A completion request carries its predecessor's id, so the server can abort the request it replaces.

```http

  "prefix": "…export function parseCsv(text: string): Row[] {\n  const lines = text.split(\"\\n\");\n  for (let i = 0; ",
  "suffix": "\n  return rows;\n}",

  "max_tokens": 64, "stop": ["\n\n"] }

data: {"request_id": "c_9f31", "line": "i < lines.length; i++) {", "show": true, "score": 0.62}
```

- **Agent tools** (the model proposes; the client's harness runs each after the policy check): `grep(pattern, path_glob)`, `find_symbol(name)`, `read_file(path, range)`, `diagnostics(paths)` (≈ 2 s), `semantic_search(query)` (arm only).
- **Writing and acting:** `edit(path, old_str, new_str)`, `apply_sketch(path, region, sketch)`, `run(command)`, `install(package, version)` (ask tier, mirror only), `web_fetch(url)` (asks per new domain).
- **Delegating and finishing:** `explore(question)` (a small-model subagent returning 1,000–2,000 tokens), `ask_developer(question)`, `finish(summary)`, plus tools from allow-listed MCP servers. Pushing and opening a pull request are harness actions, not model tools.
- **Cancellation is the default, not an error:** a superseded request is aborted on the server, and its events never count as dismissals.
- **The client decides what leaves the machine:** the secret scanner and ignore rules run before any prompt, chunk or snippet is sent, and on every tool result before it enters the model's context. Masked values become placeholders the harness substitutes back only inside the sandbox.
- **Edits must match exactly once:** `edit` with 0 or 2+ matches fails with a message the model can act on ("2 matches; include more lines").
- **Every `run` is preceded by a snapshot** of the worktree (a commit to a hidden ref); edits are checkpointed too, because checkpoints of the edit tool alone miss changes made by shell commands.
- **Policy comes from managed settings outside the workspace,** so the agent cannot write the rules that bind it.

## Data model

| Data | Store type | Why (driver ids) | Partition key | Consistency | Rejected alternative and its cost |
| --- | --- | --- | --- | --- | --- |
| Local index: sparse n-gram grep index, symbol table (tree-sitter tags, language-server definitions), Merkle tree | On the developer's machine, anchored to the git commit with a dirty-file overlay | Sub-second search with no upload (G3, G6, G9) | workspace | Strong for the local copy | A server-only index: every search pays a round trip, and the server holds the code |
| Server Merkle tree (hashes, HMAC-keyed paths) | Key-value store | Upload only changed files, for cloud tasks and the embeddings arm (G6) | `workspace_id` | Last write wins per workspace | Re-upload the tree: 3.2 MB a sync for 50,000 files |
| Chunk-embedding cache and embeddings index (arm only) | Key-value store keyed by HMAC(organisation key, chunk); a vector database, one namespace per organisation, int8 HNSW, encrypted with the organisation's key | Never re-embed an unchanged chunk (G4) | `org_id` | Eventual (≤ 2 minutes) | One index across organisations: one filter bug leaks code |
| Agent checkpoints | Locally, hidden git refs on the developer's machine; in the cloud, the task's microVM disk, deleted 24 h after the task | Undo and audit (G8) | session | Strong per session | A server checkpoint store: code at rest on our side |
| Agent sessions | <TechIcon id="oss/postgresql" /> PostgreSQL: steps, tokens, cost, outcome, pull request URL, no code; transcripts per the privacy table | Billing, caps, audit (G8) | `session_id` | Strong | Full transcripts always: breaks N8 |
| Environment snapshots | Object storage per repository, rebuilt on a lockfile change, encrypted per organisation | Cloud setup in 1 minute (G5) | `repo_id` | Versioned by lockfile hash | Clone and install per task: 8 minutes and a fresh supply-chain exposure each time |
| Telemetry | <TechIcon id="oss/clickhouse" /> ClickHouse, counts and timings only | Retained characters, p50 and p95 per stage (F7) | day | Eventual | Logging prompts: breaks N8 |
| Audit log | Append-only store per organisation, exportable | Who ran what, and which rule decided (F6) | `org_id`, day | Append-only | Mixed with telemetry: no per-organisation export |
| Offline suites | Object storage: FIM set, chat questions with gold files, 300 past-issue tasks with containers | Release gates (F7) | suite version | Versioned | Public benchmarks only: contaminated and partly broken |

Telemetry holds counts and timings, never code or paths; the audit log records every decision the policy engine made.

```sql
CREATE TABLE completion_events (           -- ClickHouse; no code, no paths
  day Date, org_id UInt32, user_hash UInt64, request_id String, model_version LowCardinality(String),
  kind LowCardinality(String),             -- 'cursor' | 'next_edit'
  shown UInt8, accepted UInt8, accepted_chars UInt16, retained_chars_10m UInt16, suggestion_chars UInt16,
  latency_ms UInt16, cancelled UInt8, cancel_stage LowCardinality(String), cache_hit UInt8, cache_hit_tokens UInt16
) ENGINE = MergeTree ORDER BY (day, org_id, model_version);

CREATE TABLE audit_events (                -- append-only, per organisation
  org_id bigint, at timestamptz, actor text, session_id uuid,
  action text,                             -- 'run' | 'install' | 'push' | 'mcp_call' | 'web_fetch' | 'policy_change'
  target text, decision text,              -- 'allow' | 'ask:approved' | 'ask:denied' | 'deny'
  rule text, PRIMARY KEY (org_id, at, session_id)
);
```

- **Access patterns:** grep and symbols by workspace on the laptop; the Merkle tree by workspace on each sync; telemetry by day, organisation and model version for A/B tests; the audit log by organisation and day for export, by session for "what did this agent run?".

## Building the architecture, step by step

- We start from one model call that completes code from the open file, and add a part only when a requirement or a driver forces it.
- Each figure shows the design after that step; the step's new parts are outlined and the moving dots show its flow.

### Step 1: A completion from the open file (F1)

The baseline: the plugin sends the code before and after the cursor to a small FIM model and shows the first line it writes.

<AnimatedDiagram spec="animated/code-assistant/architecture" step={1} caption="Step 1: the IDE plugin sends the code around the cursor through the gateway to a small FIM model we serve, and shows its first line as ghost text." />

- **Adds:** the developer and IDE plugin, the gateway (auth, region routing), the FIM model on our own GPUs.
- **Flow:**
  1. A keystroke; the plugin takes the prefix (code before the cursor) and the suffix (code after it).
  2. The gateway authenticates the device token and routes to the nearest region.
  3. The FIM model writes up to 64 tokens; the plugin shows the first line as ghost text, and Tab accepts it.
- **Why this and not that:** the simplest path that completes code (P1). A FIM model sees the suffix, so it closes brackets and matches the code below; a chat model asked to continue text does not.
- **The gap:** a request on every keystroke would be 10,500 a developer-day, most stale before they return, and the model knows only this file.

### Step 2: Make it fast and affordable: gate, cancel, reuse, context (F1, N2)

<AnimatedDiagram spec="animated/code-assistant/architecture" step={2} caption="Step 2: a context assembler in the plugin adds frozen signature, snippet and edit blocks; a debounce, a pre-request gate and cancellation decide which keys reach a GPU, and the server reuses the KV prefix." />

- **Adds:** the context assembler (client part), a typed-through cache, the pre-request gate, cancellation by `supersedes`, a show-or-suppress filter, KV-prefix reuse salted per organisation, prompt-lookup drafting, three regions, next-edit suggestions.
- **Flow:**
  1. The plugin waits 75 ms after every key; if the key matches the ghost text on screen, it trims the suggestion and sends nothing.
  2. The pre-request gate scores cheap features (position in the token, language, the last accept or reject) and drops 40% of triggers.
  3. The request carries frozen blocks (signatures, snippets from open tabs, recent edits), the prefix and the suffix, and names the request it supersedes.
  4. The server aborts the superseded request, reuses 1,510 of 2,000 tokens from its KV cache, and drafts the line from text already in the prompt.
  5. The filter shows or suppresses the line on the model's score; a new key cancels the request.
- **Why this and not that:** budget latency per stage (P5), with every suggestion on the same 225 ms; keep the prefix stable so the KV cache survives keystrokes (P7); a small model on the hot path (P3).
- **The gap:** chat questions need code from files that are not open, and a server-only index would hold every customer's code.

### Step 3: Search the repository without shipping it (F5, F6)

<AnimatedDiagram spec="animated/code-assistant/architecture" step={3} caption="Step 3: a local index on the developer’s machine keeps grep and symbols fresh within a second of a save; a Merkle tree tells the sync service which files changed, for cloud tasks and the embeddings arm." />

- **Adds:** the local index (sparse n-gram grep index, symbol table, Merkle tree), the sync service, the embeddings arm.
- **Flow:**
  1. A save updates the grep and symbol indexes on the laptop within 1 s; the index is anchored to the git commit, with dirty files as an overlay.
  2. The Merkle root changes; 30 s after the last save the sync worker compares hashes and uploads only the changed files, when a cloud task needs them.
  3. In organisations in the embeddings arm, changed chunks are secret-scanned and embedded on the server; the text is discarded.
- **Why this and not that:** keep sensitive data inside a boundary (P17); the simplest index that passes (P1). Grep finds exact names and error strings, which is most of what code questions ask.
- **The gap:** nothing yet turns search results into an answer.

A saved file changes one path of hashes from leaf to root, so the client finds it without listing the repository.

<AnimatedDiagram spec="animated/code-assistant/merkle-sync" stepper caption="One saved file changes one path of hashes: the client compares about 5.1 KB in 4 round trips and uploads only that file, and only for cloud tasks and the embeddings arm." />

- **How to read it:** step 1 is the tree of file hashes, each folder hashed from its children, with one changed path highlighted from the file to the root; step 2 shows what syncs where: grep and symbols stay local, and only cloud tasks and the embeddings arm receive changed files.

**The numbers:**

- 50,000 files at fan-out 20 is ceil(log₂₀ 50,000) = 4 levels; at 64 bytes an entry, one changed file costs 4 × 20 × 64 B ≈ 5.1 KB in 4 round trips, ≈ 200 ms at 50 ms RTT.
- When nothing changed, one root comparison ends the sync; re-uploading the whole tree instead would be 3.2 MB each time.
- The local index is 400 MB of source × 0.3 = 120 MB, built in ≈ 8 s at 50 MB a second; ripgrep answers until it is ready.

### Step 4: Chat over the repository (F2, N3)

<AnimatedDiagram spec="animated/code-assistant/architecture" step={4} caption="Step 4: chat gathers candidates from the local index, reranks them on the server, and a hosted mid-size model answers with file citations." />

- **Adds:** the context assembler (server part) with a reranker, the hosted mid-size model.
- **Flow:**
  1. The developer asks; the panel shows "searching" within 300 ms.
  2. Local grep and symbols find candidates (vectors join in parallel in the arm); the plugin uploads candidate spans, not the repository.
  3. Candidates are fused and 35 reranked by a small cross-encoder; the top ones join the rules, the open file and the question.
  4. The mid-size model streams an answer that cites file paths and lines; suggested code gets an apply button.
- **Why this and not that:** ground before you generate (P2). Rerank 35, not 200: 35 × 400 tokens is 14,000 tokens, 70 ms on one encoder, inside the 1,200 ms first-token target.
- **The gap:** chat proposes code, and someone still has to apply it, run it and fix what breaks.

### Step 5: The agent loop (F3, N4)

<AnimatedDiagram spec="animated/code-assistant/architecture" step={5} caption="Step 5: an agent orchestrator runs search, plan, edit and test steps on the mid-size model, sends open questions to a small-model explore subagent, and records each session." />

- **Adds:** the agent orchestrator, the small hosted model for `explore`, the sessions store.
- **Flow:**
  1. The task arrives; step 1 is a search, so the first tool call is out in ≈ 6.7 s (500 output tokens at 80 a second).
  2. The model plans (the developer may approve the plan), sends open questions to `explore`, and reads files by line range.
  3. It edits, runs `diagnostics` (≈ 2 s), then targeted tests; the done rules require clean diagnostics and passing tests.
  4. Context grows 2,500 tokens a step and is compacted at 100,000; parallel agents each work on their own git worktree.
  5. It finishes with a summary; the session row records steps, tokens, cost and outcome, never code.
- **Why this and not that:** manage context deliberately (P8); count and cap in tokens (P6), with thinking budgets per step type; route exploration to the small model (P3), which saves 0.20 USD a task.
- **The gap:** edits to long files are slow when the model rewrites them, and `old_str` sometimes misses.

**The numbers:**

- On this product the run is 9 mid-model steps (2 edits, 3 checks, 4 searches or reads), context 5,300 → 25,500 tokens, ≈ 0.13 USD and ≈ 2.4 minutes. Both edits are exact `str_replace` calls of about 40 tokens.

### Step 6: Apply edits fast and exactly (F4)

<AnimatedDiagram spec="animated/code-assistant/architecture" step={6} caption="Step 6: the harness applies exact search-and-replace edits itself; a sketch or a missed match goes to our fast-apply model, which rewrites only the enclosing region and returns a diff." />

- **Adds:** the fast-apply model with speculative edits, on our own GPUs.
- **Flow:**
  1. `edit(path, old_str, new_str)` matches exactly once → the harness writes it; done.
  2. A sketch from chat, or 0 or 2+ matches → the apply model rewrites the enclosing region (40 lines), drafting from the original text.
  3. The result is a diff with undo; the checkpoint is taken before it lands.
- **Why this and not that:** constrain the output (P9): one match or a failure the model can fix. Unified diffs with line numbers drift, and models count lines badly.
- **The gap:** the agent now runs commands, installs packages and calls tools that could leak data or destroy work.

Rewriting a region is fast because most of its tokens are already in the original.

<AnimatedDiagram spec="animated/code-assistant/fast-apply" stepper caption="Most of an edited region is copied from the original, so a fast-apply model drafts it and verifies in long runs; an exact search-and-replace still wins at 11.2 s." />

- **How to read it:** step 1 colours the region's tokens: long runs drafted from the original and accepted in one verification step, and short runs the model writes at the edit itself. Step 2 compares four ways to land one edit, end to end from the agent's step to the diff on screen.

**The numbers:**

- Search-and-replace: one edit step of 400 ms + (60 + 800 thinking) tokens × 12.5 ms (the hosted model at 80 tokens a second) + 10 ms in the harness ≈ 11.2 s.
- Sketch and region apply: (400 + 950 × 12.5) + 50 network + 10 prefill + 30 first token + 400 tokens at 1,000 a second ≈ 12.8 s.
- The agent model rewriting a whole 400-line file takes ≈ 60.4 s, a 2,000-line file ≈ 260 s; our apply model rewriting 2,000 lines with speculative edits would take 20 s against 260 s without (the vendor's 13×).
- The apply fleet is a floor of 3 regions × 2 replicas × 720 hours = 4,320 GPU-hours a month (use is ≈ 510), 0.108 USD a seat.

### Step 7: Sandbox, permission tiers, packages, MCP and cloud tasks (F3, F6, N7)

<AnimatedDiagram spec="animated/code-assistant/architecture" step={7} caption="Step 7: a policy engine decides every tool call from managed rules; commands run in an OS sandbox with no network, packages come through a read-only mirror, and cloud tasks run in a microVM that pushes only through a git proxy." />

- **Adds:** the policy engine, the local sandbox, the cloud microVM with a git proxy and the registry mirror, the snapshot builder, allow-listed MCP servers, the reviewer.
- **Flow:**
  1. Each tool call meets the policy engine: deny rules first, then ask, then allow, loaded from managed settings outside the workspace.
  2. Reads and workspace edits run; commands run in the sandbox with no network and no credentials.
  3. `install` is checked by the read-only mirror first (it must exist and pass the age rule), then asks the developer; install scripts stay off.
  4. MCP tools come from the organisation's allow-list; read tools run, write tools ask.
  5. A cloud task starts from an environment snapshot, sees only the mirror, and pushes through the git proxy to `agent/<task>`; a reviewer reads the pull request.
- **Why this and not that:** bound the blast radius (P12); enforce rules in code (P10), because an injected README can talk a model out of a rule; treat what the agent reads as untrusted (P13).
- **The gap:** nobody knows whether a new model helps or only gets accepted more.

### Step 8: Measure what is kept, gate every release (F7, N1)

<AnimatedDiagram spec="animated/code-assistant/architecture" step={8} caption="Step 8: telemetry counts retained characters and kept agent lines, and an evaluation gate runs the FIM set, chat questions and 300 past issues before a staged rollout." />

- **Adds:** the telemetry store, the offline suites, the evaluation and release gate.
- **Flow:**
  1. The plugin reports counts: shown, accepted, retained at 30 s, 2 and 10 minutes, and agent lines still present after 7 days.
  2. A candidate model or prompt runs the FIM set, 300 chat questions with gold files and 300 past issues × 3 runs.
  3. It rolls out to 1%, 10% for a week, 50%, then 100%, skipping organisations that pin models.
- **Why this and not that:** evaluate continuously and degrade gracefully (P16). Raw acceptance rises when a model shows less, so it cannot be the gate.
- **The gap:** none; the gate decides each release.

The walk-through follows one Brightpost developer in the EU, privacy mode on, through all three paths:

1. **Completion:** they type `for (let i = 0; ` in `src/parser.ts`. 75 ms after the space that follows `;`, the gate passes the request, and 2,000 tokens go to the EU region (490 new on average); `i < lines.length; i++) {` appears at ≈ 225 ms, and Tab accepts it.
2. **Retention:** 10 minutes later the 24 accepted characters are still there, so they count as retained.

7. **Kept lines:** seven days later both changed lines are still in the code, so they count as kept (one task, an illustration rather than a measurement).

## Component choices and why

- Every box in the final diagram: what we picked, why, and why the usual alternatives lose. G ids refer to the drivers table; F and N to the requirements.

### Completion model: a small open-weight FIM model, fine-tuned and served by us

- **Choice:** a Qwen2.5-Coder-7B-class model (Apache-2.0 and FIM use stated on the 7B model card, as of November 2026; licences differ by size, so the card of the size we ship is checked), fine-tuned weekly, FP8, on GPUs rented by the hour in three regions. Training data is permissively licensed public code and opt-in data from users outside privacy mode, never privacy-mode code.
- **Why:** chat models do FIM badly, and FIM training did not harm left-to-right quality in Bavarian et al. (2022); our own serving gives abort on cancel, a cache salt per organisation, sticky KV reuse and regional pinning (G3, G9, N2). It costs 5.20 USD a seat with the team included.
- **Why not a dedicated deployment at an inference provider:** 6.32 USD a seat with 2 people instead of 6; the right call below ≈ 47,000 seats, where the team's fixed cost dominates. At 100,000 seats it is close, and control decides.
- **Why not a per-token FIM API:** at Codestral 25.08's list price (0.3 USD per million input, 0.9 output, no cached-input price, as of November 2026) every 2,000-token request costs ≈ 0.0006 USD, cancelled or not: ≈ 48.9 USD a seat.
- **Why not a hosted chat model:** worse at FIM, and a 400 ms first token alone exceeds the budget.
- **Why not on-device:** laptops vary too much for one latency target; it stays the offline fallback.

### Triggering: one 75 ms debounce, a pre-request gate, a typed-through cache, abort by `supersedes`

- **Choice:** every key waits the same 75 ms; a gate on cheap client features keeps 60% of triggers; a key matching the ghost text trims it with no request; each request names the one it supersedes, which the server aborts.
- **Why:** one wait for every key gives every suggestion the same 225 ms, so N2 holds for all of them; from 10,500 possible triggers 5,355 are sent, 65% are cancelled, and 4,200 reach a GPU (G4, G5).
- **Why not a longer wait mid-word:** it moves latency onto the suggestions people see most; an earlier draft's 250 ms mid-identifier wait put about half of all suggestions near 400 ms at p50, over N2.
- **Why not 50 ms:** 389 GPUs instead of 355 (+10%) for 25 ms.
- **Why not 150 ms:** 200 GPUs instead of 355 (−44%), but p50 300 ms at the limit and 340 behind a proxy.
- **Why not without the gate:** 8,925 sent a developer-day instead of 5,355, and 591 GPUs instead of 355.

### Show or suppress: a gate before the request, a filter after it

- **Choice:** the pre-request gate drops what would probably be suppressed (it keeps 95% of what would be shown); a logistic-regression-class filter on the model's score and features then suppresses 68% of what completes.
- **Why:** a generated suggestion that is thrown away wastes GPU work, and a shown suggestion that is rejected costs attention (G1, G4). Both models train on counts and features, never code.
- **Why not tune the threshold for acceptance:** showing less raises acceptance and lowers what is kept (Evaluation and release gates).

### Repository search: local grep, symbols and an `explore` subagent; embeddings as an A/B arm

- **Choice:** a local sparse n-gram grep index and symbol table serve completion, chat and the agent; `explore` runs open questions on the small model; a server embeddings index is offered as `semantic_search` in an arm on repositories over 1,000 files.
- **Why:** in 2026 one vendor moved its agent to a local grep index and another never shipped one, while a third still ships embeddings (How real systems do it); a vendor A/B found +2.6% code retention with embeddings on large codebases in 2025 (G1, G6). The arm decides for our users at a minimum detectable change of ≈ 1.8% on kept lines.
- **Why not embeddings by default:** a second index to run and secure, and embeddings can be inverted back towards the text (G9).
- **Why not grep only, with no arm:** we would never learn whether large repositories need more.
- **Why not a server-only index:** a round trip on every search, and the server holds every customer's code.

### Index sync: a Merkle tree of file hashes with HMAC-keyed paths

- **Choice:** file hashes and folder hashes from their children; paths keyed with the organisation's HMAC key; a chunk-hash cache in the arm, so unchanged chunks are never re-embedded.
- **Why:** one root comparison when nothing changed, ≈ 5.1 KB and 4 round trips to find one changed file (G6). Without embeddings it still matters: a cloud task that starts from uncommitted work uploads only changed files.
- **Why not re-index on a timer:** 100M tokens each time for a 50,000-file repository.
- **Why not upload from laptops for 1M-file monorepos:** server search there is built from the git host's copy per commit.

### Chat and agent models: a hosted mid-size model, a small one for `explore`, thinking budgets per step type

- **Choice:** the mid-size model plans and edits; the small model explores; thinking budgets of 2,000 tokens to plan, 800 to edit, 400 to check and 200 to search or read.
- **Why:** plans and edits need the strongest model we can afford; exploration on the small model saves 0.20 USD a task; the budgets keep the median task at 6.1 minutes and 0.36 USD instead of 12.2 minutes and 0.65 USD with 2,000 on every step (G4, N4).
- **Why not self-host the agent model:** bursty, minutes-long sessions on a model behind the frontier.
- **Why not one model for everything:** completion cannot wait 400 ms for a first token.

### Edit application: exact search-and-replace, then a fast-apply model on the region

- **Choice:** `edit` with an exact `old_str` (or a context-anchored patch for models trained on that format); a sketch or a failed match goes to a 7B-class merge model with speculative edits, on the enclosing region only.
- **Why:** ≈ 11.2 s and ≈ 12.8 s end to end, against ≈ 60.4 s for the agent model rewriting a 400-line file and ≈ 260 s for 2,000 lines (F4, G3).
- **Why not unified diffs with line numbers:** they drift, and models count lines badly.
- **Why not a hosted fast-apply API:** a good start, but another sub-processor under privacy mode; our floor costs 0.108 USD a seat.
- **Why not predicted outputs on a hosted model:** rejected tokens are billed and tool calls are unsupported (as of November 2026).

### Sandbox: OS-level locally, a microVM per cloud task

- **Choice:** bubblewrap on Linux, Seatbelt on macOS, a native Windows sandbox where available; a microVM with its own kernel for each cloud task.
- **Why:** an OS sandbox fences the command and every subprocess with no container to start (G2, N7). Cloud tasks of many organisations share our hosts and run dependencies nobody reviewed, so each gets its own kernel; a container would make one kernel bug a cross-tenant breach.
- **Why not a container on the laptop:** Docker is not on every machine and conflicts with the OS sandbox.
- **Why not permission prompts alone:** people approve on autopilot; a sandbox removes most prompts, so the ones left get read.
- **Why not WSL2 only on Windows:** cross-file-system I/O is slow for Windows-side repositories, so WSL2 or the cloud is the fallback.

### Permissions: a policy engine in the client, deny → ask → allow, from managed settings

- **Choice:** first match wins in the order deny, ask, allow; rules come from the organisation's managed settings, and IDE, harness, MCP, hook and permission files are write-denied.
- **Why:** the order makes a broad deny unbeatable, and policy loaded from the workspace is policy the agent can write (G10, N7).
- **Why not rules in the prompt:** an injected README talks the model out of them (P10, P13).

### Privacy, cloud tasks and pricing

- **Choice:** the privacy-mode table, client scanning of prompts and tool output, a `cache_salt` per organisation; cloud snapshots built without secrets and a git proxy holding the token; an illustrative 39 USD seat with a 20 USD pooled allowance, overage at list price × 1.25.
- **Why:** ignore files are not a security boundary, and shared prefix caches leak through timing (G9). The mean seat costs ≈ 31.4 USD because the heavy decile costs ≈ 145, so a flat seat cannot carry the tail (N5).
- **Why not a 30 USD seat:** the mean organisation's margin falls to ≈ 16%, under N5.
- **Why not unlimited seats:** the heavy tail sets the price for everyone.
- **Why not clone and install per cloud task:** 8 minutes and a fresh supply-chain exposure every time, against 1 minute from a snapshot.

## Latency and cost budget

The completion budget is ten stages from the last key to ghost text, with a spread per stage for p95.

<AnimatedDiagram spec="animated/code-assistant/completion-budget" stepper caption="Every suggestion waits the same 75 ms and lands at 225 ms (≈ 308 at p95); a proxy adds 40 ms and p95 stays under 500, while a longer debounce saves GPU work only by spending p50." />

- **How to read it:** step 1 is the ten stages with each one's p95 spread; step 2 the direct and proxy bars against the 300 and 500 ms target lines; step 3 a typed-through hit (≈ 10 ms) and a developer 150 ms from a region (325 ms, outside N2's scope); step 4 the debounce curve, p50 against GPU work.

**The numbers (ms, illustrative stage values):**

| Stage | p50 | Spread (p95 − p50) | Cumulative |
| --- | --- | --- | --- |
| Debounce after the last key (every key) | 75 | 0 | 0 → 75 |
| Gather context on the client, pre-request gate | 15 | 20 | 75 → 90 |
| Network to the nearest region (kept-alive HTTP/2); spread for both legs | 25 | 60 | 90 → 115 |
| Gateway and auth; queue (M/D/1 at 41% busy) | 5 + 3 | 0 + 15 | 115 → 123 |
| Prefill, 490 new tokens | 12 | 30 (a prefix miss; freshly scaled replicas) | 123 → 135 |
| First line: 12 tokens at 1.5 drafted a step = 8 steps × 6.2 | 50 | 40 | 135 → 185 |
| Show or suppress; network back; render | 5 + 25 + 10 | 0 + 0 + 10 | 185 → 225 |
| **Ghost text** | **225** | √(20² + 60² + 15² + 30² + 40² + 10²) ≈ 83 | **p95 ≈ 308** |

- **Behind a proxy** adding 40 ms at p50 (spread 60, illustrative; 20–100 in practice): p50 265, p95 ≈ 265 + √(83² + 60²) ≈ 367; adding every spread gives an upper bound of 500, at the target. An organisation whose proxy adds more is outside N2, and its admin dashboard says so.
- **Chat first token:** 30 context + 100 local search + 25 upload + 5 fusion + 20 rerank queue + 80 rerank + 10 assemble + 40 provider hop + 700 first token + 25 back = 1,035 ms; p95 ≈ 1,642 (N3: 1,200 and 2,500).
- **Agent:** first streamed text ≈ 450 ms; first tool call ≈ 6.7 s; median task ≈ 6.1 minutes (218.0 s of model at 80 tokens a second, 19.8 s of exploration, 129.9 s of tools); p95 ≈ 18.2. Cloud tasks add 1 minute of setup on a snapshot hit, 8 on a miss.

<Callout tone="red" title="What breaks">
  The first request after an idle connection pays a TLS handshake, 50–100 ms more, and a proxy that re-inspects TLS adds it every time. Keep-alive pings, pre-warming on file focus and bypass guidance for the completion host keep the p95 under 500.
</Callout>

- **How to read it:** step 1 splits the mean seat into fixed cost, agent and chat; step 2 compares organisations of only light, only median and only heavy users: cost, revenue and margin, with the 20% floor marked.

**The numbers:**

- Fixed 5.55 USD a seat (completion 5.20, snapshots 0.08, apply 0.108, rerank 0.108, index 0.05) + usage 25.84 = ≈ 31.4 USD; the agent is 22.4 of it.
- Revenue = 39 + 1.25 × max(0, usage − 20): the mean organisation pays 46.30, a ≈ 32% margin; all-light 68%, all-median 32%, all-heavy 23%. As usage grows the margin tends to 1 − 1 ÷ 1.25 = 20%.

## Evaluation and release gates

- **What "quality" means here:** code that stays. Completion is judged by retained characters, the agent by lines still present 7 days after its diff was accepted; acceptance is a guardrail, not the goal.

| Gate or metric | How it is measured | Pass or target |
| --- | --- | --- |
| Retained characters (online, primary) | Accepted characters still present after 10 minutes, by edit distance on the client, per active developer-day | Retained AI share ≥ 25% (≈ 38% predicted); a 10% arm rolls back on a 5% drop |
| Guardrails against gaming | Acceptance, shown rate, length of shown suggestions, retained characters per shown suggestion, reverts within 14 days, undo within 10 s | No guardrail worse than control beyond its noise |
| Kept agent lines (online) | Agent-written lines in accepted diffs still present after 7 days (lines normalised for whitespace, matched on the default branch by the client or the git host's webhook, missing measurements reported as missing; human-written lines in the same files as the baseline); merged ÷ opened pull requests; tasks capped; test files the agent changed (flagged) | ≥ 70% kept |
| FIM set (offline) | Held-out repositories and commits after the model's cut-off: exact match and execution pass on single-line, multi-line and random-span infilling; latency replay | Not below the current release |
| Chat questions (offline) | 300 questions with gold files and line ranges: recall at 10, citation validity, an answer judge calibrated on 100 staff-graded answers | Not below the current release |
| Agent suite (offline) | 300 past issues from our own and consenting customers' repositories, reset before the fix, graded FAIL_TO_PASS and PASS_TO_PASS, 3 runs each (≈ 327 USD a run of the suite) | Paired per task; pass^3 (all 3 runs pass) per task not lower |
| Red-team set | Injected READMEs and issues, poisoned test output, invisible-Unicode rules files, config-write attempts, typo-squatted packages: 300 cases (illustrative) | 0 escapes and 0 leaks, so ≤ 1% at 95% (3 ÷ 300) |
| Latency | p95 per stage per region in the 1% arm, and the share of triggers whose ghost text arrived before the next key (it falls when latency rises, which N2's exclusion of cancels hides) | No 50 ms p95 regression; completion p95 ≤ 500 ms in every region |

The A/B below shows why acceptance cannot be the gate: the model that wins on acceptance keeps less code.

<AnimatedDiagram spec="animated/code-assistant/eval-metrics" stepper caption="Model B shows fewer suggestions and wins on acceptance, yet keeps fewer characters in the code: the metric that ships A is retained characters, not raw acceptance (an illustration)." />

- **How to read it:** step 1 runs models A and B through the same funnel, shown → accepted → retained characters; step 2 is the release gate strip, where every check must pass before the 1% arm grows.

**The numbers (an illustration of the mechanism, not evidence):**

- A shows 400 suggestions, accepts 30% × 40 characters × 80% kept = 3,840 retained characters; B shows 300, accepts 36% × 32 × 85% ≈ 2,938, though B keeps slightly more per suggestion shown (9.8 against 9.6).
- Acceptance would ship B; total retained characters ship A.
- Power: a 10% arm (7,000 developers) against 90%, per-user CV 1.0, gives a minimum detectable change of 2.8 × √(1/7,000 + 1/63,000) ≈ 3.5%, ≈ 4.3% with clustering by organisation, hence the 5% rollback line; a 25% arm sees ≈ 3.0%.
- Agent suite: at a 60% solve rate one run's 95% interval is ± 5.5 points, so releases are compared paired, per task.

- **Why not raw acceptance, honestly:** Ziegler et al. (2022) found acceptance best predicts how productive developers feel, so it stays on the dashboard. But METR (2025) measured experienced developers 19% slower with AI while they believed they were 20% faster, and its 2026 follow-up found no clear effect and called its own sample a poor proxy.
- **Public benchmarks only shortlist:** OpenAI's February 2026 audit of the 138 SWE-bench Verified tasks o3 did not reliably solve found flawed tests in at least 59.4% of them, a floor of 82 of 500 tasks (16.4%). In July 2026 OpenAI estimated about 30% of SWE-bench Pro tasks broken and withdrew its recommendation of it.
- **The embeddings arm:** in ≈ 300 organisations with an index built, each agent task is randomly offered `semantic_search` or not: 210,000 tasks an arm over 10 working days, minimum detectable change 2.8 × √(2 ÷ 210,000) × 1.5 × √2 ≈ 1.8% on kept lines. Randomising 150 organisations an arm could only see ≈ 9.7%.
- **Rollout:** internal dogfood → 1% → 10% for a week → 50% → 100%, per model and prompt version. Organisations that pin models get 14 days' notice and opt in.
- **Outcomes for buyers:** cycle time, merged pull requests per developer and change failure rate, quarterly by organisation, read as trends against matched teams, never as proof of speed-up.

## Safety and guardrails

The network policy is the one statement of what the agent can reach (N7):

| Mode | Allowed hosts | Notes |
| --- | --- | --- |
| Local agent, commands | None | No network and no resolver inside the sandbox; a proxy outside resolves DNS |
| Local agent, `install` (ask tier) | The organisation's registry mirror, read-only | Install scripts off; the mirror refuses publishes itself, because a proxy that does not inspect TLS cannot tell a GET from a PUT |
| Local agent, `web_fetch` | Domains approved per organisation; a new domain asks | GET only through our fetch service; query strings stripped for unapproved domains |
| Cloud setup phase (snapshot builder) | The git host (fetch) and the mirror | No secrets present; the git proxy supplies a read-only credential for that one repository |
| Cloud agent phase | The mirror, read-only; git through the git proxy | Pushes only to `agent/<task>` in the same repository; a private repository's task never pushes to a public one |

- **What still leaves through an allowed host:** a package name or URL path to the mirror can encode data, and lands in the company's own mirror logs. The mirror fetches upstream only packages that pass its existence, age and download checks, which bounds the channel but does not close it; pull request text stays in the same private repository.

The lethal trifecta is untrusted content, private data and a way out together; each mode cuts one leg:

| Mode | Untrusted content | Private data | Way out | Leg cut |
| --- | --- | --- | --- | --- |
| Local IDE agent | Repository files, dependencies, web pages, MCP results | The developer's repositories | Network, MCP write tools, `web_fetch` | Way out: no command network; MCP writes and new domains ask |
| Cloud task from a member | The issue, dependencies | The repository | The pull request, pushes | Way out: pushes only to the same private repository; no MCP write tools |
| Cloud task on a public repository | Anyone's issues and comments | Must not exist | The public pull request | Private data: the token sees only that public repository; no organisation MCP servers |

Privacy mode, the one statement of what is stored (N8):

| Data | Stored? | Where, how long |
| --- | --- | --- |
| Completion prompts and suggestions | No | In memory for the request; KV cache on our GPUs, salted per organisation, evicted in minutes |
| Chat and agent prompts at model providers | No, under zero-data-retention contracts with each provider, with the exceptions in their terms (such as abuse monitoring) | A fallback provider must have the same terms before it is enabled |
| Merkle hashes and HMAC-keyed paths | Yes | Our key-value store, until the workspace is deleted |
| Embeddings (arm only, opt-in) | Yes, encrypted with the organisation's key and treated as code | Deleted with the workspace |
| Agent checkpoints; cloud task workspace and snapshot | Local only; cloud encrypted per organisation | Hidden git refs cleaned after 30 days; task disk deleted 24 h after the task; snapshots until the lockfile changes or 30 days unused |
| Agent session transcripts | 7 days, encrypted, for the developer to review; 0 days for zero-retention organisations | An encrypted object store per organisation, keyed to the session row |
| Telemetry; training | Counts and timings only, no code or paths, 13 months; never trained on privacy-mode code | ClickHouse |

| Threat | Where it enters | Control | Code or prompt |
| --- | --- | --- | --- |
| Prompt injection in a README, issue, dependency, web page or test output | Anything the agent reads | No command network; credentials denied in the sandbox; writes only in the workspace; tool output marked as data; a trifecta leg cut per mode | Code |
| The agent raises its own permissions by writing config | `.vscode/settings.json`, `.cursor/mcp.json`, harness settings, `.git/hooks`, MCP definitions | Write-deny rules on those files; policy only from managed settings; diffs of `package.json` scripts and `Makefile` targets shown before a person runs them outside the sandbox (2025 CVEs under How real systems do it took routes through agent-written configuration and MCP files) | Code |
| Poisoned rules files | `AGENTS.md` and rules files in cloned repositories | Loaded only for trusted repositories; invisible Unicode stripped and shown | Code |
| Hallucinated, typo-squatted or malicious packages | `install` and package managers | Ask tier; the version must exist and be older than 14 days, and the package must pass a download floor; scripts off; mirror only; lockfile diffs flagged. Code models hallucinate package names (at least 5.2% for commercial models, 21.7% for open-source ones, Spracklen et al., 2025) | Code |
| Malware that drives the developer's own agent CLI | A compromised dependency on the laptop | Agent CLIs run sandboxed too, never with permission-skipping modes outside a VM | Code |
| MCP tools | Allow-listed servers | Pinned versions with hashed tool descriptions (a change needs re-approval); a narrow credential per server; read tools run, write tools ask | Code |
| Destructive command (`rm -rf src/`, `git reset --hard`) | Agent commands | Snapshot before every `run`; history-rewriting git commands ask; protected paths deny | Code |
| The sandbox falls back to unsandboxed | Harness | Unsandboxed commands disabled in managed settings; Docker and similar only as named exceptions that ask | Code |
| Secrets in the repository or in tool output | Prompts, chunks, a `cat` of a config, test logs | Client scanner on prompts, chunks and every tool result; placeholders substituted only inside the sandbox; `.env*`, `~/.ssh`, `~/.aws` denied | Code |
| Cross-tenant cache timing | KV and prompt caches | `cache_salt` per organisation on our servers; a model provider is enabled only if its terms state per-organisation cache isolation (one does, as of November 2026) | Code |
| The agent games the tests | Agent edits | Test changes flagged; CI runs the original tests; held-back tests in the suite | Code + prompt |
| Runaway cost; data leaving its region | The agent; failover | Caps (2 USD, 6M tokens, 120 steps, 30 minutes) and a repeated-call detector; residency-pinned organisations fail over only inside their geography | Code |

## Deep dives

### The completion request: trigger, cancel, reuse

- **Why cancellation matters, and where:** 65% of sent requests are cancelled. A third die before a GPU, so the fleet sizes on 4,200 arriving a developer-day (355 GPUs) instead of 5,355 (452), 22% fewer.
- **What an abort buys:** the rest still pay prefill, the binding resource, so aborting them frees decode (5,355 → 3,276 equivalents), not GPUs; their KV blocks seed the superseding request's prefix, so an abort stops decoding and keeps the blocks.
- **Why the gate, not a longer debounce:** the gate takes the fleet from 591 GPUs to 355 at no latency cost; 150 ms instead of 75 would need 200 GPUs instead of 355 (−44%) but adds 75 ms to the p50 of every suggestion, putting it at the 300 ms limit.

<AnimatedDiagram spec="animated/code-assistant/completion-sequence" stepper caption="The second keystroke cancels the first request mid-prefill; the next request reuses 1,510 of its 2,000 tokens from the KV prefix, and the ghost text lands at 225 ms." />

- **How to read it:** step 1 is the developer's `;`, 75 ms of quiet, the gate and request c_30; step 2 a space typed 120 ms later, so c_31 supersedes c_30 and the server aborts it mid-prefill; step 3 c_31 reusing the KV prefix, drafting from the prompt, and the ghost text at 225 ms, then an `i` typed through and Tab.

**The numbers:**

- A GPU is prefill-bound: 50 arriving requests a second × 490 new tokens ÷ 60,000 tokens a second = 41% busy; Little's law gives ≈ 36 a second reaching decode × ≈ 81 ms ≈ 3 streams in flight, a small batch.
- Mean decode step: 41% of steps carry a prefill chunk (8 ms), the rest 5 ms: 0.41 × 8 + 0.59 × 5 ≈ 6.2 ms; queue ≈ 0.41 × 8.2 ÷ (2 × 0.59) ≈ 3 ms.
- 294M arriving a day ÷ 86,400 = 3,403 a second; US 40%, EU 35%, Asia-Pacific 25%, each × 4 at its peak ÷ 50 × 1.3 → 142 + 124 + 89 = 355 GPUs.

<Callout tone="red" title="What breaks">
  Route a developer to a different replica on every request and the KV prefix is lost: every request prefills 2,000 tokens, and a restarted replica costs its developers one miss each (+30 ms at p95). Routing is sticky by developer, and the prefix cache is salted per organisation so it cannot leak across tenants through timing.
</Callout>

- **Losing an EU zone:** the gate keeps 30% of triggers instead of 60%, so half the EU fleet carries the load and completion degrades; EU-pinned organisations never fail over outside the EU, and losing the whole EU region makes their completion fail silent.

### Agent safety: tiers, fences, packages and the trifecta

- **The rule:** the model proposes, the policy engine decides in code, the sandbox enforces. Deny → ask → allow, from managed settings only, so a broad deny cannot be overridden by a narrower allow.

<AnimatedDiagram spec="animated/code-assistant/agent-step" stepper caption="Three tool calls, three outcomes decided in code: the test run is allowed with no network, a typo-squatted package fails the mirror's checks, and a write to the IDE's settings is denied." />

- **How to read it:** step 1 is `run("npm test")`, allowed without a prompt; a test helper's call to an outside host is refused, and the failure goes back to the model as data. Step 2 is `install("left-padd")`: the mirror finds no such package, so the developer is never asked; step 3 is a write to `.vscode/settings.json`, denied by rule.

**The numbers:**

- The three calls cost the developer no prompt at all (the install failed the mirror's check before the ask tier) and the attacker everything: no outside host was reached, no package landed, no setting changed.
- A sandbox cut permission prompts by 84% in one vendor's internal use (How real systems do it), which is the point: people read the few prompts that remain.
- Caps bind in order: on a long task at the average thinking mix, 2 USD at step 99 (≈ 28.0 minutes), just before the 30-minute cap and well before 6M input tokens at step 117.

<Callout tone="red" title="What breaks">
  Load permission rules from the workspace and the agent can write its own policy: an injected instruction adds an MCP server or a hook, and the next command runs outside every fence. Rules come only from managed settings, and those files are write-denied.
</Callout>

### Worked example: a month of one heavy seat

- **The seat (illustrative):** a heavy user runs 12 agent tasks a day at twice the median cost and 25 chat turns, on 14.7 active days a month.
- **Usage:** 14.7 × (12 × 2 × 0.363 + 25 × 0.0283 + 0.25 × 12 × 0.0142) ≈ 139.03 USD; with 5.55 USD of fixed cost the seat costs ≈ 144.6.
- **Revenue:** 39 + 1.25 × (139.03 − 20) ≈ 187.8 USD, so the margin is 1 − 144.6 ÷ 187.8 ≈ 23%.
- **Without the pool:** a flat 39 USD seat would lose ≈ 106 USD on this seat, and 10% of seats like it put the mean seat at 31.4 USD, 80% of the seat price.
- **The task cap:** none of these tasks reaches the 2 USD cap; a task that loops would stop at step 99 with a summary, at most 2 USD.

| Decision | Options considered | Choice | Decided by | What we give up | Revisit when |
| --- | --- | --- | --- | --- | --- |
| Completion serving | Self-host; dedicated provider deployment; per-token FIM API; on-device | Self-host a fine-tuned open-weight FIM model at 100,000 seats; a dedicated deployment below ≈ 47,000 | G3, G4, G9 | A model and serving team with its fine-tuning runs (1.66 USD a seat) | A provider offers abort, a per-organisation salt and weekly fine-tunes at our price |
| Triggering | Every key; per-class waits; one debounce + a gate | 75 ms for every key, pre-request gate, typed-through cache, abort | N2, G5 | 5% of would-be-shown suggestions dropped; a gate model to train | Cancel share above 75%, or the gate drops more than 10% of what would be shown |
| Repository search | Grep only; embeddings by default; grep by default + an embeddings arm | Grep, symbols and `explore`; embeddings as an arm on large repositories | G1, G6, G9 | A second index for organisations in the arm | The arm shows no gain on kept lines (then remove it) |
| Edit application | Whole file; diff; search-and-replace; fast apply | Search-and-replace, then region fast apply | F4, G3 | A self-hosted apply model (0.108 USD a seat) | Agent models land exact edits more than 99% of the time |
| Agent cost control | One model with open thinking; mid + small explorer + budgets | Mid for plans and edits, small `explore`, thinking budgets, caps | G4, N4 | A summary can drop a detail; hard steps may need more thinking | The small model fails exploration evals |
| Local isolation | Prompts only; container; OS sandbox | OS sandbox, no network, deny → ask → allow, managed rules, config writes denied | G2, G10, N7 | Docker and some tools need named exceptions | More than 5 named exceptions per organisation |

| Cloud isolation | Container; gVisor; microVM | A microVM per task, snapshots, git proxy, members-only triggers | G2, N7 | ≈ 0.01 USD a task and snapshot upkeep | Never weaker for untrusted dependencies |
| Pricing | Flat seat; seat + pooled allowance; pure usage | 39 USD seat, 20 USD pooled allowance, overage at list × 1.25 (illustrative) | N5, G4 | A usage bill organisations must watch | Margin on the mean organisation falls below 25% |
| Online metric | Acceptance; retained characters; survey | Retained characters primary; acceptance, length and survey as guardrails | N1 | A slower metric (a 10-minute window) | A merged-code metric proves more stable |

## How real systems do it

- **2025, Cursor Tab:** serves over 400M requests a day and is retrained online from accepts and rejects; the new model makes 21% fewer suggestions with a 28% higher accept rate (vendor).
- **2025 and 2026, completion latency:** GitHub's custom completion model reports 20% more accepted-and-retained characters, 12% higher acceptance and 35% lower latency, relative figures only (vendor, 2025). Alibaba's Qoder NEXT reports cutting p50 from 800 to 300 ms (vendor, 2026).
- **2025 and 2026, Cursor's indexing:** a November 2025 A/B found +2.6% code retention with semantic search on codebases over 1,000 files. In 2026 it described Merkle sync with content proofs (January) and a local regex index anchored to git commits (March); its docs in November say its search does not store embeddings of the codebase, and team replies on its forum date that to late July.
- **2025, sandboxes:** Claude Code's sandbox uses bubblewrap and Seatbelt with a network proxy and cut permission prompts by 84% internally; OpenAI's Codex runs the agent with network access off by default (vendors).
- **2025, agent configuration as an attack path:** CVE-2025-53773 (code execution in GitHub Copilot and Visual Studio), CVE-2025-54135 (Cursor's agent creating `.cursor/mcp.json` without approval) and CVE-2025-54136 (an approved MCP config swapped silently).
- **2025, the supply chain:** the Shai-Hulud worm compromised over 500 npm packages (CISA, September); malicious nx versions harvested credentials (August), and a security vendor reports the script prompted local AI agent CLIs to list files likely to hold secrets.
- **Where this design differs:** embeddings stay as a measured arm rather than gone, and the agent never installs a package outside a read-only mirror. Both cost little and answer questions the public write-ups leave open.

## Failure modes & pitfalls

- **Latency regression** (a slower model, a proxy, a far region): acceptance and retained characters fall; noticed in p95 per stage per organisation; roll back on a 50 ms p95 regression, and publish proxy bypass guidance.
- **Stale search after a branch switch:** the agent reads files that changed; noticed by the index commit differing from HEAD; the index re-anchors to HEAD with a dirty overlay, and open files are read live.
- **The model games the metric** (shorter, safer or long boilerplate suggestions): acceptance or length rises while retained characters per developer stay flat; the length and revert guardrails block the release.
- **The agent loops or overthinks:** cost per task climbs; the caps and the repeated-call detector stop it with a summary at 2 USD at most.
- **A poisoned dependency or injected README:** the agent tries to install, write config or send data; mirror checks, config deny rules and no command network refuse it, and the attempt is logged in the audit log and shown.
- **A region or zone outage:** client health checks stop sending there; EU traffic moves to the other EU zone (the gate keeps 30% of triggers); with no healthy zone in the geography, completion fails silent, with no error dialog.
- **A provider outage for chat or the agent:** fail over at a task boundary to a second provider with the same retention terms; a running task pauses at its snapshot instead of switching models mid-task.

## Interview framework

1. **Minutes 0 to 5:** features, scale, latency per feature, privacy and residency, what the agent may run, pricing.
2. **Minutes 5 to 10:** numbers: 5,355 sent and 65% cancelled a developer-day, 375M requests a day on 355 GPUs, 225 ms for every suggestion, 0.36 USD a median agent task, 31.4 USD a mean seat and ≈ 32% margin at 39 USD.
3. **Minutes 10 to 20:** steps 1 to 3: the completion path and its budget; triggering and cancellation; local search and Merkle sync.
4. **Minutes 20 to 30:** steps 4 to 6: chat context; the agent loop; applying edits.
5. **Minutes 30 to 37:** steps 7 and 8: sandbox, packages, MCP and the trifecta; retained characters and the gates.
6. **Minutes 37 to 45:** one deep dive: the completion request, or agent safety.

**What interviewers listen for:**

- **Mid:** FIM, debounce and cancellation, grep against embeddings, search-and-replace edits, a sandbox that exists.
- **Senior:** a per-stage budget at p50 and p95 including proxies; triggering and cancel cost as capacity; KV reuse with frozen blocks; deny → ask → allow; the network modes; retained characters against acceptance.
- **Staff:** self-host against dedicated against API with the team in the cost; the 2026 turn to grep and an arm to decide it; mean-seat economics and pooled pricing; the trifecta per mode; residency-bound failover; benchmark contamination.

**Red flags:**

- One pipeline for completion and the agent; a frontier chat model for completions; a 50 ms debounce with no cancellation model.
- An agent with the developer's credentials and an open network; optimising acceptance rate; a SWE-bench score as the eval; economics on the median seat.
