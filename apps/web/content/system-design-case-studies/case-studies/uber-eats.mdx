Design a food delivery app like Uber Eats: customers find nearby restaurants, order and pay, the restaurant prepares the food, a courier is dispatched to pick it up, and everyone watches the order move on a map. The hard parts are a firehose of courier GPS updates, matching orders to couriers in seconds, and charging exactly once while three apps change the same order.

## 1. Functional requirements

| # | Requirement | Notes |
|---|---|---|
| F1 | **Browse nearby restaurants** | Open restaurants that deliver to the customer's address, filtered by cuisine; view menus. |
| F2 | **Place an order and pay** | Cart → order; the card is authorised when the order is placed and captured on delivery. |
| F3 | **Restaurant handles the order** | Restaurant app receives new orders, accepts or rejects, marks them ready. |
| F4 | **Dispatch a courier** | Offer the delivery to a nearby free courier; reassign if they decline or time out. |
| F5 | **Live tracking and ETA** | Customer sees the courier on a map and an updated arrival time. |
| F6 | **Status notifications** | Customer, restaurant and courier hear about every status change, even with the app closed. |

**Out of scope** for this design: ratings and reviews, promotions, courier payouts, search ranking models, grocery.

## 2. Non-functional requirements

| Property | Target | Why it matters |
|---|---|---|
| **Latency** | Search p99 under 300 ms; status changes reach apps within 1–2 s | Customers bounce from slow search; restaurants must see orders immediately. |
| **Availability** | 99.99% for placing and updating orders | An outage at dinner time means lost orders and cold food. |
| **Correctness** | An order is created and charged **exactly once** | Retries over bad mobile networks must not double-charge. |
| **Consistency** | Orders and payments strongly consistent; positions, ETAs and search results may be seconds stale | Strictness only where money and state are involved. |
| **Freshness** | Courier positions at most ~5 s old | Dispatch and the map are wrong with older data. |
| **Scale** | Dinner peak ≈ 5× average; hundreds of thousands of GPS updates per second | Drives an in-memory location tier. |

## 3. Back-of-the-envelope estimates

Assumptions are round numbers chosen to size the system, not real Uber figures.

| Quantity | Assumption | Result |
|---|---|---|
| Daily active customers | 20 million | |
| Orders per day | 10 million | **≈ 115 orders/s** average |
| Peak order rate | 5× average (dinner) | **≈ 600 orders/s** |
| Searches | 10 per active customer per day | **≈ 2,300/s** average, **≈ 12K/s** peak |
| Menus | 1M restaurants × 100 items × 1 KB | **≈ 100 GB**, fits in a cache |
| Couriers online at peak | 1 million, GPS every 4 s | **≈ 250K location updates/s** |
| Latest positions | 1M × 100 bytes | **≈ 100 MB** in memory |
| Deliveries in flight at peak | 600/s × 40 min | **≈ 1.4 million**, so a few million live sockets |
| Order storage | 10M × 2 KB | **≈ 20 GB/day**, ≈ 7 TB/year |

What the numbers say: **orders are few but precious**, so a relational database with transactions handles them easily. **Location writes are 400× the order rate but each one is disposable**, so they belong in memory, not in the orders database. **Search is read-heavy and tolerant of staleness**, so it reads from a dedicated index and caches.

## 4. API design

Customer, restaurant and courier apps each keep one **WebSocket** for live updates; everything else is **HTTPS**.

### REST endpoints

```http
GET  /v1/restaurants?lat=..&lng=..&cuisine=..&cursor=..   # nearby, open restaurants
GET  /v1/restaurants/{id}/menu
POST /v1/orders                     # Idempotency-Key header; body: restaurant_id, items, address, payment_method_id
GET  /v1/orders/{id}
POST /v1/orders/{id}/cancel

POST /v1/restaurant/orders/{id}/accept      # restaurant app
POST /v1/restaurant/orders/{id}/ready

POST /v1/courier/offers/{id}/accept         # courier app
POST /v1/courier/orders/{id}/picked-up
POST /v1/courier/orders/{id}/delivered
```

The `Idempotency-Key` is generated by the app per checkout: a retried `POST /v1/orders` returns the order created the first time instead of a second order and a second charge. See [Idempotency](/system-design/patterns/idempotency).

### WebSocket events

| Direction | Event | Payload (key fields) |
|---|---|---|
| courier → server | `location` | `lat`, `lng`, `heading`, `ts` every 4 s |
| server → courier | `delivery_offer` | `order_id`, pickup and drop-off, payout, `expires_at` (≈ 30 s) |
| server → restaurant | `new_order` | `order_id`, items, notes |
| server → customer | `order_status` | `order_id`, `status`, `eta` |
| server → customer | `courier_location` | `lat`, `lng`, `eta`, every few seconds while out for delivery |

## 5. Database schema

Orders and payments live in a **relational database** (sharded by `order_id` once one primary is not enough). Live courier positions live in **Redis** with its geospatial commands. Search uses a **search index** (Elasticsearch-style) with a `geo_point` per restaurant, fed from the restaurants database.

### Orders and restaurants (relational)

```sql
CREATE TABLE restaurants (
  id            BIGINT PRIMARY KEY,
  name          VARCHAR(200),
  lat           DOUBLE PRECISION,
  lng           DOUBLE PRECISION,
  cuisine       VARCHAR(50),
  is_open       BOOLEAN,
  prep_minutes  INT
);

CREATE TABLE menu_items (
  id             BIGINT PRIMARY KEY,
  restaurant_id  BIGINT REFERENCES restaurants(id),
  name           VARCHAR(200),
  price_cents    INT,
  available      BOOLEAN
);

CREATE TABLE orders (
  id               BIGINT PRIMARY KEY,       -- Snowflake id
  customer_id      BIGINT,
  restaurant_id    BIGINT REFERENCES restaurants(id),
  courier_id       BIGINT,                   -- null until dispatched
  status           VARCHAR(20),              -- PLACED, ACCEPTED, READY, COURIER_ASSIGNED, PICKED_UP, DELIVERED, CANCELLED
  total_cents      INT,
  address          TEXT,
  idempotency_key  VARCHAR(64) UNIQUE,       -- makes POST /orders safe to retry
  version          INT,                      -- optimistic locking for status changes
  created_at       TIMESTAMP,
  updated_at       TIMESTAMP
);

CREATE TABLE order_items (
  order_id      BIGINT REFERENCES orders(id),
  menu_item_id  BIGINT REFERENCES menu_items(id),
  quantity      INT,
  price_cents   INT,                         -- copied: menu prices change later
  PRIMARY KEY (order_id, menu_item_id)
);

CREATE TABLE payments (
  id            BIGINT PRIMARY KEY,
  order_id      BIGINT REFERENCES orders(id),
  status        VARCHAR(20),                 -- AUTHORIZED, CAPTURED, REFUNDED, FAILED
  provider_ref  VARCHAR(100),
  amount_cents  INT
);
```

### Live state (Redis)

| Key | Value | TTL |
|---|---|---|
| `couriers:free:{city}` | geo set: `GEOADD` courier id at lng/lat | members removed when busy or stale |
| `courier:{id}` | latest position, status, current order | ≈ 30 s, refreshed by each GPS update |
| `offer:{order_id}` | courier currently holding the offer (`SET NX`) | ≈ 30 s, the offer window |

## 6. Building the architecture, one requirement at a time

We start with the smallest design that satisfies F1 and add components only when a requirement forces us to. Each diagram shows the design after that step: **green dashed outlines mark what the step adds**, the moving dots show the flow it introduces, and faded parts were added earlier.

### Step 1: Browse nearby restaurants (F1)

<AnimatedDiagram name="uber-eats/architecture" step={1} />

The customer app calls the **API gateway**, which authenticates and rate-limits, then routes to two read-only services:

- The **search service** asks the **search index** for open restaurants within delivery range of the customer's address, filtered by cuisine. Restaurants are indexed by location, using a geohash or the index's built-in geo type, so "near me" is a range lookup, not a scan of a million rows. See [Geospatial Indexing](/system-design/patterns/geospatial-indexing).
- The **restaurant service** serves menus, hours and prices from the **restaurants DB**. Changes are copied into the search index asynchronously, so a new menu item shows up in search a few seconds later.

**Why a separate search index?** The restaurants DB is the source of truth, but geo-plus-text queries at ≈ 12K/s would swamp it. The index is a read-optimised copy, and slight staleness is fine (consistency NFR). Menus (≈ 100 GB) are cached at the service and the CDN.

**The gap:** customers can look but not buy.

### Step 2: Place an order and pay (F2)

<AnimatedDiagram name="uber-eats/architecture" step={2} />

`POST /v1/orders` goes to the **order service**, the heart of the system. In one request it:

1. Checks `idempotency_key`; a retry returns the existing order.
2. Validates items and prices against the menu, copying prices into `order_items`.
3. Asks the **payment service** to **authorise** the card (reserve the money). The card is only **captured** on delivery, so a cancelled order costs nothing.
4. Writes the order as `PLACED` to the **orders DB** in one transaction, and returns the order id.

**Why authorise, then capture?** It avoids charging for food that never arrives. If the restaurant rejects the order, the order service voids the authorisation instead of issuing a refund. Order and payment together are a small [saga](/system-design/patterns/saga): every step has an undo.

**Why relational?** ≈ 600 orders/s at peak is easy for a sharded relational database, and orders need transactions, unique constraints and joins.

**The gap:** the order is stored, but the restaurant doesn't know about it.

### Step 3: Restaurant accepts, everyone hears about it (F3, F6)

<AnimatedDiagram name="uber-eats/architecture" step={3} />

Every status change becomes an event (`OrderPlaced`, `OrderAccepted`, `OrderReady`, ...) on the **event bus**, keyed by `order_id` so one order's events stay in order.

- The **notifier** consumes those events and decides who to tell. If the app has a live socket, it sends the event through the **socket gateway**, the tier that holds every app's WebSocket. Otherwise it sends a push notification via **APNs / FCM**.
- The **restaurant app** gets `new_order`, then calls `accept` and `ready` through the API gateway. Each call moves the order's state machine forward with an optimistic-lock `version` check, so two conflicting updates cannot both win.
- The **customer app** gets `order_status` for every change.

**Why a bus instead of the order service calling everyone?** The order service stays small and fast. New consumers (dispatch, analytics, fraud) subscribe without changing it, and a slow notifier never blocks an order. See [Message Queues and Pub/Sub](/system-design/patterns/message-queues).

**The gap:** the food will be ready, but no one is coming to collect it.

### Step 4: Dispatch a courier (F4)

<AnimatedDiagram name="uber-eats/architecture" step={4} />

Two new services in the core, plus an in-memory index:

- **Location service.** Each **courier app** sends its position every 4 s over its socket, ≈ 250K updates/s at peak. The location service keeps only the latest one: `GEOADD couriers:free:{city}` in the **geo index**, plus `courier:{id}` with a short TTL so a courier who goes silent drops out. Nothing touches the orders DB.
- **Dispatch service.** It consumes `OrderAccepted` from the bus (timed so the courier arrives about when the food is ready). It asks the location service for free couriers within a few kilometres of the restaurant, ranks them by distance and ETA, and claims the best one with `SET offer:{order_id} NX EX 30`. It then publishes a `delivery_offer`, which reaches the courier through the notifier and the socket gateway. If the courier accepts, the order becomes `COURIER_ASSIGNED`. If they decline or 30 s pass, dispatch tries the next courier.

**Why in memory?** The positions change every 4 s and are worthless a minute later. Writing 250K/s to a durable database would cost a lot to store data nobody reads. If the geo index restarts, it refills within one GPS interval.

**Why the `NX` lock?** Two dispatch workers can pick the same courier for two orders. The atomic claim makes one of them lose cleanly and try someone else.

### Step 5: Live tracking and ETA (F5)

<AnimatedDiagram name="uber-eats/architecture" step={5} />

While an order is out for delivery, the location service also publishes the courier's position to the event bus, keyed by `order_id`. The notifier forwards it to that order's customer as `courier_location` every few seconds. The **ETA service** recomputes arrival time from the road graph and live traffic. The location service calls it when the courier moves meaningfully, not on every ping.

**Why through the bus and not straight to the customer's socket?** The location service doesn't know which gateway server holds the customer's socket; the notifier already does. Reusing one push path keeps a single place to handle offline apps, throttling and fan-out to multiple devices.

## 7. Final architecture

<AnimatedDiagram name="uber-eats/architecture" stepper caption="Uber Eats architecture: browse, order and pay, notify, dispatch, track. Use the numbers to replay the build." />

The components are grouped by responsibility; the same groups appear in every case study on this site.

| Group | Components | Responsibility |
|---|---|---|
| **Clients** | Customer, restaurant and courier apps | Keep one WebSocket open, retry with idempotency keys, send GPS (courier). |
| **Edge** | API gateway, socket gateway | Authenticate and rate limit REST calls; hold millions of WebSockets. |
| **Application services** | Search, restaurant, payment services | Discovery, menus, card authorisation and capture. |
| **Ordering & dispatch** | Order, dispatch, location, ETA services | Order state machine, courier matching, live positions, arrival times. |
| **Async pipeline** | Event bus, notifier | Ordered order events; push to sockets or APNs / FCM. |
| **Storage** | Search index, restaurants DB, orders DB, geo index | Read-optimised search, menus, transactional orders, live courier positions. |

### An order, end to end

1. The customer searches; the search service returns nearby open restaurants from the search index.
2. `POST /v1/orders` with an idempotency key: the order service authorises the card and writes the order as `PLACED`.
3. `OrderPlaced` goes on the event bus; the notifier pushes `new_order` to the restaurant app, which accepts.
4. On `OrderAccepted`, dispatch queries the location service for nearby free couriers and offers the job to the best one.
5. The courier accepts, picks up and drives; their GPS updates flow through the location service to the customer's map, with ETAs from the ETA service.
6. On `DELIVERED`, the order service captures the payment and the notifier tells everyone.

<InterviewQuestions>
  <InterviewQuestion question="How do you find nearby available couriers quickly?" category="Geospatial" level="Mid">
    Keep only each courier's latest position in an in-memory geo index (Redis GEO, or geohash or H3 cells), split by city. Dispatch runs a radius query around the restaurant, then ranks the few candidates by road ETA rather than straight-line distance. Couriers who stop sending GPS expire through a short TTL.
  </InterviewQuestion>
  <InterviewQuestion question="How do you make sure a customer is charged only once?" category="Reliability" level="Mid">
    The app sends an idempotency key with POST /orders, and the orders table has a unique constraint on it, so a retry returns the original order. The payment provider call carries the same key, and the card is authorised at order time and captured once on delivery.
  </InterviewQuestion>
  <InterviewQuestion question="Why not store every courier GPS update in the main database?" category="Data modeling" level="Mid">
    At about 250K updates per second, almost all of which are superseded four seconds later, a durable write per update is expensive and nobody reads the old values. Keep the latest position in memory, and if history is needed for disputes, sample it into cheap time-series storage asynchronously.
  </InterviewQuestion>
  <InterviewQuestion question="Two dispatch workers pick the same courier for different orders. How do you prevent a double assignment?" category="Concurrency" level="Senior">
    Claim the courier atomically before sending the offer, for example SET courier-offer key NX with a 30 second expiry, or a conditional update on the courier's status. The loser of the race sees the claim fail and moves to its next candidate. The expiry frees the courier if the offer is never answered.
  </InterviewQuestion>
  <InterviewQuestion question="What happens if the restaurant rejects an order after the card was authorised?" category="Distributed transactions" level="Senior">
    Treat order placement as a saga: each step has a compensating action. A rejection moves the order to CANCELLED and triggers the compensation for payment, which voids the authorisation rather than refunding a captured charge. Every step is idempotent so the saga can be retried safely after a crash.
  </InterviewQuestion>
</InterviewQuestions>
