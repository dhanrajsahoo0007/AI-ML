Design a chat service like Facebook Messenger: people send text and media to one person or a group, see when messages are delivered and read, and see who is online. The hard parts are millions of persistent connections, ordering, and delivering to people who are offline.

## 1. Functional requirements

| # | Requirement | Notes |
|---|---|---|
| F1 | **One-to-one chat** | Send and receive text messages in real time. |
| F2 | **Group chat** | Groups of up to a few hundred members; add and remove members. |
| F3 | **Delivery and read receipts** | Sent, delivered and read states per message (per member in groups). |
| F4 | **Presence** | Online status and "last seen"; typing indicators. |
| F5 | **Media** | Photos, video and files as attachments. |
| F6 | **History and sync** | Scroll back through old messages; a new device catches up. |
| F7 | **Push notifications** | Offline users are notified and receive messages when they reconnect. |

**Out of scope** for this design: voice and video calls, end-to-end encryption key management, stories, payments, message search ranking.

## 2. Non-functional requirements

| Property | Target | Why it matters |
|---|---|---|
| **Latency** | p99 under 200 ms sender to online recipient (same region) | Chat feels broken above a few hundred milliseconds. |
| **Availability** | 99.99% for send and receive | Messaging is a core daily habit. |
| **Durability** | No acknowledged message is ever lost | Users trust that "sent" means stored. |
| **Ordering** | Messages appear in the same order for everyone in a conversation | Out-of-order replies change meaning. |
| **Consistency** | Per-conversation ordering is strict; presence and unread counts can be eventually consistent | Strictness only where users notice. |
| **Scale** | Hundreds of millions of concurrent connections | Drives the stateful connection tier. |
| **Efficiency** | Low battery and data use on mobile | Persistent connections and small payloads. |

## 3. Back-of-the-envelope estimates

Assumptions are round numbers chosen to size the system, not real Meta figures.

| Quantity | Assumption | Result |
|---|---|---|
| Daily active users | 500 million | |
| Messages per user per day | 40 | **20 billion messages/day** |
| Average write rate | 20 B ÷ 86,400 s | **≈ 230K messages/s** |
| Peak write rate | 3× average | **≈ 700K messages/s** |
| Message size (text + metadata) | 200 bytes | **≈ 4 TB/day**, ≈ 1.5 PB/year |
| Stored with 3 replicas | 1.5 PB × 3 | **≈ 4.4 PB/year** |
| Peak concurrent connections | 20% of DAU online | **≈ 100 million WebSockets** |
| Connections per chat server | ≈ 100K | **≈ 1,000 chat servers** (plus headroom) |
| Media share | 5% of messages, 200 KB average | **≈ 200 TB/day** of blobs |
| Text ingress at peak | 700K/s × 200 B | **≈ 140 MB/s** |

What the numbers say: writes are huge and steady, so the message store must be write-optimised and partitioned; connections are the scarce resource, so the chat tier is stateful and scaled by connection count; media dwarfs text, so it goes straight to blob storage and a CDN.

## 4. API design

Real-time traffic uses one **WebSocket** per device; everything else is plain **HTTPS**.

### WebSocket events

| Direction | Event | Payload (key fields) |
|---|---|---|
| client → server | `send_message` | `client_msg_id`, `conversation_id`, `body`, `attachment_ids` |
| server → client | `message_ack` | `client_msg_id`, `message_id`, `server_ts` |
| server → client | `new_message` | `message_id`, `conversation_id`, `sender_id`, `body`, `server_ts` |
| client → server | `receipt` | `conversation_id`, `message_id`, `type` = delivered or read |
| both | `typing` | `conversation_id`, `is_typing` |
| client → server | `heartbeat` | every 20-30 s, keeps presence and the connection alive |

`client_msg_id` is generated by the client so retries are **idempotent**: the server returns the same `message_id` for a repeated send.

### REST endpoints

```http
GET    /v1/conversations?cursor=...                  # inbox, newest first
GET    /v1/conversations/{id}/messages?before=...&limit=50   # history page
POST   /v1/conversations                             # create a group
POST   /v1/conversations/{id}/members                # add members
DELETE /v1/conversations/{id}/members/{user_id}      # remove a member
POST   /v1/media/upload-url                          # returns a pre-signed upload URL
GET    /v1/sync?since=...                            # catch up a new or offline device
```

## 5. Database schema

Two stores with different shapes: a **wide-column store** (Cassandra / HBase style) for the high-volume message data, and a **relational database** for users, conversations and membership. Short-lived state lives in **Redis**.

### Messages (wide-column, partitioned by conversation)

```sql
-- One partition per conversation and time bucket keeps partitions bounded.
CREATE TABLE messages (
  conversation_id  bigint,
  bucket           int,         -- e.g. month number, splits very old or busy chats
  message_id       bigint,      -- Snowflake id: time-sortable, unique
  sender_id        bigint,
  body             text,
  attachment_ids   list<bigint>,
  created_at       timestamp,
  PRIMARY KEY ((conversation_id, bucket), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);

-- Each user's inbox: conversations ordered by latest activity.
CREATE TABLE user_conversations (
  user_id          bigint,
  last_message_id  bigint,
  conversation_id  bigint,
  preview          text,
  unread_count     int,
  PRIMARY KEY (user_id, last_message_id, conversation_id)
) WITH CLUSTERING ORDER BY (last_message_id DESC);

-- Receipts are a pointer per member, not a row per message.
CREATE TABLE receipts (
  conversation_id    bigint,
  user_id            bigint,
  last_delivered_id  bigint,
  last_read_id       bigint,
  PRIMARY KEY (conversation_id, user_id)
);
```

### Metadata (relational)

```sql
CREATE TABLE users (
  id          BIGINT PRIMARY KEY,
  name        VARCHAR(100),
  avatar_url  VARCHAR(500),
  created_at  TIMESTAMP
);

CREATE TABLE conversations (
  id          BIGINT PRIMARY KEY,
  type        VARCHAR(10),      -- 'direct' or 'group'
  title       VARCHAR(200),
  created_by  BIGINT REFERENCES users(id),
  created_at  TIMESTAMP
);

CREATE TABLE conversation_members (
  conversation_id  BIGINT REFERENCES conversations(id),
  user_id          BIGINT REFERENCES users(id),
  role             VARCHAR(10), -- 'admin' or 'member'
  joined_at        TIMESTAMP,
  PRIMARY KEY (conversation_id, user_id)
);

CREATE TABLE media (
  id          BIGINT PRIMARY KEY,
  owner_id    BIGINT REFERENCES users(id),
  blob_key    VARCHAR(300),
  mime_type   VARCHAR(100),
  size_bytes  BIGINT
);
```

### Ephemeral state (Redis)

| Key | Value | TTL |
|---|---|---|
| `session:{user_id}` | chat server id and device ids holding a connection | refreshed by heartbeat |
| `presence:{user_id}` | online flag and last-seen time | ≈ 30-60 s |
| `recent:{conversation_id}` | last 50 message ids for fast open | minutes to hours |

## 6. Building the architecture, one requirement at a time

We start with the smallest design that satisfies F1 and add components only when a requirement forces us to. Each diagram shows the design after that step: **green dashed outlines mark what the step adds**, the moving dots show the flow it introduces, and faded parts were added earlier.

### Step 1: One-to-one chat (F1)

<AnimatedDiagram name="messenger/architecture" step={1} />

The simplest design that works: both users keep a **WebSocket** open to a **chat server**, through a **load balancer**.

1. The sender sends `send_message` over its socket.
2. The chat server writes the message to the **message store** and replies `message_ack`. This is the "sent" tick.
3. The server pushes `new_message` down the recipient's socket.

**Why WebSocket and not polling?** Polling every few seconds from 100 million devices is billions of empty requests and seconds of delay. A persistent socket lets the server push the instant a message arrives (latency NFR) and costs little battery when idle (efficiency NFR).

**The gap:** this only works if both users are connected to the *same* chat server.

### Step 2: Many chat servers (scale)

<AnimatedDiagram name="messenger/architecture" step={2} />

The estimates say about **100 million concurrent sockets**, so about **1,000 chat servers**. The sender and recipient are almost never on the same one.

The **session registry** maps `user_id → chat server` (the `session:{user_id}` key in Redis). A server registers a user when the socket opens and removes them when it closes. To deliver, the sender's server looks the recipient up and forwards the message to the right server, which pushes it down the socket.

**Why a separate registry?** Chat servers stay stateless apart from the sockets they hold. If a server dies, its clients reconnect elsewhere and simply re-register.

**The gap:** if the recipient has no open socket, there is no one to deliver to.

### Step 3: Offline users and push (F7)

<AnimatedDiagram name="messenger/architecture" step={3} />

When the registry has no entry for the recipient, the chat server hands the message to the **push service**, which sends a notification through **APNs or FCM**. The message itself is already safe in the store. When the app reconnects it asks for everything after the last message id it saw (see step 8).

**Why not keep the message in the chat server until they return?** The server could restart in the meantime. Storing first and notifying second means "sent" is never a lie (durability NFR).

**The gap:** one recipient is easy. A group has hundreds.

### Step 4: Group chat and fan-out (F2)

<AnimatedDiagram name="messenger/architecture" step={4} />

Groups add two things.

- **Membership.** Creating a group and adding members are ordinary REST calls. They go through the **API gateway** (authentication, rate limiting) to the **group service**, which stores members in the relational **metadata DB**.
- **Fan-out.** One message to a 200-person group means 200 deliveries. The chat server hands the message to **fan-out workers**. They read the member list from the **cache** (falling back to the metadata DB), look each member up in the session registry, and either forward to the member's chat server (*online*) or to the push service (*offline*).

**Why workers, not the chat server?** Delivering to 200 members inline would hold up the sender's ack and tie up a server that should be serving sockets. Workers scale on their own. See [Fan-out: Push vs Pull](/system-design/patterns/fan-out).

**The gap:** the chat server calls the store and the workers directly. If either is slow or down, messages are lost or arrive out of order.

### Step 5: A durable, ordered pipeline (durability, ordering)

<AnimatedDiagram name="messenger/architecture" step={5} />

Put a **message bus** (Kafka-style log) between the chat tier and everything downstream. The chat server assigns a time-sortable `message_id`, publishes, and acks the sender once the bus has the message.

- **Ordering:** the bus is keyed by `conversation_id`, so every message of a conversation lands in one partition, in order.
- **Durability:** the bus is replicated. If the store or the workers are down, messages wait in the log instead of being dropped.
- **Decoupling:** the store writer and the fan-out workers are independent consumers; a slow one does not slow the other.

At **≈ 700K messages/s** at peak this is a few hundred partitions. See [Message Queues and Pub/Sub](/system-design/patterns/message-queues) and [Unique ID Generation](/system-design/patterns/unique-id-generation).

### Step 6: Presence and receipts (F3, F4)

<AnimatedDiagram name="messenger/architecture" step={6} />

- **Presence.** Each app sends a `heartbeat` every 20–30 s over its socket. The chat server forwards it to the **presence service**, which refreshes `presence:{user_id}` with a short TTL. No heartbeat for a minute means the key expires and the user shows as offline with a "last seen" time. Presence is allowed to be slightly stale (consistency NFR), so it never touches the message store.
- **Receipts.** "Delivered" and "read" are small events sent back over the socket and through the same bus as messages. They update one pointer per member in the `receipts` table, not a row per message.

### Step 7: Photos and video (F5)

<AnimatedDiagram name="messenger/architecture" step={7} />

Media is about **200 TB a day**, far too much to push through chat servers. The app asks the **media service** for a **pre-signed upload URL**, uploads the file straight to the **blob store**, then sends a normal message carrying only the `attachment_id`. Recipients download through the **CDN**. See [Blob Storage, Chunking and Dedup](/system-design/patterns/blob-storage-and-chunking).

### Step 8: History and sync (F6)

<AnimatedDiagram name="messenger/architecture" step={8} />

Opening a chat or scrolling back calls the **history service**, which reads pages from the message store by `(conversation_id, bucket)` in `message_id` order. Recently opened conversations come from the cache. A new or reconnecting device calls `GET /v1/sync?since=<last message id>` and receives everything it missed; this is how offline users from step 3 catch up.

## 7. Final architecture

<AnimatedDiagram name="messenger/architecture" stepper caption="Messenger architecture: send, persist, fan out, then deliver or push. Use the numbers to replay the build." />

The components are grouped by responsibility; the same groups appear in every case study on this site.

| Group | Components | Responsibility |
|---|---|---|
| **Clients** | Mobile and web apps | Keep one WebSocket open, retry with `client_msg_id`, cache recent chats locally. |
| **Edge** | Load balancer, API gateway | Terminate TLS, route WebSockets to chat servers, authenticate and rate limit REST calls. |
| **Real-time messaging** | Chat servers, session registry, presence | Hold connections, know which server each user is on, track who is online. |
| **Application services** | Group, media and history services | Membership, upload URLs and thumbnails, paged history reads. |
| **Async pipeline** | Message bus, fan-out workers, push service | Order and persist messages, deliver to every member, notify offline devices. |
| **Storage** | Message store, cache, metadata DB, blob store + CDN | Durable messages, hot data, relational metadata, media bytes. |

### Sending a message, step by step

1. The sender's app sends `send_message` over its WebSocket; the load balancer keeps the connection on one chat server.
2. The chat server assigns a Snowflake `message_id` and publishes the message to the **message bus**, keyed by `conversation_id` so a conversation's messages stay in order on one partition.
3. A consumer **persists** it to the message store; once written, the sender receives `message_ack` (the "sent" tick).
4. **Fan-out workers** read the conversation's members and look up each member's chat server in the **session registry**.
5. Online members get `new_message` pushed over their WebSocket by the chat server that holds their connection; their app replies with a `delivered` receipt.
6. Offline members are handed to the **push service** (APNs / FCM); when they reconnect, the app calls `GET /v1/sync` to fetch what it missed.

  <InterviewQuestion question="How do you guarantee message order in a conversation?" category="Consistency" level="Mid">
    Key the message bus by conversation id so one partition holds a conversation's messages in order, and assign time-sortable message ids. Clients sort by message id, so late network arrivals still display in the right place.
  </InterviewQuestion>
  <InterviewQuestion question="How does a message reach a user connected to a different chat server?" category="Architecture" level="Mid">
    The session registry maps each user to the chat server holding their connection. Fan-out workers look the recipient up and forward the message to that server, which pushes it down the WebSocket.
  </InterviewQuestion>
  <InterviewQuestion question="How do you avoid duplicate messages when the client retries?" category="Reliability" level="Mid">
    The client sends a client-generated id with every message. The server stores it with the message and returns the existing message id for a repeat, so a retry after a timeout never creates a second copy.
  </InterviewQuestion>
  <InterviewQuestion question="How would you store read receipts for a 200-person group efficiently?" category="Data modeling" level="Senior">
    Store one pointer per member per conversation (last delivered id and last read id) instead of a row per message per member. A message is read by a member if its id is at or below their pointer.
  </InterviewQuestion>
  <InterviewQuestion question="What happens when a chat server crashes?" category="Reliability" level="Senior">
    Its clients reconnect through the load balancer to another server, which re-registers them in the session registry. No messages are lost because a message is only acknowledged after it is persisted, and clients resync from their last received message id.
  </InterviewQuestion>
