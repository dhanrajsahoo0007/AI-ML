Thousands of tiny writes a second each pay a full round trip, a request header and a system call, and the overhead costs more than the work.

- Interviewers ask about batching to see whether you can trade a few milliseconds of delay for much higher throughput, and whether you know where that trade hurts.

## Overview

- Every request pays a fixed cost: a **round trip**, headers, a system call, a log line. Small requests are mostly overhead.
- **Batching** groups many items into one request. A **linger window** (wait up to N ms) and a **size cap** (send at M items or bytes) decide when a batch goes.
- **Pipelining** sends the next request on a connection before the last reply arrives, so N requests cost about one round trip.
- **Batch APIs** need **per-item results**: one bad item must not fail the other 149.
- **Scatter-gather** sends one query to many shards and merges the answers. It waits for the slowest shard, so it needs a **deadline** and **partial results**.
- Batching hurts **tail latency** for the item that waits longest, and a **poison item** can block a whole batch.

## Mental model

- Think of a post office van. It could leave each time a single letter is posted, or every 30 minutes with a full sack.
- The full sack costs each letter up to half an hour of waiting, and saves hundreds of trips.
- Pipelining is the clerk handing over the next parcel without waiting for a receipt for the last one.
- Scatter-gather is sending a question to 20 branch offices and replying to the customer when 19 have answered, rather than waiting all day for the twentieth.

## Core concepts

- The running example is Brightpost's order events: **300/s** at the sale-day peak, each written to the search index; and product search over an index split into **20 shards**.

### Linger windows and size caps

- A batcher holds items until the **linger time** passes or the **batch is full**, whichever comes first.
- Longer lingers mean bigger batches and fewer requests, and more delay for every item.
- At low traffic the linger time sets the delay; at high traffic the size cap does, and batches leave full and early.

**The numbers:**

- 50 writes ÷ 5 per window = 10 requests: 80 % fewer round trips and request headers.
- Kafka's producer lingers 5 ms by default since Kafka 4.0 (it was 0 before) and caps each partition's batch at 16,384 bytes.

### Pipelining on one connection

- Request-reply waits for each answer before sending the next request, so N requests cost N round trips.
- Pipelining sends them back to back and reads the answers together: about one round trip, and fewer system calls on both ends.
- Order is kept: answers come back in the order the requests went out.

<AnimatedDiagram spec="animated/patterns/batch-pipeline" stepper caption="Pipelining sends the next request before the last reply arrives, so three reads cost one round trip." />

**How to read it:**

- Step 1 is three GETs, each waiting for its answer: three round trips.
- Step 2 sends the same three GETs back to back: the answers arrive together after one round trip.

**The numbers:**

- With a 250 ms round trip, request-reply manages at most 1,000 ÷ 250 = 4 requests a second, however fast the server is (Redis docs).
- Inside a data centre the round trip is well under a millisecond, but pipelining still cuts system calls: Redis reports up to about 10 times the throughput.

### Batch APIs and per-item errors

- A batch request must say what happened to each item, not just "the batch failed".
- Elasticsearch's bulk API returns an `errors` flag and one result per action, so the client retries only the failed items.
- Keep batches bounded in bytes as well as items: Elasticsearch rejects HTTP requests over 100 MB by default, and there is no single right batch size.
- The **N + 1 query** is the read-side version: one query for a list, then one per item. Batch the per-item reads into one (a DataLoader does this for GraphQL, see [GraphQL](/system-design/fundamentals/graphql)).

## Technical mechanics

### Scatter-gather and the slowest shard

- A request that waits for all N shards is slower than any one of them: it takes the maximum of N latencies.
- If each shard is slower than its p99 1 % of the time, a 20-shard query hits at least one slow shard 1 − 0.99^20 = 18 % of the time.
- Defences: a **deadline** with **partial results**, **hedged requests** to a replica of a slow shard, and fewer, larger shards.
- The full treatment: [Tail-Latency Hedging, Deadlines and Degradation](/system-design/patterns/tail-latency-and-degradation).

### When batching hurts

- **Tail latency:** the first item in a batch waits for the whole linger window. For interactive paths, keep lingers short or batch only in the background.
- **Head-of-line blocking:** in a pipeline, one slow request delays every answer queued behind it.
- **Poison items:** one item that always fails can fail or retry the whole batch forever. Use per-item results and send repeat failures to a dead-letter queue.
- **Memory:** a server answering a long pipeline queues every reply. Redis suggests sending pipelines in chunks, for example 10,000 commands.

### Worked example: order events into the search index

At the sale-day peak Brightpost writes 300 order events a second into the search index.

1. **Single writes.** Each event is one index request.
2. **Bulk writes.** The indexer buffers events and sends one bulk request every 500 ms or at 150 events, whichever comes first.
3. **A bad event.** One event has a malformed field. The bulk response marks it failed; the other 149 are indexed, and the bad one goes to a dead-letter queue.

**The numbers:**

- Single writes: 300 requests a second.
- Bulk: 300 ÷ 150 = 2 requests a second, each carrying 150 events. That is 298 fewer requests a second, over 99 %.
- Delay added: up to 500 ms, about 250 ms on average, before an order is searchable.
- At a quiet 2.3 events a second the 500 ms timer decides: about 1 event per request, so batching costs nothing at night.
- With a fixed overhead of 2 ms per request (illustrative), single writes spend 300 × 2 = 600 ms of server time a second on overhead; bulk spends 2 × 2 = 4 ms.

## Trade-offs

| Choice | Pros | Cons | When to use |
| --- | --- | --- | --- |
| One request per item | Lowest delay per item; simple errors | Overhead per item dominates | Interactive requests, low rates |
| Linger window plus size cap | Far fewer requests; bigger, cheaper writes | Up to one window of delay per item | Logs, events, index writes, producers |
| Pipelining | One round trip for many requests | Head-of-line blocking; reply memory | Many small commands to one server |
| Scatter-gather, wait for all | Complete results | As slow as the slowest shard | Small fan-out, strict completeness |
| Scatter-gather with a deadline | Bounded latency | Partial results some of the time | Search, feeds, recommendations |

## Production systems

- **Apache Kafka** (as of November 2026): the producer batches per partition up to `batch.size` (16,384 bytes by default) and waits up to `linger.ms`, which Kafka 4.0 raised from 0 to 5 ms because larger batches usually give similar or lower latency.
- **Redis pipelining**: commands are sent without waiting for replies; the docs show a 250 ms round trip limiting request-reply to 4 requests a second, and pipelining reaching about 10 times the throughput.
- **Elasticsearch bulk API**: many index, update and delete actions in one request, with an `errors` flag and per-item results; HTTP requests are limited to 100 MB by default.
- **Used in our case studies:** [Web Crawler](/system-design-case-studies/case-studies/web-crawler) · [User Data Export](/system-design-case-studies/case-studies/user-data-export) · [Metrics and Logging](/system-design-case-studies/case-studies/metrics-and-logging) · [Distributed Message Queue](/system-design-case-studies/case-studies/distributed-message-queue)

## Failure modes & pitfalls

- **All-or-nothing batches.** One bad item fails 149 good ones, and a retry fails them again. Return and handle per-item results.
- **Long lingers on interactive paths.** A user waits for a batch to fill. Keep lingers to a few milliseconds, or batch only background work.
- **Unbounded batches.** A burst builds a batch too big for the server's request limit or memory. Cap by items and by bytes.
- **Waiting for every shard.** One slow shard sets everyone's latency. Use a deadline and partial results.
- **Losing buffered items on a crash.** Items in an in-memory batch vanish with the process. Batch after a durable queue, or accept the loss for metrics.
- **N + 1 queries.** One query per item in a list. Batch the lookups.

## Interview framework

1. Count the requests a second and the fixed cost of each.
2. Introduce batching with a linger window and a size cap, and give the request rate before and after.
3. State the delay you add, and keep it off interactive paths.
4. Handle partial failure with per-item results and a dead-letter queue.
5. For fan-out reads, do the slowest-shard maths and add a deadline with partial results.

**What interviewers listen for:** the requests-per-second arithmetic, the added delay stated plainly, and per-item errors.

**Red flags:** one request per tiny event at thousands a second, or a scatter-gather with no deadline.
