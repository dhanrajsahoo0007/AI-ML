Half a million basket holds must expire at 12:10, and the one cron box that expires them dies at row 200,000.

- Interviewers ask about job scheduling to see whether you can run work later, once in effect, on a fleet where any machine can die mid-job.

## Overview

- A **job** is work to run later: expire a hold, retry a payment, transcode a video, send a reminder. Its **due time** is when it should run.
- A distributed scheduler keeps jobs in a **job store bucketed by due time**, with one **scanner** per partition moving due jobs to a queue.
- Workers **lease** a job for a fixed time. If a worker dies, the lease runs out and another worker gets the job, so delivery is **at least once** and every handler must be **idempotent**.
- A **durable workflow** (Temporal, AWS Step Functions) runs a multi-step process and records each step in an **event history**, so a new worker can replay it and carry on after a crash.

<Callout tone="violet" title="Interview edge: how this sets a senior answer apart" icon="sparkles">
  - **What most candidates say:** "A cron job scans the holds table every minute and expires the old ones."
  - **Why the interviewer pushes back:** "The table has 100 M rows, and the cron node can die mid-run. What happens then, and what if you run two?"
  - **The answer that stands out:** bucket jobs by due time across partitions, give each partition one scanner, and let workers lease jobs with a timeout and an idempotent handler. Name the cost: a job can run twice, so the handler must check state before it acts.
</Callout>

## Mental model

- Think of a hotel's wake-up calls: cards sit in a rack with one slot per minute (due-time buckets). Each minute a porter takes the current slot's cards and signs each with the time (a lease).
- A card still not marked done after 5 minutes goes back for another porter (the lease runs out). Ringing a guest who is already up does no harm (an idempotent handler).
- A durable workflow is the guest's folio: every charge is written down, so a new receptionist reads it and carries on without charging twice.

## Core concepts

- The running example is Brightpost's flash sale: **500,000 shoppers** arrive at **12:00** for **10,000 kettles**, and each gets a **10-minute hold** (illustrative: a kettle or a waiting-list place). So **500,000 expiry timers** are set by 12:01 and fall due between 12:10 and 12:11.

### Why one cron box fails

- A cron job runs `SELECT … WHERE expires_at < now()` once a minute on one machine. If that machine dies, no run happens until someone replaces it.
- A second machine on the same schedule runs every job twice, and so does a run that lasts longer than the schedule and overlaps the next.

**The numbers:**

- Due in one run: 500,000 rows. Without a good index the run scans every hold ever made: 200,000 orders a day is 73 M a year before abandoned holds, so about 100 M rows.
- One box with 20 threads at 20 ms a hold (illustrative): 500,000 × 0.02 ÷ 20 = 500 s, so the last kettle comes back more than 8 minutes late.

### Jobs, leases and at-least-once

- A **lease** (in Amazon SQS, a **visibility timeout**) hides a claimed job from other workers for a fixed time. The worker deletes the job when it finishes.
- If the worker dies, the lease runs out and the job becomes visible again: nothing is lost, but it may run twice.
- So every handler is **idempotent**: it acts only if the hold is still held.

### Durable workflows

- Some jobs are many steps with waits between them: reserve stock, wait up to 10 minutes for payment, charge £42, confirm.
- A **durable workflow** engine stores an **event history** for each run: one event per step started, finished, timer set or signal received.
- **Activities** are the steps with side effects (a card charge), retried by the engine with backoff.
- After a crash, a new worker **replays** the workflow code against the history: calls that already happened return their recorded results.

## Technical mechanics

### The job store: a delay queue bucketed by due time

- A Redis sorted set per partition holds job ids scored by due time: `ZADD jobs:p7 <due-ms> hold:4471`. Adding a job and finding due ones are both logarithmic.
- The scanner reads due jobs a page at a time (`ZRANGE … BYSCORE LIMIT 0 1000`) and **claims** each one with `ZREM`; only the caller whose `ZREM` returns 1 enqueues it.
- In a database, the same job store is a `jobs` table indexed on `(partition, due_at)`, claimed with `SELECT … FOR UPDATE SKIP LOCKED`.
- A managed queue can do this for short delays: Amazon SQS delays a message by up to 15 minutes, so a 10-minute hold fits but a 24-hour reminder does not.

### Leases, heartbeats and a late first worker

- Pick a lease longer than the usual job, and extend it with a **heartbeat** for long ones. SQS defaults to 30 s and allows at most 12 hours from the first receive.
- A worker can stall rather than die (a long garbage-collection pause, a hung call) and wake after a second worker has taken the job. The guard is in the data: expire the hold only `WHERE status = 'held'`, in the same transaction that returns the kettle.

### Retries, backoff and the dead-letter state

- Retry with **exponential backoff and jitter** (1 s, 2 s, 4 s, each plus a random fraction), so failed jobs do not all return in the same second.
- Cap the attempts: a **poison job** (bad data, a bug) fails every time. After the cap, move it to a **dead-letter state** and alert someone.
- Retry only errors that can pass (a timeout, a 503): a rejected card is a business result, not a retry.

### Timing wheels for many short timers

- A heap or a sorted set costs O(log n) per timer, which adds up with millions of short timers that are mostly cancelled.
- A **timing wheel** is a ring of slots, one per tick: a timer goes into slot (due − now) ÷ tick, and the clock empties one slot per tick, so adding and removing cost O(1).
- A **hierarchical** wheel hands longer timers to a coarser wheel, like a clock's hour hand. For Brightpost, 600 one-second slots cover every 10-minute hold, in memory: right for per-node timers, wrong for jobs that must survive a restart.

### Durable workflows: history and replay

- On replay, each command the code issues must match the next event in the history. That is why workflow code must be **deterministic**: no local clock, no random numbers, no direct network calls.
- Time, randomness and side effects go through the engine's API or into activities, so their results are recorded once. A code change needs a version check, or old runs fail to replay.

### Asynchronous request-reply

- Some requests take longer than a client will wait: a data export, a video transcode. The API answers **`202 Accepted`** at once and runs the job behind it.
- The `202` carries a `Location` header with a **status URL** and a `Retry-After` hint. The status URL answers `200` with `running` until the job ends, then `303 See Other` to the result.
- A client that can receive calls registers a **callback** instead (see [Webhooks](/system-design/fundamentals/webhooks)), or holds one request open with [long polling](/system-design/fundamentals/long-polling). An `Idempotency-Key` on the `POST` stops a retry from starting a second job.

### Worked example: 500,000 holds expire at 12:10

Follow the holds from the flash sale through the five steps of the Architecture figure.

1. **Store.** Between 12:00 and 12:01 checkout writes 500,000 expiry jobs into 16 partitions, due between 12:10 and 12:11.
2. **Scan.** From 12:10 each scanner polls once a second, finds its due jobs and claims them onto the ready queue.
3. **Lease.** Workers take each job for 30 s, run the conditional expiry in about 20 ms (illustrative) and delete it. Holds already paid change 0 rows.
4. **Crash.** A worker dies holding 20 jobs. Each comes back 30 s later and runs once more, safely.
5. **Retry.** A job whose database call times out comes back after 1 s, 2 s and 4 s, and goes to the dead letters after the fifth failure.

**The numbers:**

- Rate: 500,000 ÷ 60 s = 8,333 jobs a second created from 12:00, and 8,333 a second due from 12:10.
- Per scanner: 8,333 ÷ 16 = 521 due jobs per poll, under a page limit of 1,000.
- In flight: 8,333 a second × 0.02 s = 167 jobs at once (Little's law), so 9 workers of 20 threads (180 slots).
- Lateness: at most about 1 s (the poll) plus queue time, or about 31 s for the 20 jobs on the dead worker.

## Trade-offs

| Choice | Pros | Cons | When to use |
| --- | --- | --- | --- |
| Cron on one box | Simple; nothing to run | Single point of failure; overlapping runs; full scans | Small, idempotent housekeeping where a missed run is fine |
| Managed delay queue (SQS) | No servers; leases and dead letters built in | Delays up to 15 minutes; at-least-once | Short delays such as a 10-minute hold |
| Own job store and scanners | Any delay; you choose partitions and limits | You run scanners, leases and alerts | Many long-dated jobs: reminders, renewals, exports |
| In-memory timing wheel | O(1) timers; millions per node | Lost on restart; one node only | Request timeouts, heartbeats, retries within a process |
| Durable workflow engine | State, timers and retries survive crashes | Deterministic code; history limits; another system | Multi-step processes with waits: checkout, refunds, onboarding |

## Production systems

- **Amazon SQS** (as of November 2026): a delay queue or message timer holds a message back for up to 15 minutes; the visibility timeout defaults to 30 s and stops 12 hours after the first receive, and a standard queue allows about 120,000 messages in flight.
- **Temporal**: the event history is an append-only, durably stored log; on replay the commands the code issues are compared with it, and a mismatch is a non-deterministic error. A run is terminated past 51,200 events unless it restarts with Continue-As-New, and an activity's default retry starts at 1 s, doubles, caps at 100 s and never stops.
- **AWS Step Functions**: Standard workflows run up to one year with exactly-once workflow execution; Express workflows run up to five minutes, and asynchronous Express executions are at least once.
- **Apache Kafka** (Confluent, 2015): the request purgatory moved from a `DelayQueue` to hierarchical timing wheels with a 1 ms tick; in its benchmark at a high timeout rate the old design saturated near 25,000 requests a second and the new one reached about 105,000.
- **Kubernetes CronJob**: the docs warn that two Jobs or none may be created for one scheduled time, so Jobs should be idempotent.
- **Used in our case studies:** [Ticketmaster](/system-design-case-studies/case-studies/ticketmaster) · [Hotel Booking](/system-design-case-studies/case-studies/hotel-booking) · [Parking Garage](/system-design-case-studies/case-studies/parking-garage) · [Dropbox](/system-design-case-studies/case-studies/dropbox) · [YouTube](/system-design-case-studies/case-studies/youtube) · [S3](/system-design-case-studies/case-studies/s3) · [User Data Export](/system-design-case-studies/case-studies/user-data-export) · [Web Crawler](/system-design-case-studies/case-studies/web-crawler)

## Failure modes & pitfalls

- **A lease shorter than the job.** A slow job is handed to a second worker while the first still runs. Heartbeat to extend the lease, and keep the handler idempotent.
- **A handler that adds instead of checking.** `stock = stock + 1` on every run releases one kettle twice. Make the change conditional on the hold's state.
- **Retries with no cap and no backoff.** A poison job retries every second for ever. Use backoff with jitter, a maximum attempt count and a dead-letter state with an alert.
- **An unowned partition.** A scanner dies and its jobs go late without an error. Own partitions by lease (see [Leader Election and Consensus](/system-design/patterns/leader-election)) and alert on the age of the oldest due job.
- **Every timer due in one second.** 500,000 holds fall due in one minute because they were made in one minute; plan for that rate. Spread jobs that can wait, such as reminder emails, with jitter.

## Interview framework

1. Say what must happen later and how late is acceptable: holds expire within seconds of 12:10, not minutes.
2. Replace the cron box: a job store bucketed by due time, one scanner per partition, a ready queue.
3. Claim with a lease and heartbeats, make the handler idempotent, and add capped retries with backoff and a dead-letter state.
4. For multi-step processes with waits, use a durable workflow and say why its code must be deterministic.

**What interviewers listen for:** the rate arithmetic (8,333 expiries a second) and a handler that is safe to run twice.

**Red flags:** "a cron job runs every minute", or a lease with no idempotent handler behind it.
