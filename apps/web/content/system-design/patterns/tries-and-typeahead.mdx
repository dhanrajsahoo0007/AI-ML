The search box suggests completions as the shopper types, and the first version runs a `LIKE` query per keystroke until the database falls over at lunchtime.

- Interviewers ask about typeahead to see whether you can turn a prefix into five suggestions inside one keystroke's budget, and say where that work moves instead.

## Overview

- A **trie** (prefix tree) stores strings by their characters: every query that starts "ke" sits under one node.
- A **radix trie** merges chains of single-child nodes into one edge, so it stores far fewer nodes.
- **Top-k per node:** each node keeps its k most searched completions, so a lookup is one walk down the prefix and one list read.
- The trie is **built offline** from search logs, shipped as a snapshot and **served from memory** on replicas.
- A **fast path** merges trending queries from the last few minutes; **debounce** and **edge caching** cut the requests that reach a server.

<Callout tone="violet" title="Interview edge: how this sets a senior answer apart" icon="sparkles">
  - **What most candidates say:** "Run `LIKE 'ke%' ORDER BY count LIMIT 5` on the queries table."
  - **Why the interviewer pushes back:** "On every keystroke, for every shopper, under 50 ms?"
  - **The answer that stands out:** serve suggestions from an in-memory trie that stores the top 5 at every node, built offline from query logs, with a small trending list merged in. The cost is memory for a list on every node and suggestions that lag the logs by up to a day.
</Callout>

## Mental model

- Think of a dictionary with a thumb tab for every prefix ("k", "ke", "ket"), and a sticky note on each tab listing its five most looked-up words.
- To help a reader who has typed "ke", you open the "ke" tab and read the note. You never leaf through the section.
- Every night someone rewrites the notes from the day's lookups; during the day, a whiteboard by the door lists today's surprises.
- Tabs are trie nodes, the sticky notes are the stored top-k lists, the nightly rewrite is the offline build, and the whiteboard is the trending fast path.

## Core concepts

- Brightpost numbers on this page: **2,000,000 shoppers a day** each search about 4 times (illustrative), so **8,000,000 searches a day**; the shop's peak is 5 × its average; servers sit in **London**.

### A trie and a radix trie

- A **trie** has one node per character position: walking "k", "e", "t" reaches the node for the prefix "ket".
- A node that ends a query holds that query's **count** (how often it was searched).
- A **radix trie** (or compressed trie) stores a string on each edge instead of one letter, so a chain like "itchen scale" becomes one node.

### Top-k stored at every node

- Without help, answering "ke" means visiting every node below it and sorting what you find. Short prefixes are the worst: "k" covers most of the trie.
- **Storing the top k at every node** turns that into one walk down the prefix and one list read.
- The cost is memory (a list on every node) and updates: a new count can change every list from its node up to the root.

## Technical mechanics

### Building offline from query logs

- **Normalise** first: lower-case, trim, collapse spaces, so "Kettle " and "kettle" count as one query.
- **Filter:** drop queries searched fewer than a few times in the window, and anything on a blocklist.
- **Weight:** recent searches count more (for example, halve a count's weight every 7 days), so last winter's queries fade.
- **Build bottom-up:** a node's top 5 is the best 5 among its own query and its children's top-5 lists, so one pass computes every list.

### A fast path for trending queries

- A daily build cannot see a query that took off at 11:50. A stream job counts searches in short windows (see [Stream Processing and Windowed Aggregation](/system-design/patterns/stream-processing-and-windowing)).
- It keeps the heavy hitters of the last 10 minutes (see [Top-K, Heavy Hitters and Leaderboards](/system-design/patterns/top-k-and-leaderboards)) and pushes a short list to every server.
- At answer time the server merges trending matches for the prefix into the stored top 5, with a boost. The fast path skips the nightly filters, so it needs its own blocklist.

### Serving from memory, replicas and sharding by prefix range

- The whole trie lives in each server's memory, so a lookup touches no disk and no other machine. **Replicas** load the same snapshot and add throughput.
- When the trie outgrows one machine, **shard by prefix range** (for example a–f, g–m): each prefix lives in one range, so one request still touches one shard.
- Split the ranges by measured traffic, not the alphabet: "s" and "k" take far more searches than "x".

### Debounce and caching on the client and the edge

- **Debounce:** the client waits for a short pause in typing before it sends, so "kettle" costs a few requests, not six.
- The client drops replies for older prefixes, so a late answer for "k" never overwrites "ke". A **client cache** per prefix makes backspacing free.
- The **edge cache** keys answers by prefix with a TTL of an hour or so. Letter-only prefixes of 1 or 2 characters number 26 + 26² = 702, so they all fit.

### The search-engine alternative

- A search engine's completion feature does the job without a trie of your own. Elasticsearch's completion suggester keeps its suggestion structures in memory and sorts by a weight you supply; it matches prefixes, with optional typo tolerance.
- To match words in the middle of a title ("electric kettle" for "kett"), index **edge n-grams** in an [Inverted Index](/system-design/databases/inverted-index) and rank like any search.
- Choose it when you already run [Search Engines](/system-design/databases/search-engines) for the catalogue; build your own trie when suggestions come from query logs at high volume.

### Worked example: a shopper types "kettle"

A shopper in Manchester types "kettle" at 12:00. Follow the six steps of the Architecture figure.

1. Yesterday's 8 M searches went through the search service into the log.
2. At 02:00 the aggregation job counted 10 M distinct queries over 30 days.
3. The builder wrote a radix trie with the top 5 at every node as one snapshot.
4. All three London suggest servers loaded it and swapped it in by 03:00.
5. At 11:55 "kettle descaler" spiked during the sale; the trending list carries it.
6. "k" and "ke" are answered at the edge; "ket" reaches a server, which reads the stored top 5 at "ket", merges in "kettle descaler" and replies.

**The numbers:**

- Requests: 8 M searches × 6 suggestion requests = 48 M a day; 48 M ÷ 86,400 = 556/s on average, × 5 = 2,780/s at peak.
- Memory (illustrative): query text 10 M × 20 bytes = 200 MB; at most 20 M nodes × 32 bytes = 640 MB; top 5 as 4-byte ids, 20 M × 20 bytes = 400 MB; total about 1.24 GB.
- One server holds the trie; three replicas share the 2,780/s peak at about 927/s each.
- If a third of requests are 1- or 2-letter prefixes answered at the edge, servers see about 371/s on average.

## Trade-offs

| Choice | Pros | Cons | When to use |
| --- | --- | --- | --- |
| Trie with top-k per node, in memory | One walk and one list read; latency set by the network | A list on every node; changes wait for a rebuild | High-volume suggestions from query logs |
| Search-engine completion suggester | No custom build; weights, typo tolerance, filters | Lives in the engine's memory; one more cluster to size | You already run a search engine for the catalogue |
| Edge n-grams in an inverted index | Matches words anywhere in a title | Bigger index; relevance needs tuning | Product names where shoppers type a middle word |
| Database `LIKE` per keystroke | No new system | A scan and a sort per keystroke | Prototypes and tiny tables only |

## Production systems

- **Elasticsearch completion suggester** (docs, as of November 2026): built for search-as-you-type, held in memory and ranked by a weight you index with each suggestion. Elastic's 2013 blog describes it as an in-memory **finite state transducer** (FST) built per segment at index time.
- **Lucene FST** (Michael McCandless, 2010): 9.8 million terms from a Wikipedia index built into an FST of 69 MB.
- **Redis Stack** (as of November 2026): `FT.SUGADD` adds a string with a score to a suggestion dictionary, `INCR` updates it from live queries, and `FT.SUGGET` returns 5 suggestions by default, with an optional fuzzy match at edit distance 1.
- **Google autocomplete** (Google blog, 2018): predictions come from real searches, common and trending, and reduce typing by about 25 %.
- **Used in our case studies:** [Typeahead](/system-design-case-studies/case-studies/typeahead)

## Failure modes & pitfalls

- **Walking the subtree per keystroke.** Short prefixes cost the most. Store the top k at every node.
- **Rebuilding on the live server.** Lookups stall or see half-built lists. Build offline, swap a pointer, and keep yesterday's snapshot to roll back.
- **Offensive or spam suggestions.** The trending path skips the nightly filters. Apply the blocklist on both paths and count distinct shoppers, not searches.
- **No debounce, no cancel.** Every keystroke becomes a request and late replies overwrite newer ones. Debounce, cancel stale requests and drop out-of-order replies.
- **Personalised results at the edge.** A cached answer leaks one shopper's history to another. Cache the global list and personalise on the client or server.

## Interview framework

1. State the budget: requests per second (8 M searches × 6 = 556/s) and a latency target per keystroke.
2. Pick the structure: a radix trie with the top 5 stored at every node, in memory.
3. Draw the pipeline: logs, daily counts, offline build, snapshot to replicas, and a trending fast path.
4. Cut traffic: debounce and cancel on the client, prefix caching at the edge.
5. Size it and scale it: about 1.24 GB for 10 M queries, replicas for throughput, prefix-range shards when it outgrows one machine.

**What interviewers listen for:** top-k stored per node, an offline build with a stated staleness, and the arithmetic for requests and memory.

**Red flags:** a database `LIKE` query per keystroke, or a trie that is updated in place on every search.
