A storage node pauses for 3 s of garbage collection, a fixed timeout declares it dead, and the cluster starts moving its data. Then the node wakes up and it all moves back.

- Interviewers ask about gossip and failure detection to see whether you can keep a large cluster's view of who is alive correct and cheap, without a central monitor that becomes the next single point of failure.

## Overview

- A **failure detector** decides when a node that has gone quiet is dead. It can only guess: a crashed node and a slow one look the same from outside.
- **Gossip** spreads news (a join, a death, a new version) peer to peer: each round every node tells a few random peers. Everyone hears in about **log2 n rounds**, about 10 for 1,000 nodes.
- **SWIM** separates detection from spreading. Each node pings one peer a second, asks **k** other nodes to try when the ping fails, and marks the peer **suspect** before it declares it dead.
- The **phi accrual** detector replaces a fixed timeout with a suspicion level that grows with silence, scaled to how jittery the heartbeats have been.
- Once a node is down, a Dynamo-style store keeps writing with **hinted handoff** and a **sloppy quorum**, then fixes what was missed with **Merkle-tree repair**.

## Mental model

- Think of a large staff room with no register: every minute each person knocks on one random colleague's door. If nobody answers, they ask two others to knock too, in case the knock went unheard.
- If they get no answer either, they mention "I think Sam is out" in every chat they were having anyway.
- If Sam is in, Sam hears the rumour and says "I'm here". If not, after a while everyone agrees Sam is out.
- The knock is a **ping**, the two colleagues are an **indirect probe**, "I think" is **suspicion**, and the chats they were having anyway are **piggybacked gossip**.

## Core concepts

- The running example is Brightpost's key-value store: **1,000 nodes** (illustrative) holding the **1,000,000-product** catalogue and shoppers' baskets, read by **40 app servers** at up to **2,300 reads/s**.

### Why a central monitor flaps

- **Central monitor:** every node heartbeats to one box. That box must stay up, takes 1,000 heartbeats a second, and sees the network only from where it sits.
- **All-to-all heartbeats:** each of 1,000 nodes tells 999 others every second: 999,000 messages a second. The SWIM paper names this quadratic load as the reason classic heartbeating does not scale.
- **A fixed timeout** is one number for every network condition. Too short and a GC pause or a congested link looks like a death (a **false positive**); too long and real deaths go unnoticed.

### Gossip rounds and convergence

- Each round, every node that knows an update tells one or more random peers. The number who know roughly doubles each round.
- Nodes **piggyback** updates on messages they send anyway (pings and acks), so spreading costs no extra packets.
- **Convergence** is the moment every node holds the update. Random picks waste some messages on nodes that already know, so real clusters need a few rounds more than the best case.

## Technical mechanics

### SWIM's probe, suspicion and refutation

- Each node runs one **protocol period** at a time: ping one target, wait for the probe timeout, fall back to k indirect probes. SWIM sets the period to at least three round trips.
- Targets come from a shuffled list in **round-robin** order, so every member is probed once per pass. The SWIM paper bounds worst-case first detection to twice the group size in periods.
- With random targets, a dead member is first probed after about e ÷ (e − 1) ≈ 1.6 periods on average, whatever the cluster size.
- Load per node stays flat: one ping and one ack a period, plus rare ping-reqs. SWIM measured about 2.0 messages per member per period up to 55 members.
- Each member owns an **incarnation number**. Only the member itself raises it, when it hears it is suspected, and then gossips "alive" with the new number.
- Precedence: "alive" with a higher incarnation beats "suspect"; "dead" (SWIM's Confirm) beats both.
- memberlist scales the timer with cluster size: `SuspicionMult` 4 × log10(n) × the 1 s probe interval, so 12 s for 1,000 nodes.

### Lifeguard: when the prober is the sick one

- SWIM assumes the prober is healthy; a node short of CPU misses acks that did arrive and accuses healthy peers.
- HashiCorp's **Lifeguard** extensions add **self-awareness** (a node that misses acks slows its own probing and grows more cautious), **dogpile** (the suspicion timeout shrinks as more nodes independently confirm it) and **buddy system** (a suspect is told directly, so it can refute faster). HashiCorp reports more than 50 times fewer false positives, with no slower detection.

### Phi accrual: suspicion instead of a timeout

- The **phi accrual** detector (Hayashibara et al., 2004) keeps a sliding window of heartbeat gaps and fits their mean and spread.
- It outputs **phi = −log10 P**, where P is the chance a heartbeat comes this late. Phi 1 means about a 10 % chance the suspicion is wrong, phi 2 about 1 %, phi 3 about 0.1 %.
- The application picks a threshold. Cassandra's `phi_convict_threshold` defaults to **8**, and its docs say most users should never change it.

**How to read it:**

**The numbers:**

- Steady network: phi passes 8 after 2.1 s of silence. Jittery network: after 3.8 s.
- On the jittery network, 2.3 % of heartbeats arrive more than 2 s apart: one in 44. A fixed 2 s timeout calls a healthy node dead every 44 s or so.
- At 2 s phi on the jittery network is 1.6: by its own estimate, a verdict that would be wrong about 2.3 % of the time.

### What the cluster does next: sloppy quorum and hinted handoff

- A Dynamo-style store writes each key to **N** replicas taken from a **preference list** on the hash ring (see [Consistent Hashing](/system-design/patterns/consistent-hashing)).
- With a **sloppy quorum**, reads and writes go to the first N **healthy** nodes on that list, so a down replica does not block writes.
- The stand-in node keeps the write with a **hint** naming the intended owner, in a separate local store. When the owner returns, it hands the data back and deletes its copy: **hinted handoff**.
- Cassandra keeps hints for a down node for `max_hint_window`, 3 h by default; after that, only repair can catch the node up.

### Merkle-tree repair

- Hints cover short outages; for anything longer, replicas compare data in the background (**anti-entropy repair**).
- Each replica builds a **Merkle tree** per key range: leaves hash the values of keys, parents hash their children. Equal roots mean the range matches.
- When roots differ, the replicas swap the children's hashes and descend only where they differ. They find the bad keys in about log n levels and send only those.

- 8 leaves: 1 + 2 × 3 = 7 hash comparisons, and one leaf's keys sent.
- The 1,000,000-product catalogue in 2^20 = 1,048,576 leaves: 1 + 2 × 20 = 41 comparisons to find one differing key, instead of 1,000,000 hashes.

### Worked example: node 417 crashes at 12:00

Brightpost's 1,000-node store loses node 417 at 12:00:00. Follow the four steps of the Architecture figure, then the repair.

1. **A ping goes unanswered.** Every node probes one peer a second, so some node, say 212, probes 417 after about 1.6 s on average. No ack comes in 500 ms.
2. **Indirect probes fail.** 212 asks 3 nodes (memberlist's default) to ping 417; none gets an ack, and the 1 s period ends at about 2.6 s.
3. **417 is suspected.** The suspicion rides on pings and acks and reaches all 1,000 nodes in about 10 rounds, by about 12.6 s.
4. **417 is declared dead.** No refutation within 212's 12 s timer, so 212 declares 417 dead at about 14.6 s, and the verdict reaches everyone about 10 rounds later.
5. **Writes keep flowing.** Baskets whose preference list includes 417 go to the next healthy node with a hint. With 3 replicas per key, 3 ÷ 1,000 = 0.3 % of keys had a copy on 417.
6. **417 returns at 12:10.** The hints are handed back. Had it been away more than 3 h, a Merkle repair of its key ranges would catch it up.

**The numbers:**

- First probe at about 1.6 s; suspect at about 1.6 + 1 = 2.6 s.
- Dead at the first node at 2.6 + 12 = 14.6 s; known everywhere about 10 rounds later, at about 25 s.
- Spreading takes log2 1,000 ≈ 10 rounds at one round a second; memberlist actually gossips every 200 ms to 3 peers, so it is faster in practice.
- Probe load: about 2 messages per node per second, about 2,000 across the cluster, against 999,000 for all-to-all heartbeats.

## Trade-offs

| Choice | Pros | Cons | When to use |
| --- | --- | --- | --- |
| Central monitor with a fixed timeout | Simple; one view of the cluster | Single point of failure; one vantage point; flaps on a slow network | A few dozen nodes, or a coordination service's sessions decide anyway |
| All-to-all heartbeats | Every node sees every other directly | n² messages: 999,000 a second at 1,000 nodes | A handful of nodes |
| Gossiped heartbeat counters | No centre; spreads in log n rounds | Each node's view is eventually consistent; messages grow with membership | Peer-to-peer stores (Cassandra) |
| SWIM with suspicion | Constant load per node; fewer false positives | Seconds to detect; timers to tune | Large memberships (Consul, Nomad) |
| Phi accrual threshold | Adapts to each link's jitter | Needs a history of regular heartbeats | Wherever heartbeats arrive steadily |

## Production systems

- **Apache Cassandra** (docs, as of November 2026): every second each node gossips with one random node, runs a variant of the phi accrual detector, and convicts at `phi_convict_threshold` 8 by default. Hints are kept for 3 h (`max_hint_window`), and anti-entropy repair compares Merkle trees.
- **HashiCorp memberlist** (Consul, Nomad, Serf): SWIM with the Lifeguard extensions. LAN defaults probe every 1 s with a 500 ms timeout, use 3 indirect checks, and gossip every 200 ms to 3 nodes.
- **Amazon Dynamo** (SOSP 2007): each node contacts a random peer every second to reconcile membership. It uses a sloppy quorum with hinted handoff for temporary failures and one Merkle tree per key range for anti-entropy.

## Failure modes & pitfalls

- **Flapping on GC pauses or a busy CPU.** A healthy node is declared dead and data moves twice. Fix: a suspicion phase, phi accrual instead of a fixed timeout, and Lifeguard-style self-awareness on the prober.
- **Treating membership as consensus.** In a partition each side declares the other dead, and both may act. Fix: decisions that must be unique (one leader, one lock holder) go through [Leader Election and Consensus](/system-design/patterns/leader-election).
- **A "dead" node that keeps writing.** It was only slow, and it still serves stale or conflicting writes. Fix: incarnation numbers for membership, and fencing tokens for anything it owns.
- **Hints piling up for a long outage.** The stand-in's disk fills. Fix: cap the hint window (Cassandra: 3 h), then rely on repair.
- **Repair storms.** Building and comparing every tree at once saturates disks and links. Fix: repair one key range at a time on a schedule.

## Interview framework

1. Say why a central monitor with a fixed timeout fails: one point of failure, one vantage point, flapping.
2. Detect with SWIM: ping, k indirect pings, suspect, then dead; give the per-node load (about 2 messages a second).
3. Spread with gossip: log2 n rounds, about 10 for 1,000 nodes, piggybacked on probes.
4. Replace fixed timeouts with phi accrual where heartbeats are regular, and name the threshold.
5. Say what the cluster does with the verdict: sloppy quorum and hinted handoff now, Merkle repair later.

**What interviewers listen for:** the false-positive cost named out loud, and the 10-round arithmetic for 1,000 nodes.

**Red flags:** one monitor pinging everyone with a 1 s timeout, or using gossip membership to pick a single leader.
