When users type words and expect the best matches first, you need a search engine. Elasticsearch, OpenSearch, Solr and Typesense are built on an **inverted index**, which maps every word to the documents that contain it.

<DbProfile id="search" />

## Why `LIKE '%shoe%'` doesn't cut it

| | SQL `LIKE '%term%'` | Search engine |
|---|---|---|
| Speed | Scans every row (a leading wildcard can't use a B-tree) | Looks up the term: milliseconds |
| "Running" matches "run"? | No | Yes (stemming) |
| Typos ("shoees")? | No | Yes (fuzzy matching) |
| Ranking | None | BM25 relevance, boosts, recency |
| Facets ("Nike (120), Adidas (98)") | Expensive GROUP BYs | Built-in aggregations |

## How it works

## Keeping the index in sync

The search engine is a **derived store**. The source of truth stays in your database, and changes flow into the index:

<AnimatedDiagram name="databases/cdc-to-search" caption="Change data capture keeps the index about a second behind the database" step={1} stepper />

| Approach | How | Watch out for |
|---|---|---|
| **CDC** (recommended) | Tail the DB's WAL with Debezium → Kafka → indexer | More moving parts, but no lost updates |
| **Outbox** | Write an event row in the same transaction, then publish it | Needs a relay process |
| **Dual write** | App writes to the DB, then to the index | One write can fail. Drift between them |
| **Batch reindex** | Rebuild the index nightly | Stale for hours; fine for some catalogs |

## Scaling and consistency

- **Shards** split an index. The count is fixed at creation, so size it for growth (aim for 10–50 GB per shard).
- **Replicas** add read throughput and failover.
- **Near real time:** new documents become searchable after the refresh interval (1 s by default), so it's eventually consistent.
- **Updates are delete + reinsert** inside immutable segments, so heavy update traffic is expensive.

## In the wild

- **GitHub, Wikipedia, Uber and Netflix** run Elasticsearch / OpenSearch for search and log analytics.
- **LinkedIn's Galene** and **Twitter's Earlybird** are custom inverted-index systems for people and tweet search.
- **Hybrid search** (BM25 plus vector similarity) is now standard. Elasticsearch and OpenSearch support both in one query.

## Common pitfalls

- **Making it the source of truth.** Indices get corrupted, mappings change, and you'll need to rebuild from the database.
- **Wrong field types**: `text` where you needed `keyword` breaks filters and aggregations.
- **Too many shards**: thousands of tiny shards waste memory and slow the cluster.
- **Deep pagination** (`from: 100000`): use `search_after` cursors instead.

## How to answer in an interview

> "The catalog lives in Postgres. For search I'll stream changes via **CDC into Elasticsearch**, accepting about 1 s of lag. Title is a `text` field with an English analyzer and fuzziness, and brand and size are `keyword` fields for filters and facets. I'll re-check price and stock against Postgres at checkout."

<InterviewQuestions>
  <InterviewQuestion question="How would you keep Elasticsearch in sync with your database?" category="Consistency" level="Mid">
    Treat the database as the source of truth. Use change data capture (Debezium reading the WAL into Kafka, then an idempotent indexer) or a transactional outbox, so no committed change is lost. Avoid naive dual writes, because one side can fail. Make indexing idempotent using document ids and versions, and keep a way to rebuild the index from scratch.
  </InterviewQuestion>
  <InterviewQuestion question="Why is a search engine faster than SQL LIKE for text search?" category="Internals" level="Junior">
    LIKE with a leading wildcard can't use a B-tree index, so it scans every row. A search engine precomputes an inverted index from each term to its postings list, so a query looks up a few terms and merges small sorted lists. Analysis (stemming, lowercasing) and BM25 scoring also make results more relevant.
  </InterviewQuestion>
  <InterviewQuestion question="A product's price changed but search still shows the old one. Why, and is it OK?" category="Consistency" level="Mid">
    The index is updated asynchronously (CDC lag plus the refresh interval), so it trails the database by around a second, longer if the pipeline is backed up. That's acceptable for browsing as long as the authoritative price is read from the database on the product page and at checkout. Monitor pipeline lag and alert when it grows.
  </InterviewQuestion>
</InterviewQuestions>
