A basic RAG pipeline searches once, with the user's words, and answers from whatever came back. Agentic RAG hands the search to the model: it decides what to look for, reads the results, notices what is missing, searches again, and decides when it has enough. It answers harder questions, and it costs more model calls, time and tokens for every one of them.

## TL;DR

- **Agentic RAG** puts an LLM in a loop with retrieval as a **tool**: plan, search, read, decide, then search again or answer.
- It helps when one search cannot find everything: **multi-hop** questions, vague questions, and answers spread over several sources or systems.
- The pattern comes from **ReAct** (Yao et al., 2022): reasoning steps interleaved with actions. **IRCoT** (Trivedi et al., 2022) applied it to multi-step question answering and improved retrieval by up to 21 points.
- **Self-RAG** and **Corrective RAG** are narrower: the model or a grader checks retrieval and the answer, inside a mostly fixed pipeline.
- The cost is real: on Brightpost's question an agent with three search rounds makes **4 model calls instead of 1**, takes about **2.8 s instead of 1.5 s**, and reads **5.8 times the input tokens** (illustrative). Stopping rules and budgets are part of the design, not an add-on.

## The idea in plain English

A basic RAG system is a clerk who runs one search with your exact words and hands you the top five results. An agentic system is a researcher: they read your question, decide what to look up first, read what they find, notice "this assumes you still have your backup codes", look that up too, and stop when the answer is complete. The researcher gives better answers to hard questions and takes longer on every question, including the easy ones.

## Core concepts

The running example is Brightpost's help centre (1,200 articles, 3,600 chunks) and the question "How do I reset my password if I lost my phone?". Its answer needs three chunks; vector search ranks them 2, 4 and 7, so the ID-check article sits outside a top 5 (see [RAG Fundamentals](/ai-system-design/genai-system-design/rag-fundamentals)).

### Retrieval as a tool

The agent does not call the vector index directly. It calls a **tool**: a function with a name, a description and typed arguments, such as `search_help_centre(query, product, top_k)`. The model writes the arguments; the application runs the search, applies permission filters and returns results as text. Three design rules follow:

- **Describe tools by when to use them.** "Search help articles for how-to questions" lets the model choose between a help-centre search, a ticket search and an order-lookup API.
- **Return results the model can judge:** titles, short snippets and ids it can cite, not 5 × 400 tokens of raw text every time.
- **Keep permissions outside the model.** The tool applies the user's access filter; the model never decides who may see a document (see [RAG Access Control](/ai-system-design/genai-system-design/rag-access-control-multi-tenancy)).

[Tool Use and Function Calling](/ai-system-design/genai-system-design/tool-use-and-mcp) covers the calling mechanics and MCP.

### Multi-hop and iterative search

Some questions need the answer to one search before the next search can be written. "Which team owns the service that failed in last week's incident?" needs two hops: search the incidents and find that INC-311 hit checkout-api; then search for the owner of checkout-api and find the Payments team. No single query can name checkout-api before the first search has found it.

IRCoT (Trivedi et al., 2022) interleaves retrieval with chain-of-thought reasoning: after each reasoning sentence it retrieves again using that sentence. With GPT-3 on four multi-hop datasets (HotpotQA, 2WikiMultihopQA, MuSiQue and IIRC) it improved retrieval by up to 21 points and question answering by up to 15 points over retrieving once. When the hops follow known relations, a [knowledge graph](/ai-system-design/genai-system-design/knowledge-graph-systems) walk does the same job without a model call per hop.

### Self-RAG and corrective RAG

These add checks rather than open-ended planning. **Self-RAG** (Asai et al., 2023) trains the model to emit reflection tokens that decide whether to retrieve at all, whether a passage is relevant and whether its own output is supported. **Corrective RAG** (Yan et al., 2024) adds a small retrieval evaluator; when it rates the results as wrong, the system rewrites the query and searches the web instead. Both keep the pipeline mostly fixed and let a judgement change one branch. The [corrective loop on Advanced RAG](/ai-system-design/genai-system-design/advanced-rag) steps through one run on Brightpost's question.

A useful scale: fixed pipeline → pipeline with graders (Self-RAG, CRAG) → agent with tools (ReAct) → several agents (deep research). Each step right handles more open questions and costs more per question.

## Architecture

An agentic RAG service has four parts:

- **Agent loop:** the LLM, a system prompt with the tools and stopping rules, and the conversation so far. Each turn the model either calls a tool or answers.
- **Tools:** vector search over the help centre, keyword search for error codes, ticket search, SQL over orders, a web search when allowed. Each enforces the caller's permissions.
- **Controller:** the application code around the loop. It counts calls, tokens and seconds, stops the loop at the budget, and turns an unfinished run into "here is what I found" or a hand-off to a person.
- **Trace store:** every tool call, its arguments and results, for debugging and evaluation (see [LLMOps Observability](/ai-system-design/genai-system-design/llmops-observability)).

Simple questions should not enter the loop at all. A router (or the agent's first call) sends "how do I change my email?" straight to a single retrieval pass.

## Deep dive

### Stopping rules and budget control

The model decides when to stop, but it decides badly at both ends: it stops after one weak search, or it keeps searching for certainty it will never get. Production agents layer three controls:

1. **Explicit criteria in the prompt:** "answer when every part of the question has a cited source; search again only for a named gap."
2. **Hard budgets in the controller:** a cap on searches (three here), total tokens and wall-clock time. At the cap, the agent must answer from what it has or say what it could not find.
3. **Effort by question type:** Anthropic's write-up of its multi-agent research system put scaling rules in the prompt, such as 3 to 10 tool calls for a simple fact-finding question, because agents struggled to judge the right effort on their own.

Log the stop reason (answered, budget, no progress) for every run. A rising share of "budget" stops means a content gap or a broken tool.

### Deep research pipelines

Deep research is agentic RAG at a larger budget: a lead agent plans, starts subagents that each search one thread in parallel, and writes a long report with citations. Anthropic reports that agents use about 4 times the tokens of a chat interaction, multi-agent systems about 15 times, and that token usage alone explained 80% of the variance in performance on their BrowseComp evaluation. More tokens bought better research, at a cost only valuable tasks can carry. [Deep Research Agents](/ai-system-design/genai-system-design/deep-research-agents) covers the design.

### When agentic RAG is not worth it

Every round adds a model call and makes the next call read more. Here is the price on Brightpost's question.

**How to read it.** Row 1 counts the work: one search and one model call for basic RAG; three rounds of model call and search, then the answer call, for the agent. Row 2 is time: the searches are slivers, and the three 400 ms decision calls make up most of the extra 1.3 seconds. Row 3 is input tokens, the main driver of cost: every agent call re-reads the conversation so far, so the four calls read 215, 2,215, 4,215 and 6,215 tokens.

**The numbers.** All illustrative, from the stage latencies on [RAG Fundamentals](/ai-system-design/genai-system-design/rag-fundamentals). Basic: 20 + 15 ms to search, 2 ms to build the prompt, 1,500 ms to answer = 1,537 ms ≈ 1.5 s, and 2,215 input tokens. Agent: 3 × (400 + 35) + 2 + 1,500 = 2,807 ms ≈ 2.8 s, and 215 + 2,215 + 4,215 + 6,215 = 12,860 input tokens, 5.8 times as many.

For Brightpost, most questions are answered by one or two articles. Running every one through the agent would multiply the model bill by about six for questions basic RAG already answers. The agent earns its cost on the minority that need it: multi-hop questions, questions that span help articles and order data, and questions where the first search fails.

<Callout tone="red" title="What breaks">
  An agent with no budget loops on questions the corpus cannot answer: it rewrites the query, searches, finds nothing
  new and tries again, each round re-reading a longer context. Fix: cap rounds, stop when a search returns no chunk the
  agent has not already seen, and log those questions as content gaps.
</Callout>

## Trade-offs

| Decision                               | Option A                        | Option B                              | Guidance                                                                                       |
| -------------------------------------- | ------------------------------- | ------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Fixed pipeline vs agent                | Predictable latency and cost    | Handles multi-hop and vague questions | Route: pipeline by default, agent for the hard share                                           |
| Graders (Self-RAG, CRAG) vs full agent | One extra check, bounded cost   | Open-ended planning                   | Graders when retrieval quality is the problem; agents when the question needs several searches |
| Many small tools vs one search tool    | Model can pick the right source | Fewer wrong tool choices              | Few tools with clear "use when" descriptions                                                   |
| Tight vs loose budget                  | Fast, cheap, may stop early     | Better answers on hard questions      | Set the budget per question type and measure answer quality at each cap                        |
| Single agent vs multi-agent            | Simpler, fewer tokens           | Parallel research threads             | Multi-agent only for research-style tasks worth about 15 times the tokens                      |

## Real-world examples

- ReAct (Yao et al., 2022) let a model query a Wikipedia API between reasoning steps on HotpotQA and FEVER, and beat imitation and reinforcement learning baselines by 34 and 10 points of absolute success rate on ALFWorld and WebShop.
- Deep research features in ChatGPT, Gemini and Claude run multi-step search agents that read many sources and write cited reports.
- Anthropic's multi-agent research system (2025) outperformed a single agent by 90.2% on its internal research evaluation, using several times the tokens.

## Common pitfalls

- Sending every question through the agent, including ones a single search answers.
- No budget, so unanswerable questions loop until a timeout.
- Tool results that dump full chunks every round, so the context grows faster than the evidence.
- Letting the model choose filters that should be enforced, such as tenant or permission.
- Evaluating only the final answer, so a run that found the answer by luck after eight searches scores the same as one that needed two.

## How to answer in an interview

1. Start from the questions: what share needs more than one search, more than one source, or a follow-up?
2. Propose a router: a fixed pipeline for most questions, an agent loop for the rest.
3. Describe the loop: retrieval as a tool, plan, search, read, decide; name ReAct.
4. Give stopping rules and a budget, with what happens when the budget runs out.
5. Put numbers on cost and latency against the single pass, and say how you would evaluate both the answer and the trajectory.

**What interviewers listen for:** a reason to use an agent for a specific class of questions, and controls on cost and loops.

**Red flags:** "make it agentic" as the answer to every retrieval problem, with no budget and no evaluation of the steps.
