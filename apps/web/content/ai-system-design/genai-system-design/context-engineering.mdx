A model knows two things on any turn: what it learned in training, and the tokens you put in front of it.

- Context engineering is the work of choosing those tokens.
- Prompt engineering asks how to word the instructions; context engineering asks what else belongs next to them on this turn, in what order, and what should be dropped.
- For an agent that runs for dozens of turns, it is the difference between an assistant that stays sharp and one that slowly drowns in its own tool output.

## Overview

- The context window is a **budget**, not a bucket. Every token costs money and latency, and it competes with every other token for the model's attention.
- Context comes from six sources: **instructions, tool definitions, retrieved chunks, memory, conversation history and tool results**. The first four are roughly fixed per turn; the last two grow every turn.
- A context builder does three things on every turn: **select** what is relevant, **order** it (stable parts first, key evidence last) and **compress** what is old or bulky.
- Models use long contexts unevenly: information in the middle is used less well, and accuracy drops as input grows even on easy tasks (**context rot**).
- For long-running agents, three tools keep the window healthy: **compaction** (summarise and restart), **just-in-time retrieval** (fetch when needed, not up front) and **sub-agents** (explore in a separate window, return a summary).

## Mental model

- Imagine briefing a colleague who will take over a customer call.
- You do not hand them every email the customer ever sent, every page of the policy manual and the raw printout of every database lookup.
- You give them the policy page that matters, the last few messages, the order details that matter, and a one-paragraph summary of everything before that.
- You put the customer's actual question last, so it is the freshest thing in their head.
- That briefing is context engineering. The model is the colleague, and it reads every word you give it, useful or not.

## Core concepts

- The running example is Brightpost's support agent: a model with four tools (`get_order`, `search_help`, `create_refund`, `send_email`) that answers customers from a help centre of **3,600 chunks** (see [RAG Fundamentals](/ai-system-design/genai-system-design/rag-fundamentals)).
- One conversation starts with a lost phone and, twelve turns later, reaches "My kettle arrived cracked. It's order 4471. Can I get my money back?".

### Context as a budget

- A model's context window is the maximum number of tokens it can read in one call, and what it learns from them at request time is covered in [Context Windows & In-Context Learning](/ai-system-design/genai-system-design/context-windows-and-in-context-learning).
- Teams usually run an agent under a lower ceiling than the model allows, because cost and latency grow with every token and quality falls as the window fills.
- Anthropic's engineering team calls this the model's "attention budget": each new token draws it down, so the goal is the smallest set of high-signal tokens that does the job.

### Sources of context: instructions, knowledge, tools and memory

Every token in the window comes from one of six sources, and they behave in three different ways:

- **Fixed on every turn:** the instructions (role, policy, tone; versioned like code, see [System Prompt Design](/ai-system-design/genai-system-design/system-prompt-design)), the tool definitions (name, description and parameter schema of each tool; forty tools at 250 tokens each, illustrative, is 10,000 tokens before the customer says a word; loading them on demand is covered in [Progressive Disclosure & Agent Instructions](/ai-system-design/genai-system-design/progressive-disclosure-and-agent-instructions)) and memory, facts kept across sessions such as "prefers email" (see [Agent Memory](/ai-system-design/genai-system-design/agent-memory)).
- **Fetched per question:** retrieved chunks, the RAG part of the window.
- **Growing every turn:** the conversation history, and tool results. An order record or a web page can be thousands of tokens, and agents call tools on most turns, so these two decide how long an agent can run.

### Selecting, ordering and compressing context

The context builder makes three decisions on every turn. Here they are applied to the kettle turn.

<AnimatedDiagram
  spec="animated/rag/ctx-select-order-compress"
  stepper
  caption="The same turn costs 12,420 tokens as gathered and 5,140 after select, order and compress."
/>

**How to read it:**

- Step 1 gathers everything the builder could fetch, in the order it arrived: instructions, five password chunks still in the window from turn 1, twelve turns of history, memory, four tool definitions, five fresh chunks about damaged-item refunds, the full record for order 4471 and the new message.
- Step 2 selects: the password chunks belong to a question already answered, and a reranker keeps the best three refund chunks out of five; a dropped token costs nothing and distracts no one.
- Step 3 orders: instructions, tools and memory go first because they are the same on every turn, so a [prompt cache](/ai-system-design/genai-system-design/prompt-caching) can reuse them, and the evidence goes last, right before the message, where models use it best.
- Step 4 compresses: twelve turns become a 400-token summary plus the last two turns verbatim, and the 2,000-token order record becomes the four fields a refund needs (item, price, delivery date and status).

**The numbers:**

- 12,420 − 2,000 (password chunks) − 800 (two weak refund chunks) = 9,620.
- Then 9,620 − (3,600 − 1,000) − (2,000 − 120) = 5,140 tokens, 41 % of what was gathered. All counts are illustrative.

### Context rot and distraction

- More context is not free even when it fits. Anthropic gives the reason in one line: a transformer relates every token to every other token, which is n² pairs for n tokens, so a longer input spreads the model's attention thinner.
- Two studies show what that does to answers. The first is about where the evidence sits.
- Liu et al. (2023) found that models used information at the start or the end of a long input better than information in the middle, even models built for long contexts.

<AnimatedDiagram
  spec="animated/rag/lost-in-the-middle"

/>

**How to read it:**

- The curve is the shape of the finding, not the paper's data: accuracy is highest when the useful chunk sits at either end of the prompt, which is why step 3 above puts the evidence next to the message.

- The second is about how much surrounds it. Chroma's "Context Rot" report (Hong, Troynikov and Huber, July 2025) tested 18 models from four families on deliberately simple tasks, such as finding one fact in a long text, and changed only the length of the input.

- One more result points the same way. On LongMemEval, a test of questions about a long chat history, every model scored clearly higher on a **focused** prompt of about 300 tokens holding only the relevant turns than on the **full** history of about 113,000 tokens.
- The fix is the same in both studies: send fewer, better tokens, and put the evidence where the model uses it best.

<Callout tone="red" title="What breaks">
  Filling the window because it fits. A long-context model accepts 12,420 tokens as easily as 5,140, and nothing in the
  response says the extra 7,280 made it worse. The only way to see context rot is to measure it: run the same evaluation
  questions with short and long contexts, with and without distractors, and compare.
</Callout>

## Architecture

In a production agent one component, the context builder, assembles the model's input on every turn. Brightpost's builder grows one source at a time.

<AnimatedDiagram
  spec="animated/rag/ctx-assembly"
  stepper
  caption="Every source reaches the model through one builder, so one place decides what fits in the window."
/>

<StepCards>
  <StepCard n={1} title="Instructions and the message">
    The builder joins a versioned system prompt and the customer's message and sends them to the model. With one turn
    and no tools, there is nothing to manage yet. The model cannot answer Brightpost-specific questions because it has
    no evidence.
  </StepCard>
  <StepCard n={2} title="Add retrieved chunks">
    The builder asks the vector index for the top 5 chunks and places them before the message. Answers now cite real
    articles. The model still cannot look up an order or act on one.
  </StepCard>
  <StepCard n={3} title="Add tools and their results">
    The model can now call tools. Their results come back through the builder, not straight into the next call, so a
    2,000-token order record can be trimmed to the fields that matter. This is where the window starts to grow every
    turn.
  </StepCard>
  <StepCard n={4} title="Add memory and history">
    A memory store supplies facts about this customer, and a history store keeps every turn so the builder can replay
    the conversation. Two sources now grow without limit: history and accumulated tool results.
  </StepCard>
  <StepCard n={5} title="Compact when the budget runs low">
    When the assembled context passes 80 % of the budget, a compactor (a model call with a summarisation prompt)
    replaces old turns with a summary in the history store. The builder reads the summary instead of the raw turns from
    then on.
  </StepCard>
</StepCards>

<Callout tone="red" title="What breaks">
  Tool results appended straight into the conversation, with no builder in between, are the most common way agents run
  out of window. One large page or log can push out the instructions or the customer's question. Route every result
  through the builder and give each tool a token cap.
</Callout>

## Technical mechanics

### Compaction and summarization

- Compaction summarises a nearly full context and continues with the summary.
- The hard part is deciding what the summary must keep: decisions already made, open questions, promises to the customer, and identifiers such as order numbers.
- Anthropic describes Claude Code's compaction as keeping architectural decisions and unresolved bugs and continuing with the five most recently accessed files; it suggests tuning the summary prompt for recall first, then cutting what is not needed.
- The lightest form is **tool-result clearing**: old raw tool output is removed and the call is left in place.
- Anthropic reported that context editing (clearing stale tool calls and results) cut token use by 84 % in a 100-turn web-search evaluation.
- A third option is **note-taking**: the agent writes progress to a file or memory store outside the window and reads it back later.
- When to compact and when to reset, what a hand-off note holds, and how to keep state in files and databases outside the window are covered in depth in [Context Compaction, Resets & State](/ai-system-design/genai-system-design/context-compaction-resets-and-state).

### Just-in-time retrieval versus preloading

- **Preloading** retrieves before the model runs: the builder searches with the customer's message and adds the top 5 chunks to every turn, needed or not.
- This is how classic RAG works. **Just-in-time** retrieval gives the agent a search tool, or lightweight references such as file paths, stored queries and links, and lets it load only what it decides it needs.
- Here are two turns of the kettle conversation, run both ways.

<StepCards>

    - Preload: the builder searches with the raw message and adds 5 chunks before the only model call.
    - Just in time: the first model call sees no chunks, decides it needs the refund rule and calls `search_help` with its own query, "damaged item refund".
    - The tool returns the top 3 chunks, and a second call writes the reply.
  </StepCard>
  <StepCard n={2} title='The "thanks" turn, and the totals'>
    Preload searches and adds 5 chunks again, though the reply needs none of them (ringed). Just in time fetches
    nothing. Over the two turns, preload makes fewer calls and just in time sends fewer tokens.
  </StepCard>
</StepCards>

**The numbers:**

- Preload: 5 × 400 = 2,000 chunk tokens per turn, 4,000 over both turns, in 2 model calls.
- Just in time: 3 × 400 = 1,200 tokens over both turns, in 3 model calls.
- On the kettle turn, at 1.5 s per model call and 0.3 s per search (illustrative), preload takes 0.3 + 1.5 = 1.8 s and just in time 1.5 + 0.3 + 1.5 = 3.3 s.

This is the call the model makes in step 1 and the result it gets back, in the Claude Messages API shape (chunk text shortened):

```json
[
  { "type": "tool_use", "id": "toolu_02", "name": "search_help", "input": { "query": "damaged item refund" } },
  {
    "type": "tool_result",
    "tool_use_id": "toolu_02",
    "content": [
      { "type": "text", "text": "Damaged on arrival: full refund within 30 days of delivery. …" },
      { "type": "text", "text": "…" },
      { "type": "text", "text": "…" }
    ]
  }
]
```

- The first object comes back in the model's response; the second goes in the next request.
- The cost of just in time is latency and judgement: each fetch is another model call, and the agent must know what to look for.
- Anthropic recommends a hybrid in many cases: Claude Code puts its `CLAUDE.md` instruction files into the context up front and finds everything else with `glob` and `grep`.
- For Brightpost, a hybrid keeps the instructions, tools and customer memory up front and leaves help-centre knowledge to `search_help`.
- How to keep the up-front part small (a short root file, skills that load on demand) is on [Progressive Disclosure & Agent Instructions](/ai-system-design/genai-system-design/progressive-disclosure-and-agent-instructions), and [Agentic RAG](/ai-system-design/genai-system-design/agentic-rag) is the retrieval side of the same idea.

### Isolating context with sub-agents

Some tasks need far more reading than one window holds. A sub-agent is a separate model call with its own fresh window and a narrow task; it explores, then returns a short summary to a lead agent.

<AnimatedDiagram
  spec="animated/rag/ctx-subagents"
  stepper
  caption="Each sub-agent spends its own window exploring; the lead reads 4,500 tokens of findings instead of 60,000."
/>

**How to read it:**

- In step 1 the lead agent reads the orders, the refund policy and the past tickets itself, and 60,000 tokens do not fit its 32,000-token budget.
- In step 2 each source goes to a sub-agent that reads it in its own window and sends back only its findings.
- The lead sees three short reports and keeps room to reason.

**The numbers:**

- 3 × 20,000 = 60,000 tokens read in one window, against 3 × 1,500 = 4,500 in the lead's window (illustrative; Anthropic reports sub-agent summaries of often 1,000 to 2,000 tokens).
- The total spent goes up, not down: Anthropic's research system used about 15 times the tokens of a chat.
- Sub-agents buy focus, not savings. See [Multi-Agent Systems](/ai-system-design/genai-system-design/multi-agent-systems).

### Worked example: one turn, five model calls

- The [select, order and compress figure](#selecting-ordering-and-compressing-context) builds the kettle turn's context once.
- An agent calls the model several times in one turn, so the builder runs before every call.
- Here is the turn on the happy path from [Agent Architectures](/ai-system-design/genai-system-design/agent-architectures), with `search_help` called just in time.
- Each call starts from the same 3,820 tokens: the stable prefix (instructions 1,200 + four tools 1,000 + memory 600 = 2,800), the 1,000-token summary of the earlier turns and the 20-token message.
- Every tool call the model writes adds about 30 tokens (illustrative).

| Call | New in the window since the last call                                                           | Input tokens | The model asks for                                                                                               |
| ---- | ----------------------------------------------------------------------------------------------- | ------------ | ---------------------------------------------------------------------------------------------------------------- |
| 1    | The message                                                                                     | 3,820        | `get_order(4471)`                                                                                                |
| 2    | That call (30) and the order record, trimmed by the builder from 2,000 tokens to 4 fields (120) | 3,970        | `search_help("damaged item refund")`                                                                             |
| 3    | That call (30) and 3 chunks (1,200)                                                             | 5,200        | `create_refund(4471, 42.00)`: £42 is over £30, so the harness waits for the support agent, who approves at 10:20 |
| 4    | That call (30) and "refund R-2291" (20)                                                         | 5,250        | `send_email(customer, "Your refund")`                                                                            |
| 5    | That call (30) and "Email sent" (10)                                                            | 5,290        | Nothing: it writes the reply                                                                                     |

**The numbers:**

- The five calls read 3,820 + 3,970 + 5,200 + 5,250 + 5,290 = **23,530** input tokens.
- The 2,800-token prefix is the same in every call: 5 × 2,800 = 14,000 tokens, **60 %** of the input, can come from the [prompt cache](/ai-system-design/genai-system-design/prompt-caching).
- Call 3's window holds the same parts as step 4 of the figure, 5,140 tokens, plus the two tool calls.
- Without the builder, every call would also carry the raw history (3,600 − 1,000 = 2,600 more tokens) and, from call 2, the raw order record (2,000 − 120 = 1,880 more): 2,600 + 4 × 4,480 = 20,520 extra tokens, nearly double. All counts are illustrative.

Three things to take from it:

- **Context is rebuilt per call, not per turn.** A rule such as "trim tool results" runs inside the loop, before each call, or the 2,000-token record rides along four times.
- **Stable parts first pays on every call.** Put the timestamp or the chunks before the tools and the cache misses five times a turn.
- **The approval pause is a state problem, not a context problem.** If the support agent approves an hour later, the harness reloads the run from saved state and rebuilds call 4's context; see [Context Compaction, Resets & State](/ai-system-design/genai-system-design/context-compaction-resets-and-state).

## Trade-offs

| Decision             | Option A                                 | Option B                  | Choose A when                                                                          |
| -------------------- | ---------------------------------------- | ------------------------- | -------------------------------------------------------------------------------------- |
| Getting knowledge in | Preload top-k every turn                 | Just-in-time via a tool   | Most turns need the knowledge and latency matters                                      |
| Old history          | Keep verbatim                            | Summarise                 | Conversations are short and exact wording matters                                      |
| Tool results         | Keep raw                                 | Trim or clear after use   | The model must quote the raw output later                                              |
| Large tasks          | One agent, one window                    | Sub-agents with summaries | The task fits in one window and steps depend on each other                             |
| Context layout       | Stable prefix first, volatile parts last | Newest material first     | Almost always A: it keeps the prompt cache valid and puts evidence next to the message |

## Production systems

- **Coding agents** such as Claude Code load project instruction files up front, find other files with search tools on demand, and compact long sessions into a summary.
- **Anthropic's multi-agent research system** has a lead agent spawn sub-agents that search in parallel, each in its own context window, and return condensed findings.
- **Support assistants** retrieve help-centre chunks per question, cap tool output and summarise long chats before handing them to a person.

## Failure modes & pitfalls

- Treating a larger window as a fix. A million-token window still rots, costs more per call and hides bad selection.
- Leaving every tool result in the history forever.
- Loading dozens of tool definitions on every turn when the task needs three.
- Putting volatile parts (timestamps, retrieved chunks) before stable ones, which breaks [prompt caching](/ai-system-design/genai-system-design/prompt-caching).
- No token accounting per source, so nobody knows which part of the window grew.
- Building the context once per turn, when an agent calls the model several times in a turn. Trimming and clearing must run before every call.
- Letting the task drift out of view in a long run. Restate the goal and the current plan near the end of the context, where the model reads it last.

## Interview framework

1. Define it (choosing the tokens the model sees on each turn), list the sources and say which grow: history and tool results.
2. Walk through select, order and compress with numbers for one turn.
3. Name context rot and lost in the middle as the reason "more context" is not free.
4. For long-running agents, cover compaction, just-in-time retrieval and sub-agents, with the cost of each.

**What interviewers listen for:** a per-source token budget, a compaction trigger, and evidence placed where the model uses it.

**Red flags:** "just use a bigger context window", or no plan for what happens on turn 50.

    category="Failure modes"

    question="How do you lay out the context so prompt caching keeps working across an agent's calls?"
    category="Architecture"
    level="Senior"

    - Put what never changes first: instructions, then tool definitions in a fixed order, then long-lived memory.
    - Put what changes on every call after it: the history summary, retrieved chunks, tool results and the new message.
