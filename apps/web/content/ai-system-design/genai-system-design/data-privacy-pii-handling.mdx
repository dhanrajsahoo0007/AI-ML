Every support ticket is personal data: names, emails, card numbers, addresses. Interviewers ask where that data goes once an LLM touches it, because a prompt, a log line and a cache entry are all copies.

## Overview

- **Detect, replace, restore.** Find personal data, swap each item for a **placeholder** such as `EMAIL_1`, send placeholders to the model, and put the real values back in the reply.
- **Detect in layers.** Patterns and check-digit tests for emails and card numbers, a name-finder model for people and places, and review for the uncertain cases. No detector is complete.
- **Every store is a copy.** Prompt logs, traces, caches, fine-tuning sets and the model provider each need a control and a **retention period**.
- **Minimise.** Send the model only what the task needs. Brightpost's assistant does not need a card number to explain a refund, so it never receives one.
- **Read the provider's terms.** As of November 2026, OpenAI keeps abuse-monitoring logs for up to 30 days by default; zero data retention needs approval. Anthropic offers zero data retention by agreement. Check the current page for yours.

## Mental model

- A hotel front desk takes your passport to check you in, then hands it back.
- It does not photocopy it for the kitchen, the cleaners and the bar.
- Each department gets a room number, which is all it needs, and only the front desk can link the number to your name.
- Redaction does the same for an LLM: the model works with "room numbers" (placeholders) and the front desk (your own service) keeps the key.
- A privacy review then asks the questions an auditor would: who else holds a copy, and for how long?

## Core concepts

The running case is a Brightpost ticket that contains an email address and a card number. The help centre has 1,200 articles; the refund case is order 4471, a cracked kettle, £42.

1. **Personal data.** Under the GDPR, any information about an identified or identifiable person (Art. 4(1)). A name is clear; an email, a customer ID or an IP address can also identify someone.
2. **PII.** The common term for personal data, mostly used in the United States. This page uses the GDPR's terms where it matters.
3. **Processing, controller and processor.** Processing is any operation on personal data, including storing and deleting it. The controller decides why and how; the processor handles data on the controller's behalf. Brightpost is the controller; a model provider that processes tickets is a processor.
4. **Detection.** Patterns (regular expressions) for structured items, a checksum such as the Luhn test to separate a card from a random 16-digit number, a trained name finder for people and places, and context rules. Microsoft's Presidio, an open-source toolkit, combines these kinds of recognisers and states that automated detection cannot guarantee finding all sensitive data.
5. **Pseudonymisation.** Replacing identifiers so data cannot be linked to a person without extra information kept apart (Art. 4(5)). Placeholders plus a separate map are pseudonymisation. It reduces risk; the data is still personal data.
6. **Anonymisation.** Removing identification so it cannot be reversed. Hard to prove for free text.
7. **Data minimisation and storage limitation.** Collect only what is necessary, and keep it no longer than necessary (Art. 5(1)(c) and (e)).
8. **Erasure.** A person can ask a controller to delete their data when stated grounds apply (Art. 17). A copy in a log, a cache or a fine-tuning set has to be findable to be erased.
9. **Differential privacy.** Calibrated noise added to a statistic or to training so one person's data barely changes the result. It suits aggregates, not individual replies.

## Technical mechanics

### Detecting in layers

Run the cheap, exact detectors first and escalate the uncertain.

1. **Patterns and checksums** for emails, phone numbers and card numbers. Exact and fast. A Luhn test stops a 16-digit order reference being mistaken for a card.
2. **A name-finder model** for people, places and organisations, with a language check per segment. Needed because names have no pattern.
3. **An LLM or a person** for the uncertain spans and for context ("my neighbour's address is..."). An LLM labeller can invent labels and sees the sensitive text itself, so do not make it the only gate in a high-risk flow.
4. **An allow list** for what must stay readable, such as the order number.

- Measure the detector like any classifier: precision and recall per type on a labelled set of tickets, and a recall target for the types that matter most (card numbers first).
- A missed card is worse than a masked word. See [Quality Metrics](/ai-system-design/genai-system-design/quality-metrics).

### Where the data rests

The model call is one copy. The others are the stores that keep it.

- **Prompt logs and traces.** Redact before the write, and give each a short retention period. Brightpost keeps traces for 30 days (illustrative), which matches the trace store on [Tracing & Logging](/ai-system-design/genai-system-design/tracing-logging).
- **Semantic cache.** A cached answer can contain another customer's details. Redact before embedding, key entries by tenant, and set a time to live. See [Semantic Caching](/ai-system-design/genai-system-design/semantic-caching).
- **Fine-tuning sets.** Scrub the 5,000 resolved tickets before training. A model cannot be made to forget one ticket, so what goes in stays in until the model is retired.
- **The provider.** Read the data terms. OpenAI's documentation (checked November 2026) says abuse-monitoring logs are kept for up to 30 days by default, that API data is not used for training unless you opt in, and that zero data retention, which excludes customer content from those logs, needs approval and covers only some endpoints.
  - Anthropic's documentation (checked November 2026) says retained data is never used for training without your express permission, and that zero data retention is an arrangement made with Anthropic, with some features excluded.
  - Terms change; cite the page and the date in your design.
- **Audit trail.** A record that something was accessed or deleted is also personal data. Keep it, and see [Compliance & Audit Logging](/ai-system-design/genai-system-design/compliance-audit-logging).

### Regions and transfers

- Where a copy rests matters as much as how long.
- The GDPR restricts sending personal data to a country outside the EU unless its transfer rules are met (Art. 44), so a provider's region is a design input.

### Prompt injection and leaks

- An attacker can try to make the assistant repeat its system prompt, a tool result or a memory that holds personal data.
- Defences: keep secrets and other customers' data out of the model's context, filter output for secret and card patterns, and limit tool results to the current customer.
- See [Prompt Injection & Jailbreaks](/ai-system-design/genai-system-design/prompt-injection-and-jailbreaks).

### Worked example: the ticket with a card number

1. **Arrive:** a customer writes the ticket above with an email and a card number.
2. **Detect:** the email and card match patterns, and the card passes the Luhn test. The order number 4471 is allow-listed.
3. **Swap:** `EMAIL_1` and `CARD_1` replace them. The map holds both values for this request.
4. **Minimise:** Brightpost does not need the card number to start the refund; the payment provider refunds to the original card. So `CARD_1` is dropped from the prompt entirely.
5. **Model:** the assistant sees order 4471, a cracked kettle and `EMAIL_1`, and asks for approval because £42 is over the £30 limit.
6. **Store:** the trace stores the placeholders. The prompt log is redacted before the write and deleted at 30 days (illustrative).
7. **Restore:** the confirmation email address is put back for the reply, and the map is discarded.
8. **Erase:** if the customer later asks for deletion, the ticket ID finds the one record that matters; the logs hold no email to search for.

<Callout tone="red" title="What breaks">
  The detector misses a card number typed with dashes and a space, "4242-4242 4242 4242". The raw number reaches the prompt log, the cache and the provider. Fix: test each detector on messy real formats, add a second pass on the output and the logs, and set a recall target for card numbers.
</Callout>

## Trade-offs

| Choice | Pros | Cons | When to use |
| --- | --- | --- | --- |
| Patterns and checksums | Exact, fast, cheap | Only structured items | Emails, phones, cards |
| Name-finder model | Finds names and places | Misses, slower, language-bound | Free text with people |
| LLM detection | Understands context | Can invent labels, sees the data | Second pass, with review |
| Placeholders with a map | Reversible, joins preserved | The map is a target | Replies that need the value back |
| Irreversible masking | Nothing to steal | Loses detail | Logs, analytics, fine-tuning |
| Zero data retention | Provider stores nothing at rest | Approval, fewer features | Sensitive tickets |
| Short retention | Smaller breach, easy erasure | Less debugging history | Prompt logs, traces, caches |
| Differential privacy | A provable bound on leakage | Costs accuracy, spends a budget | Aggregates, not single replies |

## Production systems

- **Presidio** (Microsoft, open source): an analyzer finds personal data and an anonymizer replaces it; its docs warn that automated detection cannot find everything.
- **OpenAI API data controls:** abuse-monitoring logs for up to 30 days by default, and zero data retention on approval (documentation, checked November 2026).
- **Anthropic API:** retained data is not used for training without permission, and zero data retention is available by agreement (documentation, checked November 2026).
- **Brightpost** redacts before every store, keeps traces for 30 days (illustrative), and drops the card number from the prompt entirely.

## Failure modes & pitfalls

- **Redacting only the prompt.** The cache, the traces and the fine-tuning set are separate copies.
- **A detector with no recall target.** Test it on messy real formats.
- **Logs kept forever.** Set a retention period for every store, and enforce it.
- **Assuming a placeholder is anonymous.** Placeholders plus a map are pseudonymised, not anonymous.
- **Sending what the task does not need.** If the model does not need the card, do not send it.
- **No answer to an erasure request.** Know where each person's data can sit before you are asked.

## Interview framework

1. Draw the path: detect, replace with placeholders, model, restore. Say the model never sees the values.
2. Explain layered detection: patterns and checksums, a name finder, review; state that none is complete.
3. List every place the data rests and give a control and a retention period for each.
4. Cover the provider: its retention, training use and region, with the date you checked.
5. Close with minimisation and erasure: send less, and be able to delete.

**What interviewers listen for:** every copy of the data, not only the prompt; recall measurement; correct GDPR terms (controller, processor, pseudonymisation); and retention periods.

**Red flags:** "we trust the provider", "regex is enough", "the model will ignore it", or no plan for deletion requests.
