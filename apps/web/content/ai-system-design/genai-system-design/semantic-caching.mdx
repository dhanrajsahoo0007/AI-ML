---
title: Semantic Caching
description: Reuse LLM responses for similar requests via embedding similarity, careful invalidation, and monitoring to cut cost and latency without stale or wrong answers.
---

Many questions a support assistant gets are the same question in different words.

- A semantic cache notices that and returns the answer it already paid for, in milliseconds instead of seconds.
- The hard part is not the lookup; it is knowing when two questions that look alike need different answers, and when a stored answer has gone stale.

## Overview

- An **exact-match cache** misses as soon as a user rephrases. A **semantic cache** keys each request by an embedding of its normalised text and serves a stored answer when a past question is close enough.
- The **similarity threshold** is a policy choice, not a tuning detail. Higher means fewer wrong answers and fewer hits; lower means more hits and more answers served to questions they do not fit.
- A **false hit** (serving a cached answer to a question that needed a different one) is worse than a miss. "Change my password" and "reset my password" look alike and need different steps.
- **Invalidation** needs three tools: a TTL, busting by the version of the source documents and tools, and a purge by tenant.
- Measure **hit rate, net savings and the error rate of cached answers against fresh ones**, and start in shadow mode.

## Mental model

- A help-desk worker who has answered "how do I reset my password?" fifty times keeps a sheet of model answers.
- When a customer asks "how can I reset it?", they read from the sheet.
- A good worker also knows when not to: "how do I change my password?" sounds the same but has different steps, and a sheet written before last week's policy change is wrong.
- A semantic cache is that sheet, with an embedding model deciding what counts as "the same question".

## Core concepts

- The running example is Brightpost's support assistant from the RAG pages: a help centre of **1,200 articles** in **3,600 chunks**, answering with retrieval and an LLM.
- Every answer it generates costs about **2,215 input tokens** and 1.5 seconds.

### Exact keys and semantic keys

- An exact-match cache hashes the request text and looks the hash up.
- It is cheap and never wrong, and it misses whenever the wording changes by one character.
- Semantic caching keys requests by an embedding of normalised text (and optionally structured context such as locale or model parameters), then searches a store of past (query embedding, response, metadata) pairs for neighbours above a similarity threshold.
- On a hit, you can return the cached completion immediately or use it as a draft for a cheaper verification pass.

- The architecture parallels the nearest-neighbour retrieval used in recommendation, but it optimises for equivalence of task outcomes rather than personalisation: two questions are neighbours only if the same answer is right for both.
- It is also different from [prompt caching](/ai-system-design/genai-system-design/prompt-caching), where the provider reuses the computed state of an **exact** prompt prefix and the model still generates a fresh answer. A semantic cache skips the model entirely.

### What goes into the key

The embedding decides "same question"; everything else that changes the answer belongs in the key as exact fields, filtered before the similarity search:

- **Tenant and permission scope.** A cached answer built from a staff-only runbook must never reach a customer (see [RAG Access Control & Multi-Tenancy](/ai-system-design/genai-system-design/rag-access-control-multi-tenancy)).
- **Prompt, model and tool versions.** Multi-field keys help, for example hashing tool definitions and schema versions into the cache key so a prompt or capability change does not silently reuse incompatible answers.
- **Locale and output format.** "Wie setze ich mein Passwort zurück?" may embed close to the English question and still needs a German answer.

### The similarity threshold

- Similarity thresholds encode a policy choice: higher thresholds reduce false reuse where wording differences actually change the answer, while lower thresholds increase hit rate but risk serving incorrect or noncompliant text for subtly different constraints.

<Callout tone="red" title="What breaks">
  "Change my password" (signed in, knows the old one) scores 0.94 against a cached "reset my password" (locked out) and gets the wrong procedure. Raising the threshold alone costs good hits. Add an exact check on the words that flip the answer, or a cheap verifier on hits in the overlap band.
</Callout>

## Architecture

The cache sits in front of the whole RAG pipeline, so a hit skips retrieval and generation together.

/>

<StepCards>
  <StepCard n={1} title="Normalise the question and build the key">
    Lower-case the text, trim whitespace and strip greetings, then attach the exact fields: tenant, permission scope, prompt and model versions. Normalising alone turns some rephrasings into exact matches. It cannot see that "how can I reset it" asks the same thing, which is why the next step exists.
  </StepCard>
  <StepCard n={2} title="Embed the normalised question">
    The embedding model turns the question into a 1,536-dimension vector, about 20 ms (illustrative). If the cache uses the same model as retrieval, a miss can reuse this vector for the vector search. The vector still has to be compared with past questions.
  </StepCard>
  <StepCard n={3} title="Find the nearest cached question">
    A vector index over past questions, filtered by the exact key fields, returns the nearest one: "how can i reset my password" at 0.97. This is one more nearest-neighbour search, about 5 ms (illustrative). The cache now needs a rule for when "nearest" is near enough.
  </StepCard>
  <StepCard n={4} title="Hit: return the stored answer">
    0.97 is above the threshold of 0.92, so the stored answer goes back to the user, about 25 ms after the question arrived. No retrieval, no LLM call, no tokens. Questions nobody has asked before still need the full pipeline.
  </StepCard>
  <StepCard n={5} title="Miss: retrieve and generate as usual">
    Below 0.92 the request continues into RAG: the top 5 chunks, the prompt and the LLM, about 1.5 seconds in all (illustrative). The user gets a fresh, cited answer. Nothing has been learned for the next person who asks the same thing.
  </StepCard>
  <StepCard n={6} title="Store the answer with a TTL, the tenant and article versions">
    - The answer is written to the cache with its question vector, the key fields, a TTL (24 hours here) and the ids and versions of the articles it cites.
    - Those versions are what lets an article edit find every answer built from it later.
    - The cache now hits on the next paraphrase, and on anything else that scores above 0.92.
  </StepCard>
  <StepCard n={7} title="False hit: a different question above the threshold">
    "Change my password" scores 0.94 against the cached reset question and gets the reset steps. This is the failure that decides how far to push the threshold, and why Technical mechanics adds verification and invalidation.
  </StepCard>
</StepCards>

**The numbers:**

- Hit: 20 ms to embed + 5 ms to search = 25 ms. Miss: 25 + 15 (vector search) + 2 (prompt) + 1,500 (answer) = 1,542 ms. At an illustrative 10,000 questions a day and a 30% hit rate, 3,000 answers skip an LLM call of 2,215 input tokens; at an illustrative 3 US dollars per million input tokens that is about 0.0066 dollars each, roughly 20 US dollars a day, before subtracting the embedding and cache costs.

## Technical mechanics

### Invalidation

- Invalidation is harder than for byte-identical caches, because one article edit can make answers to dozens of differently worded questions wrong.
- You need rules for TTL on time-sensitive topics, explicit busting when underlying documents or tools change version, and per-tenant purge APIs for privacy requests.

**How to read it:**

- Each entry carries its tenant, the article versions it was built from and a TTL.
- Step 2: the sale answer was stored for one hour, because sale dates change, and it expires.
- Step 3: an editor saves version 8 of "Reset a forgotten password"; both entries built from version 7 go, although their questions are worded differently.
- Step 4: Tenant B asks for a purge and all its entries go. The parcel answer survives all three.

- The edit event is the same one that re-embeds the article's chunks in [Index Freshness & Updates](/ai-system-design/genai-system-design/index-freshness-and-updates): the update pipeline should publish "article X is now v8" once, and both the vector index and the cache act on it.
- For regulated answers, prefer shorter TTLs or disable semantic reuse entirely.

### Verifying a hit

False positives are more damaging than a cache miss, so conservative thresholds and optional lightweight judges often pay for themselves. Three guards, cheapest first:

- **Exact checks on answer-changing words.** Keep a short list of verbs and entities that flip the answer (reset or change, order or subscription) and require them to match.
- **A small verifier model** that reads the new question and the cached question and answers "same answer, yes or no". It costs a fraction of a full RAG call and runs only on hits in the overlap band.
- **Re-check the evidence.** Store the ids of the retrieved chunks with the entry and, for high-risk topics, re-run retrieval and serve the cached answer only if the same chunks come back.

### Monitoring

- Monitoring should track hit rate, estimated savings in US dollars, and downstream error rates attributed to cache hits versus misses: thumbs-down, follow-up questions such as "that's not what I asked", and escalations to a human.
- Log the similarity of every hit so you can plot errors against it.
- Start in shadow mode: look up, log the would-be hit, and serve the fresh answer anyway; comparing the two gives the false-hit rate before any customer sees one.
- See [LLMOps Observability](/ai-system-design/genai-system-design/llmops-observability).

## Trade-offs

Trade-offs include storage growth, embedding compute on every request, and the cold-start period before the cache is warm.

| Decision | Option A | Option B |
| --- | --- | --- |
| Threshold | High (0.96): few false hits, fewer hits | Low (0.90): more hits, more wrong answers |
| Key | Question vector only: highest hit rate | Plus tenant, scope, versions, locale: safe, lower hit rate |
| On a hit | Serve at once: about 25 ms | Verify first: slower, catches near misses |
| Expiry | Long TTL: more reuse | Short TTL or version busting: fresher |
| Scope | Shared across users: more hits | Per user: no leaks, rarely hits |

## Production systems

- **GPTCache** (open source, from Zilliz) splits a semantic cache into an embedding generator, a cache store, a vector store, a similarity evaluator and eviction policies (LRU, FIFO, LFU and random). GPTCache and similar libraries illustrate embedding backends, vector stores, and eviction policies you can adapt to your stack.
- **Azure API Management** has a semantic cache lookup policy for LLM APIs with a `score-threshold` from 0.0 to 1.0 where lower is stricter, a `vary-by` expression to partition the cache per user or subscription, and a store policy whose TTL is set in seconds. Microsoft's docs warn that similarity-based reuse can surface incorrect, outdated or unsafe responses.
- **RedisVL `SemanticCache`** uses a cosine distance threshold (0 identical, 2 opposite), optional TTLs, filterable tag fields such as a user or tenant id, and calls to drop individual entries or clear the cache.
- Research moves beyond one global threshold: vCache (Schroeder et al., 2025) learns a separate threshold for each cached entry so the error rate stays under a bound the user sets.
- **Used in our case studies:** [AI Answer Engine](/genai-system-design/case-studies/ai-answer-engine) · [LLM Platform and Gateway](/genai-system-design/case-studies/llm-platform-gateway)

## Failure modes & pitfalls

- One threshold for every topic: a password procedure needs a stricter one than "what are your opening hours".
- Leaving tenant or permission scope out of the key and serving one user's answer to another.
- No link from cache entries to source versions, so an edited article keeps answering from the cache for a full TTL.
- Caching answers that contain personal data ("your order 1234 ships Tuesday").
- Counting gross savings and forgetting the embedding call, the cache store and any verifier.
- Changing the embedding model without re-embedding the cached questions or re-tuning the threshold.

## Interview framework

1. Contrast exact-match, prompt and semantic caching in one sentence each.
2. Draw the request path: normalise, embed, nearest cached question, hit or miss, store with metadata.
3. Say what goes in the key besides the vector: tenant, permission scope, prompt and model versions.
4. Treat the threshold as a policy, tuned per segment in shadow mode, and name a false hit you would expect.
5. Explain invalidation: TTL, busting by document version, purge by tenant.
6. Close with metrics: hit rate, net savings, and errors on hits against misses.

**What interviewers listen for:** that a false hit is worse than a miss, and a concrete invalidation story.

**Red flags:** a single global threshold with no measurement, or a cache key without tenant or permissions.
