A 128,000-token prompt is easy to accept and hard to serve: its KV cache can be larger than the GPU, and its prefill can take tens of seconds. Interviewers ask about long context because the answer needs arithmetic (bytes per token), a parallelism idea (split the sequence, not the layers) and an honest view of what compression costs in accuracy.

## TL;DR

- Long context breaks **memory first, then time**. The KV cache grows linearly with tokens (**2.62 MB per token** for the 80-layer, 64-KV-head model used here, so **335.5 GB** for 128,000 tokens), and attention arithmetic grows with the square of the length.
- **Ring Attention** (Liu et al., 2023) cuts the sequence into one block per GPU. Each GPU keeps its **query block** and passes **key/value blocks round a ring**, computing while the next block arrives. The sequence can be **as many times longer as there are devices**, with exact attention.
- The transfer hides behind the compute when a block holds at least **F ÷ B tokens** (compute rate over link bandwidth): about **1,000** on NVLink and about **25,000** on InfiniBand for an A100.
- **KV-cache quantisation** stores keys and values in **FP8, INT8 or INT4**: half or a quarter of the bytes, so **2× or 4× the tokens** in the same memory. KIVI quantises **keys per channel** and **values per token**; KVQuant reports **under 0.1 perplexity loss at 3 bits**. Always measure on your own task.
- **Chunked prefill** (Sarathi) slices a long prompt into pieces mixed with other users' decode steps, so one huge prompt does not freeze every stream. **Prefill-decode disaggregation** goes further and gives each phase its own GPUs.
- The techniques **stack**: context parallelism divides the cache across GPUs, quantisation shrinks each share, and RoPE scaling decides whether the model can use the extra length at all.

## The idea in plain English

Picture a 1,000-page report that a team of four editors must cross-check, page against page. One editor cannot hold all the pages on her desk. So each editor takes 250 pages as her own and keeps them for the whole job. To compare her pages with everyone else's, a courier carries a stack of pages round the table: each editor checks her own pages against the stack in front of her, then passes it to her neighbour and receives the next. After four rounds every page has been checked against every other page, and nobody ever held more than their own pages plus one stack.

That is Ring Attention. Quantisation is a different fix for the same overflowing desk: photocopy every page at lower resolution so a stack takes a quarter of the space. Chunked prefill is how the office reads a very long report without making every other customer wait at the counter.

## Core concepts

### Context parallelism and Ring Attention across GPUs

**Context parallelism** (CP) splits one sequence across GPUs along the token dimension. Tensor parallelism splits each layer's matrices and pipeline parallelism splits the layers; neither helps when one sequence's activations or cache do not fit, because every GPU still holds all tokens of its share.

Attention is the hard part, because every query needs every earlier key and value. **Ring Attention** (Liu, Zaharia and Abbeel, 2023) solves it with blockwise attention. A query block's attention over a set of key/value blocks can be computed in any order, as long as each block's softmax statistics (running maximum and sum) are combined correctly. So GPU *i* keeps query block Q*i* and, in each round, computes against whichever KV block it holds, while sending that block to GPU *i+1* and receiving one from GPU *i−1*. After N rounds the result is **exact**, not an approximation.

Two other designs matter in practice. Llama 3 trained at 128K with an **all-gather** variant: each GPU gathers all keys and values, then attends for its own query chunk. The Llama 3 authors chose it because it handles document masks more simply, and because with grouped-query attention the keys and values are small next to the queries. vLLM exposes **decode context parallelism** (`-dcp`), which shards the KV cache along the token dimension; its prefill context parallelism, including a ring variant, is described as under active development (docs, November 2026).

### KV cache quantization (FP8, INT8, INT4) and token eviction

The cache stores 16-bit numbers by default. **Quantisation** stores each as an 8-bit float (**FP8**, in the E4M3 or E5M2 layout), an 8-bit integer (**INT8**) or a 4-bit integer (**INT4**), plus a small **scale** (and for asymmetric schemes a zero point) per group of values, and converts back when attention reads it. Bytes per token halve at 8 bits and quarter at 4. Unlike weight quantisation, the cache is written at run time, so its scales must be chosen on the fly or calibrated in advance. See [Quantization & Optimization](/ai-system-design/genai-system-design/quantization-optimization) for the weight side.

**Token eviction** is the other way to shrink the cache: throw tokens away. StreamingLLM keeps the first few tokens (the "attention sinks") and a recent window, and runs stably on streams of millions of tokens. It cannot answer a question about a token it has dropped. Quantisation keeps every token at lower precision; eviction keeps some tokens at full precision. Combine them only after measuring recall on your task.

### Chunked prefill and prefill-decode disaggregation

**Prefill** reads the whole prompt at once and is compute-bound; **decode** makes one token per step and is memory-bound. Mixed in one batch, a 128,000-token prefill makes that step last seconds, and every other user's next token waits.

**Chunked prefill** (Sarathi, Agrawal et al., 2023) cuts the prompt into chunks of a fixed token budget and builds each batch from one chunk plus as many decode steps as fit. The compute-bound chunk keeps the GPU busy; the decodes ride along cheaply. Sarathi reports up to 1.25× to 1.33× end-to-end throughput on a single GPU and up to 10× higher decode throughput on LLaMA-13B. In vLLM V1 it is on by default whenever possible, decodes are scheduled first, and `max_num_batched_tokens` is the budget: smaller values (the docs give 2,048 as an example) help inter-token latency, larger ones help time to first token. See [LLM Inference Engine](/ai-system-design/genai-system-design/llm-inference-engine).

**Prefill-decode disaggregation** runs the two phases on different GPUs and ships the KV cache between them. DistServe (Zhong et al., 2024) reports serving 7.4× more requests, or meeting a 12.6× tighter latency target, than colocated systems. The price is transfer: the cache you built has to cross a link.

### RoPE scaling and mid-training context extension

Memory and compute are only half of it. A model trained on 8,000-token windows has never seen position 100,000, and rotary position embeddings (RoPE) fail outside the trained range. See [Positional Encodings](/ai-system-design/genai-system-design/positional-encodings) for the mechanics.

**Position interpolation** (Chen et al., 2023) rescales positions so a longer sequence maps into the trained range, then fine-tunes briefly: the paper extends LLaMA to 32,768 tokens within 1,000 steps. **YaRN** (Peng et al., 2023) refines the rescaling and reports needing 10× fewer tokens and 2.5× fewer steps than earlier methods. Large models extend **gradually**: Llama 3 raised its window from 8K to 128K in six stages on about 800 billion tokens, moving on only when short-context scores had recovered and needle-in-a-haystack tests passed, and set its RoPE base frequency to 500,000.

A bigger window is not a better reader. See [Context Windows and In-Context Learning](/ai-system-design/genai-system-design/context-windows-and-in-context-learning) for lost-in-the-middle and RULER.

## Deep dive

### Overlap of KV block communication and compute

Ring Attention is free only if the send finishes before the compute does. Take a block of *c* tokens and hidden size *d*. Attention scores and their product with the values cost about 4·d·c² FLOPs; sending a key block and a value block in 16-bit costs 4·c·d bytes (Liu et al., §3). With compute rate F and link bandwidth B, the send hides behind the compute when 4dc²/F ≥ 4cd/B, that is **c ≥ F/B**. The block size is the only knob.

The paper's Table 2 puts the minimum block at about 1.0 thousand tokens for an A100 on NVLink (312 TFLOPS over 300 GB/s) and about 24.5 thousand over InfiniBand (12.5 GB/s). Compute grows with c² and traffic with c, so bigger blocks help. Each GPU also needs memory for six blocks' worth of activations (its query, the current key and value, the incoming key and value, and the output), independent of total length.

Three caveats. The count ignores the projections and the feed-forward layers, which add compute but no traffic. A causal mask means about half the block pairs have nothing to compute, so a naive ring leaves the first GPUs idle; Llama 3 balances this by giving each GPU two chunks from opposite ends of the sequence. And on slow links the minimum block can exceed what a GPU can hold, so keep context parallelism inside the fast domain (one NVLink node) where you can.

### Accuracy vs. compression ratio in KV quantization

Cutting bits is not the hard part; the hard part is outliers. A group of numbers is stored as integers between its minimum and maximum, so one huge value stretches the range and leaves everything else with few distinct levels. KIVI (Liu et al., 2024) measured real caches and found that **keys have a few fixed channels with very large magnitudes**, while **values have no such pattern**.

**How to read it.** Each grid is a cache with 8 tokens as rows and 8 channels as columns; stronger colour means larger (shape only, not measured). Grouping keys by token lets the two strong columns set every row's range (red). Grouping by channel gives each column its own scale (green), so a big channel only stretches its own range. Values are grouped by token: attention output is a weighted sum of value rows, attention is sparse, so an error confined to one token barely touches the important ones.

KIVI uses group size 32 and keeps the newest tokens in full precision (a residual of 128 in its experiments), because a per-channel group needs enough tokens to form. At 2 bits it reports about 2.6× less peak memory including weights, up to 4× larger batches and 2.35× to 3.47× higher throughput on Llama, Falcon and Mistral models, with quality close to 16-bit. KVQuant (Hooper et al., 2024) adds more: keys quantised before RoPE, non-uniform levels per layer and per-vector outliers kept apart. It reports under 0.1 perplexity increase at 3 bits on Wikitext-2 and C4.

In vLLM, FP8 is a flag: `--kv-cache-dtype fp8` (E4M3 or E5M2 layouts). With no calibration every scale is 1.0; the docs recommend calibrating with llm-compressor, which also unlocks per-attention-head scales on the FlashAttention backend, and note that sliding-window layers are more sensitive, so a skip-layers option leaves them in the native type (vLLM docs, November 2026).

**What the papers do not promise.** Perplexity is a gentle test. Retrieval of one exact fact from 100,000 tokens, long arithmetic and code are harder. Run your own long-context evaluation before and after.

### Latency and VRAM budgets at 128k to 1M tokens

Two budgets decide the design. **Memory:** cache bytes = tokens × bytes per token. For the 80-layer, 64-KV-head model at 16 bits, 128,000 tokens take 335.5 GB and 1,000,000 tokens take 2,621 GB, about 33 GPUs of 80 GB for the cache alone; at 4 bits, 655 GB. **Time:** every decode step reads the cache, so step time is at least bytes read ÷ bandwidth. Prefill is quadratic: 4·d·s² per layer is about 5.4 × 10¹⁴ FLOPs at 128,000 tokens, or about 34 s of attention alone on four A100s at peak (illustrative, no causal saving).

Real models use fewer KV heads. Llama 3 70B has 80 layers and 8 KV heads of 128 dims, so 327,680 bytes per token, about 8× less than the 64-head figure; its 128,000-token cache is 41.9 GB. [Efficient Attention](/ai-system-design/genai-system-design/efficient-attention) and [Multi-Head Latent Attention](/ai-system-design/genai-system-design/multi-head-latent-attention) shrink the cache by design, and quantisation multiplies on top. Prefix reuse (see [Prompt Caching](/ai-system-design/genai-system-design/prompt-caching)) removes repeated prefill.

### Worked example: Brightpost reviews a year of orders

A wholesale customer asks Brightpost's assistant to review a year of order and support history: **128,000 tokens**, against the usual 2,200. Brightpost's decode budget is 4.4 ms per token (1,500 ms full answer, 400 ms first token, 250 tokens). The figure uses the model from the KV cache page and an illustrative 200 GB cache budget.

**Putting the pieces together.** On four GPUs with context parallelism, each holds a 32,000-token block, 83.9 GB of cache at 16 bits and 21.0 GB at 4 bits. Each decode step reads that share: at an illustrative 3 TB/s, 83.9 GB ÷ 3,000 GB/s = 28 ms per token at 16 bits against 21.0 GB ÷ 3,000 = 7 ms at 4 bits. Neither meets 4.4 ms, which is why Brightpost sends such requests to a separate long-context pool with its own latency target. Chunked prefill with a budget of 8,192 tokens cuts the prompt into ⌈128,000 ÷ 8,192⌉ = 16 chunks, so ordinary users' streams continue between chunks. If prefill and decode ran on separate GPUs, the 2,200-token ordinary prompt of an 8B model (128 KiB per token) would ship 275 MiB, about 6 ms on an illustrative 50 GB/s link.

<Callout tone="red" title="What breaks">
  A cache in 4-bit with a per-token scheme for keys can pass perplexity and still lose the one order number the customer asked about. Another failure: one 128,000-token request admitted to a pool sized for 2,200-token ones empties the free blocks and forces preemption for everyone. Cap prompt length per pool, and evaluate recall at the longest length you will serve.
</Callout>

## Trade-offs

| Choice | Pros | Cons | When to use |
| --- | --- | --- | --- |
| Ring Attention / context parallelism | Exact attention; sequence length scales with GPUs; per-GPU memory independent of length | Needs fast links and big blocks; load imbalance under causal masks; more engineering | One sequence is too big for one GPU's memory or prefill time |
| All-gather context parallelism | Simpler, handles document masks, cheap with grouped-query attention | Each GPU briefly holds all keys and values | Moderate lengths, GQA models, training at 128K |
| FP8 / INT8 KV cache | About 2× the tokens, small accuracy risk, a flag in vLLM | Needs calibration for best accuracy; sliding-window layers sensitive | Default first step when memory-bound |
| INT4 or lower KV cache (KIVI, KVQuant) | 4× or more the tokens; more batch | Custom kernels, outlier handling, larger accuracy risk | Very long contexts after you measured recall |
| Token eviction | Fixed memory for endless streams | Dropped tokens are gone | Chat streams where old detail does not matter |
| Chunked prefill | Stable streams during long prompts | Slightly later first token for the long prompt | Any mixed-length workload |
| Prefill-decode disaggregation | Each phase tuned to its own latency target | KV transfer cost and a second pool to run | Strict first-token and per-token targets at scale |

## Real-world examples

- **Ring Attention** (Liu et al., 2023) reports sequences up to device count times longer than earlier memory-efficient transformers, and over 1 million tokens for a 7B model on 32 A100 GPUs in training.
- **Llama 3** (Meta, 2024) trained to a 128K window in six stages on about 800 billion tokens and used all-gather context parallelism; the 70B model has 80 layers and 8 KV heads.
- **KIVI** and **KVQuant** report 2-bit and 3-bit caches with small quality loss; KVQuant reports 1 million tokens of LLaMA-7B context on one A100-80GB and 10 million on eight GPUs.
- **vLLM** documents FP8 KV cache (`--kv-cache-dtype fp8`), decode context parallelism and chunked prefill by default in V1 (docs checked 15 November 2026).
- **Sarathi** and **DistServe** are the research behind chunked prefill and disaggregation: up to 4.25× decode throughput for LLaMA-33B, and 7.4× more requests served, respectively.

## Common pitfalls

- Sizing GPUs from the weights and forgetting that the cache at 128,000 tokens can be larger than the model.
- Assuming a bigger window means better recall: check lost-in-the-middle and RULER-style results.
- Reading a perplexity result as proof that retrieval still works at 4 bits.
- Using Ring Attention across slow links with small blocks, so the transfer shows up as idle GPUs.
- Leaving the FP8 scale at 1.0 and never calibrating, then blaming the format.
- Admitting long and short prompts to the same pool with no cap on prompt tokens per step.

## How to answer in an interview

1. Start with the bytes: 2 × layers × KV heads × head size × bytes per value, per token, then times the length and the batch.
2. Say which resource breaks first (cache memory, then prefill time) and name the fixes: shrink the cache, split the sequence, schedule the prefill.
3. Explain Ring Attention in one breath: queries stay, KV blocks rotate, compute overlaps the send, the answer is exact, and the block must be at least F ÷ B tokens.
4. Explain KIVI's asymmetry (keys per channel because of outlier channels, values per token) and why you would still run your own recall test.
5. Close with operations: separate long-context pool, chunked prefill budget, prompt-length caps and metrics (free blocks, inter-token latency, recall at max length).

**What interviewers listen for:** a bytes-per-token number, the overlap condition, the reason keys and values are quantised along different axes, and the difference between compressing the cache and splitting it.

**Red flags:** treating context length as free, claiming Ring Attention is an approximation, or calling quantisation lossless without a test.
