title: Long-Term Vector Memory
description: Persist and recall unstructured knowledge with embeddings, vector indexes, and hybrid retrieval patterns that scale while staying filterable and observable.
---

Long-term vector memory stores what an agent learned about a user as vectors, so that a new message can find the past facts that matter to it.

- Interviewers use it to test whether you can run retrieval per user: keep one customer's memories away from another's, decide what to embed, avoid duplicates, forget what is stale and delete on request.
- [Agent Memory](/ai-system-design/genai-system-design/agent-memory) covers the policies (what to remember, how to score it, how to resolve conflicts); this page is about the storage underneath.

## Overview

- Each memory is a short fact, its **embedding** (a vector of numbers that places similar meanings close together) and **metadata**: the user, the type, the dates, the source and the embedding model.
- Recall embeds the new message with the **same model**, filters to **this user only**, and returns the nearest few memories with their similarity scores.
- The user filter is a security boundary. Use a **namespace per user or tenant**, or a filter that runs **inside** the search. Filtering after the search returns too few results and invites leaks.
- **Embed the extracted fact**, not the raw conversation. One fact per memory makes updates, dedupe and deletion possible.
- **Dedupe on write**: search for near neighbours before adding, and let a rule or a model decide add, update or drop.
- **Decay**: a recency term such as 0.995 per hour fades memories that are never used. Each recall resets it.
- **Deletion** must remove the record, the vector and every copy (summaries, caches, backups), and be provable.

## Mental model

- A shop assistant who knows you keeps a card file.
- Each card holds one note: "refund approved for the cracked kettle", "prefers email".
- When you walk in and say "has my refund gone through?", the assistant pulls your cards, not everyone's, and reads the few that fit what you said.

- Vector memory is that card file for an agent.
- The "fits what you said" part is similarity between vectors.
- The "your cards, not everyone's" part is a filter.
- Most of the engineering is in the filter, the cards and the clear-out, not in the similarity search.

## Core concepts

- Every figure on this page follows Brightpost, the shop from [Agent Architectures](/ai-system-design/genai-system-design/agent-architectures).
- On 12 Nov a support agent approved a £42 refund for customer 1847's cracked kettle, order 4471.
- On 19 Nov the customer writes again: "Has my kettle refund gone through? Text me from now on, not email."

1. **Memory record.** One fact in plain text ("4471: £42 refund approved"), its vector, and metadata: `customer_id`, type (semantic for facts and preferences, episodic for events), source, dates, status and the embedding model's name and version.
2. **Embedding.** An embedding model turns text into a fixed-length vector; Brightpost's has 1,536 numbers. Similar meanings land close together, measured by cosine similarity. See [Embeddings & Representation Space](/ai-system-design/genai-system-design/embeddings-and-representation-space).
3. **Namespace or filter.** The boundary that keeps a search inside one user's memories: a separate partition per user or tenant, or a metadata filter applied during the search.
4. **Top-k recall.** The search returns the k nearest memories (here k = 3), with scores. A scorer may then re-rank them by recency and importance before they enter the prompt.
5. **Write path.** After a conversation, a memory writer extracts facts, compares each with its nearest stored memories and adds, updates or drops it.
6. **Lifecycle.** Memories are superseded, decay, get archived and get deleted. Each state change must reach the vector index as well as the record.

### Where the vectors live

- Managed services such as Pinecone, open-source engines such as Qdrant and Weaviate, and Postgres with the pgvector extension can all hold memory vectors.
- They differ in operational model, how expressive their filters are, how they replicate and how cost grows with size. The placement choices are the same for each:

- **Beside the operational data.** pgvector keeps the memory row, its vector and the customer's account in one database, one transaction and one backup. A delete removes the row and its vector together.
- **In a dedicated search tier.** A vector database scales search on its own and offers namespaces, but every write and delete now spans two systems.
- **Replicated per region.** For low-latency recall near the user, and to keep personal data in its region. Deletions must reach every replica.

- Per-user memory is small. At 1,536 numbers × 4 bytes = 6,144 bytes per vector, a customer with 200 memories (illustrative) holds 200 × 6,144 = 1.2 MB of raw vectors.
- The scale problem is the number of users, not the size of any one search.

### Indexes: HNSW and IVF

- An approximate nearest-neighbour (ANN) index finds close vectors without comparing against all of them.
- The indexes themselves are covered on [Vector Databases](/ai-system-design/genai-system-design/vector-databases#hnsw-search-layer-by-layer); what matters for memory is:

- **HNSW** (a layered graph of neighbours) gives strong query performance and takes inserts one at a time, at the cost of more memory and sometimes slower index builds. pgvector's documentation says it has a better speed-recall trade-off than IVFFlat, but slower builds and more memory.
- **IVF** partitions the space into clusters and searches only the nearest few. It helps very large corpora when its parameters are tuned to the data, builds faster and uses less memory, but needs data to train its clusters.
- **No index at all** is often right for one user's memories. Filter to the customer's 200 rows first, then compare against all of them: 200 × 1,536 = 307,200 multiply-adds is exact and fast.

### Hybrid search and reranking

- Dense similarity blurs rare strings: an order number, a SKU, an exact name.
- **Hybrid search** adds lexical signals such as BM25, either by running dense and sparse retrieval in parallel and fusing the scores, or by using lexical prefiltering to shrink the candidate set.
- "Order 4471" matches the refund memory exactly, even if its embedding sits near every other refund.
- For agents, recall often adds a **reranking** step, a cross-encoder or a small LLM that reorders the top k before they enter the prompt, trading compute for precision.
- Details are on [Hybrid Search & Re-ranking](/ai-system-design/genai-system-design/hybrid-search-and-reranking).

## Technical mechanics

### Namespaces and filters per user

- There are three ways to keep a search inside one customer's memories.
- [Access Control & Multi-Tenancy in RAG](/ai-system-design/genai-system-design/rag-access-control-multi-tenancy#tenant-isolation-per-tenant-indexes-versus-a-shared-index) compares them for documents; for memory the trade-offs shift because each user's slice is tiny.

- **A namespace per user or tenant.** Pinecone recommends one namespace per tenant on a serverless index. Each namespace is stored separately, so a query cannot reach another tenant's data, and deleting a tenant is one `delete_namespace` call. Cost follows namespace size: Pinecone's guide gives 1 read unit per GB searched, so filtering inside one 100 GB namespace costs 100 units where a 1 GB tenant namespace costs 1.
- **One collection with a tenant field.** Qdrant recommends one collection for many small tenants, with a `group_id` payload filter on every query. Marking that field's index `is_tenant: true` stores each tenant's vectors together, so one tenant's search reads them in one pass.
- **A table with a `customer_id` column.** In pgvector, a `WHERE customer_id = '1847'` with a B-tree index lets Postgres fetch the customer's rows and compare exactly, which suits a few hundred memories.

<Callout tone="red" title="What breaks">
  Post-filtering with a selective filter. With an approximate index, pgvector applies `WHERE` after the index scan. Its
  documentation's example: at 10 % selectivity and the default `hnsw.ef_search` of 40, only about 4 rows match. One
  customer among 100,000 is a selectivity of 0.001 %, so 40 × 0.00001 = 0.0004 rows: recall returns nothing and the
  agent "forgets" everyone. Fix: filter inside the search (a namespace, a filtered index, or pgvector's iterative index
  scans, added in 0.8.0), or skip the ANN index and search the customer's rows exactly.
</Callout>

- Two rules apply whichever you pick. The filter value comes from the authenticated session, never from the model or the request body; a tool that takes `customer_id` as an argument lets a tricked model read anyone's memories.
- And memory reads go through one retrieval service that adds the filter, so no code path can forget it.

### What to embed

What you embed decides what can be found, merged and deleted.

- **Embed the extracted fact, not the transcript.** "prefers email" is 2 words and one fact. A 40-turn chat embedded whole becomes one vector that is near everything and precisely about nothing, and you cannot delete one fact from it.
- **One fact per record.** "Prefers email; kettle refunded" as one memory cannot be half-updated when the customer switches to texts.
- **Write the fact so it stands alone.** "4471: £42 refund approved" still makes sense next week. "Yes, that one was approved" does not.
- **Keep exact fields as metadata, not only text.** The order number, dates and type go in fields you can filter and sort on. Similarity should never be the only way to find "order 4471".
- **Record the embedding model and version.** Vectors from two models cannot be compared. When the model changes, re-embed every memory from its stored text before switching reads; see [Embedding Models & Selection](/ai-system-design/genai-system-design/embedding-models-and-selection#changing-embedding-models-and-re-indexing).

### Dedupe on write

- Without a check, a customer who mentions their refund in three chats gets three refund memories, and all three fill the top 3.
- The write path searches the customer's memories for the nearest neighbours of each new fact, then decides: add, update (supersede the old one), or drop.
- The decision and its examples ("prefers text" replaces "prefers email"; a repeated refund is dropped) are on [Agent Memory: the write policy](/ai-system-design/genai-system-design/agent-memory#the-write-policy).

- The vector store's job is the first half: the neighbour search must use the same customer filter and include superseded memories, so the writer can see what was replaced.
- A cosine threshold alone should not decide. "Chased refund 4471" and "4471: £42 refund approved" sit close together and are two different events.

### Decay and forgetting

- Old memories should not compete equally with fresh ones.
- Generative Agents (Park et al., 2023) gives every memory a recency term, 0.995 raised to the hours since it was last retrieved, and adds it to importance and relevance.
- The full score is worked through on [Agent Memory](/ai-system-design/genai-system-design/agent-memory#which-memories-to-recall); here is the decay alone, for three of customer 1847's memories.

    The refund is recalled on 19 Nov, so its recency goes back to 1 and a week later it is at 0.43 again. Gift wrap is

  </StepCard>
</StepCards>

**The numbers:**

- 0.995^24 = 0.89, about 11 % lost a day. 0.995^168 = 0.43 and 0.995^720 = 0.03.
- Half-life: ln 0.5 / ln 0.995 = 138 hours, about 5.8 days.
- Gift wrap on 26 Nov: 0.995^(48 + 168) = 0.995^216 = 0.34.

- Decay changes the ranking; it does not delete anything.
- Forgetting is a separate, explicit policy, and it usually depends on type and importance: archive episodic memories unused for 90 days and rated below 4, keep a stated preference until the customer changes it (both thresholds illustrative).
- Archiving moves the record out of the searchable index, so it stops costing search time and stops being recalled.

<Callout tone="red" title="What breaks">
  Updating `last_used` on every candidate the search returns, not on the memories that reached the prompt. Every memory
  that is often near a query stays fresh, used or not, and decay stops working. Reset the clock only for memories the
  agent actually received.
</Callout>

### Deletion and privacy

Memory is personal data. When customer 1847 asks to be forgotten, GDPR Article 17 requires erasure "without undue delay" (where it applies), and the customer will not accept "we hid it".

- **Delete the vector as well as the row.** A record marked deleted whose vector stays in the index can still be recalled by any path that skips the status check.
- **Expect index deletes to be lazy.** Graph indexes often mark deleted points and clean them up later. pgvector notes that dead rows can reduce the number of results an HNSW query returns and that vacuuming HNSW indexes can take a while. Plan the vacuum or compaction, and track when the data is gone, not only when the call returned.
- **Find every copy.** Conversation summaries, semantic caches, evaluation datasets, logs with memory text and backups all hold copies. Record where each memory was copied, or keep copies short-lived.
- **Make per-user deletion cheap by design.** A namespace per user or tenant turns "delete everything about 1847" into one call. In a shared index it is a delete by filter, which must be verified.
- **Let users see and edit.** A memory page that lists what is stored, with delete buttons, catches wrong memories before they cause harm.
- **Do not store what you should not.** Run the writer's output through the same PII rules as any other store; never embed card numbers or passwords.

<Callout tone="red" title="What breaks">
  Deleting the source but keeping derived memories. The customer deletes a chat, but "prefers email" and the refund
  memory were extracted from it and live on. Link each memory to its source chat, and delete or re-derive memories when
  their source is deleted.
</Callout>

### Watching recall quality

- Without measurement, vector memory becomes a slow drift problem: retrieved memories stay plausible but are wrong or out of date.
- Log the recalled memory ids and their scores with every answer.
- Sample conversations for human labels ("was the right memory recalled? was a stale one used?") and track proxy metrics: the share of recalls with no memory above the floor, how often a superseded memory is returned, and how often users correct the agent.
- Re-run a fixed set of multi-session test cases after every change to the embedding model, the filter or the scorer.

### Worked example: the customer returns

This follows the [architecture figure](#architecture) on 19 Nov, when customer 1847 writes "Has my kettle refund gone through? Text me from now on, not email."

| Step | What happens                                                                               | Result                                                                        |
| ---- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| 1    | The chat service takes `customer_id` 1847 from the signed-in session, not from the message | Filter value fixed before any model call                                      |
| 2    | The message is embedded with `brightpost-embed-v2`, the model named on the stored records  | 1,536 numbers                                                                 |
| 3    | The search runs with `customer_id = 1847` and `status = active` inside it                  | 2210's memory (0.86) never seen                                               |
| 4    | The 3 nearest return with cosines                                                          | refund 0.82, cracked kettle 0.74, prefers email 0.61; gift wrap 0.20 left out |
| 5    | The scorer re-ranks by recency, importance and relevance; the memories enter the prompt    | About 3 × 20 = 60 tokens (illustrative)                                       |
| 6    | The recalled memories' `last_used` is set to 19 Nov                                        | Their recency resets to 1                                                     |
| 7    | After the reply, the writer adds "prefers text" and supersedes "prefers email"             | Next visit recalls "prefers text"                                             |

Step 3 in pgvector, with `<=>` as cosine distance (1 − distance = similarity):

```sql
SELECT id, text, 1 - (embedding <=> $1) AS cosine
FROM memories
WHERE customer_id = '1847' AND status = 'active'
ORDER BY embedding <=> $1
LIMIT 3;
```

Three things to take from it:

- **The filter came first.** The nearest memory in the whole store belonged to someone else. Only the filter kept it out.
- **The scores are kept.** A floor such as "drop anything below 0.5 cosine" (illustrative) stops recall from padding the prompt with gift wrap when nothing relevant exists.
- **Reads write.** Updating `last_used` in step 6 is a write on every recall, so the read path needs write access to the memory store, and that write should not slow the reply.

## Trade-offs

| Decision                                           | Option A                                    | Option B                                        | Guidance                                                                  |
| -------------------------------------------------- | ------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------- |
| Vectors beside OLTP data vs a search tier          | One transaction, one delete, one backup     | Independent scaling, namespaces                 | pgvector until search load or size needs its own tier                     |
| Namespace per tenant vs shared index with a filter | Physical isolation, one-call deletion       | Fewer partitions, cross-tenant queries          | Namespace per tenant; a mandatory filter per user inside it               |
| HNSW vs IVF                                        | Fast queries, incremental inserts, more RAM | Faster builds, less memory, needs training data | HNSW for live memory writes; exact search for one user's few hundred rows |
| Dense only vs hybrid                               | Simpler, one index                          | Catches order numbers and names                 | Hybrid when memories hold identifiers                                     |
| Rerank vs top-k as is                              | Better precision                            | Lower latency and cost                          | Rerank when recall feeds actions, not only replies                        |
| Decay vs no decay                                  | Fresh memories win                          | Old facts stay as strong                        | Decay episodes; pin stated preferences until changed                      |

## Production systems

- Generative Agents (Park et al., 2023) ranks memories by recency (0.995 per hour since last retrieval), importance and relevance, summed with equal weights.
- Mem0 (Chhikara et al., 2025) compares each new fact with the most similar stored memories and has a model choose ADD, UPDATE, DELETE or NOOP.
- LangGraph stores long-term memories as JSON documents under a namespace tuple such as `(user_id, context)` and a key, with optional semantic search configured by an embedding function and its dimensions (docs checked November 2026). Its docs contrast writing memories "in the hot path" against writing them in the background.
- Pinecone's multitenancy guide recommends a namespace per tenant and describes deleting one as "almost instant" (checked November 2026).
- pgvector 0.8.0 added iterative index scans (`hnsw.iterative_scan`), which keep scanning until enough rows pass the filter; the current release is 0.8.7 as of November 2026.

## Failure modes & pitfalls

- Embedding whole transcripts instead of extracted facts.
- Filtering after the search, or taking the user id from the model.
- Mixing vectors from two embedding models in one index.
- Writing every mention as a new memory, so duplicates fill the top k.
- Updating `last_used` for every candidate, which turns decay off.
- Deleting the record but not the vector, the summaries or the backups.
- Returning the top k with no similarity floor, so irrelevant memories pad the prompt.

## Interview framework

1. Define the record: fact text, vector, owner, type, dates, source, status, model version.
2. Draw the write path (extract, embed, dedupe, store) and the read path (embed, filter, search, re-rank, inject).
3. Make the user boundary explicit: namespace or in-search filter, value from the session.
4. Pick an index for the scale, and say why per-user search can be exact.
5. Cover lifecycle: supersede, decay, archive, delete everywhere, re-embed on model change.

**What interviewers listen for:** isolation by construction, and a deletion story that covers derived copies.

**Red flags:** "put the chat history in a vector DB", or a filter that runs after the search.
