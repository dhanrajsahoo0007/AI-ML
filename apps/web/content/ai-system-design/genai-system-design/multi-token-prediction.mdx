Almost every LLM is trained to guess one token ahead. Multi-token prediction (MTP) asks it to guess several, and DeepSeek-V3 made it part of a frontier training recipe. Interviewers ask about it because it connects three topics they care about: the pre-training objective, model architecture, and speculative decoding at serving time.

## TL;DR

- **Next-token prediction** trains each position on one target, token $t + 1$. **MTP** adds extra outputs so each position is also trained on $t + 2, t + 3, \dots, t + n$.
- **Meta's design** (Gloeckle et al., 2024) puts **n independent heads on a shared trunk**, usually $n = 4$. Its 13B code model solved **12% more HumanEval** and **17% more MBPP** problems than a matched next-token model, but MTP **hurt small models** (0.3B to 0.6B parameters).
- **DeepSeek-V3** chains **sequential MTP modules** that also read the true next token, so the **causal chain is kept**. It uses depth **D = 1**, a loss weight of **0.3 then 0.1**, and the module adds **14B parameters** to the 671B main model.
- At inference the extra heads can be **thrown away**, or used as a **built-in draft model** for speculative decoding: **3.0× faster** on code for Meta's 7B model, **1.8× tokens per second** for DeepSeek-V3 with an **85–90%** acceptance rate for the second token.
- MTP costs **extra parameters, extra logits memory and some training time**, and it pays off mainly at **scale and on structured text such as code**.

## The idea in plain English

Picture a chess student who, after every move, writes down only the opponent's next reply. Now picture a second student who writes down the next three moves each time. The second student cannot score every guess, but the exercise forces them to think about where the game is heading, not only about the move in front of them. MTP is the second student. It also brings a bonus at game time: if the student's three-move guesses are usually right, the coach can check three moves at a glance instead of waiting for them one by one. That check is speculative decoding.

## Core concepts

1. **Beyond next-token prediction.** A standard language model minimizes the cross-entropy of the next token at every position:

   $$
   L_1 = -\sum_t \log P_\theta(x_{t+1} \mid x_{1:t})
   $$

   MTP adds terms for tokens further ahead. With $n$ outputs, position $t$ is trained on $x_{t+1}$ through $x_{t+n}$, so the same text yields up to $n$ times as many training signals. The model still reads only the tokens up to $t$.

2. **Parallel prediction heads and a shared trunk.** In Gloeckle et al. (2024) a shared Transformer trunk turns the context into a vector $z_t$ for position $t$. On top sit $n$ independent heads, each one Transformer layer, and all heads share one unembedding matrix (the final Linear layer that maps a vector to vocabulary logits). The loss sums the heads' cross-entropies:

   $$
   L_n = -\sum_t \sum_{i=1}^{n} \log P_\theta(x_{t+i} \mid z_t)
   $$

   To keep the parameter count equal to the baseline, the $n - 1$ extra head layers are taken from the trunk. Because every head must work from the same $z_t$, the trunk is pushed to encode information about several future tokens, not only the next one.

3. **Head 1 is the ordinary model.** The first head predicts $t + 1$, exactly like a normal language model. At inference you can keep only that head and discard the rest, so an MTP-trained model can be served as a plain next-token model with no change to decoding.

4. **Auxiliary training signal.** DeepSeek-V3 treats MTP as an extra loss on top of the main one: $L = L_{\text{main}} + \lambda L_{\text{MTP}}$. The weight $\lambda$ was 0.3 for the first 10T training tokens and 0.1 for the remaining 4.8T. The extra signal is said to densify training and to help the model "pre-plan" its representations for future tokens.

5. **Long-horizon planning and choice points.** Gloeckle et al. argue that some tokens matter more than others. A "choice point" (which variable to return, which branch of an argument to take) shapes many tokens after it. A loss that also scores $t + 2, t + 3, \dots$ rewards getting those decisions right, because a wrong choice is paid for several times. In small synthetic tests, MTP also helped models form induction heads (the copy-a-pattern circuit behind in-context learning, see [Context Windows & In-Context Learning](/ai-system-design/genai-system-design/context-windows-and-in-context-learning)) at around 30M parameters; the advantage disappeared by about 100M.

6. **Sequential MTP modules.** DeepSeek-V3 replaces independent heads with $D$ modules in a chain. Module $k$ combines the previous depth's hidden state with the embedding of the true token $t + k$, normalizes both with RMSNorm, concatenates them, projects them back to width $d$ with a matrix $M_k$, and runs one Transformer block:

   $$
   h'^{\,k}_t = M_k\big[\operatorname{RMSNorm}(h^{k-1}_t);\ \operatorname{RMSNorm}(\operatorname{Emb}(x_{t+k}))\big]
   $$

   The embedding layer and output head are shared with the main model. Because module $k$ sees token $t + k$, its prediction of $t + k + 1$ is conditioned on everything before it: the causal chain holds.

7. **Turning MTP heads into built-in speculative drafters.** Speculative decoding (Leviathan et al., 2023; Chen et al., 2023) lets a cheap draft model propose several tokens, then the large model checks them all in one forward pass and keeps the longest correct prefix. With greedy decoding the output is identical to normal decoding. MTP heads are a free draft model that lives inside the same network, so no second model has to be trained, stored or scheduled. This is called self-speculative decoding; Gloeckle et al. use blockwise parallel decoding (Stern et al., 2018).

8. **Related drafting heads: Medusa and EAGLE.** Medusa (Cai et al., 2024) bolts extra decoding heads onto an already trained model, each a single feed-forward layer with a residual connection, and verifies many candidate continuations at once with tree attention. EAGLE (Li et al., 2024) drafts at the feature level, autoregressing on the second-to-top layer's hidden states. Both are added after pre-training; MTP builds the heads in from the start, and the training objective itself changes.

## Architecture

The two published designs differ in one choice: whether each extra prediction can see the tokens before it.

<AnimatedDiagram
  spec="animated/llm/mtp-architectures"
  caption="Meta's heads all read the same trunk output and guess t + 1 … t + 4 independently; DeepSeek-V3's module feeds the main model's hidden state together with the true next token into one more Transformer block, so its guess for t + 2 knows t + 1."
/>

1. **Parallel heads (left).** Tokens pass through the embedding and the shared trunk. The trunk's output $z_t$ goes to $n = 4$ heads at once, each one Transformer layer.
2. All heads use the same unembedding matrix and softmax to produce distributions for $t + 1$ to $t + 4$. Each prediction depends only on $z_t$.
3. **Sequential module (right).** The DeepSeek-V3 main model runs as usual and predicts $t + 1$ with its output head.
4. Its last hidden state $h^0_t$ is normalized and concatenated with the normalized embedding of the true token $t + 1$, projected by $M_1$, and passed through one more Transformer block.
5. The shared output head turns the result into a distribution for $t + 2$. During training both losses are added; at inference the module is dropped or used as a drafter.

## Deep dive

### Sequential vs. independent MTP head designs

Independent heads guess every future token from the same vector. If head 2 must predict "noon" without knowing whether head 1 said "Friday" or "Monday", it can only hedge. That makes the drafts less consistent with each other as $n$ grows. DeepSeek's sequential modules fix this by feeding in the real token $t + 1$ during training, at the cost of running the modules one after another. In practice DeepSeek-V3 uses only one module ($D = 1$), so the chain is one link long.

The choice of $n$ is task-dependent. In Meta's 7B ablation on 200B tokens of code, $n = 4$ scored best on HumanEval and MBPP, while $n = 6$ was best on APPS/Intro. A byte-level 7B model trained with $n = 8$ solved 67% more MBPP problems and 20% more HumanEval problems (pass@1) than next-byte prediction, because bytes carry less information each and benefit more from looking ahead. On natural-language multiple-choice benchmarks, $n = 2$ matched the baseline and $n = 4$ was slightly worse.

### Training memory overhead and vocabulary projection cost

The expensive part of an extra head is not its Transformer layer but its logits. Each head produces one score per vocabulary token at every position. For a 4,096-token sequence and a vocabulary of about 128,000 tokens, one head's logits in 32-bit floats take

$$
4{,}096 \times 128{,}000 \times 4 \text{ bytes} \approx 2.1 \text{ GB}
$$

per sequence, before gradients. Four heads at once would need about 8.4 GB. Gloeckle et al. avoid this by running the forward and backward pass of each head in turn, accumulating gradients at the trunk, which lowers peak memory from $O(nV + d)$ to $O(V + d)$ without slowing training down. Their measured training time was 1.07× to 1.22× the baseline for $n = 4$, largest for the smallest model, and they attribute it to their sharding setup rather than to MTP itself.

Parameters are a smaller cost. Meta's heads are taken from the trunk, so the total stays equal. DeepSeek-V3's one module adds 14B parameters to 671B, about 2%, and DeepSeek places it on the same pipeline stage as the embedding and output head so those weights are physically shared rather than copied.

### Acceptance rates when paired with speculative verification

The speedup from drafting depends on the acceptance rate $\alpha$, the chance that a draft token matches what the main model would produce. If each of $k$ drafts is accepted with probability $\alpha$ until the first miss, the expected number of tokens per verification pass is

$$
\frac{1 - \alpha^{k+1}}{1 - \alpha}
$$

(Leviathan et al., 2023). With $k = 3$, $\alpha = 0.8$ gives about 2.95 tokens per pass and $\alpha = 0.6$ gives about 2.18. With DeepSeek-V3's single module, $k = 1$ and $\alpha$ of 0.85 to 0.90 give 1.85 to 1.90 tokens per pass; DeepSeek reports 1.8× tokens per second, the gap being the cost of running the module and the verification. Meta reports 2.5 of 3 drafts accepted on average on code, and 3.0× faster decoding on code and 2.7× on text.

Real acceptance rates are not constant. They fall for tokens further ahead (Xiaomi's MiMo-7B reports about 90% for its first MTP layer and above 75% for its third on AIME 2024 problems), and they are higher for code and other predictable text than for open-ended prose. Higher sampling temperatures also lower acceptance, because the main model's own choice becomes harder to guess. See [Speculative Decoding](/ai-system-design/genai-system-design/speculative-decoding) for the verification rule with sampling and for tree-shaped drafts.

## Trade-offs

| Choice | Pros | Cons | When to use |
| --- | --- | --- | --- |
| Next-token only | Simplest; no extra memory or parameters | No built-in drafter; one signal per position | Small models; tight training budgets |
| Parallel heads (Meta) | Same parameter count; heads draft up to n tokens in one pass | Heads guess independently; hurts small models | Large code-heavy models; self-speculative decoding |
| Sequential modules (DeepSeek) | Keeps the causal chain; strong second-token acceptance | Extra parameters; modules run one after another | Frontier pre-training; deployed MTP drafting |
| Post-hoc heads (Medusa, EAGLE) | Works on any existing model; no re-pre-training | Separate training stage; drafts not shaped by pre-training | Speeding up a model you cannot retrain |
| Separate draft model | Draft can be tuned independently | Second model to train, store and schedule | Model families with a small sibling |

## Real-world examples

- **Meta's MTP code models (2024).** Models from 0.3B to 13B parameters; the 13B model solved 12% more HumanEval and 17% more MBPP problems than a next-token model, and the 7B $n = 4$ model decoded 3.0× faster on code with self-speculative decoding.
- **DeepSeek-V3 (December 2024).** One MTP module ($D = 1$), loss weight 0.3 then 0.1. In DeepSeek's ablation on a 228.7B-parameter MoE, adding MTP raised HumanEval from 44.5 to 53.7 and GSM8K from 72.3 to 74.0, while MMLU dipped from 67.5 to 66.6. Used as a drafter, the module's second token is accepted 85–90% of the time, for 1.8× tokens per second.
- **MiMo-7B (Xiaomi, 2025).** One MTP layer during pre-training (more layers gave no further gain), copied and fine-tuned into extra layers for speculative decoding at inference.
- **Medusa (2024).** Extra heads on a frozen Vicuna-7B gave about 2.18× speedup (Medusa-1); training heads and backbone together gave about 2.83× (Medusa-2).
- **EAGLE (2024).** Feature-level drafting gave a 2.7× to 3.5× latency speedup on LLaMA2-Chat 70B with the output distribution preserved.

## Common pitfalls

- Saying MTP generates several tokens per step at inference by default. Without a verification step, only head 1 is used.
- Assuming MTP helps every model. Meta's results were worse than the baseline at 0.3B and 0.6B parameters, and on some language benchmarks $n = 4$ regressed.
- Forgetting the logits cost: each head adds a full vocabulary projection per position, which dominates memory unless heads are run one at a time.
- Treating the acceptance rate as fixed. It drops for tokens further ahead, for creative text and at higher temperatures.
- Confusing MTP with non-autoregressive generation (see [Diffusion LLMs & Non-Autoregressive Generation](/ai-system-design/genai-system-design/diffusion-llms-and-non-autoregressive-generation)). MTP models stay autoregressive; the extra heads only add training signal and drafts.
- Quoting the speedup as tokens per pass. Draft and verification overheads mean wall-clock gains are lower, as DeepSeek's 1.85–1.90 expected tokens vs 1.8× measured shows.

## How to answer in an interview

1. Write the next-token loss, then show how MTP adds terms for $t + 2 \dots t + n$ at every position.
2. Draw the two designs: parallel heads on a shared trunk (Meta) and sequential modules that keep the causal chain (DeepSeek-V3).
3. Give the evidence: gains grow with scale and are largest on code; small models get worse.
4. Explain self-speculative decoding: heads draft, one pass verifies, the matching prefix is kept, output unchanged under greedy decoding; quote the acceptance math.
5. Close with costs: logits memory per head, extra parameters, training time, and acceptance that falls with depth and temperature.

**What interviewers listen for:** that head 1 is a normal language model, the difference between independent and sequential heads, concrete numbers (n = 4, D = 1, 85–90% acceptance, 1.8×), and the logits-memory trick.

**Red flags:** "MTP outputs four tokens per step so it is 4× faster", not knowing how drafts are verified, or claiming MTP always improves quality.

  <InterviewQuestion question="Compare Meta's parallel MTP heads with DeepSeek-V3's sequential MTP modules." category="Architecture" level="Mid">
    Meta puts n independent heads, each one Transformer layer, on a shared trunk, and every head predicts its future token from the same trunk output. The heads run in parallel but cannot see each other's guesses. DeepSeek-V3 chains modules: each one combines the previous depth's hidden state with the embedding of the true next token, then runs a Transformer block and the shared output head. That keeps the causal chain, so the prediction for t + 2 is conditioned on t + 1, at the cost of extra parameters and running the modules one after another. DeepSeek-V3 uses a single module.
  </InterviewQuestion>
  <InterviewQuestion question="How do MTP heads speed up inference without changing the output?" category="Architecture" level="Mid">
    The extra heads act as a built-in draft model. In one forward pass, head 1 gives the next token and the other heads guess the tokens after it. The next pass runs the model on all drafted tokens at once, and the next-token head at each position says what greedy decoding would have chosen. Drafts are kept up to the first mismatch, and the model's own token replaces the wrong one, so the text is identical to greedy decoding while several tokens can come out of one pass.
  </InterviewQuestion>
  <InterviewQuestion question="DeepSeek-V3 reports 85–90% acceptance for its second token. What speedup should you expect, and why is the measured number lower?" category="Scaling" level="Senior">
    With one drafted token accepted with probability alpha, each verification pass yields 1 + alpha tokens on average, so 1.85 to 1.90 tokens per pass. DeepSeek measured 1.8 times the tokens per second. The gap comes from the extra work: the MTP module itself must run, and the verification pass processes more positions than a plain decoding step. With more drafted tokens the formula is (1 − alpha^(k+1)) / (1 − alpha), but acceptance usually falls for tokens further ahead, so returns shrink.
  </InterviewQuestion>
  <InterviewQuestion question="You add four MTP heads to a large-vocabulary model and training runs out of memory. What is going on and how do you fix it?" category="Failure modes" level="Senior">
    Each head produces logits over the whole vocabulary at every position, and those logits and their gradients dominate memory: for a 4,096-token sequence and about 128,000 tokens of vocabulary, one head's logits alone are about 2.1 GB in 32-bit floats. Four heads materialized together multiply that. The fix from Gloeckle et al. is to run the forward and backward pass of one head at a time and accumulate gradients at the trunk, which drops peak memory from order nV to order V. Sharing the unembedding matrix across heads also avoids storing n copies of the largest weight matrix.
  </InterviewQuestion>
  <InterviewQuestion question="Would you add MTP to a 500M-parameter model trained for a chat product? Defend your answer." category="Trade-offs" level="Senior">
    Probably not as a quality improvement. Meta's results show MTP models underperforming the next-token baseline at 0.3B and 0.6B parameters, with gains appearing only at larger sizes and mostly on code. It also costs training memory and time. If inference latency is the real goal, a post-hoc drafter such as Medusa or EAGLE heads, or a small separate draft model, gives speculative-decoding gains without changing pre-training. I would revisit MTP for a larger, code-heavy model, where both the quality and the self-drafting benefits have been measured.
