A fine-tuned model goes stale: customers change what they ask, policies change, and yesterday's training set stops matching today's traffic.

- Interviewers ask about automated retraining because a strong answer covers what starts a run, how a candidate is checked, and how to avoid a model that learns the new and forgets the old.

## Overview

- **Three triggers start a run:** a schedule, a drift or quality alarm, and enough new labelled data. Combine them in one rule with a **guard** so a noisy signal cannot start a run storm.
- **A run is a pipeline, not a script:** collect, curate, train, a gate, a registry entry, then a canary. Nothing goes straight to production.
- **Adapter fine-tuning keeps runs cheap.** LoRA freezes the base and trains small adapters; QLoRA stores the frozen base in 4 bits. Check the adapter matches the exact base revision and tokenizer served.
- **The gate has two halves:** the new golden set and a frozen **old suite**. A candidate trained on new data only can score higher on new tickets and fail the old ones (in the worked example, 99 of 120 against a floor of 112).
- **Compare against the champion on live traffic.** At 200 graded samples the 95 % interval is about ±4.3 points, so a 10 % canary can fail to rule out a drop.
- **Every run leaves a record:** the trigger, the data snapshot, the code commit, the scores and the decision.

## Mental model

- A newspaper keeps a style guide. Each month editors learn what changed: a new product, a new refund rule.
- They do not throw the guide away and start again, and they do not scribble on it unchecked.
- They draft a revision, test it on last month's articles and on a pile of classic ones, print it for one desk first, and keep the old edition to hand.
- Automated retraining is that routine, run by a pipeline: a draft revision (the candidate), two test piles (the gate), one desk first (the canary) and the old edition (the champion, ready for rollback).

## Core concepts

### 1. Triggers: schedule, quality, drift and data

- **Schedule.** The first of each month: 12 runs a year, predictable, good for seasonal patterns. It wastes a run when nothing changed.
- **Quality (performance).** A weekly sample of live answers is graded; the pass rate falls under a floor. It ties retraining to user-visible harm, but needs a large enough sample and a minimum window so a noisy day does not fire it.
- **Drift.** Inputs, label mix or embeddings shift away from a reference window (see [Drift Detection](/ai-system-design/genai-system-design/drift-detection)). It can catch a silent upstream change before accuracy moves.
- **Data.** Enough new labelled examples exist: for Brightpost, 1,000 newly resolved tickets is 20 % of the 5,000-ticket set.

**How to read it:**

- Each trigger fires on its own number: the calendar, a graded sample of 166 of 200 (83 %, under the 85 % floor) and a counter of 1,000 tickets.
- One rule lets any of them start a run, with a guard of at most one run in 7 days and none while one is in flight.

### 2. Idempotent orchestration

- A run must be repeatable. Snapshot the training data, pin the code commit and the base model revision, request a fixed GPU quota, log metrics and artefacts to experiment tracking, and write the result to the registry as a candidate rather than to production.
- If a run dies half-way, rerunning it with the same inputs must give the same plan.

### 3. Data freshness

- New data helps only if it is current and labelled.
- Labels can lag: a ticket counts as resolved days after it opens, and refunds may be reversed later.
- Use only tickets past their settling window, and check that the features the model sees at training match what serving provides.

### 4. Adapters for cheap runs

- Retraining the whole model every month is costly.
- LoRA freezes the base weights and trains small low-rank adapters; QLoRA also stores the frozen base in 4-bit form to cut memory (see [LoRA, QLoRA & PEFT](/ai-system-design/genai-system-design/lora-qlora-and-peft)).
- Adapters also forget less: Biderman et al. (2024) found LoRA underperforms full fine-tuning on code and maths in their settings, but preserves the base model's abilities outside the target domain better.
- Verify that an adapter was trained on the exact base revision and tokenizer that inference loads.

### 5. Forgetting and replay

- Training on new data alone can overwrite old behaviour, known as catastrophic forgetting (Kirkpatrick et al., 2017, studied it and a method to slow learning on important weights).
- The common practical defences are replaying a share of old training examples, lowering the learning rate, training fewer epochs and using adapters.
- The defence is only trusted if the gate tests for it.

### 6. Gates, champions and challengers

- The **champion** is the live model. The **challenger** is the new candidate.
- Both are scored on the same golden set and then on live traffic, first in a shadow or a small canary and then at larger shares (see [Rollback & Blue-Green Deployment](/ai-system-design/genai-system-design/rollback-blue-green-deployment) and [A/B Testing](/ai-system-design/genai-system-design/ab-testing-prompts-models)).
- The model registry stores the candidate with its lineage and stage (see [Model Registry & Governance](/ai-system-design/genai-system-design/model-registry-governance)).

## Technical mechanics

### The forgetting check

The old suite is a frozen set of cases from earlier incidents and earlier capabilities. It never shrinks and it is not trained on. A candidate must not fall far below the champion on it.

<AnimatedDiagram
  spec="animated/finetune/forgetting-check"
  caption="Candidate A scores higher on the new set and still fails, because it forgot. Candidate B gives up two points on the new set and keeps the old behaviour. Counts are illustrative."
/>

**The numbers:**

- The champion passes 114 of 120 on the old suite (95 %).
- A candidate may fall at most 2 points, so the floor is (0.95 − 0.02) × 120 = 111.6, rounded up to **112**.
- Candidate A, trained on new data only, passes 188 of 200 (94 %) on the new golden set but 99 of 120 (82.5 %) on the old suite, and is blocked.
- Candidate B, with 700 replayed tickets, passes 184 of 200 (92 %) and 113 of 120 (94.2 %), and goes to the registry.

<Callout tone="red" title="What breaks">
  A gate with only a new-data score ships Candidate A: the number goes up while the model forgets how to handle returns, tone or older products. The old suite is the only thing that sees it.
</Callout>

### Champion against challenger

A golden set is a fixed sample; live traffic is the real test. Send a small share to the challenger and grade samples from both with one rubric.

<AnimatedDiagram
  spec="animated/finetune/champion-challenger"
  caption="Both models answer real traffic and the same judge grades them. At 200 samples the challenger's interval still holds the floor. Pass counts are illustrative."
/>

**The numbers:**

- At the average 2.3 requests/s there are 2.3 × 3,600 = 8,280 requests an hour, so 10 % is 828 to the challenger.
- It passes 178 of 200 = 89 %. The 95 % interval is 1.96 × √(0.89 × 0.11 ÷ 200) = ±4.3 points, or 84.7 % to 93.3 %.
- That holds the 85 % floor, so the check cannot rule out a drop.
- The answer is a larger share (50 %), not an early promotion.

### Cost and the run storm

- Each run costs GPU time, an evaluation pass (200 tickets × 2,450 tokens, plus the judge) and review attention.
- Too many triggers fragment the model lineage and burn budget; too few let slow decay build until an incident forces a rushed retrain.
- The guard (one run in 7 days, none in flight) and a minimum sample size before an alarm fires are the controls.
- Log every trigger decision with the statistics behind it.

### Worked example: Brightpost's monthly refresh

1. **Trigger.** The counter reaches 1,000 resolved tickets (20 % of 5,000). The monthly schedule is not due, and the guard allows a run.
2. **Curate.** 700 tickets survive. The golden set stays out.
3. **Train.** A LoRA run on 700 new and 700 replayed tickets from [Fine-Tuning LLMs](/ai-system-design/genai-system-design/fine-tuning-llms).
4. **Gate.** The first attempt, without replay, scores 188 of 200 on the golden set but 99 of 120 on the old suite and is blocked. With replay: 184 of 200 and 113 of 120. It passes.
5. **Register.** Bundle 42 is stored beside live bundle 41, with the data snapshot and scores.
6. **Canary.** Shadow, then 1 % and 10 %. At 10 % the interval holds the floor, so the run goes to 50 % before promotion. If it fails, traffic returns to bundle 41 with one switch.

All counts except the triggers and the golden set are illustrative.

```yaml
run: ft-2026-11-b
trigger: new_data   # 1000 tickets
data_snapshot: tix-2026-11-01..2026-11-14
base: support-base-r3        # exact base revision
adapter: lora r=16
gate: {golden: 184/200, old_suite: 113/120, decision: pass}
candidate: bundle-42
```

This is an illustrative run record, not a standard format.

## Trade-offs

| Choice | Pros | Cons | When to use |
| --- | --- | --- | --- |
| Schedule trigger | Predictable; simple | Wastes runs; can miss fast change | Seasonal or slow-moving domains |
| Quality trigger | Tied to user harm | Needs samples; noisy short-term | Online grading exists |
| Drift trigger | Early warning | Drift without harm is common | Silent upstream changes |
| Data-count trigger | Retrains when there is something to learn | Labels lag; quality varies | Steady labelled flow |
| Adapter (LoRA/QLoRA) run | Cheap; fast; forgets less | May underfit big shifts | Style, format, narrow policy |
| Full fine-tune run | Highest capacity | Costly; more forgetting risk | Large shifts in behaviour |

## Production systems

- **Brightpost's monthly refresh.** The worked example above: counter trigger, replay, two-part gate, canary.
- **LoRA in practice.** Biderman et al. (2024): LoRA learned less than full fine-tuning on code and maths but forgot less outside the target domain.
- **Elastic weight consolidation.** Kirkpatrick et al. (2017) slowed learning on weights important to earlier tasks, to show forgetting could be reduced.
- **Continuous training in MLOps.** Google's MLOps guidance describes triggers, data and model validation, and a registry in automated pipelines (see Further reading).

## Failure modes & pitfalls

- A gate that tests only new data, so forgetting ships.
- No minimum sample or window, so one noisy day fires a run.
- Training on tickets whose labels have not settled.
- Promoting on a canary whose interval still holds the floor.
- Loading an adapter on a different base revision or tokenizer than it was trained on.
- Retraining with no data snapshot, so a bad model cannot be reproduced.

## Interview framework

1. Name the triggers (schedule, quality, drift, data) and the guard that combines them.
2. Walk the pipeline: collect, curate, train, gate, register, canary, with the run stopping at the gate.
3. Say why adapters keep runs cheap, and the compatibility check for base and tokenizer.
4. Raise forgetting yourself: replay, a frozen old suite and a floor relative to the champion.
5. Close with champion against challenger on live traffic, including an interval and a rollback.

**What interviewers listen for:** a two-part gate, a guard on triggers, a registry step with lineage, and a rollback plan.

**Red flags:** "retrain nightly", pushing the new model straight to production, or evaluating only on new data.

    - It also tends to forget less outside the target domain.
    - Full fine-tuning fits when the domain differs strongly from pretraining or when adapter capacity limits quality after evaluation.
