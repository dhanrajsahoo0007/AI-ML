A coding agent that stops after every turn and waits for you to type "continue" has turned you into its loop.

- **Loop engineering** is designing the program that does that job instead: it starts each round of work, checks the result against a goal, and decides whether to go round again, stop or ask a person.
- Interviewers use it to test three things: how you know an agent is done, how you stop one that is not getting anywhere, and what happens when a long run crashes.
- This page sits one level above [Harness Engineering](/ai-system-design/genai-system-design/harness-engineering): the harness decides what one turn can do, and the loop decides whether there is another.

## Overview

- A loop has four parts: a **goal** a program can test, a round of work (**act**), a **check** against the goal and a **decision**: go on, stop or ask.
- "The agent says it is done" is a claim, not a proof. The check must rest on evidence the agent did not write: an exit code, a test report, a second model's verdict.
- Write the goal as a test and run it **before** the first edit. A goal you cannot test is not ready for a loop.
- Cap every loop with **budgets** for turns, tokens, time and money, checked before each turn.
- Add a **circuit breaker**: when the same failure comes back three times, more turns will not help. Stop, save state and escalate.
- Prefer **deterministic exit criteria**. Use a model-graded check only for what code cannot judge, and run it on a different model with a fresh context.
- **Checkpoint** after every round that passes its checks, so a crash costs one round, not the run.

## Mental model

- A thermostat does not ask you whether the room is warm enough.
- You set a target, 21 °C. It measures the room, switches the heater, measures again and stops when the target is met.
- If the heater breaks, a good thermostat does not run the boiler all night: it trips and shows an error.

- An agent loop is the same machine. You set a goal, such as "all 18 tests pass".
- The loop runs the agent, measures the result with the test suite, and runs it again until the suite passes.
- If the same test keeps failing in the same way, the loop trips and calls a person.
- Your work moves from typing prompts to choosing the goal, the check and the limits.

### From single-turn prompting to closed-loop execution

- A plain agent run is already a loop: the model calls tools until it answers without one (see [Agent Architectures](/ai-system-design/genai-system-design/agent-architectures#architecture)).
- But the model decides when that loop ends. It is an **open loop**: nothing outside the model checks whether the work is done.

- A **closed loop** adds a check the model does not control.
- After each **round** the harness tests the result against the goal.
- If the goal is not met, the loop starts another round with the failure attached.
- A round is one pass through act, check and decide; it can hold several **turns**, where a turn is one model response and the tool calls it asks for, as agent SDKs count them.

Anthropic's June 2026 guide to loops sorts them by what you hand over:

| Kind       | Starts when      | Stops when                           | You hand over                  |
| ---------- | ---------------- | ------------------------------------ | ------------------------------ |
| Turn-based | You prompt       | The agent judges it done             | Routine checking within a turn |
| Goal-based | You state a goal | The goal is met or a turn cap is hit | The decision to stop           |
| Time-based | A clock fires    | You cancel it or the work completes  | The decision to start          |
| Proactive  | An event fires   | Each task's goal is met              | The prompt itself              |

- Each row down gives you more time back and removes a moment where a person would have noticed a problem.
- Move down one row at a time. This page is mostly about the goal-based loop, the one interviewers ask you to design.

### Machine-verifiable goals and TDD agent loops

- A **machine-verifiable goal** is one a program can check without judgement: a test suite exits 0, a type checker reports no errors, a queue is empty, a file is under 400 lines.
- "Make the parser better" is a wish. "All 18 tests pass, and no test file changes" is a goal.

- Test-driven development (TDD) gives an agent loop its shape: write or find a failing test, change the code, run the test, repeat until it passes.
- The order matters. Run the test **before** the first edit, so you know the bug is real and the goal is testable.
- In this loop the harness runs it as round 0, before the model's first turn.

### Budgets: steps, tokens, wall-clock time and cost caps

A **budget** is a limit the harness checks before every turn. A loop needs one for each way it can run away: turns, tokens in the window, wall-clock time and money.

<AnimatedDiagram
  spec="animated/agents/budgets-and-breakers"
  stepper
  minWidth={620}
  caption="Budgets cap how much a loop may spend; the breaker stops it early when more turns would only repeat the same failure. The turn cap and the time are illustrative."
/>

**How to read it:**

- Step 1 shows the bug-fix run against its three budgets.
- It used 6 of 20 model turns (the 5 tool calls and the summary), 24,000 of 32,000 tokens and 2 of 10 minutes.
- Step 2 is a variant run, described in the next section, where the second fix keeps failing. Step 3 is the breaker.

**The numbers:**

- Turns 6 / 20 = 30 %. Tokens 24,000 / 32,000 = 75 %.
- Time 2 / 10 = 20 %. The token budget is closest to its cap, so a longer task would need [compaction](/ai-system-design/genai-system-design/context-compaction-resets-and-state) before it needed more turns.

- Turn and money caps are built into agent SDKs.
- The Claude Agent SDK takes `max_turns` and `max_budget_usd`, both unlimited by default, and ends the run with a result whose `subtype` says which cap was hit.
- The OpenAI Agents SDK raises `MaxTurnsExceeded`.
- When the turn cap ends a run, the SDK result looks like this (shape from the Claude Agent SDK docs; values illustrative):

```json
{
  "type": "result",
  "subtype": "error_max_turns",
  "num_turns": 20,
  "total_cost_usd": 1.84,
  "session_id": "3f1c…",
  "is_error": true
}
```

There is no `result` text on an error subtype, but the cost, the turn count and the session id are always there, so the loop can log the spend and resume later.

<Callout tone="red" title="What breaks">
  A money cap treated as a hard ceiling. The Agent SDK compares spend with the cap after each model response arrives, so
  the response that crosses it still completes, and running subagents can add more before they stop. Set the cap below
  what you can afford by at least one response, and add a separate cap per day across runs.
</Callout>

### Circuit breakers and detecting repeated failure loops

- A budget stops a loop that runs too long. It does not notice a loop that is going nowhere.
- A **circuit breaker** does. The pattern comes from distributed systems: after a set number of failures, the breaker trips and further calls fail at once instead of reaching the broken service (Martin Fowler, 2014, after Michael Nygard's _Release It!_).

- In an agent loop, the breaker watches failures, not calls.
- The harness takes a **fingerprint** of each failure, such as the test name plus the error message with line numbers and timestamps removed, and counts how many times in a row the same fingerprint comes back.
- In the variant run of the figure, the second fix fails "parses an empty file" with the same error at turns 6, 7 and 8.
- On the third the breaker trips: the loop saves its state, stops and asks a person.

- **The numbers:** The breaker trips at turn 8 of 20. Without it, the turn cap would have allowed 20 − 8 = **12 more turns** of the same failure.

Three signals are worth a breaker each:

- **The same failure** three times in a row, by fingerprint.
- **The same tool call** with the same arguments three times in a row: the agent is re-reading or re-running instead of changing anything.
- **No tool use** for several turns: the agent is talking instead of working. Claude Code's `/goal` stops the loop and hands control back when this happens.

<Callout tone="red" title="What breaks">
  A fingerprint taken from the raw error text. If the message includes a timestamp, a temporary path or a line number
  that moves with each edit, no two failures look the same and the breaker never trips. Normalise the error before you
  hash it.
</Callout>

<StepCards>
  <StepCard n={1} title="A goal a program can test">
    "All 18 tests pass" is set before the first round and never changes during the run. The model can read it; it cannot

  </StepCard>
  <StepCard n={2} title="Act: the agent takes its turns">
    The harness assembles the context (the goal, the last check result, the state so far), calls the model and runs the

  </StepCard>
  <StepCard n={3} title="Check the result against the goal">
    The harness, not the model, runs the check: here the test suite, lint and types. The ringed box is the part that
    decides whether the loop is any good. [The verification
    ladder](/ai-system-design/genai-system-design/harness-engineering#core-concepts) covers which checks to run and in
    what order.
  </StepCard>
  <StepCard n={4} title="Decide: go round again, or leave">
    The decision reads the verdict, the budgets and the breaker. Not met, with budget left and no repeated failure: the
    next round starts with the failure attached (dashed arrow). Otherwise the loop leaves by one of three exits: done,
    stop and report, or ask a person.
  </StepCard>
</StepCards>

The order inside the decision matters. Here is a sketch of it in TypeScript:

```ts
async function decide(run: Run): Promise<"done" | "next" | "stop" | "ask"> {
  const verdict = await check(run.goal); // tests, lint, types: run by the harness
  if (verdict.met) return "done"; // a goal met on the last allowed round is done, not over budget
  if (run.breaker.record(verdict.fingerprint) >= 3) return "ask"; // same failure three times
  if (run.turns >= run.caps.turns || run.costUsd >= run.caps.usd) return "stop";
  if (isRisky(run.nextStep)) return "ask"; // merge, deploy, delete: always a person
  await saveCheckpoint(run); // only after the checks have run
  return "next";
}
```

- Goal first, so a run that succeeds on its last round reports success.
- Breaker before budgets, so a stuck run asks for help instead of reporting "out of turns".
- The risky-step gate last, because it applies even to a healthy run.

## Technical mechanics

### Worked example: the CSV fix as a goal-based loop

- This follows the [TDD loop figure](#machine-verifiable-goals-and-tdd-agent-loops) round by round, with what the decision saw each time.
- The goal is "all 18 tests pass, lint and types clean, no test file changes"; the caps are 20 turns and 32,000 tokens.

| Round | Act                                              | Check                           | Breaker             | Turns used | Decision                       |
| ----- | ------------------------------------------------ | ------------------------------- | ------------------- | ---------- | ------------------------------ |
| 0     | Harness runs `run_tests()`                       | 1 failed: keeps the last line   | 1 (new fingerprint) | 0          | Not met: go on                 |
| 1     | Search, read, edit the loop bound, `run_tests()` | 1 failed: parses an empty file  | 1 (new fingerprint) | 4          | Not met, new failure: go on    |
| 2     | Return `[]` for empty input; summary             | 18 passed, lint and types clean | reset               | 6          | Met: stop, open a pull request |

**The numbers:**

- 3 rounds held the 6 model turns of the harness trace: 0 + 4 + 2.
- The breaker never reached 2, because each failure was new.
- Tokens grew from 3,800 to 24,000 (illustrative, from the [context window figure](/ai-system-design/genai-system-design/harness-engineering#core-concepts)), so the loop ended with 6 of 20 turns and 8,000 tokens to spare.

Three things to take from it:

- **A changing failure is progress.** Round 1 failed, but on a different test. A loop that only counted failures would have treated it like round 0.
- **The model never decided it was done.** The suite decided, and the person who merges the pull request decides whether it ships.
- **The variant run is the same loop.** Had the second fix failed the same way at turns 6, 7 and 8, the breaker would have stopped it with 12 turns unspent, as in the [budgets figure](#budgets-steps-tokens-wall-clock-time-and-cost-caps).

### Designing deterministic vs. LLM-graded exit criteria

An **exit criterion** is the condition that ends the loop with success. It can be checked by code or by a model.

<AnimatedDiagram
  spec="animated/agents/exit-criteria"
  stepper
  minWidth={620}
  caption="An exit code cannot be argued with, but it checks only what the tests encode. An evaluator model can judge prose, but only from what the agent chose to show it."
/>

**How to read it:**

- Step 1: the deterministic check reads the test runner's exit code; a script decides, and the answer is met or not met.
- Step 2: the model-graded check gives the goal condition and the transcript to an evaluator model, which answers met, not yet or impossible, with a reason.
- Here it judges something the tests cannot: whether the pull-request summary names the empty-file case. The ringed cell is its blind spot.

- Claude Code's `/goal` command is a model-graded loop.
- After every turn a small, fast model (Haiku by default on the Claude API) checks the condition against the conversation.
- It cannot run commands or read files, so the docs advise writing the condition as something the agent's own output can show, such as "`npm test` exits 0", and bounding it with a clause like "or stop after 20 turns".

Four rules for choosing:

1. **Deterministic first.** Anything a test, a type checker or a script can check, check that way. It costs no tokens and gives the same answer every time.
2. **Model-graded only for what code cannot judge:** a summary's accuracy, a design's quality, whether a fix addresses the issue as written.
3. **Never let the worker grade itself.** Anthropic found that agents "reliably skew positive when grading their own work"; a separate evaluator with a sceptical brief is easier to tune than a self-critical worker. See [Planner, Generator & Evaluator Loops](/ai-system-design/genai-system-design/planner-generator-evaluator-loops).
4. **Combine them with AND.** The suite must pass **and** the evaluator must say met. The cheap check runs every round; the model-graded one runs only once the cheap one passes, as on the [verification ladder](/ai-system-design/genai-system-design/harness-engineering#core-concepts).

<Callout tone="red" title="What breaks">
  An evaluator that believes a sentence. If the agent writes "all tests pass" without running them, an evaluator that
  reads only the transcript may accept it. Require the evidence itself in the transcript (the test runner's output, not
  the agent's summary of it), or have the harness run the suite and hand the evaluator the result.
</Callout>

### Handling partial progress and checkpoint resumption

- A long loop will crash: a container is recycled, a rate limit hits, the laptop sleeps.
- A **checkpoint** is saved state from which a new run can carry on.
- For a coding loop the cheapest checkpoint is a git commit plus a line in a progress file.

<AnimatedDiagram
  spec="animated/agents/checkpoint-resume"
  stepper
  minWidth={620}
  caption="Save state after every round that passes its checks. A crash then costs one round, not the whole run. The run is illustrative."
/>

**How to read it:**

- Step 1: the loop commits after each round whose checks pass, here after rounds 2 and 4.
- Round 5 crashes. Step 2: the resumed run loads the last checkpoint (ringed) and repeats only round 5.
- Restarting from the beginning would repeat 5 rounds; resuming repeats 1.

- Anthropic's harness for long-running coding agents (November 2025) works this way.
- A first session writes a JSON feature list in which every feature starts as failing, a progress file and an initial commit.
- Every later session reads the git log and the progress file, picks one unfinished feature, tests it end to end and commits.
- The model may change only each feature's `passes` field; the post says it is "unacceptable to remove or edit tests".

Two rules make resumption safe:

- **Checkpoint only after the checks.** A checkpoint taken mid-edit resumes into broken code.
- **Keep budgets outside the session.** When you resume a Claude Code session with an active `/goal`, the condition carries over but the turn count, timer and token baseline reset. A loop that crashes and resumes every hour never hits its cap. Keep the run's total spend in your own store.

The full picture (threads, runs, checkpoint records and how they link) is on [State Persistence & Retrieval](/ai-system-design/genai-system-design/state-persistence-retrieval).

### When to stop, pivot strategy or escalate to a human

Every decision the loop makes falls into one of four actions. Map each signal to one in advance:

| Signal                                                         | Action                                                                                | Why                                          |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------- | -------------------------------------------- |
| Goal met, every check passes                                   | **Stop**: report and hand over                                                        | The only good exit                           |
| Not met, and the failure changed                               | **Continue** with the new error attached                                              | The last round made progress                 |
| The same failure twice                                         | **Pivot**: revert to the last checkpoint, start a fresh context, try another approach | A third identical try rarely differs         |
| The same failure three times, or no tool use for several turns | **Escalate**: breaker trips, save state, ask a person                                 | More turns only cost money                   |
| A budget is nearly spent                                       | **Wrap up**: commit what passes, write a summary                                      | A clean partial result beats a cut-off one   |
| The evaluator judges the goal impossible                       | **Stop and report** the reason                                                        | The goal or the environment is wrong         |
| The next step is a merge, deploy, delete or payment            | **Ask a person**, every time                                                          | Irreversible actions are not the loop's call |

- The pivot is the step most loops miss. A loop that only retries keeps the context full of failed attempts, and the agent starts repeating them.
- Reverting to the checkpoint and starting a fresh context with a short note ("approach A failed twice with this error") gives the next try a clean start.
- [Human-in-the-Loop & Approvals](/ai-system-design/genai-system-design/human-in-the-loop-and-approvals) covers what the person sees when the loop asks.

## Trade-offs

| Decision                                      | Option A                                | Option B                          | Guidance                                                               |
| --------------------------------------------- | --------------------------------------- | --------------------------------- | ---------------------------------------------------------------------- |
| Deterministic vs model-graded exit            | Certain, free, repeatable               | Judges prose and intent           | Deterministic for everything code can check; add a graded check on top |
| Tight vs loose turn cap                       | Cheap failures, more human resumes      | Finishes more tasks unattended    | Start tight; raise it when traces show runs ending one turn short      |
| Breaker at 2 vs 3 repeats                     | Stops waste early                       | Gives one retry after a pivot     | 3 with a pivot after 2                                                 |
| Fresh context per round vs one long session   | No stale attempts, needs state in files | Keeps reasoning, fills the window | Fresh context for long loops; one session for short ones               |
| Checkpoint every round vs every passing round | Nothing lost                            | Never resumes into broken code    | Only after checks pass                                                 |

## Production systems

- **Ralph** (Geoffrey Huntley, July 2025) is the smallest loop: `while :; do cat PROMPT.md | claude-code ; done`. Each round starts with a fresh context and reads its plan from files. It has a goal, an act and a check (the tests), and no stop: Huntley watches it.
- **Anthropic's long-running harness** (November 2025) runs coding sessions against a JSON feature list of over 200 features, with a progress file and git commits as checkpoints, and end-to-end browser tests as the check.
- **Claude Code's `/goal`** (2026) keeps a session working until an evaluator model judges the condition met or impossible; it stops by itself when the agent stops using tools.
- **Agent SDKs** cap loops in code: the Claude Agent SDK with `max_turns` and `max_budget_usd`, the OpenAI Agents SDK with `max_turns` and `MaxTurnsExceeded`, LangGraph with `recursion_limit` and `GraphRecursionError`.
- **Adoption is early.** Lulla et al. (arXiv, August 2026) mined about 36,700 repositories and found autonomous loops in 217. Almost none committed the state files that published advice recommends.

## Failure modes & pitfalls

- A goal that only the model can judge ("the code is clean").
- No turn or money cap, so a stuck loop runs all night.
- Letting the agent edit the tests, the lint config or the goal.
- Counting failures without looking at whether they changed.
- Retrying in the same crowded context instead of pivoting from a checkpoint.
- A model-graded exit check run by the same model that did the work.
- Budgets that reset on every resume.

## Interview framework

1. Name the four parts: goal, act, check, decide. Say which part the model owns (the act) and which the harness owns (the rest).
2. Make the goal machine-verifiable, and run it before the first edit.
3. Set budgets for turns, tokens, time and money, and a breaker on repeated failures.
4. Choose deterministic exit criteria first; add a model-graded check on a separate model only for what code cannot judge.
5. Checkpoint after passing rounds, and say when the loop escalates to a person.

**What interviewers listen for:** a check the agent cannot write or edit, and more than one way out of the loop.

**Red flags:** "the agent tells us when it is done", or a loop with no cap.
