A language model outputs a score for every vocabulary token rather than text, and a decoding strategy turns those scores into one chosen token per step.

- Every product knob—temperature, top-p, JSON mode, and output determinism—lives here.

## Overview

- At each step the output head produces **logits**; a **softmax** turns them into a probability distribution, and a **decoding strategy** picks one token. Generation repeats this once per token.
- **Temperature** divides the logits before the softmax: below 1 sharpens the distribution, above 1 flattens it, and close to 0 it behaves like **greedy** decoding.
- **Greedy and beam search** chase the most likely text. That suits translation, but open-ended text comes out bland and repetitive, so chat models **sample**, usually after cutting the unreliable tail with **top-k, top-p or min-p**.
- **Penalties, logit bias and grammar masks** edit logits before sampling. A grammar mask sets forbidden tokens to −∞, so the output is **guaranteed to parse**.
- **Logprobs** expose the model's confidence per token, but post-trained models are often **poorly calibrated**.
- **Temperature 0 is not a determinism guarantee**: on shared servers, batch size changes the floating-point math, so the same prompt can produce different text.

<KeyIdea>Decoding is a short chain of edits to the logits, a softmax and one pick per token, and every product knob (temperature, top-p, JSON mode, determinism) lives in that chain.</KeyIdea>

## Mental model

- **Greedy tapping vs. weighted dice:** Think of the word suggestions above your phone keyboard ranked by likelihood—always tapping the first suggestion is greedy decoding (which soon gets stuck in repetitive loops), whereas rolling a die weighted by the scores gives varied, sometimes surprising sampling.
- **Temperature:** Decides how heavily the weighted die favors the top suggestions.
- **Top-p truncation:** Tells the sampler to ignore the long shots that together barely matter.
- **Grammar mask:** Acts like the keyboard graying out keys that would make the text invalid, such as letters in a phone-number field.

## Core concepts

1. **Logits and softmax:**
   - **Linear projection:** The last decoder layer's vector for the newest position goes through the output head (a linear layer, see [Transformer Architecture](/ai-system-design/genai-system-design/transformer-architecture)) and becomes one logit $z_i$ per vocabulary token.
   - **Probability conversion:** The softmax turns logits into probabilities that sum to 1:

   $$
   p_i = \frac{\exp(z_i)}{\sum_j \exp(z_j)}
   $$

   - **Shift invariance:** Only differences between logits matter—adding the same number to every logit changes nothing.

2. **Temperature:**
   - **Logit scaling:** Divide every logit by a temperature $T$ before the softmax, $p_i \propto \exp(z_i / T)$.
   - **Rank preservation:** The ranking of tokens never changes, only how far apart their probabilities are.
   - **Limits:** As $T \to 0$, all the mass moves to the top token (greedy); large $T$ moves toward a uniform distribution.

3. **Greedy decoding:**
   - **Rule:** Take the arg-max token at every step.
   - **Trade-off:** Fast and deterministic in principle, but a locally best token can lead to a worse sentence overall, and in open-ended text greedy decoding falls into repetition loops.

4. **Beam search:**
   - **Multi-hypothesis tracking:** Keep the $B$ best partial sequences (the beam), scored by total log-probability $\sum_t \log p(y_t \mid y_{<t})$; at each step, extend every beam by its candidates and keep the best $B$.
   - **Length penalty:** Because longer sequences collect more negative log terms, systems add a length penalty—the original Transformer used a beam of 4 with length penalty $\alpha = 0.6$ for translation.

5. **Top-k sampling:**
   - **Fixed cutoff:** Keep only the $k$ most likely tokens, renormalize their probabilities to sum to 1, and sample (Fan et al., 2018 used $k = 10$ for story generation).
   - **Weakness:** Because $k$ is fixed, it keeps too many tokens when the model is sure and too few when many continuations are reasonable.

6. **Top-p (nucleus) sampling:**
   - **Adaptive cutoff:** Keep the smallest set of tokens whose cumulative probability reaches $p$, renormalize, and sample.
   - **Dynamic width:** The set grows when the model is unsure and shrinks when it is confident; Holtzman et al. (2019) introduced it and reported their main results at $p = 0.95$.

7. **Min-p sampling:**
   - **Relative threshold:** Keep every token whose probability is at least $p_{base} \times p_{max}$, where $p_{max}$ is the top token's probability.
   - **Worked example:** In the distribution above, $p_{base} = 0.1$ gives a threshold of $0.1 \times 0.355 \approx 0.036$, keeping 6 tokens ("orange" at 0.039 survives, "bright" at 0.024 does not).
   - **High-temperature stability:** Because the threshold scales with the model's confidence, min-p stays coherent at higher temperatures; its authors suggest $p_{base}$ between 0.05 and 0.1.

8. **Repetition, frequency and presence penalties:**
   - **Multiplicative repetition penalty:** Edits logits of tokens that already appeared; the CTRL paper divides those logits by $\theta$ (about 1.2 worked well with greedy decoding), while Hugging Face divides positive logits and multiplies negative ones so both move toward "less likely".
   - **Additive API penalties:** OpenAI-style APIs subtract instead—a **frequency penalty** grows with how many times the token appeared, and a **presence penalty** subtracts a flat amount once it has appeared at all.
   - **Logit bias:** Adds a fixed number to chosen token ids, for example to ban a specific word.

## Architecture

- Every generated token runs the same short pipeline (the decoder stack and KV cache are covered in [Efficient Attention](/ai-system-design/genai-system-design/efficient-attention); decoding is everything after the output head).

<AnimatedDiagram
  spec="animated/llm/decode-pipeline"
  caption="Every generated token runs this loop once: the logits are edited by a chain of processors, turned into probabilities, and one token is picked and fed back in."
/>

1. **Decoder forward pass:** The decoder stack processes the newest token, reusing cached keys and values for the earlier ones.
2. **Output projection:** The output head turns the last position's vector into one logit per vocabulary token.
3. **Logits processor chain:** Penalties and logit bias run first, followed by a grammar mask if output must follow a format, division by temperature, and then top-k, top-p, or min-p (removed tokens get a logit of −∞).
4. **Softmax and sampling:** Softmax gives probabilities, and the sampler draws one token (or takes the arg-max for greedy).
5. **Stream and repeat:** The token is streamed to the user and appended to the input, repeating until a stop token, a stop string, or the token limit.

<Callout tone="red" title="What breaks">
  Identical settings across engines. Libraries do not agree on the order of step 3—the min-p paper notes that Hugging Face Transformers and vLLM apply temperature before the min-p threshold, so identical settings can behave differently across engines.
</Callout>

## Technical mechanics

### Logprobs and confidence signals

The log-probability of each generated token is a free by-product of decoding, and many APIs return it (OpenAI's chat API returns up to 20 alternatives per position through `top_logprobs`).

- **Sequence scores:** The sum of token logprobs is the log-likelihood of the whole answer; dividing by the length gives a per-token average, and its negative exponent is the perplexity.
- **Cheap classification:** Ask for a one-token label and read the probabilities of "yes" and "no" instead of parsing text, giving a continuous score you can threshold.
- **Uncertainty flags:** Low-probability spans often mark guesses, which a pipeline can route to retrieval or a human.
- **Calibration warning:** Confidence is not correctness—the GPT-4 technical report shows the pre-trained model was well calibrated on a subset of MMLU, whereas post-training reduced calibration significantly.
- **Reporting order warning:** Check whether a provider reports logprobs before or after temperature and truncation, as it changes the numbers and is not always documented.

### Constrained and grammar-guided decoding

- **Hard syntax guarantee:** Asking for JSON in the prompt works most of the time, whereas constrained decoding makes it work every time.
- **Parser state tracking:** A parser for the target format (a regular expression, a JSON schema, or a context-free grammar) tracks where the output is, and at each step a mask removes every token that could not continue a valid string.

<AnimatedDiagram
  spec="animated/llm/decode-grammar-mask"
  stepper
  caption="Without a mask, 0.68 of the probability sits on tokens that would break the JSON; the grammar mask sets their logits to −∞, so the softmax spreads all the mass over “true” and “false”."
/>

- **Precomputed FSM masks:** Checking every vocabulary token against the parser at every step is slow; Willard and Louf (2023), the paper behind the Outlines library, compile a regular expression into a finite-state machine and precompute allowed tokens per state so the per-step cost becomes `O(1)` on average.
- **Pushdown automata for JSON:** For nested formats such as JSON, they extend the idea to pushdown automata—the same pattern behind "structured outputs" in hosted APIs and grammar options in open-source servers (see [Structured Output Generation](/ai-system-design/genai-system-design/structured-output-generation) for the product side).
- **Syntax vs. truth caveat:** A mask guarantees syntax, not truth—the model above still has to choose correctly between `true` and `false`.

<Callout tone="red" title="What breaks">
  Distribution shift. Forcing a format the model would rarely choose can pull it into low-probability, lower-quality text, so always describe the schema in the prompt as well.
</Callout>

### Determinism, seeds and reproducibility

- **Why a seed is not enough:** Sampling uses a random number generator whose draws are fixed by a **seed**, but the logits themselves can still change between runs.
- **Batch-size floating-point drift:** Floating-point addition is not associative, and GPU kernels may sum in a different order depending on the batch size, which varies with server load.
- **Measured divergence:** A study by Thinking Machines (2025) sent the same prompt 1,000 times at temperature 0 to Qwen3-235B and got 80 different completions; with batch-invariant kernels, all 1,000 matched.
- **Provider guarantees and mitigations:** OpenAI documents `seed` as best effort ("not guaranteed") and returns a `system_fingerprint` to track backend changes; for reproducible evaluations, log the full request (model version, sampling parameters, seed), store outputs instead of regenerating them, and pin engine versions with batch-invariant kernels when self-hosting.

## Trade-offs

<Compare caption="Decoding strategies: what each one buys, what it costs and where it fits.">

| Choice | Pros | Cons | When to use |
| --- | --- | --- | --- |
| Greedy | Fast, simple, mostly repeatable | Repetition loops in long open-ended text; misses better sequences | Short factual answers, extraction, classification |
| Beam search | Finds higher-likelihood sequences | B times the compute; bland, repetitive open-ended text | Translation, speech recognition, short constrained outputs |
| Temperature sampling alone | Diverse, one knob | Long tail of junk tokens at high T | Rarely alone; combine with a truncation method |
| Top-k | Simple, cheap | Fixed k ignores how confident the model is | Older pipelines, small vocabularies |
| Top-p | Adapts to the shape of the distribution | Still admits a long tail when the distribution is flat | Default for most chat products |
| Min-p | Scales with confidence; stable at higher T | Newer, fewer hosted APIs expose it | Creative writing, open-source serving stacks |
| Grammar-constrained decoding | Output always parses | Mask-building cost; can push the model off its natural path | JSON, function arguments, SQL, any machine-read output |

</Compare>

## Production systems

- **Measured degeneration.** Holtzman et al. (2019) counted how often GPT-2 Large text ended stuck in a loop (a phrase repeated at least three times at the end): 73.66% of greedy generations and 28.94% with beam width 16, against 0.36% for nucleus sampling at $p = 0.95$ and 0.28% for human text.
- **Translation.** The original Transformer decoded with beam size 4 and length penalty $\alpha = 0.6$ (Vaswani et al., 2017), the length penalty coming from Google's neural machine translation system.
- **OpenAI API.** Chat completions accept `temperature` from 0 to 2 (default 1), `frequency_penalty` and `presence_penalty` from −2.0 to 2.0, `logit_bias` from −100 to 100, and `top_logprobs` from 0 to 20. The reference recommends changing temperature or `top_p`, not both.
- **Providers differ.** Which sampling parameters an API accepts, their ranges and their defaults vary between providers and can change between model versions; some newer reasoning models fix sampling settings and ignore or reject them. Check the current API reference before you tune.
- **Open-source engines.** Min-p sampling is available in Hugging Face Transformers and vLLM, and libraries such as Outlines add grammar-constrained decoding to open models.

## Failure modes & pitfalls

- Treating temperature 0 as a guarantee of identical outputs. Batching and kernel choices still change the numbers.
- Turning up temperature for "creativity" without a truncation method, which lets nonsense tokens through.
- Setting temperature and top-p together without testing: their effects compound, and the order they run in differs by engine.
- Using beam search for chat. Higher likelihood is not higher quality for open-ended text.
- Reading logprobs as calibrated probabilities of being correct, especially after RLHF.
- Assuming constrained decoding makes the content right. It guarantees the shape, not the facts.

## Interview framework

1. Start with the loop: logits, softmax, pick a token, append, repeat; mention the KV cache.
2. Write the temperature formula and say what low and high values do.
3. Contrast maximization (greedy, beam) with sampling, and explain why open-ended text needs sampling.
4. Compare top-k, top-p and min-p with a concrete distribution, then mention penalties and logit bias.
5. Close with production concerns: constrained decoding for JSON, logprobs for confidence, and why outputs are not reproducible even at temperature 0.

**What interviewers listen for:** the formula, the reason beam search degenerates on open-ended text, concrete parameter values, and awareness that providers expose different knobs.

**Red flags:** "temperature makes the model smarter", "temperature 0 is always deterministic", or claiming JSON mode guarantees correct values.

  <InterviewQuestion question="What does temperature do, mathematically?" category="Concepts" level="Junior">
    - **Logit division:** Temperature divides every logit by `T` before the softmax.
    - **Sharpness vs. flatness:** Below 1 it widens the gaps between logits so the top tokens take more probability mass; above 1 it shrinks the gaps and flattens the distribution.
    - **Order and limits:** Token rankings never change, and as `T` approaches 0 all mass goes to the arg-max token (greedy decoding).
  </InterviewQuestion>
  <InterviewQuestion question="Compare top-k, top-p and min-p sampling." category="Concepts" level="Mid">
    - **Shared mechanism:** All three remove the unlikely tail and renormalize the remaining probabilities before sampling.
    - **Top-k:** Keeps a fixed number of tokens `k`, which is too many when the model is confident and too few when many continuations are reasonable.
    - **Top-p:** Keeps the smallest set whose probabilities sum to `p`, adapting dynamically to the shape of the distribution.
    - **Min-p:** Keeps tokens whose probability is at least a fraction of the top token's probability, scaling the cutoff with confidence and staying coherent at higher temperatures.
  </InterviewQuestion>
  <InterviewQuestion question="Why is beam search standard for translation but rarely used for chat?" category="Trade-offs" level="Mid">
    - **Constrained vs. open-ended:** In translation the input closely pins down the output so the highest-likelihood sequence is usually good, whereas in open-ended generation the most likely text is generic and falls into repetition loops (as measured by Holtzman et al.).
    - **Compute and streaming cost:** Beam search costs about `B` times the compute per step and must finish before returning the best beam, which hurts token streaming.
    - **Chat alternative:** Chat systems therefore sample with temperature and top-p instead.
  </InterviewQuestion>
  <InterviewQuestion question="A model keeps repeating the same sentence. What can you change at decoding time?" category="Failure modes" level="Mid">
    - **Root cause:** Repetition loops are typical of greedy or low-temperature decoding because each repeat makes the next repeat even more likely.
    - **Sampling fix:** Switching to sampling with top-p or min-p and a moderate temperature usually breaks the loop.
    - **Penalties and stops:** Apply a repetition or frequency penalty to lower logits of already-seen tokens, add a stop sequence or max-token limit, and tune penalties carefully so the model does not avoid legitimate words like names or code keywords.
  </InterviewQuestion>
  <InterviewQuestion question="You set temperature to 0 but get different answers for the same prompt. Why, and what do you do?" category="Failure modes" level="Senior">
    - **Why logits shift:** Temperature 0 removes sampling randomness, but floating-point addition is not associative—on a shared server, varying batch sizes change how GPU kernels sum numbers, which can flip the arg-max when two tokens are close.
    - **Best-effort seeds:** Hosted `seed` parameters are documented as best effort for the exact same reason.
    - **How to mitigate:** Log the full request and model version, store outputs for evaluation instead of regenerating them, and use deterministic or batch-invariant kernels with a pinned engine version when self-hosting.
  </InterviewQuestion>
  <InterviewQuestion question="How would you guarantee that an LLM returns valid JSON for a given schema?" category="Architecture" level="Senior">
    - **Grammar masking:** Compile the schema into a grammar, track the parser state as tokens are generated, and set the logits of every token that cannot continue a valid string to minus infinity before each sampling step.
    - **Fast state lookup:** Precompute allowed tokens per parser state using finite-state machines (as Outlines does) rather than scanning the full vocabulary at each step.
    - **Validation and prompting:** Still validate the parsed values and describe the schema in the prompt, because the mask guarantees syntactic structure, not factual correctness.
  </InterviewQuestion>
  <InterviewQuestion question="Can you use token logprobs as a confidence score in production?" category="Trade-offs" level="Senior">
    - **Practical uses:** Logprobs are cheap to obtain and useful for ranking candidates, thresholding a one-token classification, or flagging low-confidence spans for review.
    - **Calibration gap:** They are not calibrated probabilities of correctness, especially after RLHF—the GPT-4 report showed post-training reduced calibration significantly.
    - **Best practices:** Calibrate logprobs on labeled data from your own task, and verify whether your provider reports them before or after temperature and truncation.
