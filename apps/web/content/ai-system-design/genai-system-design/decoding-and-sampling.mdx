A language model never outputs text. It outputs a score for every token in its vocabulary, and a decoding strategy turns those scores into one chosen token, again and again. Interviewers ask about it because every product knob (temperature, top-p, JSON mode, "why is the output different every time?") lives here, and because the answers mix math, product sense and serving details.

## TL;DR

- At each step the output head produces **logits**; a **softmax** turns them into a probability distribution, and a **decoding strategy** picks one token. Generation repeats this once per token.
- **Temperature** divides the logits before the softmax: below 1 sharpens the distribution, above 1 flattens it, and close to 0 it behaves like **greedy** decoding.
- **Greedy and beam search** chase the most likely text. That suits translation, but open-ended text comes out bland and repetitive, so chat models **sample**, usually after cutting the unreliable tail with **top-k, top-p or min-p**.
- **Penalties, logit bias and grammar masks** edit logits before sampling. A grammar mask sets forbidden tokens to −∞, so the output is **guaranteed to parse**.
- **Logprobs** expose the model's confidence per token, but post-trained models are often **poorly calibrated**.
- **Temperature 0 is not a determinism guarantee**: on shared servers, batch size changes the floating-point math, so the same prompt can produce different text.

## The idea in plain English

Think of the word suggestions above your phone keyboard. The phone ranks a few next words by how likely it thinks they are. If you always tap the first suggestion, you get greedy decoding, and you will soon be stuck in a loop that repeats the same phrase. If you instead roll a die weighted by the scores, you get sampling: more varied, sometimes surprising. Temperature decides how heavily the die favors the top suggestions. Top-p says "ignore the long shots that together barely matter". A grammar mask is the keyboard graying out keys that would make the text invalid, like letters in a phone-number field.

## Core concepts

1. **Logits and softmax.** The last decoder layer's vector for the newest position goes through the output head (a linear layer, see [Transformer Architecture](/ai-system-design/genai-system-design/transformer-architecture)) and becomes one logit $z_i$ per vocabulary token. The softmax turns logits into probabilities that sum to 1:

   $$
   p_i = \frac{\exp(z_i)}{\sum_j \exp(z_j)}
   $$

   Only differences between logits matter: adding the same number to every logit changes nothing.

2. **Temperature.** Divide every logit by a temperature $T$ before the softmax, $p_i \propto \exp(z_i / T)$. The ranking of tokens never changes, only how far apart their probabilities are. As $T \to 0$, all the mass moves to the top token (greedy); large $T$ moves toward a uniform distribution.

3. **Greedy decoding.** Take the arg-max token at every step. It is fast and deterministic in principle, but a locally best token can lead to a worse sentence overall, and in open-ended text greedy decoding falls into loops.

4. **Beam search.** Keep the $B$ best partial sequences (the beam), scored by total log-probability $\sum_t \log p(y_t \mid y_{<t})$. At each step, extend every beam by its candidates and keep the best $B$. Because longer sequences collect more negative log terms, systems add a length penalty: the original Transformer used a beam of 4 with length penalty $\alpha = 0.6$ for translation.

Follow a beam of width 2 for three steps, using a toy model whose probabilities are fixed in advance.

5. **Top-k sampling.** Keep only the $k$ most likely tokens, renormalize their probabilities to sum to 1, and sample. Fan et al. (2018) used $k = 10$ for story generation. The weakness: $k$ is fixed, so it keeps too many tokens when the model is sure and too few when many continuations are reasonable.

6. **Top-p (nucleus) sampling.** Keep the smallest set of tokens whose cumulative probability reaches $p$, renormalize, and sample. The set grows when the model is unsure and shrinks when it is confident. Holtzman et al. (2019) introduced it and reported their main results at $p = 0.95$.

/>

7. **Min-p sampling.** Keep every token whose probability is at least $p_{base} \times p_{max}$, where $p_{max}$ is the top token's probability. In the example above, $p_{base} = 0.1$ gives a threshold of $0.1 \times 0.355 \approx 0.036$, which keeps 6 tokens ("orange" at 0.039 survives, "bright" at 0.024 does not). The threshold scales with the model's confidence, so min-p stays coherent at higher temperatures. Its authors suggest $p_{base}$ between 0.05 and 0.1.

8. **Repetition, frequency and presence penalties.** These edit the logits of tokens that already appeared. The repetition penalty from the CTRL paper divides those logits by $\theta$ (about 1.2 worked well with greedy decoding); the Hugging Face implementation divides positive logits and multiplies negative ones, so both move toward "less likely". OpenAI-style APIs instead subtract: a **frequency penalty** grows with how many times the token appeared, a **presence penalty** is a flat amount once it has appeared at all. **Logit bias** adds a fixed number to chosen token ids, for example to ban a word.

## Architecture

Every generated token runs the same short pipeline. The decoder stack and its KV cache are covered in [Efficient Attention](/ai-system-design/genai-system-design/efficient-attention); decoding is everything after the output head.

<AnimatedDiagram
  spec="animated/llm/decode-pipeline"
  caption="Every generated token runs this loop once: the logits are edited by a chain of processors, turned into probabilities, and one token is picked and fed back in."
/>

1. The decoder stack processes the newest token, reusing cached keys and values for the earlier ones.
2. The output head turns the last position's vector into one logit per vocabulary token.
3. Logits processors run in a chain: penalties and logit bias, a grammar mask if output must follow a format, division by the temperature, then top-k, top-p or min-p. A removed token gets a logit of −∞.
4. Softmax gives probabilities; the sampler draws one token (or takes the arg-max for greedy).
5. The token is streamed to the user and appended to the input, and the loop repeats until a stop token, a stop string or the token limit.

Libraries do not agree on the order of step 3. The min-p paper notes that Hugging Face Transformers and vLLM apply temperature before the min-p threshold, so the same settings can behave differently across engines.

## Deep dive

### Logprobs and confidence signals

The log-probability of each generated token is a free by-product of decoding, and many APIs return it (OpenAI's chat API returns up to 20 alternatives per position through `top_logprobs`). Uses:

- **Sequence scores.** The sum of token logprobs is the log-likelihood of the whole answer; dividing by the length gives a per-token average, and its negative exponent is the perplexity.
- **Cheap classification.** Ask for a one-token label and read the probabilities of "yes" and "no" instead of parsing text. This gives a score you can threshold.
- **Uncertainty flags.** Low-probability spans often mark guesses, which a pipeline can route to retrieval or a human.

Two warnings. First, confidence is not correctness: the GPT-4 technical report shows the pre-trained model was well calibrated on a subset of MMLU, and post-training reduced calibration significantly. Second, check whether a provider reports logprobs before or after temperature and truncation; it changes the numbers, and it is not always documented.

### Constrained and grammar-guided decoding

Asking for JSON in the prompt works most of the time. Constrained decoding makes it work every time. A parser for the target format (a regular expression, a JSON schema or a context-free grammar) tracks where the output is, and at each step a mask removes every token that could not continue a valid string.

<AnimatedDiagram
  spec="animated/llm/decode-grammar-mask"
  stepper
  caption="Without a mask, 0.68 of the probability sits on tokens that would break the JSON; the grammar mask sets their logits to −∞, so the softmax spreads all the mass over “true” and “false”."
/>

The cost is in building the mask. Checking every vocabulary token against the parser at every step is slow. Willard and Louf (2023), the paper behind the Outlines library, compile a regular expression into a finite-state machine and precompute, for each state, which tokens are allowed; the per-step cost becomes O(1) on average. For nested formats such as JSON they extend the idea to pushdown automata. The same pattern sits behind "structured outputs" features in hosted APIs and grammar options in open-source servers. See [Structured Output Generation](/ai-system-design/genai-system-design/structured-output-generation) for the product side.

Two caveats. A mask guarantees syntax, not truth: the model above still has to choose correctly between `true` and `false`. And forcing a format the model would rarely choose can pull it into low-probability, lower-quality text, so describe the schema in the prompt as well.

### Determinism, seeds and reproducibility

Sampling uses a random number generator, so a **seed** fixes which draws happen. That is not enough for identical outputs, because the logits themselves can change between runs. Floating-point addition is not associative, and GPU kernels may sum in a different order depending on the batch size, which depends on how busy the server is. A study by Thinking Machines (2025) sent the same prompt 1,000 times at temperature 0 to Qwen3-235B and got 80 different completions; with batch-invariant kernels, all 1,000 matched.

Providers say this plainly. OpenAI documents its `seed` parameter as best effort, with determinism "not guaranteed", and returns a `system_fingerprint` so you can tell when the backend changed. For reproducible evaluations: log the full request (model version, every sampling parameter, seed), store outputs instead of regenerating them, and when you self-host, pin the engine version and enable batch-invariant or deterministic kernels if your engine offers them.

## Trade-offs

| Choice | Pros | Cons | When to use |
| --- | --- | --- | --- |
| Greedy | Fast, simple, mostly repeatable | Repetition loops in long open-ended text; misses better sequences | Short factual answers, extraction, classification |
| Beam search | Finds higher-likelihood sequences | B times the compute; bland, repetitive open-ended text | Translation, speech recognition, short constrained outputs |
| Temperature sampling alone | Diverse, one knob | Long tail of junk tokens at high T | Rarely alone; combine with a truncation method |
| Top-k | Simple, cheap | Fixed k ignores how confident the model is | Older pipelines, small vocabularies |
| Top-p | Adapts to the shape of the distribution | Still admits a long tail when the distribution is flat | Default for most chat products |
| Min-p | Scales with confidence; stable at higher T | Newer, fewer hosted APIs expose it | Creative writing, open-source serving stacks |
| Grammar-constrained decoding | Output always parses | Mask-building cost; can push the model off its natural path | JSON, function arguments, SQL, any machine-read output |

## Real-world examples

- **Measured degeneration.** Holtzman et al. (2019) counted how often GPT-2 Large text ended stuck in a loop (a phrase repeated at least three times at the end): 73.66% of greedy generations and 28.94% with beam width 16, against 0.36% for nucleus sampling at $p = 0.95$ and 0.28% for human text.
- **Translation.** The original Transformer decoded with beam size 4 and length penalty $\alpha = 0.6$ (Vaswani et al., 2017), the length penalty coming from Google's neural machine translation system.
- **OpenAI API.** Chat completions accept `temperature` from 0 to 2 (default 1), `frequency_penalty` and `presence_penalty` from −2.0 to 2.0, `logit_bias` from −100 to 100, and `top_logprobs` from 0 to 20. The reference recommends changing temperature or `top_p`, not both.
- **Providers differ.** Which sampling parameters an API accepts, their ranges and their defaults vary between providers and can change between model versions; some newer reasoning models fix sampling settings and ignore or reject them. Check the current API reference before you tune.
- **Open-source engines.** Min-p sampling is available in Hugging Face Transformers and vLLM, and libraries such as Outlines add grammar-constrained decoding to open models.

## Common pitfalls

- Treating temperature 0 as a guarantee of identical outputs. Batching and kernel choices still change the numbers.
- Turning up temperature for "creativity" without a truncation method, which lets nonsense tokens through.
- Setting temperature and top-p together without testing: their effects compound, and the order they run in differs by engine.
- Using beam search for chat. Higher likelihood is not higher quality for open-ended text.
- Reading logprobs as calibrated probabilities of being correct, especially after RLHF.
- Assuming constrained decoding makes the content right. It guarantees the shape, not the facts.

## How to answer in an interview

1. Start with the loop: logits, softmax, pick a token, append, repeat; mention the KV cache.
2. Write the temperature formula and say what low and high values do.
3. Contrast maximization (greedy, beam) with sampling, and explain why open-ended text needs sampling.
4. Compare top-k, top-p and min-p with a concrete distribution, then mention penalties and logit bias.
5. Close with production concerns: constrained decoding for JSON, logprobs for confidence, and why outputs are not reproducible even at temperature 0.

**What interviewers listen for:** the formula, the reason beam search degenerates on open-ended text, concrete parameter values, and awareness that providers expose different knobs.

**Red flags:** "temperature makes the model smarter", "temperature 0 is always deterministic", or claiming JSON mode guarantees correct values.

  <InterviewQuestion question="Compare top-k, top-p and min-p sampling." category="Concepts" level="Mid">
    All three remove the unlikely tail and renormalize what is left before sampling. Top-k keeps a fixed number of tokens, which is too many when the model is confident and too few when many continuations are reasonable. Top-p keeps the smallest set whose probabilities add up to p, so the set adapts to the shape of the distribution. Min-p keeps tokens whose probability is at least a fraction of the top token's, so the cut scales with confidence and stays sensible at higher temperatures.
  </InterviewQuestion>
  <InterviewQuestion question="Why is beam search standard for translation but rarely used for chat?" category="Trade-offs" level="Mid">
    In translation the input pins down the output closely, so the most likely sequence is usually a good one, and beam search finds higher-likelihood sequences than greedy. In open-ended generation the most likely text is not what people write: it is generic and falls into repetition loops, which Holtzman et al. measured directly. Beam search also costs about B times the compute per step and must finish before it can return the best beam, which hurts streaming. Chat systems therefore sample with temperature and top-p instead.
  </InterviewQuestion>
  <InterviewQuestion question="A model keeps repeating the same sentence. What can you change at decoding time?" category="Failure modes" level="Mid">
    Repetition loops are typical of greedy or low-temperature decoding, because each repeat makes the next repeat more likely. Switching to sampling with top-p or min-p and a moderate temperature usually breaks the loop. A repetition penalty or a frequency penalty lowers the logits of tokens that already appeared, and a stop sequence or max-token limit caps the damage. Tune penalties carefully: too strong and the model avoids words it legitimately needs, like names or code keywords.
  </InterviewQuestion>
  <InterviewQuestion question="You set temperature to 0 but get different answers for the same prompt. Why, and what do you do?" category="Failure modes" level="Senior">
    Temperature 0 removes sampling randomness, but the logits can still differ between runs. Floating-point addition is not associative, and on a shared server the batch size changes with load, which changes how GPU kernels sum numbers; when two tokens are close, the arg-max flips and the rest of the text diverges. Hosted seeds are documented as best effort for the same reason. For reproducibility, log the full request and model version, store outputs for evaluation instead of regenerating them, and when self-hosting use deterministic or batch-invariant kernels with a pinned engine version.
  </InterviewQuestion>
  <InterviewQuestion question="How would you guarantee that an LLM returns valid JSON for a given schema?" category="Architecture" level="Senior">
    Use constrained decoding: compile the schema into a grammar, track the parser state as tokens are generated, and before each sampling step set the logits of every token that cannot continue a valid string to minus infinity. The output then always parses. To keep it fast, precompute for each parser state which tokens are allowed, as Outlines does with finite-state machines, rather than scanning the vocabulary each step. Still validate the values and describe the schema in the prompt, because the mask guarantees structure, not correctness.
  </InterviewQuestion>

But they are not calibrated probabilities of being correct, especially after RLHF; the GPT-4 report showed post-training reduced calibration significantly. Calibrate them on labeled data from your task, and check whether the provider reports them before or after temperature and truncation.
