A benchmark is a fixed exam for models: same questions, same scoring, one number at the end. Interviewers test whether you know why leaderboard scores get misread and what they leave out about your own product.

## Overview

- A **benchmark** is **tasks + a harness + a scoring rule**. Change the prompt wording, the number of worked examples or the answer extraction and the same model gets a different score.
- **Public benchmarks** (MMLU: 15,908 questions; GPQA: 448, with a 198-question Diamond subset; SWE-bench Verified: 500 tasks) help you **shortlist** models. Your **own golden set** (Brightpost: 200 tickets) tells you what to **ship**.
- **Contamination** means test items leaked into the training data. A public test set eventually reaches the web crawl; the score then measures memory as well as skill. Detect it with overlap checks, and defend with **private held-out splits**.
- The public order and your order can **differ**. In the illustrative example below a model that is last of three on a public benchmark is first on Brightpost's tickets, by 9 points.
- Report **intervals, paired comparisons and per-slice results**, and run a **fast smoke set on every commit** and a **full suite nightly**.

## Mental model

- **Public benchmark as a driving test:** Standard, comparable, and a good first filter, like passing a driving exam.
- **Golden set as a trial shift:** Passing a driving test does not prove someone can find a flat in the rain at six o'clock with a parcel on the seat; your golden set tests your actual job.
- **Contamination as leaked exam papers:** If the test questions were published in last year's revision guide, a high mark may only mean the candidate memorised the guide.

## Core concepts

- The running example is **Brightpost**, an online shop with a support assistant handling **200,000 requests a day**.
- Its team keeps a **golden set** of **200 real tickets**, each with a reference answer, and uses it to choose between candidate models.

### What a benchmark is made of

- **Suite components:** A suite has **tasks** (inputs with answer keys, or a checker such as unit tests), a **harness** (the code that formats the prompt, calls the model, extracts the answer and scores it) and a **leaderboard** that ranks models by score.
- **MMLU** (Hendrycks et al., 2020): 15,908 multiple-choice questions across 57 subjects, of which 14,079 are the test set (sizes checked 15 November 2026).
- **GPQA** (Rein et al., 2023): 448 multiple-choice science questions written by experts; the **Diamond** subset is 198 of them. In the paper, domain experts scored 65 % and skilled non-experts with unrestricted web access 34 %, which is what "Google-proof" means here.
- **SWE-bench Verified**: 500 software tasks that human annotators checked as solvable and fairly tested; OpenAI announced it with the SWE-bench authors on 13 August 2024. A task passes when the project's tests pass.
- **HELM** (Liang et al.): 42 scenarios, with 7 metrics (accuracy, calibration, robustness, fairness, bias, toxicity, efficiency) measured on its core scenarios. Its repository says it entered maintenance mode on 1 June 2026.
- **Chatbot Arena** (Chiang et al., 2024): not a fixed test but crowdsourced pairwise votes. A user sees answers from two anonymous models and votes; the ranking is estimated with a Bradley-Terry model. The platform has been renamed since the paper, so check its current name.

**How to read it:**

- **Colour roles:** Blue is the data, green the model under test, grey the harness that runs them together, lime the scores, and violet the stored ranking.
- **Why the harness is ringed:** Prompt wording, number of worked examples, sampling settings, and answer extraction all sit in the harness and quietly move the score.
- **Comparability rule:** Two reports of "MMLU" are only comparable if they used the exact same harness settings.

### Scoring methods

- **Grader types:** Automated scoring spans **exact match**, **fuzzy metrics**, **execution-based checks** for code (running unit tests), **LLM judges** with fixed rubrics, and **deterministic validators** such as JSON-schema conformance.
- **Multi-dimensional scoring:** Score several dimensions at once because a model can improve at summarising while silently breaking JSON mode.
- **Version control:** Version every asset (prompts, judge prompts, scoring code) in git with the same discipline as application code.

### Contamination

- **Contamination** is test items appearing in the training data.
- A public test set gets copied, quoted and discussed, and web-scale training crawls it.
- The score then rises without the model getting better at the skill.

### Public against private splits, and detection

- **Public vs private splits:** A **public split** is open for reproducibility and eventually leaks; a **private** (held-out) split is never released and is scored by the maintainer so it stays clean, though outsiders cannot inspect it.
- **Detection tools and limits:** Detect leakage with **overlap checks** (n-grams or embeddings for paraphrases), **clean-versus-dirty score comparisons**, and **canary strings**; however, overlap checks miss paraphrases and require access to the training corpus (unavailable for API models).
- **Dynamic evaluation defence:** Refreshing evaluation sets from licensed or internal text created after the model's training cutoff is the strongest defence against memorisation.
- **Real-world benchmark retirement:** On 23 February 2026 OpenAI stopped reporting SWE-bench Verified scores, citing contamination and flawed tests (59.4 % of 138 problems its o3 model did not solve consistently had substantive test or prompt flaws), recommending SWE-bench Pro instead.

## Architecture

A benchmark practice for a product has two layers: public benchmarks to shortlist, and your own offline suite, in tiers, to decide.

1. **Public benchmarks** narrow many models to a few. Treat the score as a secondary signal, not a verdict.
2. **A frozen holdout** from your own tickets is never used to tune prompts. It guards against overfitting during iteration.
3. **A development set** is where prompts and judges are tuned; it will be overfit, so keep it separate.
4. **A smoke set** of a few dozen cases with deterministic checks runs on every commit in about a minute.
5. **A nightly suite** runs the full golden set, the safety probes and the multilingual slices, and stores score JSON and diffs as artifacts.
6. **A production feed** adds new failures, approved by a person, to the development set (see [Building Eval Datasets](/ai-system-design/genai-system-design/building-eval-datasets)).

## Technical mechanics

### Golden datasets and slices

- **Slice coverage:** Combine broad capability checks with domain scenarios drawn from real failures, edge cases for tool use and structured output, multilingual slices, and safety probes.
- **Case metadata:** Tag each case with difficulty, expected tools, required citations, or numeric tolerances so regressions can be triaged by slice.
- **Preventing dataset rot:** Expert-curated golden sets rot as products and user language evolve; mine new negatives from production with human approval and refresh on a schedule.

### Statistical rigour

- **Intervals and stratification:** Report **confidence intervals** for paired win rates, correct for **multiple testing** across many metrics, and report **stratified** results so aggregate lifts do not hide slice harm.
- **Interval math:** At n = 200 and an accuracy of 0.8, the 95 % interval is 1.96 × sqrt(0.8 × 0.2 ÷ 200) = **±5.5 points**.
- **Power vs runtime:** Larger suites lower variance but slow CI, which is why suites are tiered (see [Automated Regression Testing](/ai-system-design/genai-system-design/automated-regression-testing) for gates and noise bands).

### Making CI fast and stable

- **Execution speed and determinism:** Cache deterministic fixtures, shard across workers, pin judge models and seeds, and retry only known transient provider faults with a cap.
- **Noise-aware gating:** Fail a build on a statistically meaningful drop against a precomputed baseline rather than a single noisy point.

**The numbers:**

- **Confidence intervals:** Using 1.96 × sqrt(p × (1 − p) ÷ 200), the 95 % intervals are ±6.0 for A, ±6.5 for B, and ±5.1 for C.
- **Decision significance:** C leads A by 9 points (exceeding either interval, so the new order is likely real), whereas A vs B (7 points) is borderline and requires inspecting paired flips.
- **Why rankings diverge:** The public test rewards exam-style general knowledge, whereas Brightpost's tickets reward following refund policy, calling the approval tool for order 4471 at £42, and matching tone; the team ships C and adds discovered failures to the golden set.

<Callout tone="red" title="What breaks">
  A team ships the public leader without running its own set, and the assistant quotes the wrong refund limit on a day with 200,000 requests. Separately, a team tunes prompts against the 200 tickets until they pass, then reports that set as its score: the result is overfit. Keep a frozen holdout that nobody tunes on.
</Callout>

## Trade-offs

| Choice | Pros | Cons | When to use |
| --- | --- | --- | --- |
| Public benchmark | Comparable across vendors, free to run | Contamination risk; measures general skill, not your task | Shortlisting models |
| Own golden set | Measures your task and failures | Costs expert time; rots; small, so wide intervals | Choosing and gating releases |
| Private held-out split | Stays clean; resists gaming | Outsiders cannot inspect it; the owner must be trusted | Final gates and leaderboards |
| Dynamic or refreshed evaluation | Newer than any training cutoff | Scores shift between refreshes | Contamination-sensitive decisions |
| LLM-judged suite | Scales to open-ended answers | Judge bias; needs calibration | Quality dimensions with no rule |
| Smoke set on every commit | Fast feedback | Low power; misses small drops | Pull requests |
| Full nightly suite | High power, broad coverage | Slow and costly | Release candidates |

## Production systems

As of November 2026, from each source's own pages:

- **MMLU** (57 subjects, 15,908 questions) and **GPQA** (448 questions, Diamond 198) are the common public knowledge and hard-science benchmarks; GPQA ships with a canary string.
- **SWE-bench Verified** (500 human-validated tasks) became a standard coding-agent benchmark; OpenAI later stopped reporting it, citing contamination and flawed tests.
- **HELM** from Stanford CRFM reports several metrics per scenario instead of one score, and runs public leaderboards.
- **Chatbot Arena** replaces fixed questions with live, crowdsourced pairwise votes, which resist static contamination, with the bias that voters' own prompts and taste shape the ranking.

## Failure modes & pitfalls

- **Quoting a leaderboard number without its harness settings.** Prompt, shots and extraction change it.
- **Tuning on the set you report.** Keep a frozen holdout.
- **Assuming a public set is clean.** If it has been online, test for leakage or use a private split.
- **Reading a 2-point gap on 200 cases as a win.** The interval is ±5.5 points.
- **One aggregate score.** It hides regressions in a slice or a rare costly case.
- **A golden set that never changes.** It rots; refresh it from production with human approval.

## Interview framework

1. Define a benchmark as tasks, a harness and a scoring rule, and say that the harness changes the number.
2. Explain the roles: public benchmarks shortlist, your own golden set decides.
3. Explain contamination, how to detect it (overlap checks, clean against dirty scores, canaries) and the defence (private or refreshed splits).
4. Show the Brightpost example: the public order and your order differ, and the interval says which gap is real.
5. Close with practice: tiered suites, pinned judges, intervals and per-slice reporting.

**What interviewers listen for:** a private holdout, an awareness of contamination, intervals and paired comparison, and treating public scores as secondary.

**Red flags:** "we picked the model at the top of the leaderboard", no frozen holdout, or a single accuracy number with no interval.

  <InterviewQuestion question="A vendor reports 92 % on a well-known benchmark for its new model. What do you ask before believing it?" category="Failure modes" level="Senior">
    - **Harness details:** Ask which split and harness were used, including prompt template, few-shot count, sampling parameters, and answer extraction logic.
    - **Contamination checks:** Ask whether the test set was public, whether training overlap was measured, and what the clean-subset score, private-split ranking, and confidence intervals look like.

    - **Private holdout with canaries:** Keep an internal held-out ticket set that is never published or pasted into external prompts, and embed canary strings to test memorisation.
    - **Quarterly dynamic refresh:** Build a fresh slice every quarter from expert-labelled tickets created after the candidate model's training cutoff.
    - **Paired, audited scoring:** Score all candidates on the same pinned harness with intervals and paired comparisons, track offline-to-online correlation, and retire any set whose scores drift up without product gains.
