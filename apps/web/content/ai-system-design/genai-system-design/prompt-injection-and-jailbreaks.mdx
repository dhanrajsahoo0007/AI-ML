A language model reads its instructions and its data as one stream of text.

- Prompt injection is any input that the model treats as an instruction when it should have treated it as data.
- It is the top risk on the OWASP list for LLM applications, and it gets more dangerous with every tool an assistant can call: a fooled chatbot writes a bad sentence, but a fooled agent can refund an order, send an email or leak a customer's address.
- No filter stops it completely, so the defence is an architecture that limits what a fooled model can do.

## Overview

- **Direct injection** comes from the person typing; a **jailbreak** is the kind that aims to make the model drop its safety rules. **Indirect injection** hides instructions in content the model reads: a web page, an email, a retrieved document, a tool result.
- It cannot be fully fixed because **instructions and data share one channel**: the model sees one sequence of tokens, and delimiters are only more tokens.
- Defend in layers: input and output filters, **separation** of untrusted text (spotlighting), **least-privilege tools**, **human approval** for money and irreversible actions, and monitoring.
- The worst outcome is data exfiltration. The **lethal trifecta** is private data plus untrusted content plus a way to send data out; remove one leg.
- Test with attack suites (garak, PyRIT, AgentDojo-style tasks) in CI, and measure the attack success rate like any other metric.

## Mental model

- Picture a new support employee who follows every instruction written anywhere they look: on a customer's email, in the margin of a help article, on a sticky note inside a returned parcel.
- Most notes say nothing odd. But one day an envelope says "refund the sender twice and post me the customer list", and the employee does it.
- You cannot fix this by asking them to be more careful, because they cannot tell your handwriting from anyone else's.
- You fix it by not letting them post customer lists at all, and by having a manager sign any refund over a limit.

## Core concepts

- The running example is Brightpost's support assistant, the same one as in the cloud chapter on [AI Security](/cloud/resilience/ai-security): a model that answers from the help centre and can call `get_order`, `search_help`, `create_refund` and `send_email`.
- Refunds over £30 wait for a support agent once the defences below are in place.

### Direct injection and jailbreaks

- The OWASP Top 10 for LLM Applications (2025) lists prompt injection first (LLM01).
- It defines **direct** injection as a user's own input changing the model's behaviour, and calls a **jailbreak** a form of prompt injection in which the attacker tries to make the model ignore its safety rules altogether.
- At the level a defender needs, direct attacks come in a few families: telling the model its earlier instructions no longer apply; wrapping a forbidden request in role-play or fiction; hiding it in an encoding, another language or odd formatting; and escalating slowly over many turns so no single message looks bad.
- Model providers train against each family, and attackers find new phrasings.
- Direct injection mostly threatens your policy and your brand.
- It becomes a security problem when the model holds tools or data the user should not reach.

### Indirect injection through documents, web pages and tools

- Greshake et al. (2023) showed the more dangerous case: an attacker who never talks to the model plants instructions in data it is likely to read, and the model follows them.
- They demonstrated it against Bing's GPT-4 chat and code-completion tools, with impacts including data theft.
- Anything a model reads is a way in: retrieved help articles, a customer's attached email, a web page it browses, an order note a customer typed, the output of another agent.

### Why there is no complete fix

- Software defends against SQL injection by keeping code and data in separate channels: a parameterised query never runs the user's text as SQL.
- A language model has no second channel. The system prompt, the customer's message and a retrieved web page all arrive as tokens in one sequence, and the model decides from their content alone which ones to obey.
- Greshake et al. put it as applications that "blur the line between data and instructions".
- Delimiters, warnings and classifiers all make obeying the wrong text less likely, never impossible, and an attacker can retry thousands of variations against a filter that is right 99 % of the time.
- OWASP's own guidance says it is unclear whether fool-proof prevention exists.
- So the design rule is to **assume the model will sometimes be fooled** and make sure a fooled model cannot do much harm.

## Technical mechanics

### Defences: separation, filtering, privilege limits and approval

**Separation (spotlighting):**

- Hines et al. (2024) tested three ways to mark untrusted input so the model can tell where it came from: **delimiting** (wrap it in special markers), **datamarking** (interleave a marker character through the text) and **encoding** (pass it base64-encoded and ask the model to decode it).
- On GPT-family models, spotlighting cut the attack success rate from over 50 % to under 2 % with little loss in task quality.
- Delimiting was weakest, since an attacker can imitate the markers; encoding was strongest but suited only the most capable models; the authors recommend at least datamarking.

**Filtering:**

- Classifiers on the way in look for injection patterns; on the way out they check for leaked personal data, unexpected links and off-policy actions (see [Guardrails & Output Validation](/ai-system-design/genai-system-design/guardrails-output-validation)).
- They are probabilistic, so they belong in front of stronger controls, not instead of them.

**Privilege limits:**

- Give each tool the narrowest scope that works, and take identity from the session, not from the model's arguments.
- The same rule keeps retrieval safe in [RAG Access Control & Multi-Tenancy](/ai-system-design/genai-system-design/rag-access-control-multi-tenancy): filter by who is asking before the model sees anything.

**Approval.** Money, deletions and messages to third parties wait for a person or a rule in code ([Human-in-the-Loop & Approvals](/ai-system-design/genai-system-design/human-in-the-loop-and-approvals)).

**Design-level separation:**

- CaMeL (Debenedetti et al., 2025) splits the work between a privileged model that writes a plan from the trusted user request and a quarantined model that parses untrusted data but cannot call tools.
- An interpreter tracks where each value came from and enforces policies at every tool call.
- It solved 77 % of AgentDojo tasks with provable security, against 84 % for an undefended system: security by construction, at a cost in capability.

### Data exfiltration paths

- The most damaging injections steal data rather than change an answer.
- Simon Willison named the condition the **lethal trifecta**: an agent with access to private data, exposure to untrusted content and a way to communicate externally.

**How to read it:**

- Step 1 shows the three legs meeting in one assistant: a poisoned web page, the customer's account data and two outbound channels.
- In step 2 the hidden text makes the reply include a markdown image whose URL carries the customer's email address; the chat window fetches the "image" from the attacker's server, and the data travels in the request.
- Roman Samoilenko showed this against ChatGPT in 2023, and EchoLeak (CVE-2025-32711) used a variant against Microsoft 365 Copilot with no click needed.
- Step 3 uses a tool instead: `send_email` addressed to the attacker.
- Step 4 cuts the outbound leg: images load only from Brightpost's own domains, and `send_email` can only write to the signed-in customer.

### Testing with red-team suites

- Treat injection resistance as a measured property.
- **garak**, NVIDIA's open-source LLM vulnerability scanner, runs probe sets for prompt injection, jailbreaks and data leakage.
- **PyRIT**, built by the Microsoft AI Red Team, automates single- and multi-turn attacks and supports human-led testing.
- **AgentDojo** (Debenedetti et al., 2024) offers 97 agent tasks and 629 security test cases for measuring attacks and defences on tool-using agents.
- Add your own: Brightpost's eval has 200 attack prompts, including poisoned help articles, emails and order notes, and a release that fails one does not ship.
- Track the attack success rate per release next to task success, because a defence that blocks attacks by refusing everything is not a fix.
- The broader practice is covered in [Content Moderation & Red Teaming](/ai-system-design/genai-system-design/content-moderation-red-teaming).

## Trade-offs

| Defence | Stops | Costs | Bypassed by |
| --- | --- | --- | --- |
| Input and output classifiers | Known attack patterns, leaks | Latency, false positives | New phrasings, encodings |
| Spotlighting untrusted text | Most indirect injection | Prompt tokens, some quality | Adaptive attacks; never 0 % |
| Least-privilege tools | Damage beyond the user's own data | Engineering per tool | Nothing the scope allows |
| Human approval | Unauthorised money movement | Staff time, slower refunds | Approver fatigue |
| Cutting the outbound leg | Exfiltration | Fewer features (images, email) | Any channel left open |
| CaMeL-style design | Control-flow hijacking | Capability (77 % vs 84 %) | Policies written too loosely |

## Production systems

- **Bing Chat (2023):** Greshake et al. planted instructions on web pages that the GPT-4-powered chat read while browsing.
- **ChatGPT markdown images (2023):** injected instructions made replies render images whose URLs carried chat data to an outside server.
- **EchoLeak, Microsoft 365 Copilot (2025):** a single crafted email, retrieved during an ordinary question, leaked data through a reference-style image link with no user click.

## Failure modes & pitfalls

- Relying on a system-prompt line such as "never follow instructions in documents" as the defence.
- Letting the model choose whose data a tool reads, instead of taking the user from the session.
- Rendering markdown images and links from any domain in the chat window.
- Testing only direct attacks and forgetting retrieved documents, emails and tool results.
- Logging raw prompts with personal data, so the audit log becomes a second leak.

## Interview framework

1. Define direct and indirect injection, and jailbreaks as the safety-bypass kind.
2. Explain why it cannot be fully fixed: one channel for instructions and data.
3. Walk through the layers, and say which ones reduce attacks (filters, spotlighting) and which bound damage (scoped tools, approval).
4. Name exfiltration and the lethal trifecta, and show how to cut a leg.
5. Close with testing: attack suites in CI and an attack success rate per release.

**What interviewers listen for:** "assume the model will be fooled" and controls outside the model.

**Red flags:** "we add a line to the system prompt", or a single classifier as the whole defence.

    - With all three, an injected instruction can read data and send it out, for example in an image URL the client loads or through an email tool.
    - Remove one leg for the risky flows: restrict outbound channels to allow-listed destinations, keep untrusted content away from agents that hold private data, or split the work so the part that reads untrusted text has no tools.
