A connector is the code between a source system and your pipeline: it authenticates, finds what changed, fetches it within the source's limits and hands over one clean document. Every RAG index and feature pipeline is only as fresh and as correct as its connectors, so this page covers what they must do and how they fail.

## TL;DR

- Production systems read from many sources at once: **operational databases, object stores of documents, event streams, SaaS APIs and ad hoc files**. Connectors are the boundary between them and your pipelines.
- The hard part is not reading once but **staying in sync** with acceptable lag, cost and correctness.
- Three ways to learn about changes: **change data capture** (CDC) from a database log, **webhooks** pushed by the source, and **polling** with a saved cursor.
- Every connector has five duties: **auth, incremental sync, rate limits, deletes and permissions**. Missing deletes and permissions are the two that cause incidents.
- Output **one normalised document format**, and land raw payloads so you can replay. Buy connectors for common sources, build them for proprietary or tightly secured ones.

## The idea in plain English

Imagine a newspaper's clipping service. Every morning it could re-read every newspaper ever printed to find today's stories, or it could ask each paper "what did you print since yesterday?". The second is far cheaper, but it only works if each paper keeps a reliable list of new pages, and it never tells you which old stories were retracted. A connector is that clipping service for your data: it decides how to ask each source what changed, and it must find out about retractions some other way.

## Core concepts

The running example is Brightpost's help assistant. Its knowledge comes from four places: the help-centre CMS (**1,200 articles**), a ticketing system with solved tickets, an internal wiki with support runbooks, and a shared drive of PDFs and slides.

### Sources and what they give you

Production ML systems rarely sit on a single tidy table. They ingest operational databases, object stores full of documents, event streams, SaaS APIs, and ad hoc files. Structured data usually arrives with explicit schemas. Unstructured data such as PDFs, HTML, images and chat logs needs parsing, normalisation and often enrichment before it is model-ready ([Document Processing & Chunking](/ai-system-design/genai-system-design/document-processing-chunking) covers that step).

### Three ways to learn about changes

- **Change data capture (CDC)** reads a relational database's transaction log. It minimises load on the primary database and captures inserts, updates **and deletes** in order, which matters when downstream features depend on temporal consistency.
- **Webhooks** (push subscriptions) let the source call you when something changes. They cut latency but need a durable endpoint, signature verification, and replay handling when delivery fails.
- **Scheduled polling** is for APIs and legacy systems that only expose pull. It is simpler to reason about but costs more, and it can miss rapid changes between polls unless you track high watermarks carefully.

### Incremental sync with a cursor

A **cursor** (or high watermark) is the last position a connector has read: usually the largest `updated_at` value it saw, sometimes an opaque token the API returns. The next run asks only for records past the cursor, then saves the new one. Here is the difference it makes for the help centre.

<Callout tone="red" title="What breaks">
  Cursor-based sync never sees a hard delete, so the deleted article's 3 chunks stay in the index and keep being cited.
  Two more traps: two records with the same `updated_at` across a page boundary (compare with "greater than or equal"

</Callout>

### Schema evolution

Schema evolution is a first-class concern. Additive columns are easy; renames, type changes and nested structure drift break naive consumers. Version your data contracts, run compatibility checks in CI, and keep transformation layers that tolerate several schema generations during a rollout. For document sources the "schema" is the API's JSON shape and the HTML template, and a CMS redesign can break a parser as surely as a renamed column.

## Architecture

Each source gets its own connector, and every connector does the same five jobs around one fetch loop.

/>

**How to read it.** Step 1 shows four sources with four different APIs feeding one fetch loop. Steps 2 to 6 add a duty each: a scoped, read-only credential; changes since the saved cursor; back-off when the API answers HTTP 429 (Too Many Requests); deletions recorded as tombstones; and each document's access-control list. Step 7 is the contract with the rest of the system: one normalised document (id, source, URL, title, text, updated time, ACL, deleted flag) that the ingestion pipeline parses, chunks, embeds and indexes.

The connector is the first stage of the [RAG pipeline](/ai-system-design/genai-system-design/rag-fundamentals): everything after it inherits a missed delete or a missing ACL, all the way to the answer.

## Deep dive

### Rate limits, retries and idempotency

SaaS APIs cap requests per minute and return HTTP 429 when you exceed the cap, often with a `Retry-After` header. Back off with jitter, keep a request budget per source and per tenant, and run work through a durable queue or workflow engine so a retry repeats a step instead of the whole sync. Make writes idempotent: upsert by document id and version, so fetching the same page twice changes nothing. A first backfill is where limits bite: at an illustrative 100 requests a minute, fetching 1,200 articles one by one takes about 12 minutes; a 50,000-ticket history takes over 8 hours.

### Deletes and permissions

These are the two duties that a "fetch new content" connector forgets. A delete must reach the index as a tombstone, or the chunk lives on (see [Index Freshness & Updates](/ai-system-design/genai-system-design/index-freshness-and-updates)). Permissions must be captured with the content and synced on their own schedule, because an ACL change does not always touch `updated_at`. Brightpost's runbook is only safe if the wiki connector copies its "support staff only" ACL onto every chunk; [Access Control & Multi-Tenancy](/ai-system-design/genai-system-design/rag-access-control-multi-tenancy) shows what happens in the gap.

### Landing raw data

Teams often land raw data in a data lake for flexibility and keep a warehouse or curated marts for query performance and governance. For a RAG pipeline the same idea applies: store each raw payload (the API's JSON, the original PDF) before parsing, keyed by source, id and version. When the parser or chunker improves, you rebuild from the lake instead of re-crawling every source within its rate limits. Keep raw payloads only as long as your retention policy allows.

### Watching connectors

Connectors fail quietly: an expired token or a changed API does not break the answer, it only stops new content from arriving. Track per source the age of the cursor (now minus the newest change read), records fetched per run against their usual range, the rate of 429 and 5xx responses, and the gap between the source's id count and the index's (1,200 articles in the CMS should mean 1,200 documents in the index). Alert on the cursor age first: it is the one number that catches every kind of stall.

## Trade-offs

| Decision         | Option A                   | Option B              | Guidance                                                                                           |
| ---------------- | -------------------------- | --------------------- | -------------------------------------------------------------------------------------------------- |
| Change detection | CDC or webhooks            | Polling with a cursor | Push where the source supports it; poll with a cursor otherwise, and reconcile periodically        |
| Sync scope       | Incremental                | Full                  | Incremental for every run; a periodic full id listing to catch deletes and drift                   |
| Buy vs build     | Managed connector platform | Custom connector      | Buy for common SaaS sources; build for proprietary protocols, strict cost or tight security models |
| Raw landing      | Keep raw payloads          | Parse and discard     | Keep them: replays are cheaper than re-crawls                                                      |

Managed connector frameworks such as Airbyte and Fivetran shorten time to value with prebuilt sources, scheduling and monitoring. Custom connectors win when you need proprietary protocols, aggressive cost control, or tight coupling to internal security models. The trade-off is operational burden against control: frameworks reduce engineering toil but can hide failure modes, lock in certain semantics, and charge per row or per connector in ways that do not scale for very high-cardinality streams.

## Real-world examples

- **Airbyte's** incremental sync filters on a cursor field such as `updated_at`, roughly "rows where the cursor is at least the last value seen", and points to log-based CDC for the cases a cursor cannot handle.
- **Debezium** connectors read a database's transaction log (the MySQL binlog, the PostgreSQL logical replication stream) and publish each change, deletes included, to Kafka.
- **Enterprise search and RAG products** (Azure AI Search indexers, Microsoft Graph connectors) sync content and permission metadata from sources such as SharePoint, and show results only to users the synced permissions allow.

## Common pitfalls

- Treating the first full load as the design and bolting on incremental sync later.
- Cursor sync with no delete path, so removed documents keep being retrieved.
- Dropping the source's permissions at the connector.
- No raw landing, so every parser fix means re-crawling every source.
- Retries that are not idempotent and create duplicate documents.

## How to answer in an interview

1. List the sources and, for each, how it can report changes (log, webhook, pull-only API).
2. Describe the connector duties: auth, cursor-based incremental sync, rate limits, deletes, permissions.
3. Define the normalised document and where raw payloads land.
4. Say how you detect a broken connector: lag per source, error rate, and a periodic reconciliation of ids.
5. Give a buy-versus-build call with a reason.

**What interviewers listen for:** deletes and permissions mentioned without prompting, and a cursor that survives restarts.

**Red flags:** "we re-crawl everything nightly" with no cost estimate, or no answer for deleted data.

  <InterviewQuestion question="When would you prefer CDC over nightly batch extracts from an OLTP database?" category="Architecture">
    CDC is preferable when you need fresher features or analytics with lower load on the production database, when deletes matter for correctness, or when row-level ordering is important for downstream deduplication. Nightly batches are simpler and cheaper for low freshness requirements and small tables, but they stress the database with large scans and can miss intraday changes unless you add incremental logic anyway.
  </InterviewQuestion>
  <InterviewQuestion question="How do you integrate a SaaS API that rate-limits aggressively and returns paginated JSON?" category="Integration">
    Use a durable queue or workflow engine so retries are idempotent, persist cursors or updated-at watermarks per object type, backoff with jitter on 429 responses, and shard work across workers respecting per-tenant limits. Normalize responses into a staging schema, validate against a contract, and log raw payloads briefly for forensic replay while respecting retention policies.
  </InterviewQuestion>
  <InterviewQuestion question="What are the main trade-offs between buying a connector platform and building custom ingestion?" category="Trade-offs">
    Purchased platforms reduce engineering time, ship monitoring and many sources, and centralize connector maintenance. Custom builds optimize for proprietary formats, strict latency or cost targets, and security constraints such as air-gapped deployments. The risk of platforms is opaque failure handling, pricing that grows with volume, and limited control over backpressure semantics; custom code trades faster iteration on features for ongoing maintenance every time an upstream API changes.
