A model, benchmark score, or RAG answer is trustworthy only when you can prove which data produced it.

- Data versioning keeps every dataset snapshot reachable, while lineage records how each version was built so you can reproduce results and roll back bad changes.

## Overview

- Machine learning experiments are only **reproducible** if you can reconstruct the exact inputs and code that produced a model.
- **Content addressing** (DVC) and **branches over object storage** (LakeFS) give every data version a stable id without putting terabytes in Git.
- Treat used datasets as **immutable**: append new versions with metadata, never overwrite a snapshot in place.
- **Lineage** connects sources through transformations to features, training sets, models and, in RAG, to every chunk and answer.
- For RAG, version the **index** too: each snapshot records its embedding model and corpus version, so a bad re-embed is undone by pointing back at the previous snapshot.

## Mental model

- **The lab notebook analogy:** A good lab notebook records which batch of chemicals went into each experiment so anyone can repeat it or diagnose what went wrong.
- **Data versioning:** Keeps every batch on the shelf with a permanent label that never changes.
- **Lineage:** Acts as the notebook itself, recording which batches and transformation steps produced each result.
- **Why both matter:** Without both immutable batches and step-by-step provenance, a claim like "it worked last month" cannot be verified.

## Core concepts

The RAG examples use the running example of these pages: Brightpost's help centre of **1,200 articles**, cut into **3,600 chunks** of 400 tokens and embedded into a vector index.

### Content addressing

- **Hash-based identity:** Data versioning tools such as DVC treat large artifacts as **content-addressed** blobs—each file is identified by a hash of its bytes, and a small metadata file holding that hash is committed to Git while the data lives in a cache and remote store.
- **Verifiable diffs:** Diffs stay reviewable without committing terabytes, and two machines (or the same machine two months later) can prove they refer to identical bytes even if file paths differ.
- **Per-document RAG hashing:** A hash of each article's text tells you which of the 1,200 articles changed since the last build (see [Index Freshness](/ai-system-design/genai-system-design/index-freshness-and-updates)).

### Branches and snapshots over object storage

- **Git-like lake branching:** LakeFS layers Git-like branching over object storage so teams can isolate ETL changes on a branch, run experiments on snapshots, and merge curated datasets with atomic promotions without copying data.
- **Complementary safeguards:** Object-store branching and DVC complement rather than replace database migrations and contract tests—migrations guard the live schema while versioning guards historical snapshots.

### Immutable datasets and schema versions

- **Never overwrite in place:** Once a snapshot is used for a benchmark or a regulatory submission, treat it as immutable and append new versions with explicit metadata (schema hash, row counts, and sampling strategy).
- **Schema registries:** Track schema versions explicitly in Avro, Protobuf, or JSON Schema registries so producers and consumers negotiate compatibility rules rather than failing silently when a new column appears.

### Lineage graphs

- **End-to-end provenance:** Lineage graphs connect raw sources through transformations to features, training sets, and exported models.
- **OpenLineage standard:** Describes each step as a job, its execution as a run, and its inputs and outputs as datasets, unifying metadata across Spark, dbt, and orchestrators such as Airflow.
- **Impact analysis:** Answers blast-radius questions such as which models and dashboards depend on a deprecated source column.

**How to read it:**

- **Step 1 (User answer):** Shows what the user saw—the answer, its trace id, citation `[2]`, and the prompt version.
- **Step 2 (Chunk and index):** Follows the citation to chunk 2 of the article (the 400 tokens from 350 to 750) and records which embedding model embedded it and which index snapshot served it.
- **Step 3 (Document version):** Finds the document version that chunk was cut from, identified by its content hash and the corpus version that included it.
- **Step 4 (Source record):** Reaches the record in the help-centre CMS—revision 7, who edited it, and who may read it.

**The numbers:**

- **Chunk offsets:** Chunks start every 400 − 50 = 350 tokens, so chunk 2 spans tokens 350 to 750.
- **Lookup cost:** Each hop is a single id lookup; nothing is recomputed or guessed.

<Callout tone="red" title="What breaks">
  If the chunk id is derived from its position alone, re-chunking reuses "a-0412#2" for different text, and an old trace points at the wrong words. Fix: store the chunk's own content hash and the document version beside its id, and keep both in the answer log.
</Callout>

### Reproducibility

- **Sources of nondeterminism:** Reproducibility breaks when floating-point summation order varies across hardware, distributed shuffles run without fixed seeds, splits are time-dependent ("the last 30 days" shifts daily), or vendor snapshots update silently.
- **Countermeasures:** Record random seeds, pin dependency and model versions, write split boundaries as fixed dates, and hash any external extract on arrival.

## Architecture

In RAG, every arrow of the ingestion lane is a lineage edge. Record a version at each one and the lineage figure above comes for free.

<AnimatedDiagram spec="animated/rag/pipeline" path="sources>parse>chunk>embed>index" caption="Each step of ingestion produces a new version of the data; record its id, its input's id and the code version." />

What to record at each step:

- **Sources → parse:** the source record id and revision, the parser version, and a content hash of the parsed text.
- **Parse → chunk:** the chunker settings (400 tokens, 50 overlap) and each chunk's id, span and content hash.
- **Chunk → embed:** the embedding model name and version; vectors from two models cannot be mixed.
- **Embed → index:** the snapshot id, built from one corpus version with one model.
- **Answer time:** a trace with the question, the snapshot that served it, the chunk ids, the prompt version and the LLM version.

## Technical mechanics

### Versioning a RAG index: snapshots and rollback

An index that is updated in place has no past: after a bad change there is nothing to return to. Treating each build as an immutable snapshot, and sending questions through an alias, makes rollback one move.

<AnimatedDiagram spec="animated/rag/index-snapshots" stepper caption="A snapshot that is never changed in place can be returned to in one move; the alias is the only thing that changes." />

**How to read it:**

- **Step 1 (Active alias):** Shows two snapshots, each labelled with its embedding model and corpus version; the live alias points at snapshot 2.
- **Step 2 (New build):** Builds snapshot 3 with a new embedding model from the same corpus—changing one thing at a time—and moves the alias to it.
- **Step 3 (Regression detected):** Runs the golden set of evaluation questions on snapshot 3 and finds recall@5 down (see [RAG Evaluation](/ai-system-design/genai-system-design/rag-evaluation)).
- **Step 4 (Instant rollback):** Points the alias back at snapshot 2 while keeping snapshot 3 around for debugging.

**The numbers:**

- **Re-embed volume:** Snapshot 2 re-embedded only the 12 changed articles × 3 = 36 chunks; snapshot 3 re-embedded all 3,600 chunks (1.44 million tokens).
- **Recall drop:** The recall figures (0.84 → 0.71) are illustrative.
- **Storage footprint:** Raw vectors take about 22 MB per snapshot, so keeping three costs about 66 MB—storage is rarely the reason to delete old snapshots.

<Callout tone="red" title="What breaks">
  Switching the alias without switching the question embedder: snapshot 2 needs questions embedded by embed-v2. Fix: version the alias and the query-side model together, as one deployment.
</Callout>

### Governance

- **Auditability:** Governance adds retention policies, access logs, and PII tagging so lineage is both technical and auditable.
- **Right to erasure:** When a customer asks for their data to be removed, the lineage graph lists every chunk, snapshot, and training set that holds it.
- **Snapshot expiry:** Snapshots kept for rollback must still honour deletions and retention rules, so give each snapshot an explicit expiry date.

### Where lineage has gaps

- **Ungoverned ML paths:** Completeness breaks across ad hoc notebooks, third-party SaaS extracts, and manual human labels unless ingestion is forced through governed paths.
- **RAG blind spots:** A document pasted into the index by hand, or a connector that does not report revisions, leaves a lineage hop with no id.

## Trade-offs

| Decision | Option A | Option B | Guidance |
| --- | --- | --- | --- |
| Keep many snapshots vs few | Easy rollback and audits | Lower storage cost | Keep recent ones and those used for releases; expire the rest |
| Catalogue every query vs only pipelines | Complete lineage | Faster exploration | Govern production paths; let notebooks stay light |
| DVC vs LakeFS | Ties data to code commits in one repo | Branches over a shared data lake | Many teams use both |
| Index snapshots vs in-place updates | One-move rollback | Less storage, simpler | Snapshot for model or chunking changes; incremental updates within one |
| Fast tooling vs strict process | Engineers use it | Full auditability | Make the governed path the fastest path |

## Production systems

- DVC commits small metadata files with an md5 hash to Git while the data goes to a cache and a remote store.
- LakeFS offers branches over object storage with zero data copy and rollback after a data incident.
- OpenLineage, an LF AI & Data Foundation project, lists integrations for Airflow, Spark, dbt, Flink and Trino.
- Vector search services such as Elasticsearch and OpenSearch support index aliases, the switch used in the snapshot figure.

## Failure modes & pitfalls

- Overwriting a dataset or an index that a benchmark or a release already used.
- Chunk ids that change meaning when chunking changes.
- Logging the answer but not the snapshot, chunk ids and prompt version behind it.
- Rolling the index back without rolling the query embedder back.
- Lineage that stops at notebooks, SaaS extracts and hand labels.
- Keeping snapshots forever, so deletion and retention rules are broken.

## Interview framework

1. Start with the goal: reproduce a result, explain an answer, undo a change.
2. Explain content addressing and immutable versions with metadata.
3. Draw lineage from source to model or answer, and say what id is recorded at each hop.
4. For RAG, version the index as snapshots behind an alias, with the embedding model and corpus version recorded.
5. Cover governance (retention, access logs, PII, deletion) and the cost trade-offs.

**What interviewers listen for:** immutability, ids recorded at write time, and a rollback that takes one step.

**Red flags:** "we keep the latest data in S3" with no versions, no lineage and no way to reproduce last month's result.

  <InterviewQuestion question="Why is content addressing useful for large training datasets?" category="Reproducibility">
    - **Byte-level verification:** Content hashes let you verify that two machines—or the same machine two months later—refer to identical bytes even if file paths differ.
    - **Immutability and deduplication:** Hashing prevents accidental overwrites, supports deduplication across experiments, and provides a stable identifier to log next to model checkpoints.
    - **Human discoverability:** Pair cryptographic hashes with human-readable aliases or tags so scientists can discover datasets without memorizing digests.
  </InterviewQuestion>
  <InterviewQuestion question="How does LakeFS differ from only using DVC for data versioning?" category="Tooling">
    - **LakeFS (data-lake layer):** Operates with branches, merges, and isolation for ETL jobs against object storage, supporting multi-team workflows on shared tables.
    - **DVC (Git-centric layer):** Sits closer to Git-centric ML projects and excels at tying specific data revisions to code commits for single-repo experiments.
    - **Combined usage:** Many organizations use both—LakeFS for warehouse-scale isolation and DVC for project-scoped experiment bundles.
  </InterviewQuestion>
  <InterviewQuestion question="What metadata belongs on a lineage edge between two pipeline tasks?" category="Governance">
    - **Core execution metadata:** Capture source and destination identifiers, transformation name and version, runtime environment fingerprint, start and end timestamps, row counts or byte metrics, and success status.
    - **Compliance metadata:** For regulated workloads, also log operator identity, purpose codes, and whether PII was transformed or masked.
    - **Blast-radius analysis:** Rich edges make impact analysis accurate when you need to invalidate downstream assets after a bad ingest.
  </InterviewQuestion>
