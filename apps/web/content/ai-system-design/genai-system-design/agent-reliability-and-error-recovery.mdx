An agent that works in a demo can still fail one customer in three. Each step can go wrong, and a long run has many steps. This page covers why errors compound, how to retry a tool call without doing it twice, how to survive a crash, how to stop a loop that is going nowhere, and how to measure whether the agent is dependable. Interviewers ask about it because it separates a prototype from a system that moves money.

## TL;DR

- If each step succeeds with probability p, a run of n steps succeeds with **pⁿ**. At 95 % per step, 20 steps finish cleanly 0.358 of the time. Shorter runs and better steps both help.
- A **timeout does not mean failure**. The tool may have acted. Retry only with an **idempotency key**, an id the service uses to spot a repeat, built and saved before the first call.
- **Checkpoint** after every step, so a crash costs one step, not the run. Durable execution engines do this for you.
- **Budgets** cap turns, tokens and time. **Breakers** stop a loop that repeats the same call or failure.
- **Verify** against the world, not the model's own claim. Measure with **pass^k**: the chance that k runs in a row all succeed.

## The idea in plain English

Think of a relay race with 20 runners who each drop the baton one time in 20. Each runner looks reliable. The team finishes without a drop only about one race in three. An agent run is that relay. Every model call and tool call is a hand-over.

You make the team dependable in four ways: fewer hand-overs, better runners, a rule for picking up a dropped baton safely, and a referee who stops the race when it goes round in circles.

## Core concepts

Every example on this page follows the Brightpost refund from [Agent Architectures](/ai-system-design/genai-system-design/agent-architectures). Customer 1847 writes: "My kettle arrived cracked. It's order 4471. Can I get my money back?" The happy path takes five model calls and four tool calls, and the £42 refund waits for a support agent because it is over £30.

### How errors compound over steps

Assume each step succeeds on its own with probability p, and a run succeeds only if every step does.

  caption="A step that works 95 % of the time sounds reliable, but a 20-step run then finishes cleanly only about one time in three. Moving each step to 99 % lifts the same run to 0.818."
/>

**How to read it.** The horizontal axis counts steps in a row; the vertical axis is the chance that none of them failed. The dashed curve is 95 % per step, the solid one 99 %. Both start at 1.0 and only fall.

**The numbers.** 0.95¹⁰ = **0.599**, 0.95²⁰ = **0.358** and 0.99²⁰ = **0.818**. Going from 95 % to 99 % per step cuts the failure rate per step by five, and lifts the 20-step run from 36 % to 82 %. Halving the run from 20 steps to 10 at 95 % lifts it from 36 % to 60 %.

The model is a simplification. Real steps are not independent: one wrong order number poisons every later step. And some errors are caught and repaired, which is the point of the rest of this page. Anthropic's "Building effective agents" names the same risk: autonomy brings "the potential for compounding errors".

### Tool failures, retries and idempotency

Tool calls fail in three ways, and each needs a different response:

- **Retryable:** a timeout, a 429 rate limit, a 5xx error. Retry with exponential backoff and jitter, a random spread in each wait so clients do not retry in step. Marc Brooker's analysis (AWS, 2015) found backoff without jitter the "clear loser". LangGraph's default retry policy is 3 attempts, starting at 0.5 s and doubling, with jitter on.
- **Fixable by the model:** a missing argument or an unknown order id. Return the error to the model with `is_error: true` and say what to try next. Anthropic's docs report that Claude retries an invalid call 2 to 3 times with corrections.
- **Fatal:** a refused permission or a policy limit. Stop, save state and escalate to a person.

The trap is the timeout. It tells you the reply did not arrive, not that nothing happened. Here `create_refund` times out after the payments service has already paid.

  </StepCard>

The call the harness sends on both attempts. The key is the same both times; that is what makes the second safe:

```json
{
  "tool": "create_refund",
  "input": { "order_id": "4471", "amount": 42.0 },
  "idempotency_key": "run_8f3a:toolu_03"
}
```

Stripe's API is the model to copy. It takes the key in an `Idempotency-Key` header of up to 255 characters, saves the status and body of the first request, returns them to any retry with the same key, and rejects a retry whose parameters differ. Keys can be pruned after 24 hours, so the key only protects retries inside that window.

<Callout tone="red" title="What breaks">
  A key made at call time, such as a fresh UUID per attempt. Every retry gets a new key, and the payments service sees
  two different requests. The key must be durable before the side effect runs: build it in an earlier step and save it
  in the checkpoint, as LangGraph's fault-tolerance guide requires.
</Callout>

### Checkpoints and durable execution

Retries cover a failed call. A **checkpoint** covers a failed worker: the run's state, saved after every step, so another worker can pick it up. [State Persistence & Retrieval](/ai-system-design/genai-system-design/state-persistence-retrieval) builds this in full; here is the same refund run with a crash in the worst place.

<AnimatedDiagram
  spec="animated/agents/checkpoint-timeline"
  stepper
  minWidth={660}
  caption="A crash costs one step, not the run. Worker B starts from cp_4, and the refund it repeats is safe because the key was saved in cp_3, before any money moved."
/>

**How to read it.** Each dot is a checkpoint. Worker A dies after the payments service paid but before `cp_5` was saved. Worker B loads `cp_4` and re-runs only `create_refund`, with the key from `cp_3`, so the payments service answers from its saved reply.

**The numbers** (latencies illustrative: 1.5 s per model call, 0.3 s per tool call). Resuming from `cp_4` repeats one tool call: 0.3 s. Restarting from the message repeats three model calls and two tool calls, 3 × 1.5 + 2 × 0.3 = **5.1 s**, asks the support agent to approve again, and refunds £84 without the key.

**Durable execution** is this pattern packaged as an engine. Temporal records every step in an event history and replays it after a crash; it recommends idempotent activities and suggests the workflow run id plus the activity id as the key. LangGraph saves a checkpoint per step and, on resume, re-runs only the step that did not finish. Neither can close the gap between "the service acted" and "the result was saved". Only the key can.

### Loop, step and budget limits

A run without limits can loop until it runs out of money. Give every run three budgets, checked before each turn: **turns** (model calls), **tokens** and **wall-clock time**, plus a cost cap where calls are priced. "Building effective agents" recommends stopping conditions "such as a maximum number of iterations". When a budget runs out, the run saves its state and hands over to a person; it does not stop in silence. [Loop Engineering](/ai-system-design/genai-system-design/loop-engineering-and-verification-loops#budgets-steps-tokens-wall-clock-time-and-cost-caps) draws the three meters for the bug-fix agent.

Set the budget from data: run the evaluation set, take the 95th percentile of turns for successful runs and add headroom. The Brightpost happy path needs 5 model calls, so an illustrative cap of 12 leaves room for one or two repairs without allowing a runaway.

## Architecture

The reliability layer sits in the harness, around the loop, not in the prompt:

| Layer                | What it does                                                 | On the refund run                                    |
| -------------------- | ------------------------------------------------------------ | ---------------------------------------------------- |
| Tool wrapper         | Timeout, retry with backoff and jitter, error classification | `create_refund` gets 10 s (illustrative), 3 attempts |
| Idempotency          | Key built before the call, sent on every attempt             | `run_8f3a:toolu_03` saved in `cp_3`                  |
| Checkpointer         | State after every step; resume from the latest               | `cp_1` to `cp_7` in Postgres                         |
| Budgets and breakers | Turn, token and time caps; repeat detection                  | 12 turns (illustrative); trip on 3 identical calls   |
| Verifier             | Checks the outcome against the system of record              | Reads refund R-2291 back before replying             |
| Fallback             | Smaller scope, another model, or a person                    | Hand the thread to the support agent                 |

Each layer handles a failure the one before it cannot. Retries handle a flaky call. The key makes retries safe. Checkpoints handle a dead worker. Breakers handle a model that keeps trying the same thing. The verifier catches a run that finished but is wrong.

## Deep dive

### Worked example: the refund run with a timeout and a retry

Follow the [retry figure](#tool-failures-retries-and-idempotency) end to end, with every layer from the table in play.

1. **Calls 1 and 2.** The model calls `get_order(4471)` and `search_help("damaged item refund")`. The harness saves `cp_1` and `cp_2`.
2. **Call 3.** The model asks for `create_refund(4471, 42.00)`. £42 is over £30, so the harness holds the call, builds the key `run_8f3a:toolu_03` and saves both in `cp_3`. The run waits.
3. **Approval.** The support agent approves at 10:20; the harness saves `cp_4`.
4. **The timeout.** The harness sends the refund with the key. The payments service makes R-2291, and the reply is lost. After 10 s (illustrative) the wrapper classifies the timeout as retryable.
5. **The retry.** After a jittered 0.5 s the wrapper sends the same request with the same key. The payments service returns the saved reply: R-2291. No money moves. The harness saves `cp_5`.
6. **Verify.** Before the reply, the harness reads the order's refunds back from the payments service: one refund, £42. The check passes.
7. **Finish.** Call 4 sends the email, call 5 writes the reply. Turns used: 5 of 12.

**The numbers.** The retry cost about 10.5 s of waiting and one extra tool call, and £0. Without the key the same run pays £84 and passes every check that looks only at the transcript.

What if every attempt times out? The wrapper must not tell the model "failed". The model would call `create_refund` again, with a new tool-call id and so a new key. Return the honest state instead:

```json
{
  "type": "tool_result",
  "tool_use_id": "toolu_03",
  "content": "Outcome unknown: the payments service did not reply after 3 attempts. Do not call create_refund again. The harness is checking the refund status.",
  "is_error": true
}
```

The harness then queries the payments service for refunds on order 4471, as LangGraph's guide advises: treat a lost reply as unknown, not as proof that nothing happened.

### Detecting stuck and looping agents

A budget stops a long run; it does not notice a run that is going nowhere. Three signals catch that. The **same tool call** with the same arguments three times in a row: `get_order(4471)` three times means the agent is re-reading, not progressing. The **same failure** three times, by a fingerprint of the normalised error. And **no tool use** for several turns: the agent is talking, not working.

Repeated steps are common: in the MAST study of multi-agent traces, step repetition was 15.7 % of failures ([Multi-Agent Systems](/ai-system-design/genai-system-design/multi-agent-systems#why-multi-agent-systems-fail)). The response to a trip is the same as to a spent budget: save state, stop, and escalate or change strategy. The [breaker figure](/ai-system-design/genai-system-design/loop-engineering-and-verification-loops#circuit-breakers-and-detecting-repeated-failure-loops) shows one tripping on the third repeat.

### Verification steps and self-correction

A model's claim that it succeeded is not evidence. Anthropic's advice is that agents need "ground truth" from the environment at each step. For Brightpost that means reading the refund back from the payments service, not trusting the transcript. For the coding agent it means running the tests.

Self-correction works when the check is external. A failed check goes back to the model as an error with a reason, and the model repairs. A model grading its own work without a new signal tends to approve it ([Planner–Generator–Evaluator Loops](/ai-system-design/genai-system-design/planner-generator-evaluator-loops)). Put deterministic checks first, and a model grader only where no deterministic check exists.

### Measuring reliability: pass^k and consistency

A single success rate hides how often the same task fails on a rerun. Measure **pass^k**, the chance that all k runs of a task succeed, defined by tau-bench (Yao et al., 2024).

<AnimatedDiagram
  spec="animated/agents/pass-k"
  stepper
  minWidth={620}
  caption="Same agent, same 70 % per run. Give it four tries and it almost always passes once (0.992); ask it to pass four times in a row and it manages that only 24 % of the time."
/>

**How to read it.** pass@k, at least one of k runs passing, climbs; pass^k falls. A support agent gets one run per customer, so pass^k is the number that matches what customers see.

**The numbers.** At p = 0.7: pass@4 = 1 − 0.3⁴ = **0.992** and pass^4 = 0.7⁴ = **0.240**. [Agentic AI Evaluation](/ai-system-design/genai-system-design/agentic-ai-evaluation) explains how to estimate it from n runs. Add fault injection to the evaluation set: force a timeout on `create_refund` in one run in four and check that the refund total is still £42.

## Trade-offs

| Choice                        | Gain                                | Cost                                            |
| ----------------------------- | ----------------------------------- | ----------------------------------------------- |
| More retries                  | Fewer failed runs from flaky tools  | Longer waits; unsafe without keys               |
| Checkpoint every step         | Crash costs one step                | A write per step; schema versions to manage     |
| Durable execution engine      | Retries, timers and replay built in | New infrastructure; deterministic workflow code |
| Tight budgets                 | Bounded cost and latency            | Hard tasks stop early and escalate              |
| Verifier on every side effect | Catches wrong outcomes              | One more read per action                        |
| Fallback to a person          | Safe end state                      | Staff time; slower answer                       |

## Real-world examples

- **Stripe** idempotency keys: the reference design for safe retries of payments (as of November 2026).
- **Temporal** runs long workflows as durable executions with automatic activity retries; its docs recommend the run id plus activity id as the key.
- **LangGraph** checkpointers and per-node retry policies, with a fault-tolerance guide on keys and lost acknowledgements.
- **Claude Code** hands control back when its `/goal` loop stops making tool calls, a no-progress breaker ([Loop Engineering](/ai-system-design/genai-system-design/loop-engineering-and-verification-loops)).

## Common pitfalls

- Treating a timeout as "nothing happened" and retrying a side effect without a key.
- A new key per attempt, or a key built inside the step that retries.
- Telling the model a call "failed" when the outcome is unknown; it calls again with a new id.
- Retrying permanent errors (a refused permission) with backoff.
- Restarting a crashed run from the first message instead of the last checkpoint.
- Budgets with no hand-over: the run stops and the customer hears nothing.
- Trusting the transcript instead of reading the result back from the system of record.
- Reporting one success rate instead of pass^k on reruns.

## How to answer in an interview

1. Start with the arithmetic: pⁿ, and 0.95²⁰ = 0.358. Reliability is about steps.
2. Classify failures: retryable, fixable by the model, fatal. Give each its handling.
3. For every side effect, name the idempotency key, where it is built and when it is saved.
4. Add checkpoints and say where the run resumes after a crash.
5. Add budgets, breakers, a verifier and a fallback to a person.
6. Measure pass^k with fault injection.

**What interviewers listen for:** "a timeout is not a failure", a key saved before the call, and verification against the real system.

**Red flags:** "add more retries", or "the model will notice and fix it".
