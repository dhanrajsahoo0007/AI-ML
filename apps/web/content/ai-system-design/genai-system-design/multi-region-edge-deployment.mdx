A web app copies its servers to a second region and is done. An LLM service cannot, because GPUs are scarce in each region, a provider may not host your model there, prompts are personal data, and the KV caches that make follow-up turns cheap stay where they were built. Interviewers ask this to see whether you can place models for latency, residency and failure at once. This page covers what changes for LLMs; the general patterns (DNS, anycast, one writer, replication) are on [Multi-Region, Global Routing and Data Replication](/cloud/resilience/multi-region).

## TL;DR

- **Capacity is the first constraint.** With N regions, each must be sized for the peak split over the survivors: **peak ÷ (N − 1)**. Brightpost's 12 requests/s needs **24 requests/s of capacity across 2 regions (4 GPUs)** or **18 across 3 (3 GPUs)** (illustrative GPU rates).
- **Residency covers prompts, outputs and logs, not weights.** Model weights are identical everywhere; what must stay in a region is the traffic, the vector index and the traces. Provider controls differ, so check each one (as of November 2026).
- **Caches do not travel.** A failover lands conversations on a region with cold prefix caches, so size headroom for the full prefill cost (88 ms per Brightpost request), not the cached cost.
- **Distance adds to time to first token.** A 250 ms round trip on a new connection costs up to **750 ms** before prefill starts; a nearby region costs about 20 ms. Reuse connections and put the gateway in each region.
- **The edge buys the network trip and privacy, not quality.** A small model on the device or an edge site answers easy requests in **152 ms** against **396 ms** from the cloud; hard ones still go to the large model.
- **Health checks must tell a regional outage from a bad model release**, or traffic shifts spread a bad deployment to every region.

## The idea in plain English

Think of a bakery chain that sells one special cake that needs a rare oven. Opening a shop in a second city means buying a second rare oven, and the ovens in a city may be sold out. The recipe book stays the same in every shop, but customers' orders, which name them and their addresses, may have to stay in the local shop's ledger. If one shop burns down, the others must already have spare oven time, or the queue just moves and gets longer. A corner kiosk can sell cupcakes without calling anyone, but it cannot bake the special cake.

## Core concepts

1. **A region is a failure, latency and legal domain.** It is where GPUs, copies of the weights and the prompts of local users live. Treat each as an independent deployment pinned to an immutable model digest.
2. **Geo-DNS or anycast steers users.** Both send a user to the nearest healthy region; the general mechanics are in the [cloud page](/cloud/resilience/multi-region). Health checks decide what "healthy" means.
3. **GPU capacity is regional and lumpy.** A region has a quota and a stock of GPUs; adding a replica may be a request to a provider. A region needs at least one whole GPU (or group), so small fleets round up.
4. **Provider model availability differs by region.** A hosted model may exist in one geography first. Global routing options launch first and cost least; regional ones come later (Azure Foundry docs, November 2026).
5. **Data residency covers more than the request.** Prompts, retrieved chunks, embeddings, outputs, logs, traces and evaluation sets all count. See [Data Privacy & PII Handling](/ai-system-design/genai-system-design/data-privacy-pii-handling).
6. **Regional stores.** Separate vector indexes built only from locally ingested documents, and regional logging sinks. Replicate metadata only where a contract allows it.
7. **KV and prefix caches are local.** They live in a replica's GPU memory. A request that moves region pays full prefill again. See [Load Balancing & Auto-Scaling](/ai-system-design/genai-system-design/load-balancing-autoscaling).
8. **Failover headroom.** The other regions must hold enough spare capacity to absorb the failed one, at its peak, with cold caches.
9. **Edge inference** runs a small quantised model on a device, a point of presence or an on-premises box. Runtimes such as ONNX Runtime and TensorFlow Lite target constrained hardware. The hard part is the update channel, not the model.
10. **Control plane.** A manifest says which model digest is active in each region, promoted region by region to limit the blast radius. The [LLM Gateway](/ai-system-design/genai-system-design/llm-gateway) holds the routing rules.

## Architecture

Brightpost runs a gateway and a GPU pool in each region. A global front door sends each shopper to the nearest healthy region, and the gateway there picks the model.

1. The user's request reaches the global front door.
2. The front door picks the nearest healthy region.
3. That region's gateway applies limits and routes by model and by [fallback rules](/ai-system-design/genai-system-design/multi-model-routing-fallbacks).
4. The engine on local GPUs prefills and streams tokens back.
5. Traces and logs go to a sink in the same region.
6. If the region fails its checks, new requests go to the next nearest region, which must have spare GPUs.

## Deep dive

### What residency covers for an LLM

The cloud section shows the pattern: an allowed-regions guardrail, a data perimeter and keys you hold.

  caption="A region guardrail and a data perimeter keep copies in allowed regions. For an LLM service, the same rules cover the log sink, the vector index and the evaluation set."

**How to read it.** Step 2 of the original is the failure: a tool copies data to a third region. For Brightpost's assistant, replace "analytics store" with "prompt log" or "traces". A debugging copy that leaves the region breaks the rule as surely as the model call would.

Provider controls (checked against official documentation, November 2026):

| Provider | What you can choose | Notes |
| --- | --- | --- |
| Anthropic API | `inference_geo` of `"us"` or `"global"` per request or workspace default; workspace geo (storage) `"us"` only | US-only inference costs 1.1× on Claude 4.6 and later models; rate limits are shared across geos |
| Amazon Bedrock | Geographic or global cross-Region inference profiles | Geographic keeps processing within e.g. US, EU or APAC at standard price; global is about 10% cheaper; CloudTrail records `inferenceRegion` |
| Azure Foundry | Global, Data Zone (US, EU, APAC) or Azure geography deployments | At rest data stays in the geography; processing follows the deployment type; Data Zone interruptions affect all traffic routed to that region |
| OpenAI API | Region choice per project | Which regions cover storage and which cover processing differs; read its data controls guide before promising anything |

Two cautions. A provider's "region" for inference is not your region: if you need Europe-only processing, confirm the exact value your plan supports. And residency of the model call does not cover your own gateway logs, which usually hold the full prompt.

### Edge against cloud: a small model near the user

A device or an edge site removes the long network trip and keeps data local, but it runs a smaller model. The gateway should choose.

<AnimatedDiagram
  spec="animated/serving/edge-cloud-split"
  stepper
  caption="One request on three routes: a phone, a nearby edge GPU and the home-region cloud. Rates are illustrative."
/>

**How to read it.** Each bar is split into network (grey), prefill (teal) and decode (green). Step 1 is an easy request: 300 tokens in, 60 out. Step 2 is Brightpost's full request, on a scale 5 times longer. Step 3 states the routing rule.

**The numbers (all rates illustrative).** Easy request: device 0 + 300 + 1,500 = **1,800 ms**; edge 20 + 12 + 120 = **152 ms** (first token 34 ms); cloud 120 + 12 + 264 = **396 ms**. The edge saves 244 ms: 100 ms of network and 144 ms because its model decodes at 2 ms per token against 4.4. Hard request: device 2,200 + 6,250 = **8,450 ms**; edge 608 ms but with a small model that may get the refund policy wrong; cloud 120 + 88 + 1,100 = **1,308 ms**, inside the 1,500 ms target.

Edge deployments also need an update channel: differential bundles, staged rollouts and signature checks for devices that connect rarely. Large checkpoints should not sit on a generic CDN without signed URLs and byte-range integrity. For making a model small, see [Quantization & Optimization](/ai-system-design/genai-system-design/quantization-optimization) and [Distillation & Small Models](/ai-system-design/genai-system-design/distillation-and-small-models).

### Spare capacity for a failed region

If one of N regions fails, its traffic splits over the other N − 1. Each region is sized for **peak ÷ (N − 1)**, so the fleet carries **peak × N ÷ (N − 1)**.

<AnimatedDiagram
  spec="animated/serving/region-failover-headroom"
  stepper
  caption="Brightpost’s 12 requests/s peak over two regions and over three. Each bar’s line is the capacity the region is sized for."
/>

**How to read it.** Step 1: two regions each carry 6 requests/s; when A fails, B carries 12, which fills it, so each must be sized for 12. Step 2: three regions carry 4 each; after a failure each survivor carries 4 + 2 = 6. Step 3 compares the designs.

**The numbers.** One request is 2,200 × 0.04 ms = 88 ms of prefill (illustrative); keep a GPU under 60% busy. Two regions: 12 × 0.088 ÷ 0.6 = 1.76, so 2 GPUs each, **4 in all**, against 2 for one region. Three regions: 6 × 0.088 ÷ 0.6 = 0.88, so 1 GPU each, **3 in all**. In requests/s the fleets are 24 (2.0× the peak) and 18 (1.5×). More regions lower the spare fraction to 1 ÷ (N − 1), but each region needs at least one whole GPU group, and you pay for every region's gateway, index and on-call. These counts leave out the spare replica each region already keeps for its own failures ([LLM Serving & Inference](/ai-system-design/genai-system-design/llm-serving-inference)).

<Callout tone="red" title="What breaks">
  Failover onto cold caches. The survivors have none of the failed region's prefixes, so every follow-up turn pays full prefill. The sizing above uses the full 88 ms, so it already covers this; sizing with the cached cost (about 11 ms for a second turn) would under-provision by up to 8 times. Also check that the survivors have quota and that the provider has the model in that region.
</Callout>

### Time to first token across regions

A user in Sydney calling London adds a round trip, about 250 ms (the figure on the [cloud page](/cloud/resilience/multi-region)). On a reused connection time to first token is 250 + 88 + 4.4 ≈ 342 ms, just inside the 400 ms target. On a new connection, TCP and TLS 1.3 each take a round trip before the request travels: 3 × 250 + 88 ≈ 838 ms. A region 20 ms away gives 20 + 88 + 4.4 ≈ 112 ms. See [Streaming & Time to First Token](/ai-system-design/genai-system-design/streaming-and-time-to-first-token).

### Keeping versions consistent

Pin each region to an immutable digest, keep a manifest of approved digests per region, and promote one region at a time with checks. A bad model is not a regional outage: health checks should include a canary prompt set so a bad release does not pass as healthy, and a failed region should not receive traffic from a region that is also failing.

### Worked example: Brightpost opens a Sydney region

Brightpost serves London and Sydney shoppers at a 12 requests/s combined peak.

1. **Latency.** Sydney shoppers currently pay 250 ms per round trip, so a new connection puts time to first token at about 838 ms. A Sydney gateway and engine bring it to about 112 ms.
2. **Capacity.** Two regions need 4 GPUs (2 each) to survive a failure; a third region would need 3 in all. Brightpost starts with two and checks GPU quota in Sydney before launch.
3. **Residency.** Australian prompts and traces stay in a Sydney log sink; the Sydney vector index is built only from locally ingested articles. A provider fallback for Sydney traffic must use an allowed geography.
4. **Edge.** The mobile app answers "where is my order?" with an on-device small model when offline; refunds go to the cloud.
5. **Failover.** If London fails, Sydney takes 12 requests/s with cold caches, which the sizing covers.

A gateway route for this follows the shape of the [gateway](/ai-system-design/genai-system-design/llm-gateway) rules (illustrative):

```yaml
route: support-chat
region_preference: [nearest, next-nearest]
allowed_regions: [london, sydney]     # never route outside these
fallback:
  - same model, other allowed region
  - smaller model, same region
logs: regional-sink                    # prompts never leave the region
```

[Capacity Planning & Cost Estimation](/ai-system-design/genai-system-design/capacity-planning-and-cost-estimation) turns the GPU counts into a monthly bill.

## Trade-offs

| Choice | Pros | Cons | When to use |
| --- | --- | --- | --- |
| One region | Cheapest; simple | Far users wait; a region failure is an outage | Early products, one market |
| Two regions, active-active | Lower latency; survives a region | 2× the peak in capacity; two stacks to run | Two markets or a strict availability target |
| Three or more regions | Lower spare fraction (1 ÷ (N − 1)) | More quota, indexes and logs to manage | Global traffic |
| Provider global routing | Best availability and price | Processing location not yours | No residency rule |
| Provider regional or data-zone | Meets residency | Fewer models; later launches; less capacity | Regulated data |
| Edge small model | No network; private | Weaker; update channel; device limits | Easy, private or offline requests |
| Self-hosted per region | Control of data and capacity | You hold GPUs and scale them | High volume, strict residency |

## Real-world examples

- **Anthropic API data residency:** per-request `inference_geo` of `"us"` or `"global"` with a 1.1× price for US-only inference and shared rate limits across geos (documentation, November 2026).
- **Amazon Bedrock cross-Region inference:** geographic profiles keep processing within a geography, global profiles route worldwide for about 10% lower cost, and CloudTrail records the region that served each call.
- **Azure Foundry deployment types:** Global, Data Zone and geography options trade price and availability against processing location.
- **On-device models:** phones and edge appliances run quantised small models through runtimes such as ONNX Runtime or TensorFlow Lite for easy or offline tasks.

## Common pitfalls

- Replicating weights globally but sending prompts, logs or traces to a central sink.
- Sizing every region for its own peak and assuming failover will work.
- Assuming the provider has the same model, quota and rate limits in every region.
- Ignoring cold caches and new-connection round trips when estimating failover latency.
- Health checks that only test "is the endpoint up", so a bad model release spreads everywhere.
- Putting multi-gigabyte checkpoints on a generic CDN without signed URLs and integrity checks.

## How to answer in an interview

1. Ask the constraints: user geography, latency target, residency rules, availability target.
2. Place regions and a front door; keep weights, gateway and stores per region.
3. Size capacity: peak ÷ (N − 1) per region, with GPU counts and quota.
4. Cover residency for prompts, indexes and logs, and the provider's region options.
5. Add the edge for easy or private requests, and the update channel.

**What interviewers listen for:** peak ÷ (N − 1), cold caches on failover, residency beyond the model call, and time to first token including round trips.

**Red flags:** "just replicate everything", treating the edge as a drop-in for the large model, and logging full prompts centrally.
