A RAG system is only as accurate as the freshness of its index: the moment a policy, price, or help article changes in the source system, old vectors serve confident, cited, wrong answers.

- Interviewers ask how you detect edits and deletions, re-embed only what changed, and bound the staleness window without re-indexing the entire corpus.

## Overview

- **Event-driven incremental updates + periodic reconciliation:** Use webhooks or change data capture (CDC) for low-latency updates (seconds to minutes) and a scheduled content-hash scan to catch missed events and deletions.
- **Content-hash diffing:** Store a SHA-256 hash of each document and chunk so workers re-chunk and re-embed only modified spans (1% of the corpus instead of 100%).
- **Delete-then-insert by document ID:** When an edit shifts chunk boundaries, delete all existing vectors for that `document_id` (or swap versioned records) before inserting new chunks so orphan vectors never linger.
- **Explicit staleness window:** Measure lag from source commit to searchable vector (`publish_ts` vs `indexed_at`) and expose source timestamps to the application so time-sensitive queries can warn or fall back.
- **Zero-downtime full rebuilds:** When swapping embedding models or chunking rules, build a shadow index in the background and flip an index alias atomically once recall checks pass.

## Mental model

- **Library catalog vs shelf books:** If a shop replaces its refund policy page in the binder but the search catalog still points to last month's Photocopy #4, the assistant will hand customers the old rules with a real citation.
- **The staleness window:** Every second between the editor hitting "Save" in the CMS and the new vectors landing in the index is a window where the source of truth and the RAG index disagree.
- **Diffing by fingerprint:** Instead of re-reading and re-embedding all 1,200 articles every night, compare each article's short SHA-256 fingerprint against the last indexed fingerprint and process only the 12 that changed.

## Core concepts

1. **Staleness window (index lag):** The elapsed time between a committed write in the source system (CMS, database, Git) and the updated chunk becoming searchable in the vector and lexical indexes.
2. **Change Data Capture (CDC):** Tails the source database's write-ahead log (e.g., Postgres logical replication via Debezium) and publishes create, update, and delete events to a durable queue without dual writes in application code.
3. **Content hashing:** Computes a deterministic cryptographic hash (such as SHA-256) over normalized document or chunk text so unchanged content skips the embedding model completely.
4. **Idempotent upsert & tombstoning:** Keying vectors by deterministic IDs (`doc_id#chunk_idx#version`) and deleting retired chunks ensures retries and boundary shifts never create duplicate or orphaned passages.
5. **Reconciliation crawl:** A scheduled background job that compares source document IDs and hashes against the index metadata table to heal dropped webhooks and purge deleted documents.
6. **Shadow index & atomic alias swap:** Building a new index collection offline and repointing a logical alias (`help_chunks_live -> help_chunks_v4`) in a single metadata operation when changing embedding models or chunking parameters.

**How to read it:**

- **Step 2 — Log tailing via CDC:** A connector such as Debezium reads the database write-ahead log (WAL) and publishes each committed row change to a Kafka topic.
- **Step 3 — Re-chunk, re-embed, and upsert:** An indexer worker consumes the event, normalizes and re-chunks the modified text, calls the embedding model, and upserts the new vectors.
- **Step 4 — Near-real-time reads:** Search queries read the updated index, trailing the database only by the queue, embedding, and refresh latencies.

**The numbers (illustrative):**

- **Incremental event path:** $1\text{ s}$ (queue) $+ 30\text{ s}$ (micro-batch wait) $+ 1\text{ s}$ (re-chunk) $+ 2\text{ s}$ (embed 3 chunks) $+ 1\text{ s}$ (upsert & refresh) $= \mathbf{35\text{ s}}$ staleness window.
- **Nightly batch rebuild:** Leaves a staleness window of up to **24 hours ($86,400\text{ s}$)** while re-embedding all 3,600 chunks every night.

<Callout tone="red" title="What breaks">
  If a webhook is dropped, the event never reaches the queue and the staleness window never closes: the index serves the old article indefinitely. Fix: run a periodic reconciliation job that compares every source article's content hash against the index and enqueues any mismatch.
</Callout>

## Technical mechanics

### Content-hash diffing and selective re-embedding

- **Document and chunk fingerprints:** Store a SHA-256 hash of the normalized text alongside every indexed document and chunk (`doc_hash`, `chunk_hash`).
- **Skip unchanged text:** When a CMS save touches only metadata (tags, author) or edits a single paragraph in a 50-page manual, comparing `chunk_hash` values skips embedding calls for every unchanged chunk.

**How to read it:**

- **Step 1 — Stored vs current hashes:** Compares the SHA-256 hash stored at last indexing against today's text hash across Brightpost's 1,200 help articles.
- **Step 2 — Isolate modified documents:** Only "Reset a forgotten password" differs in the sample (12 articles changed across the entire help centre this week).
- **Step 3 — Embed only the delta:** Only the 36 chunks from those 12 articles go to the embedding model instead of all 3,600 chunks.

**The numbers:**

- **Chunk volume:** $12\text{ articles} \times 3\text{ chunks} = \mathbf{36\text{ chunks}}$ instead of $3,600$ (**99% reduction**).
- **Token volume:** $36 \times 400 = \mathbf{14,400\text{ tokens}}$ embedded instead of $1,440,000\text{ tokens}$.

<Callout tone="red" title="What breaks">
  A per-article hash catches edits but misses deletions (a deleted article has no new hash, leaving its 3 old chunks searchable) and boundary shifts (if an edit changes chunk count from 3 to 4, upserting by index leaves chunk 4 orphaned when shortened back to 3). Fix: delete all chunks matching `document_id` before inserting the new set, and tombstone documents missing from the source reconciliation scan.
</Callout>

### Handling deletions, permissions, and out-of-order events

- **Monotonic version checks:** Attach a source `version` or `updated_at` sequence number to every event; reject or skip worker writes if the index already holds a newer version for that `document_id`.
- **ACL & permission sync:** When a document's access control list changes in Google Drive or Confluence without a text edit, update the metadata filter fields on all its chunks immediately without re-running the embedding model.
- **Soft deletes and tombstones:** Mark deleted document IDs in a fast deny-list cache if vector deletion is asynchronous (e.g., waiting for HNSW segment compaction) so deleted chunks are filtered out at query time immediately.

### Orchestration, backfills, and alias swaps

- **Separate incremental and backfill lanes:** Run real-time CDC/webhook events on a high-priority queue and bulk backfills on a rate-limited background queue so a 100,000-document backfill never starves live edits.
- **Atomic alias swap for full re-indexing:** When upgrading the embedding model, populate a new index (`chunks_v2`), run recall evaluations in shadow mode, and switch the read alias from `chunks_v1` to `chunks_v2` atomically.

## Trade-offs

| Strategy | Staleness Window | Compute & API Cost | Operational Complexity | Best Fit |
| --- | --- | --- | --- | --- |
| Full nightly rebuild | Up to 24 hours | High (re-embeds 100% of corpus) | Lowest (single cron job) | Small static corpora (< 5,000 chunks) |
| Scheduled hash-diff scan (hourly) | Up to 1 hour | Low (embeds changed chunks only) | Low (stateless batch job) | Internal wikis, documentation sites |
| Webhook / CDC streaming + micro-batch | Seconds to ~1 minute | Low (delta only + queue infra) | Medium (queues, idempotency, ordering) | Customer support, pricing, policy RAG |
| Synchronous dual-write on save | 0 ms (read-your-writes) | High tail latency on author saves | High (distributed failure modes) | Rarely used; prefer async + source fallback |

## Production systems

- **Debezium + Kafka:** Standard CDC pipeline that tails PostgreSQL WAL or MySQL binlog to stream row-level creates, updates, and deletes into indexing workers.
- **Elasticsearch / OpenSearch Index Aliases:** Atomic pointer swap across versioned index collections for zero-downtime schema or embedding migrations.
- **LlamaIndex / LangChain Indexing API (`RecordManager`):** Tracks `doc_id`, content hashes, and timestamps in SQLite/Postgres to deduplicate unchanged chunks and purge deleted source documents automatically.

## Failure modes & pitfalls

- **Upserting chunks without purging old chunk IDs:** When an edited document shrinks from 8 chunks to 5, chunks 6–8 remain in the vector store as stale ghosts unless deleted by `document_id`.
- **Relying solely on webhooks without reconciliation:** Dropped webhooks leave documents permanently stale until a periodic hash-comparison scan heals the gap.
- **Re-embedding on metadata-only changes:** Permission or tag updates should update vector payload metadata in place rather than paying to re-embed unchanged text.
- **Sharing one queue for live edits and bulk backfills:** A full corpus backfill floods the queue and pushes live edit lag from 30 seconds to hours.
- **Waiting for segment compaction on hard deletes:** HNSW indexes mark deleted vectors with a bitmask until compaction; ensure queries honor the tombstone mask immediately.

## Interview framework

1. **Define the freshness SLA by data tier:** Separate sub-minute targets (pricing, policies, support tickets) from daily targets (archived blogs).
2. **Draw the hybrid update pipeline:** Event-driven CDC/webhooks for low-latency deltas + a periodic content-hash reconciliation job for dropped events and deletions.
3. **Explain the per-document update mechanics:** Normalize → compare SHA-256 content hash → re-chunk modified spans → delete old vectors by `document_id` → upsert new vectors with `version` guard.
4. **Cover deletions and ACL updates:** Immediate metadata updates for permissions, tombstones for deletes, and monotonic version checks for out-of-order events.
5. **Explain zero-downtime full rebuilds:** Shadow index build + offline evaluation gate + atomic alias swap.

**What interviewers listen for:** Content hashing to avoid redundant embedding spend, deleting orphaned chunks when boundaries shift, and combining event streams with periodic reconciliation.

**Red flags:** Re-embedding the entire corpus on a cron schedule at scale, or ignoring what happens when a source document is shortened or deleted.
