## Ingestion Orchestration (ETL/ELT)

ETL and ELT orchestration schedules work that lands data in lakes, warehouses, and feature stores. Airflow remains common for cron-style DAGs with rich operator ecosystems; Dagster emphasizes software-defined assets and data-aware dependencies; Prefect and similar tools focus on dynamic workflows and developer ergonomics for Python-native tasks. The right choice depends on team skills, how strongly you want assets as first-class objects, and whether you need fine-grained per-run parameterization without redeploying DAG definitions.

Idempotency is the backbone of reliable ingestion. Tasks should be safe to retry: write to partitioned staging locations, merge with deterministic keys, and use upsert semantics or merge statements that collapse duplicates. Backfills are routine after logic bugs or late-arriving facts; design partitions so you can reprocess bounded date ranges without rewriting entire tables. Exactly-once end-to-end semantics are rare outside managed streaming stacks; in batch land you usually aim for effectively-once behavior via idempotent sinks and deduplication keys.

DAG design should reflect failure domains: separate extract, transform, and load stages so a transform bug does not force re-pulling terabytes from an external API. Keep fan-in and fan-out explicit to avoid hidden resource contention. Retry policies should distinguish transient network errors from data errors that will never succeed without code changes, surfacing the latter to alerting channels quickly.

Operations benefit from SLA timers on critical paths, data quality checks as sensors or tasks, and observability into queue depth and executor saturation. Trade-offs include orchestrator operational overhead versus glue scripts, and centralization versus team autonomy when many micro-DAGs create cross-dependencies that are hard to visualize.

## Continuous Data & Knowledge Integration

RAG and agentic systems are only as current as the corpora they retrieve from. Continuous integration for knowledge means pipelines that ingest new documents, update structured records, and refresh vector indexes without taking the whole system offline. Architecture usually splits bulk backfills from incremental updates: message queues or change-data-capture streams carry create, update, and delete events from source systems into workers that normalize text, deduplicate by content hash, and enqueue embedding jobs.

Document change detection compares source revision ids, content hashes, or extracted entity signatures so unchanged paragraphs do not force redundant embedding calls. Incremental indexing strategies include per-collection segment files with periodic compaction, dual-write to shadow indexes followed by atomic swap, or versioned index aliases in Elasticsearch-style clusters. Embedding update strategies range from full re-embed on any text change to selective re-embed when semantic diff exceeds a threshold, trading fidelity against API cost and latency during peak update windows.

Stale data handling belongs in product policy as much as in engineering. Some answers should carry freshness timestamps or disclaimers when source-of-truth systems lag. Freshness SLAs define maximum acceptable lag per data class: regulatory filings might need sub-hour propagation while marketing blogs tolerate a day. Operational monitors track ingestion backlog depth, embedding queue age, and retrieval hit rates for newly added content to catch silent failures in connectors.

Trade-offs include eventual consistency versus read-after-write expectations for internal tools. Stronger guarantees often require synchronous write paths that increase user-perceived latency on authoring flows. Another tension is global versus regional indexes: unified indexes simplify routing but may violate data residency; sharded indexes add routing complexity but align with compliance boundaries.

## Knowledge Base Update Automation

Retrieval-augmented systems go stale the moment documentation, pricing, or policies change without the index noticing. Automated document ingestion pipelines watch sources such as CMS webhooks, git repositories, ticketing exports, and blob storage prefixes. Each detected change should enqueue normalization jobs that extract text, preserve provenance metadata, and apply access-control tags so multi-tenant indexes never leak restricted sections. Batch crawls still matter as a safety net when events are missed, but event-driven updates reduce time-to-freshness for critical pages.

Change detection goes beyond file hashes: semantic diffing can skip re-embedding paragraphs that moved but did not edit, while structural edits in HTML might alter chunk boundaries enough to require full section re-chunking. Incremental re-embedding strategies embed only new or altered chunks and update vector stores with delete-insert semantics keyed by stable document and chunk identifiers. Stale content detection complements push updates by scoring last-reviewed dates, decaying trust for pages with conflicting numeric facts, or comparing live fetches to cached snapshots when legal requires periodic reaffirmation.

Knowledge graph updates introduce entity resolution challenges: merging synonyms, deprecating nodes, and validating new edges against ontology rules. Freshness scoring helps rankers prefer recently verified facts without ignoring stable reference material. Scheduled jobs suit predictable publisher releases; event-driven workers suit bursty wiki edits. Reliability demands idempotent consumers, dead-letter queues for poison documents, and shadow indexing environments where new corpora are evaluated for retrieval precision and hallucination rate before the router switches production traffic.

  <InterviewQuestion question="How would you architect incremental re-embedding when documents are large and edits are small?" category="Architecture">
    Parse documents into stable chunk IDs based on headings or content hashes, diff at chunk granularity, and enqueue embedding jobs only for changed chunks while tombstoning removed spans in the vector index. Maintain a mapping table from chunk IDs to vector IDs in the store. For boundary shifts, detect overlap with neighboring chunks and re-embed affected windows to avoid orphaned partial text.
  </InterviewQuestion>
  <InterviewQuestion question="What automation patterns balance freshness against cost for a million-document corpus?" category="Automation">
    Tier sources by business criticality: high-value namespaces update in near real time with streaming workers, while archival tiers refresh weekly. Cache embedding models in warm pools, batch embed within latency budgets, and deduplicate identical boilerplate across pages. Use sampling-based audits to catch drift instead of re-embedding everything on a short cadence.
  </InterviewQuestion>
  <InterviewQuestion question="What reliability issues appear when webhook-driven ingestion is the only update path?" category="Reliability">
    Missed deliveries, duplicate events, and out-of-order updates can leave the index inconsistent unless consumers are idempotent with monotonic version vectors per document. Network partitions between the CMS and workers cause silent staleness unless reconciled by periodic full scans or cursor-based backfills. Always monitor lag percentiles and alert when any namespace exceeds freshness SLOs.
