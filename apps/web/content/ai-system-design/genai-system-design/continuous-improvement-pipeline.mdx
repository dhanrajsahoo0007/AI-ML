A model that ships once gets worse as the world moves, and one that ships weekly can still get worse if nobody checks.

- Interviewers ask about the improvement loop because it ties together everything else in the section: traces, evaluation sets, experiments, release gates and rollback.

## Overview

- **Quality is a time series, not a milestone.** The loop is: **trace, mine failures, add test cases, make one change, evaluate offline, canary, promote, trace again.**
- **Failures become tests.** Every production failure you understand is added to the evaluation set, so it cannot come back unnoticed. Brightpost's set grows from **200 to 214 cases** in one week.
- **Choose the lever from the failure, not from habit.** A missing fact needs retrieval, a broken rule needs a check, a style gap may need fine-tuning. Start with the cheapest change that works.
- **Two gates, different jobs.** Offline evaluation compares the candidate with the baseline on the whole set; a **canary** on a small share of real traffic checks what the set cannot. Keep rollback one step away.
- **Measure the loop itself:** time from a flagged issue to the fix in production (**102 hours** in the worked example), the share of regressions caught before release, and cost per quality point.

## Mental model

- A restaurant kitchen keeps a notebook. Every time a dish comes back, the cook writes down what was wrong and tests the next batch against that note before it goes out.
- Over months the notebook becomes the kitchen's real recipe.
- A kitchen without one fixes each complaint once and repeats it a year later.
- The improvement pipeline is that notebook plus a rule that no change reaches every table without a taste test first.

## Core concepts

- The running example is Brightpost's support assistant: **200,000 requests a day**, a **200-ticket golden set**, and a refund rule (order 4471, a cracked kettle, £42; refunds over £30 need approval).
- All counts in this page's example are illustrative.

1. **Signals.** What production tells you: thumbs-down and edits, hand-offs to a person, retries, errors, latency, cost and business outcomes such as refunds issued. See [Human Evaluation & Feedback](/ai-system-design/genai-system-design/human-evaluation-and-feedback).
2. **Traces.** One record per request: question, retrieved passages, tool calls, answer, versions and timings. Without them you can only count failures, not explain them.
3. **Failure mining.** Reading a sample of failed traces by hand and giving each failure a name, then counting. The count says what to fix first (see [LLM Evaluation Fundamentals](/ai-system-design/genai-system-design/llm-evaluation-fundamentals)).
4. **The test set.** The golden set, grown from production. Each fixed failure adds cases (see [Building Eval Datasets](/ai-system-design/genai-system-design/building-eval-datasets)).
5. **The lever.** The kind of change: a prompt edit, a code check, a retrieval fix, a model switch or a fine-tune. The failure picks the lever.
6. **Offline evaluation.** Run the candidate and the baseline on the whole set and compare case by case: which cases were fixed, which broke (see [Automated Regression Testing](/ai-system-design/genai-system-design/automated-regression-testing)).
7. **Canary.** A time-limited release to a small share of real traffic with automatic checks, as in the SRE definition: a partial deployment and its evaluation (see [Rollback & Blue-Green Deployment](/ai-system-design/genai-system-design/rollback-blue-green-deployment)).
8. **Triggers.** What starts a loop outside the weekly rhythm: a drift alarm, a provider model update, a new product feature, or a safety incident (see [Drift Detection](/ai-system-design/genai-system-design/drift-detection)).
9. **Velocity.** How fast a signal becomes a fix, and how much of the risk is caught before customers see it.

## Technical mechanics

### From a failure to a test case

- A trace is evidence; a test case is a repeatable question with a grader.
- Turning one into the other takes three decisions: what the correct behaviour is (written by a person who owns the policy), how to grade it (a code check if the right behaviour can be tested mechanically, a judge if not), and what to remove (customer names, card digits, anything personal).
- Here is one of the 14 Brightpost cases, in a format we use for illustration, not a standard:

```json
{
  "id": "refund-over-limit-0007",
  "source_trace": "tr_7c1e",
  "input": "My kettle arrived cracked. Order 4471, it cost 42 pounds. Please refund me.",
  "expected": { "must_call": "request_refund_approval", "must_not_call": "issue_refund" },
  "grader": "code",
  "labels": ["refund", "over-limit"],
  "added": "2026-11-17"
}
```

It is the Tuesday step of the weekly loop at the end of this page. A code grader is cheap and exact; use a judge only where code cannot decide.

### Choosing the lever

The question is what kind of gap the failure shows. [Prompt vs RAG vs Fine-Tuning](/ai-system-design/genai-system-design/prompt-vs-rag-vs-fine-tuning) draws the decision, and the improvement loop reuses it as is.

<AnimatedDiagram
  spec="animated/rag/choose-approach"
  caption="The lever follows the gap, and you only know the gap after you have measured the best prompt."
/>

**How to read it:**

- Start from the best prompt you can write and the evaluation set.
- Read what is still wrong. Missing facts point to retrieval, a format or behaviour gap points to fine-tuning, both point to both, and nothing left means ship.
- Brightpost's failures sort like this (illustrative counts out of 50 thumbs-down traces):

| Failure (count) | Gap | Cheapest lever that works |
| --- | --- | --- |
| Refund over £30 sent with no approval (14) | The rule exists in the prompt but the model skips it | A code check in the refund tool, then the prompt |
| Invented a policy (9) | Facts the model lacks | Retrieval and a rule to say "I do not know" |
| Wrong order id in a tool call (8) | Format | Tool schema validation, then examples |
| No hand-off to a person (7) | Behaviour | Prompt rule and a trigger check |
| Tone or length off (5) | Style | Prompt; fine-tune on the 5,000 resolved tickets if it persists |
| Right article not retrieved (4) | Retrieval | Chunking, reranking |

- A rule the model must never break belongs in code, not in a prompt: code runs every time.
- The loop's order of preference is code check, prompt, retrieval, then fine-tuning, because each step costs more and is slower to undo.
- See [Automated Retraining & Fine-Tuning](/ai-system-design/genai-system-design/automated-retraining-finetuning) for when a fine-tune earns its place.

### Gates: offline first, then the canary

- Offline evaluation is fast and repeatable but only knows the cases you have.
- The canary sees real traffic but is slow and exposes some customers.
- Use both, in that order. For the offline gate read the flips, not just the total: a candidate that fixes 5 cases and breaks 3 has a net gain of 2, but the 3 may be the ones that matter.
- For the canary, compare against the baseline running at the same time (a small A/B test; see [A/B Testing for Prompts & Models](/ai-system-design/genai-system-design/ab-testing-prompts-models)), with limits agreed in advance on quality, p95 latency, cost and hand-offs, and an automatic rollback.
- Once it is live, [online production evaluation](/ai-system-design/genai-system-design/online-production-evaluation) keeps watching.

### Triggers and automation

- Run the weekly loop on a schedule, and add event triggers.
- Automate when a drift test crosses its threshold on large, representative traffic, when rolling quality on labelled slices falls significantly, or when a knowledge index refresh completes.
- Keep a person in the loop for rare safety incidents, single-customer spikes, ambiguous metric moves (which may be an instrumentation bug) and any regulated domain.
- A single threshold on a small sample oscillates; combine drift statistics, a sequential test on held-out slices and a human approval for high-risk changes.

### Root cause: where the failure actually is

- A bad answer can come from retrieval staleness, a tokenizer or template change, a tool that changed its output, a provider's silent model update, or the weights.
- Link in one place: model version, prompt version, index snapshot id and dependency health for every trace.
- Then a regression is a diff between two version sets.
- Keep training jobs on their own orchestration so a long GPU run does not block a hotfix, but record the same metadata for both, so every production model points to the data, code commit and evaluation report that justified it.

### Measuring the loop

- Three numbers make the pipeline legible: the **time from a flagged issue to the fix in production**, the **share of regressions caught before release**, and the **cost per quality point** gained.
- They show whether you improve faster or just churn.

### Worked example: one week at Brightpost

<StepCards>
  <StepCard n={1} title="Monday: read the failures">
    From 200,000 daily requests, take 50 thumbs-down traces. 14 are a refund above £30 sent with no approval: 14 ÷ 50 = 28 %.
  </StepCard>
  <StepCard n={2} title="Tuesday: turn them into test cases">
    The 14 become cases like the one above, de-identified and labelled by two people. The set grows from 200 to 214.
  </StepCard>
  <StepCard n={3} title="Wednesday: change it and test it offline">
    The rule becomes a code check in the refund tool. Offline, the baseline passes 172 of 214 (80.4 %). The candidate fixes 5 of the old cases, breaks 3, and passes 13 of the 14 new ones: 172 + 5 − 3 + 13 = 187, which is 87.4 %.
  </StepCard>
  <StepCard n={4} title="Thursday: a small live canary">
    The team reads the 3 broken cases. Two are judge noise on rerun; one is real: a £28 refund was wrongly sent for approval. They fix it, then start a 5 % canary: 200,000 × 0.05 = 10,000 requests a day.
  </StepCard>
  <StepCard n={5} title="Friday: promote">
    The gates hold, so the change goes to 25 % at 09:00 and 100 % at 15:00, with rollback ready. The next Monday's 50 thumbs-down traces hold 3 such failures instead of 14.
  </StepCard>
</StepCards>

**The loop's own numbers:**

- Flagged Monday 09:00, fully released Friday 15:00: 4 × 24 + 6 = **102 hours**.
- One real regression (the £28 case) was caught offline, before any customer saw it.
- The cost: a few hours of a person's time reading 50 traces, and one afternoon of engineering.
- A team that avoids Friday releases moves the ramp to Monday, and the clock reads 7 days 6 hours.

<Callout tone="red" title="What breaks">
  The team keeps adding cases and tuning until the 214-case set passes at 100 %. Production quality does not follow, because the prompt now fits the set and the set stopped growing from fresh traffic. Keep a hidden slice, refresh from new traces every week, and watch the online metric, not only the offline score.
</Callout>

## Trade-offs

| Choice | Pros | Cons | When to use |
| --- | --- | --- | --- |
| Weekly manual loop | Cheap; a person understands each failure | Slow; depends on one reader | Early product, a small team |
| Automated retrain trigger | Fast response to drift | Can oscillate or train on bad data | Large stable traffic, low-risk domain |
| Human gate before promotion | Catches policy and safety issues | Slows the loop | Regulated or high-risk changes |
| Offline gate only | Fast and cheap | Misses live behaviour | Low-risk changes with a strong set |
| Canary plus offline gate | Real evidence with limited exposure | Takes days; needs traffic and rollback | Any change customers will notice |
| Heavy process, many gates | Few incidents | Slow, and teams route around it | Where one failure is costly |
| Light process | Fast | Untracked changes make incidents unrecoverable | Prototypes only |

## Production systems

- **Canarying at Google.** The SRE workbook defines a canary as a partial, time-limited deployment of a change together with its evaluation, used to decide whether a rollout should continue.
- **Evals as the engine of improvement.** Husain's widely cited write-up describes three levels, unit-test assertions, human and model review of logged traces, and A/B tests, and notes that the same infrastructure feeds debugging and fine-tuning data (2024).
- **Criteria drift.** Shankar et al. (2024) found that people's own evaluation criteria shift as they grade outputs, which is why the test set must be revisited as failures are read.
- **Feedback loops in ML systems.** Sculley et al. (2015) warn about hidden feedback loops and undeclared dependencies, the failure modes a version-linked trace is built to expose.
- **Used in our case studies:** [Customer Support Agent](/genai-system-design/case-studies/customer-support-agent)

## Failure modes & pitfalls

- **Fixing without a test.** The failure returns after the next prompt edit.
- **Several changes at once.** A prompt, a model and a retrieval change together tell you nothing about which one helped.
- **A set that stops growing.** It stops matching production and the score stops meaning anything.
- **Reaching for fine-tuning first.** It is the slowest and hardest lever to undo; a code check or a prompt fix often does the job.
- **Judging only the total.** A net gain can hide the one case that matters most.
- **No rollback path.** A canary without an automatic stop is only a slow release.

## Interview framework

1. Describe the loop in one breath: trace, mine, add cases, change, offline gate, canary, promote.
2. Say how a failure becomes a test case, and who owns the label.
3. Choose the lever from the failure type, cheapest first, and name the one you would not start with.
4. Name both gates and what each catches that the other cannot; mention the flips, the noise band and the rollback.
5. Give the loop's own metrics: time to fix, regressions caught before release, cost per quality point.

**What interviewers listen for:** failures turned into permanent tests, one change at a time, a canary with limits agreed in advance, and a version-linked trace for root cause.

**Red flags:** retraining on a schedule with no evaluation gate, shipping on an aggregate score, and treating the evaluation set as finished.

  <InterviewQuestion question="How would you run root cause analysis for a sudden rise in toxic outputs?" category="Failure modes" level="Senior">
    - Segment by language, topic, region and version to see whether the spike lines up with a release or a traffic shift.

    - Inspect retrieval corpora and tool outputs for poisoned content, and compare token distributions against a baseline.

  </InterviewQuestion>
