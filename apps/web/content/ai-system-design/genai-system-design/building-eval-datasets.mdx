Every evaluation score is only as trustworthy as the cases behind it. Interviewers ask how you would build a golden set because the answer shows whether you have ever had to defend a number: where the cases came from, who labelled them, what they cover and how sure you are.

## TL;DR

- A **golden set** is a fixed, labelled set of cases that you run on every change. Brightpost's has **200 tickets**: **120** sampled from production logs, **50** written by experts and **30** synthetic.
- **Real traffic first.** Logs give the real wording and the real mix. Experts add the rare and risky cases logs hardly contain; synthetic cases fill the cells that stay thin, and a person checks each one.
- **Coverage beats count.** Lay the set out as a grid (intent by difficulty) and look at the smallest cell. A total of 200 can hide a cell of **4**.
- **Size is about uncertainty.** At 200 cases a measured 80 % carries about **±5.5 points** (95 % interval). Four times the cases halves that.
- A set is **versioned, owned and refreshed**. Two annotators label, a lead settles disagreements, and a holdout that nobody tunes on guards against overfitting.

## The idea in plain English

A driving examiner does not test you on the one loop of roads you practised on. The route has a roundabout, a hill start, a narrow street and, if the weather allows, rain, and the examiner marks each skill on a written sheet. Pick the route from real roads, add the awkward corners that real roads rarely offer, and use the same sheet for every candidate. If learners memorise the route, a pass tells you nothing, so the examiner changes it. A golden set is that route and that sheet for your model.

## Core concepts

The running example is Brightpost's support assistant. Its **golden set is 200 tickets**, each with a reference answer and a rubric. Every number below is illustrative: the counts were chosen to teach, and the totals are checked so they add to 200.

### Writing labels and rubrics

A case is more than a question. It holds the input, what a good answer must contain, and the tags you will slice by.

```json
{
  "id": "gs-0147",
  "source": "logs",
  "intent": "refund",
  "difficulty": "medium",
  "input": "My kettle from order 4471 arrived cracked. Can I get my £42 back?",
  "reference": "Apologise, confirm £42, send the refund for approval (over £30).",
  "rubric": ["acknowledges the damage", "states £42", "sends for approval, does not promise payment"],
  "version": "golden-v1"
}
```

This is an illustrative record, not a standard format. Prefer a **rubric of yes/no lines** to a single "is it good" label: each line can be checked by a code rule, a judge model or a person, and two people disagree less about a concrete line than about a feeling. Write the lines before you label, and revise them when annotators disagree (see [Human Evaluation & Feedback](/ai-system-design/genai-system-design/human-evaluation-and-feedback) and [LLM-as-Judge Evaluation](/ai-system-design/genai-system-design/llm-as-judge-evaluation)).

### Coverage: slices, edge cases and adversarial cases

The traffic mix is not the mix you need to test. Most tickets are easy, so a random sample is mostly easy and its pass rate flatters the system. Lay the set out as a grid and fill it on purpose.

<AnimatedDiagram
  spec="animated/eval/dataset-coverage-grid"
  stepper
  caption="A total of 200 hides the shape of the set: the hard refund cell holds four cases, so its pass rate moves 25 points per answer. Counts are illustrative."
/>

**How to read it.** Rows are intents, columns are difficulty, and each cell is a count. Step 2 adds the totals: rows 46 + 40 + 36 + 44 + 34 = 200 and columns 90 + 70 + 40 = 200. The red cell is the thinnest, and step 3 names the problem. Refunds and returns, hard, has 4 cases; one wrong answer moves that cell's pass rate by 1 ÷ 4 = 25 points. Refunds are where money leaves the shop, so this is the cell to grow first, with expert-written cases.

Three kinds of case deserve a deliberate quota: **slices** (an intent, a language, a customer tier), **edge cases** (an empty order number, a refund exactly at £30) and **adversarial cases** (a ticket that tries to talk the assistant into a refund; see [Prompt Injection & Jailbreaks](/ai-system-design/genai-system-design/prompt-injection-and-jailbreaks)). Tag each case so the grid can be rebuilt at any time. Read a cell's rate as a flag, not as an estimate: four cases cannot estimate anything.

## Architecture

A golden set is a small pipeline with an owner. It runs in five stages and loops back each month.

    Freeze the set as golden-v1 with a content hash, the rubric version, an owner and a date. A score only compares with scores from the same version.
  </StepCard>
  <StepCard n={5} title="Refresh">
    Each month retire cases the policy has changed and add cases from new failures, then freeze golden-v2 and start again.
  </StepCard>

## Deep dive

### How many examples you need

The question is not "how many is enough" but "how wide an interval can I live with". A pass rate measured on n cases is an estimate. With the normal approximation, the 95 % interval around a pass rate p has half-width 1.96 × √(p (1 − p) ÷ n).

<AnimatedDiagram
  spec="animated/eval/dataset-size-interval"
  stepper
  caption="At 200 tickets a pass rate of 80 percent carries about plus or minus 5.5 points; halving that costs four times the cases. Computed with the normal approximation."
/>

**How to read it.** The curve falls fast and then flattens: width shrinks with the square root of n, so each extra case buys less. Step 2 marks Brightpost's 200 tickets. Step 3 shows that 800 cases give half the width.

**The numbers.** For p = 0.8 and n = 200: 1.96 × √(0.16 ÷ 200) = 1.96 × 0.0283 = 0.0554, about **±5.5 points**. A measured 80 % means the true rate is probably between 74.5 % and 85.5 %. At n = 800 the width is ±2.8. One intent with 34 cases has ±13.4.

Three consequences. First, a change that moves the score by 3 points on 200 cases is inside the noise. Run both versions on the same cases and compare case by case, which narrows the interval, as [Automated Regression Testing](/ai-system-design/genai-system-design/automated-regression-testing) describes. Second, the normal approximation is rough when n is small or the rate is near 0 % or 100 %. At 190 of 200 passing it gives ±3.0, and the **Wilson interval** gives about 91.0 % to 97.3 %, which is not symmetric. Use Wilson when in doubt (Brown, Cai and DasGupta, 2001). Third, a smaller set is fine to start: 50 well-chosen cases that you read catch more than 5,000 you never open.

### Keeping the set fresh and avoiding overfitting

Two things age a golden set. The **world changes**: a policy is rewritten, a product is retired, customers start asking about a new feature, and old cases then test a business that no longer exists. And **you overfit**: every time the team reads a failing case and edits the prompt to fix it, the prompt learns the set. The pass rate climbs and the real quality does not.

Guard against both. Refresh on a schedule, adding cases from new failures and thumbs-down (see [Continuous Improvement Pipeline](/ai-system-design/genai-system-design/continuous-improvement-pipeline)). Keep a **holdout**, a slice of the set or a separate fresh sample that nobody reads while tuning, and report both numbers. If the tuning score rises and the holdout score does not, you have overfit. Never put golden cases in prompts, few-shot examples or fine-tuning data, and keep the set out of any code the model can read.

### Versioning and ownership

Treat the set like code. Give every release an id (golden-v1), a content hash and a changelog that says which cases were added or retired and why. Never edit a case in place; add a new one and retire the old, so earlier scores stay reproducible. Store the rubric version with the scores. Name one **owner** who approves changes, and write down how disagreements are settled. Without an owner, the set drifts, and a score from March cannot be compared with a score from June.

### Worked example: Brightpost builds golden-v1 and refreshes it

The team follows the lifecycle figure. **Sample:** 120 tickets from 30 days of logs, a set share per intent, personal data removed. **Label:** two support leads label all 200 cases, 400 labelled copies. **Adjudicate:** they disagree on 22 cases (11 %), a third lead settles them from the written policy, and three repeat disputes become rubric rules. Agreement is 178 ÷ 200 = 89 %.

The grid then shows the weak spot: refunds and returns, hard, has 4 cases. The set is frozen as golden-v1 anyway, and the gap goes on the owner's list.

A month later, 12 cases are retired because the delivery policy changed, and 12 are added from thumbs-down tickets. Six of the 12 are expert-written hard refund cases, which take that cell from 4 to 10. The set is golden-v2, still 200. Even at 10 cases a rate in that cell has a rough interval of about ±25 points, so the cell stays a flag and the team reads every case in it by hand. They compare golden-v2 scores only with golden-v2 scores, and keep a separate 30-case holdout, drawn from fresh traffic, that nobody opens during tuning. When a prompt change lifts the tuning score 4 points and the holdout score 0, the team treats the lift as overfitting.

<Callout tone="red" title="What breaks">
  The team tunes the prompt against the 200 tickets for two weeks. The score goes from 78 % to 91 %, the release ships, and customers see no change: thumbs-down stay flat. The prompt had learned the set. A holdout or a fresh monthly sample would have shown the gap, and the interval (±5.5 on 200) would have warned that a 3-point move was noise.
</Callout>

## Trade-offs

| Choice | Pros | Cons | When to use |
| --- | --- | --- | --- |
| Cases from production logs | Real wording and real mix | Mostly easy; needs privacy cleaning; rare cases are missing | The base of every set |
| Expert-written cases | Cover rare, costly and adversarial situations | Slow and costly; reflect what experts imagine | Money, safety or policy cases |
| Synthetic cases | Cheap and fast; fill thin cells | More uniform than real tickets; can share the generator's blind spots | Gaps in the grid, always checked by a person |
| A small set (50 to 200) | Cheap to label and read | Wide intervals; thin slices | Early work, and fast regression checks |
| A large set (1,000 and up) | Narrow intervals, per-slice estimates | Labelling cost; harder to keep fresh | A mature product with many slices |
| A frozen set | Scores are comparable over time | Goes stale; invites overfitting | Regression gates, with a refresh schedule |

## Real-world examples

- **SWE-bench Verified** is a 500-task subset of SWE-bench that human annotators screened for clear problem statements and fair tests. SWE-bench itself has 2,294 task instances from 12 Python repositories (Jimenez et al., 2023). The lesson is that human review of the set raises its value.
- **MT-bench** is a small set of 80 multi-turn questions used with an LLM judge, which agreed with human preferences over 80 % of the time (Zheng et al., 2023). Small, hand-written and well chosen can be enough for comparison.
- **Brightpost's golden set** (this page) combines logs, experts and synthetic cases, with a grid, double labelling and a monthly refresh.

## Common pitfalls

- **Only sampling traffic.** The sample is mostly easy cases, so the pass rate flatters the system and rare costly cases are missing.
- **One annotator, no rubric.** The labels carry one person's taste, and nobody knows the agreement.
- **Reading a thin cell as a rate.** Four cases give a 25-point step per answer; use the cell as a flag.
- **Editing cases in place.** Earlier scores can no longer be reproduced.
- **Letting the set leak.** Golden cases pasted into a prompt, few-shot examples or training data make the score meaningless.
- **Never refreshing.** The policy changes, the set does not, and the team ends up optimising for last year's shop.

## How to answer in an interview

1. State the goal: a labelled set that you can run on every change and trust, with a known uncertainty.
2. Name the sources and what each is for: logs for the real mix, experts for the rare and risky, synthetic for the gaps.
3. Describe labelling: rubric of yes/no lines, two annotators, adjudication, and the agreement you measured.
4. Show coverage and size: the grid, the smallest cell, and the interval (±5.5 points at 200 and 80 %).
5. Close with lifecycle: versioning, an owner, monthly refresh and a holdout.

**What interviewers listen for:** coverage over count, an interval rather than a bare score, double labelling with adjudication, and a plan against overfitting and staleness.

**Red flags:** "we used 1,000 synthetic prompts", a single reviewer, a score with no interval, and a set that never changes.
