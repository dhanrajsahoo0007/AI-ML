## In one sentence

<KeyIdea>
  Fix a leaking account in order of harm: stop what an attacker is using now, close what anyone can reach, then make sure it cannot reopen.
</KeyIdea>

## The brief

Brightpost has bought a framing workshop, the framing shop, so it can sell framed posters. [Migration and Modernization](/cloud/operations/migration-and-modernization) moves its back-office servers. The shop also has a small cloud account of its own. A freelancer built it 3 years ago for the photo-upload site, where customers send a photo to be printed and framed, about 40 a day. Nobody has looked inside since he left. On the Monday the purchase closes, Asha gets the one admin password and spends the morning reading. She writes down six findings.

1. **Keys in the code.** Two long-lived access keys sit in the site's code repository, which was public for its first 8 months. One key has full admin rights. Its last-used record shows calls 2 days ago from a network abroad.
2. **A public bucket.** Anyone online can list and download the photos <Term id="object-storage">bucket</Term>: about 21,000 photos from about 8,000 customers, with order numbers in the file names.
3. **Firewall rules open to the world.** One server runs both the site and its database. Its rules accept remote login (SSH, port 22) and the database port (5432) from any address. Its login log shows about 3,000 password guesses a day.
4. **One shared admin login.** The account's owner login is shared by 3 people: the workshop manager, an assistant and the freelancer. It has no <Term id="mfa">MFA</Term>.
5. **No audit trail.** There is only the cloud's default record of setting changes, which nobody has read. Nothing records who reads a file, and no alarm watches anything.
6. **Unencrypted backups.** Every night a script writes the whole database to a plain dump file in a second bucket: names, emails, home addresses and orders. It keeps 400 nights, in the same account the admin key opens.

The interviewer's version is one line: "Here is the account. Rank the risks, fix them in order, and tell me what each fix costs."

## How to approach it

Four steps, in this order, for any account review.

1. **Contain.** Ask whether anything is being used against you right now. Stop that first, and keep the evidence.
2. **Rank.** Score every other finding on four questions: who can reach it, what it exposes, whether anyone is using it, and how long the fix takes.
3. **Fix.** One finding at a time, highest first, each with a check that proves it worked.
4. **Prevent.** Add the alarm that would catch it again and the rule that stops it coming back.

The backups rank last only because finding 1 is their real door. Once the admin key is dead, nobody outside can reach them.

## Decision 1: Contain the leaked keys first

<Callout tone="blue" title="Decide first">
  The admin key was used 2 days ago from abroad. Do you delete it, rotate it, or something else? And what do you look for before you touch the bucket?
</Callout>

**The answer.** Deactivate both keys, do not delete them yet. A deactivated key is refused at once, but it can be switched back on, and its last-used record survives. Then look for what the stranger left behind. The default record of setting changes shows a user nobody made, `support-backup`, created 6 days ago with its own admin key. Asha deactivates that too. She lists every identity, key and machine in every region: nothing else is new. She changes the owner password, because the admin key could change sign-in settings, and turns on the audit trail so the next hour is recorded.

The site still needs to write photos. Its server gets an attached <Term id="service-account">service identity</Term> instead of a key, with permission to write to the photos bucket and nothing else. The database password, also in the code, moves to a secret store that the server reads with that identity.

<AnimatedDiagram spec="animated/cloud/iam-role-chain" step={3} minWidth={620} caption="The same repair on the shop's own diagram: the key is gone, the server's attached identity gets a 1-hour token, and a copy of the old key is refused." />

**The trade-off.** Uploads fail from the moment the keys die until the server has its identity, about 40 minutes. Two customers see an error and try again later. Rotating instead, a new key in place of the old one, would keep uploads working, but the new key sits in the same code. Deleting at once loses the last-used record, the only evidence of where the key was used.

<AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={1} minWidth={620} caption="The database password leaves the code: the server proves who it is with its own identity and reads the secret from the store." />

## Decision 2: Close the public bucket

<Callout tone="blue" title="Decide first">
  The site shows each customer a preview of their photo, loaded straight from the bucket. Blocking public access breaks that preview. Block now, or change the site first?
</Callout>

**The answer.** Block now, and block for the whole account, not bucket by bucket. An account-wide setting means no bucket in it can be made public, including one created next year. Then the preview page switches to a **signed URL**: a link the app makes for one file, with a signature and an expiry, here 15 minutes. A stranger who guesses a file name gets a refusal. A customer gets a link that works for their own photo only.

Check it from outside: an anonymous request for a photo is refused, and listing the bucket is refused. The preview page loads a photo through its signed link.

<AnimatedDiagram spec="animated/cloud/landing-zone" step={2} minWidth={620} caption="The same shape as the photo bucket: an account outside the organisation, so the no-public-buckets guardrail never reaches it, and anyone online can download." />

**The trade-off.** For about 2 hours, until the signed-URL change ships, the preview shows a grey placeholder. Orders still go through. Compare that with 21,000 photos open to anyone for another 2 hours. Closing the bucket cannot answer the harder question, whether anyone already downloaded them. Decision 5 deals with that.

Concept pages: [Object storage](/cloud/data/object-storage) and [Landing zones](/cloud/fundamentals/landing-zones), where Brightpost's wholesale team made the same mistake.

## Decision 3: Shrink the firewall

<Callout tone="blue" title="Decide first">
  The freelancer's monthly sales report connects to the database from his laptop. The assistant restarts the site over SSH from home. What stays open to the internet?
</Callout>

**The answer.** Nothing. Asha deletes both rules that allow any address. The database runs on the same machine as the site, so it now listens only on that machine, and port 5432 accepts nothing from the network at all. When the database moves to its own server later, its rule will name the site's <Term id="security-group">security group</Term>, not an address.

SSH is replaced by an identity-checked remote access service: the cloud opens a shell after a sign-in with MFA, and no inbound port is open. The monthly report becomes a scheduled export into a private bucket.

<AnimatedDiagram spec="animated/cloud/firewall-layers" step={6} minWidth={620} caption="Remote access with no open port: the person signs in, and the cloud's own service opens the shell on the server." />

Check it from outside: both ports time out, and the login log's 3,000 guesses a day drop to 0.

**The trade-off.** The freelancer's report stops, which is the point, because his access is ending. The assistant learns a new way in, a browser shell after sign-in, which adds about 20 seconds to each restart. Opening port 22 to "just the office" is weaker: the office address changes, and anyone on the office network gets it too.

Concept pages: [Firewalls](/cloud/networking/firewalls) and [Zero trust](/cloud/resilience/zero-trust).

## Decision 4: One person, one identity, with MFA and roles

<Callout tone="blue" title="Decide first">
  Three people share one owner login. The manager asks for "the same access as now, but safer". Who gets what, and what happens to the owner login?
</Callout>

**The answer.** Each person gets their own sign-in through Brightpost's single sign-on, with MFA, and a role through a group. The role is what the job needs, which is <Term id="least-privilege">least privilege</Term>.

- **The workshop manager:** read-only access and the bill. He changes nothing himself.
- **The assistant:** one narrow role that may start and stop the site's server, and nothing else.
- **Asha:** Brightpost's existing developer group.
- **The freelancer:** removed. If he is hired again, he gets a contractor role that expires.

The owner login stays, because a few tasks need it, such as closing the account. It gets a new long password in a safe, a hardware MFA key and no access keys. Nobody uses it day to day.

<AnimatedDiagram spec="animated/cloud/iam-role-chain" step={5} minWidth={620} caption="People sign in once, with a password and a second proof, and their group decides which role they get." />

**The trade-off.** Changes slow down: the manager used to edit settings in minutes, and now he asks Asha, which can take a day. Everyone gets an MFA prompt. In return, every line in the audit trail names one person, and removing someone from the directory closes every door at once.

Concept page: [Identity and Access](/cloud/fundamentals/identity-and-access), Step 7.

## Decision 5: Turn on audit and detection

<Callout tone="blue" title="Decide first">
  Brightpost must tell customers whether their photos were taken. What must the account record so that, next time, the answer takes an hour instead of "we do not know"?
</Callout>

**The answer.** Three layers, built on the trail Asha started in Decision 1.

1. **An audit trail** for every region. It records every setting change, plus every read of the photos and backup buckets, because reads are not recorded by default. A copy goes to Brightpost's log archive in the audit account, where nobody in this account can delete it.
2. **A threat detector** that reads the trail, the network's flow logs and its DNS logs, and raises findings such as "a key used from an unknown network".
3. **An alert rule** that sends high findings to the on-call engineer's phone. Brightpost learned on [Threat detection](/cloud/resilience/threat-detection) that a finding in a weekly email waits 55 hours.

<AnimatedDiagram spec="animated/cloud/detection-pipeline" step={6} minWidth={620} caption="High findings go to the on-call engineer's phone within minutes; low ones stay in the weekly email." />

**The trade-off.** Read records add a log line for every photo read, and the logs line of the bill grows. So Asha records reads only on the 2 buckets that hold customer data. The detector bills by the volume it reads.

The cost of not having it is already known. With no read records, nobody can say whether the photos or the dumps were downloaded. So Brightpost writes to all 8,000 customers.

Concept page: [Threat detection](/cloud/resilience/threat-detection).

## Decision 6: Encrypt, then bring the account under guardrails

<Callout tone="blue" title="Decide first">
  The storage service already encrypts files at rest. Does encrypting the backups add anything? And what stops the next freelancer from undoing decisions 1 to 5?
</Callout>

**The answer, part one: encryption.** Encryption at rest by the storage service stops a stolen disk. It does not stop a caller with read permission, because the service decrypts for anyone allowed to read. So the backup job now encrypts each dump itself with <Term id="envelope-encryption">envelope encryption</Term>: a fresh data key per file, wrapped by a managed key in the <Term id="kms">key service</Term>. Reading a dump then needs two permissions, one to read the file and one to use the key. Only the restore role has both.

The dumps move into the backup vault in the audit account, with a delete lock. 400 nights become 35. The key gets an `owner` tag and the longest deletion wait, the lesson from [Encryption and keys](/cloud/resilience/encryption-and-keys).

<AnimatedDiagram spec="animated/cloud/encryption-states" step={3} minWidth={620} caption="Each state of the data has its own control and its own key holder. A key the storage service holds protects against a stolen disk, not against a caller." />

**Part two: guardrails.** A guardrail is a rule set at the top of the <Term id="organization">organisation</Term> that no account below can override. The framing account joins Brightpost's organisation, in the production folder. On arrival the root guardrails reach it: 2 allowed regions, and no public buckets. Brightpost adds one more at the root: no new long-lived keys. Now the fixes from decisions 1 and 2 cannot be undone from inside the account.

<AnimatedDiagram spec="animated/cloud/landing-zone" step={3} minWidth={620} caption="The account joins the tree, the root guardrail reaches it, and the public read is refused." />

**The trade-off.** A restore gains one step, unwrapping the data key, about 10 minutes. A lost key means lost backups, hence the tag and the wait. Before the move, Asha checks the site runs in one of the 2 allowed regions, because a guardrail that blocks the site's own region would take it down. It does.

Concept pages: [Encryption and keys](/cloud/resilience/encryption-and-keys), [Backups and vaults](/cloud/resilience/backups-and-vaults) and [Landing zones](/cloud/fundamentals/landing-zones).

## On AWS, Google Cloud and Azure

The order is the same on all three clouds: contain, rank, fix, prevent. The controls have different names, and two defaults differ in ways that matter.

<Tabs title="On each cloud">
  <Tab label="AWS">
    - **Leaked keys:** IAM access keys. Deactivate first, delete later. The credential report and each key's last-used data show which keys are live.
    - **Public storage:** S3 Block Public Access, switched on for the whole account. Presigned URLs for one-photo links.
    - **Firewall:** security groups with no inbound rule for port 22. Session Manager in AWS Systems Manager opens a shell with no open port.
    - **People:** IAM Identity Center users and groups with MFA. The root user gets MFA and no access keys.
    - **Audit and detection:** CloudTrail event history keeps 90 days of management events. A trail keeps them longer, in another account, and can add S3 data events. GuardDuty detects; Security Hub collects findings.
    - **Encryption and guardrails:** AWS KMS keys with key policies. The account joins AWS Organizations by invitation, and service control policies (SCPs) then cap it.

    **The difference that changes a design.** With SSE-KMS, reading an S3 object needs permission to use the KMS key as well as to read the object. So a key policy that names only the backup and restore roles keeps a leaked storage credential away from the dumps. On the other two clouds the storage service uses the key on the caller's behalf. There, the same split needs encryption inside the backup job.
  </Tab>
  <Tab label="Google Cloud">
    - **Leaked keys:** service account keys. Disable first, delete later. An organization policy constraint can forbid creating new ones.
    - **Public storage:** public access prevention, on a bucket or enforced by organization policy, blocks grants to `allUsers`. Signed URLs for one-photo links.
    - **Firewall:** VPC firewall rules. The default network comes with rules that allow SSH and RDP from anywhere, so check for them. IAP TCP forwarding gives SSH with no public address.
    - **People:** Cloud Identity or Google Workspace accounts and groups, with 2-Step Verification. Avoid the basic Owner role.
    - **Audit and detection:** Admin Activity audit logs are always on. Data Access audit logs are off by default for most services, Cloud Storage included. Security Command Center detects and collects findings.
    - **Encryption and guardrails:** data at rest is always encrypted; Cloud KMS gives a key you control (CMEK). The project moves into a folder of the organization.

    **The difference that changes a design.** Grants and policies inherit down the tree. When the project moves under the production folder, every role granted on that folder reaches it on arrival, and so does every organization policy. Review the folder's grants before the move, because the bought project's people may get more than you meant.
  </Tab>
  <Tab label="Azure">
    - **Leaked keys:** storage account keys and service principal secrets. Regenerate both storage keys, then turn off Shared Key authorization so only Microsoft Entra ID sign-in works.
    - **Public storage:** turn off anonymous blob access on the storage account. A user delegation SAS gives one-photo links.
    - **Firewall:** network security groups. Azure Bastion opens SSH from the portal with no public address on the VM.
    - **People:** Microsoft Entra ID users and groups, with MFA through Conditional Access. Privileged Identity Management grants admin roles on demand.
    - **Audit and detection:** the Activity log keeps control-plane events for 90 days. Diagnostic settings send it, and storage read logs, to a Log Analytics workspace. Microsoft Defender for Cloud detects.
    - **Encryption and guardrails:** storage and managed disks are encrypted at rest by default; Key Vault holds customer-managed keys. The subscription moves under a management group, and Azure Policy applies.

    **The difference that changes a design.** A bought subscription often sits in the seller's own Entra tenant. Moving it into Brightpost's tenant deletes all of its role assignments, and managed identities must be set up again. Plan the move as a small migration: list every assignment and identity first, then recreate them in the new directory.
  </Tab>
</Tabs>

## Common mistakes in this interview

- **Fixing the scariest finding first.** Open ports look alarming, but the admin key was in use. Ask "what is being used right now?" before "what looks worst?".
- **Deleting the key at once.** It destroys the last-used record and leaves no way back if the site breaks. Deactivate, investigate, then delete.
- **Rotating into the same place.** A new key in the same repository is the same finding with a new date. Replace keys with an attached identity.
- **Forgetting what the attacker left.** The `support-backup` user would have survived every other fix. List every identity and key the account holds, not only the ones you know.
- **Calling encryption the fix for a public bucket.** The storage service decrypts for anyone allowed to read, and "public" means everyone is allowed.
- **Stopping at the fix.** Without guardrails, the next freelancer can reopen any of the six. Every fix needs a rule or an alarm that keeps it shut.

## Interview questions

<InterviewQuestions>
  <InterviewQuestion question="You find an admin access key in a repository that was public for 8 months. What do you do in the first hour?" level="Senior" category="Cloud">
    **Short answer.** Deactivate the key, then check what it did and what it left behind, then replace it with an attached identity. I keep the key's records as evidence and turn on the audit trail before I change anything else.

    **Why.** A key that was public for 8 months has been copied; the only question is by whom. Deactivating refuses it at once and keeps its last-used record. At the framing shop that record showed calls from abroad, and the settings history showed a user nobody made, with its own admin key. Rotating would put a new key in the same code. Uploads failed for about 40 minutes, which was the price.

    <AnimatedDiagram spec="animated/cloud/iam-role-chain" step={2} caption="A valid key works for whoever holds it, and the cloud cannot tell the stranger from the owner." />

    **Follow-ups the interviewer may ask.**
    - What else could an admin key have created that survives its deletion?
    - When do you finally delete the key?

    **Watch out for.** Deleting the key first. It feels decisive, but it removes the one record of where the key was used.
  </InterviewQuestion>

  <InterviewQuestion question="An account has six security findings and you can fix one at a time. How do you rank them?" level="Senior" category="Cloud">
    **Short answer.** First anything in use right now, then anything open to anyone, then the rest by exposure and effort. I score each on who can reach it, what it exposes, whether it is being used, and how long the fix takes.

    **Why.** At the framing shop the admin key ranked first, because it had been used 2 days earlier and opened everything. The public bucket came second: anyone online, 21,000 photos. The open ports came third: scripts tried 3,000 passwords a day. The plain backups ranked last, because the admin key was their only door, and it was already shut. Quick wins with high exposure go early, whatever their category.

    **Follow-ups the interviewer may ask.**
    - Would you ever fix a low-ranked item first?
    - How does the ranking change if the bucket held payment data?

    **Watch out for.** Ranking by category, such as "identity first, always". The order comes from this account's facts, not from a list.
  </InterviewQuestion>

  <InterviewQuestion question="A colleague says the public bucket is safe because the storage service encrypts everything at rest. Is that right?" level="Senior" category="Cloud">
    **Short answer.** No. Encryption at rest protects data from someone who steals the disk. The storage service decrypts for every caller it allows, and a public bucket allows everyone.

    **Why.** Each place data lives has its own control and its own key holder. When the storage service holds the key, the only thing between a stranger and a photo is the permission check, and "public" turns that check off. Encryption earns its keep when the key needs a separate permission. The framing shop's dumps are now encrypted by the backup job itself, so reading one needs both the file and the key, and only the restore role has both.

    <AnimatedDiagram spec="animated/cloud/encryption-states" step={2} caption="Each control stops one thing: encryption at rest stops a stolen disk, not a caller the store lets in." />

    **Follow-ups the interviewer may ask.**
    - When does a key you manage yourself add real protection?
    - What is the new risk once you manage the key?

    **Watch out for.** Treating "encrypted" as "private". They answer different questions.
  </InterviewQuestion>

  <InterviewQuestion question="Three people share one owner login and work from home. How do you move them off it without locking anyone out?" level="Senior" category="Cloud">
    **Short answer.** Give each person a named sign-in through single sign-on with MFA, and a role through a group that matches their job. Test each one, and only then lock the owner login away with a new password and a hardware key.

    **Why.** A shared login means the audit trail can never name a person, and nobody can remove one of the three. At the framing shop the manager got read-only and billing, the assistant a role that may only restart the site's server, and the freelancer nothing. The owner login still exists for a few account-level tasks, kept in a safe. Changes now take up to a day, because the manager asks instead of clicking.

    <AnimatedDiagram spec="animated/cloud/iam-role-chain" step={5} highlight={["sso", "dev"]} caption="People sign in once with MFA, and the group decides the role." />

    **Follow-ups the interviewer may ask.**
    - What if the single sign-on service itself is down?
    - How do you give the freelancer access for one week next month?

    **Watch out for.** Adding MFA to the shared login and calling it done. It is still one login for 3 people, with no names in the records.
  </InterviewQuestion>

  <InterviewQuestion question="The account kept no audit trail of its own. What can you still learn about the intrusion, and what will you never know?" level="Senior" category="Cloud">
    **Short answer.** You can learn what changed: the cloud's default record of setting changes, each key's last-used data, and logs on the server itself. You cannot learn what was read, because reads were never recorded.

    **Why.** At the framing shop the settings record showed the stranger's new user, created 6 days earlier. The key's last-used data showed a network abroad. Nothing showed whether anyone downloaded the 21,000 photos or the 400 dumps. So Brightpost had to treat all 8,000 customers as affected and write to every one. Read records on the 2 buckets would have cost a little on the logs bill.

    <AnimatedDiagram spec="animated/cloud/detection-pipeline" step={1} caption="Every call written to a trail, with a locked copy in the log archive: the record the framing account never had." />

    **Follow-ups the interviewer may ask.**
    - Why must the copy live in a different account?
    - Which reads would you record, and which would you skip?

    **Watch out for.** Saying "the logs show nothing happened". A log that never recorded reads cannot show that.
  </InterviewQuestion>

  <InterviewQuestion question="You bought a company that has its own cloud account. How do you bring it under your guardrails without breaking its site?" level="Senior" category="Cloud">
    **Short answer.** Contain the urgent findings first, then compare the account with every guardrail before it joins. Fix or plan for each conflict, then move it into the right folder, where the guardrails apply on arrival.

    **Why.** A guardrail is enforced the moment the account joins, so a conflict becomes an outage. The framing account's site had to run in one of Brightpost's 2 allowed regions, and it did. Its preview page used a public bucket, so the signed-link change shipped first. The new rule against long-lived keys could only join after the site's keys were gone. Inheritance also brings grants, so the production folder's roles are checked too.

    <AnimatedDiagram spec="animated/cloud/landing-zone" step={3} caption="The account joins the production folder, and the root guardrail refuses the public read." />

    **Follow-ups the interviewer may ask.**
    - What changes if the account sits in the seller's own directory?
    - Would you rather rebuild the site in a new account?

    **Watch out for.** Moving the account on day one "so the guardrails fix it". A guardrail refuses things; it does not repair them, and the site goes down with the bucket.
  </InterviewQuestion>
</InterviewQuestions>
