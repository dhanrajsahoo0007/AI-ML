AWS gives you two ways to orchestrate containers and two ways to supply the machines underneath them, and the four combine freely. That is why "ECS or EKS? Fargate or EC2?" confuses people: they are answers to two different questions.

## The idea

An orchestrator keeps a written list of which containers should run, and keeps changing the machines until they match that list. On AWS you pick who keeps the list (ECS, or Kubernetes in EKS) and, separately, who runs the machines under it.

With EKS, AWS runs the whole orange control plane and you see only its API. ECS replaces that box with AWS's own scheduler, which has no Kubernetes API and no version for you to upgrade.

## TL;DR

- **Two questions, not one.** *Who schedules the containers?* ECS (AWS's own orchestrator) or EKS (Kubernetes). *What runs them?* Fargate (no servers), EC2 (your instances) or AWS-managed instances.
- **Default to ECS on Fargate** for a new service on AWS: no control-plane fee, no hosts, fewest moving parts.
- **Pick EKS when Kubernetes itself is the requirement:** existing skills, Helm charts and operators, or one platform across clouds. Use **Auto Mode** unless you need custom nodes.
- **Move to EC2 capacity** for GPUs, very large tasks, or steady high load where Savings Plans beat Fargate's per-task price.
- **App Runner is closed to new customers** (since April 30, 2026). The equivalent today is **ECS Express Mode**.

## The two questions

| | **Fargate** (no servers) | **EC2** (your instances) | **Managed instances** (AWS runs EC2 you choose) |
|---|---|---|---|
| **ECS** | The default: per-task billing, nothing to patch | GPUs, big tasks, bin-packing, Spot and Savings Plans | ECS Managed Instances: EC2 choice without host operations |
| **EKS** | Fargate profiles: no nodes, but no DaemonSets | Managed node groups + Karpenter: full control | EKS Auto Mode: AWS provisions, patches and right-sizes nodes |

Go across a row and you change **who runs the machines**. Go down a column and you change **which API you deploy with**. Each step to the right of "EC2" removes a job from your team and adds a little cost or a little less control. The general idea, column by column, is in [Kubernetes Concepts](/cloud/compute/kubernetes-concepts), step 10.

## Services

### Amazon ECS

<CloudServiceProfile id="aws-ecs" />

ECS has three building blocks. A **task definition** is the blueprint: image, CPU, memory, ports and IAM role. A **task** is one running copy of it. A **service** keeps N tasks running behind a load balancer, replaces failed ones and rolls out new versions. **Capacity providers** decide where tasks land: Fargate, Fargate Spot, an Auto Scaling group of EC2 instances, or Managed Instances. You can mix them, for example a base of on-demand Fargate with burst capacity on Fargate Spot.

For service-to-service calls inside the cluster, **ECS Service Connect** gives each service a short name, client-side load balancing, retries and per-call metrics without a separate service mesh.

### Amazon EKS

<CloudServiceProfile id="aws-eks" />

The real cost of EKS is people, not the cluster fee. At least once a year someone upgrades the control plane, the nodes and the add-ons (VPC CNI, CoreDNS, kube-proxy, the load balancer controller). Then they test every Helm chart against the new version. **EKS Auto Mode** takes nodes and core add-ons off that list. It is the right default for a new cluster unless you need custom AMIs, special kernel settings or tight control over the instance mix.

### AWS Fargate

<CloudServiceProfile id="aws-fargate" />

Fargate is a capacity type, not an orchestrator. You always use it through ECS or EKS. Because each task gets its own micro-VM, tasks never share a kernel with another customer or with each other, which makes it a good fit for multi-tenant work.

### ECS Express Mode

Express Mode, launched in November 2025, is the shortest path from an image to a running web service. One command or console form creates the ECS service on Fargate, an Application Load Balancer with HTTPS, autoscaling, and a URL. The result is a normal ECS service: when you outgrow the defaults, you edit it like any other.

## How the choice plays out

| Situation | Pick | Why |
|---|---|---|
| A new API, a small team, uneven traffic | ECS on Fargate | Nothing to patch, no control-plane fee, scales per task |
| A web app that needs only a URL | ECS Express Mode | Load balancer, TLS and autoscaling in one step |
| WebSocket servers holding millions of connections | ECS on EC2 behind an NLB | Large network-optimised instances, steady load, Savings Plans |
| Kafka consumers or queue workers | ECS on Fargate (Spot for retryable work) | Scale on queue depth, interruptions are safe |
| GPU inference | EKS or ECS on EC2 GPU instances | Fargate has no GPUs |
| Ten teams, shared platform, Helm everywhere | EKS Auto Mode | Kubernetes namespaces, quotas and tooling without node work |
| Same platform on AWS, GCP and on-prem | EKS (+ EKS Anywhere / Hybrid Nodes) | One API everywhere |

The [Facebook Messenger](/system-design/case-studies/facebook-messenger) design is a good test. The chat servers hold long-lived WebSockets and run at steady high load, which points to ECS on large EC2 instances behind a Network Load Balancer. The fan-out workers and history service are ordinary stateless consumers, which fit ECS on Fargate.

## Common mistakes

- **Choosing EKS because it is popular.** Kubernetes pays off with many teams and services. For three services it is mostly upgrade work.
- **Comparing Fargate and EC2 on list price alone.** EC2 needs headroom, patching time and bin-packing work. Fargate usually wins below steady high utilisation.
- **Requesting far more CPU and memory than tasks use.** Fargate bills what you request. Right-size from real metrics.
- **Forgetting image pull time.** New tasks take tens of seconds to start. Scale on a leading signal (queue depth, request rate), not only CPU.
- **Running everything in one Availability Zone.** Spread services across at least three.

  <InterviewQuestion question="ECS or EKS for a new service on AWS?" category="Cloud" level="Mid">
    **Short answer.** ECS, unless Kubernetes itself is a requirement. ECS has no control-plane fee and far fewer parts to upgrade. EKS earns its place when the team already runs Kubernetes or needs one platform across clouds.

    **Why.** With ECS, AWS runs the scheduler and there is no Kubernetes version to keep current. Task roles, load balancer target groups and CloudWatch work with no add-ons. EKS gives you the standard Kubernetes API: Helm charts, operators and the same manifests on other clouds. The price is people. Someone upgrades the cluster at least once a year and retests every add-on. For a team of 3 engineers, that is a large share of a week.

    <AnimatedDiagram spec="animated/cloud/k8s-cluster-anatomy" cloud="aws" highlight={["api", "store", "controllers", "scheduler"]} minWidth={620} caption="With EKS, AWS runs these four parts, but you still choose their version and upgrade the add-ons around them." />

    **Follow-ups the interviewer may ask.**
    - If you start on ECS and move to EKS later, what carries over?
    - What does ECS Service Connect give you that a service mesh would?

    **Watch out for.** Picking EKS because "everyone uses Kubernetes". It pays off with many teams and services, not with three.

  <InterviewQuestion question="When is Fargate the wrong choice?" category="Cloud" level="Mid">
    **Short answer.** When you need GPUs, tasks bigger than Fargate's largest size, or access to the host. Also when load is steady and high enough that EC2 with a Savings Plan is clearly cheaper per vCPU-hour.

    **Why.** Fargate gives each task its own isolated slice of a machine and hides the host. That rules out anything that needs the host: DaemonSets on EKS (one pod on every node, such as a log agent), privileged containers and custom kernels. Fargate bills by the second for what each task requests. With uneven load that wins, because no idle host is waiting. With steady load near full use, a commitment on EC2 instances costs less. The general idea is on [Pricing Basics](/cloud/fundamentals/pricing-basics).

    **Follow-ups the interviewer may ask.**
    - How would you ship logs from Fargate tasks without a DaemonSet?
    - When would ECS Managed Instances beat both Fargate and plain EC2?

    **Watch out for.** Comparing list prices only. EC2 also needs spare headroom, patching time and bin-packing work.
  </InterviewQuestion>

  <InterviewQuestion question="What does EKS Auto Mode change?" category="Cloud" level="Senior">
    **Short answer.** AWS takes over the nodes. It launches right-sized instances for pending pods, patches and replaces them, and runs the core add-ons. You keep the Kubernetes API and your workloads, pay a management fee on those instances, and give up some control of node settings.

    **Why.** In the cluster picture, the nodes are the bottom band. With managed node groups that band is yours: instance types, machine image updates and the node autoscaler. Auto Mode moves it to AWS, using Karpenter underneath. What stays yours: when to upgrade the Kubernetes version, pod requests and limits, and readiness checks. Brightpost's 90-second warm-up gap, from the concept page, would break an Auto Mode cluster in exactly the same way.

    <AnimatedDiagram spec="animated/cloud/k8s-cluster-anatomy" cloud="aws" highlight={["kubelet1", "kubelet2", "kubelet3"]} minWidth={620} caption="Auto Mode moves the node band to AWS: it picks, patches and replaces the machines the kubelets run on." />

    **Follow-ups the interviewer may ask.**
    - Which workloads would you keep on a node group you manage yourself?
    - How is Auto Mode different from running pods on Fargate profiles?

    **Watch out for.** Calling Auto Mode "serverless Kubernetes". You still own the cluster version, the manifests and the pod sizes.
  </InterviewQuestion>

  <InterviewQuestion question="How would you run WebSocket servers for a chat app on AWS?" category="Cloud" level="Senior">
    **Short answer.** ECS services on network-optimised EC2 instances behind a Network Load Balancer, spread across three Availability Zones. A registry in ElastiCache records which user is connected to which server.

    **Why.** A WebSocket stays open for minutes or hours, so the load is steady and long-lived. A Network Load Balancer passes long-lived TCP connections through with little overhead. Large instances hold many connections each, and steady use suits a Savings Plan. The user-to-server registry lets any server forward a message to the server that holds the recipient. On deploys, drain connections gradually so clients reconnect in waves, not all at once.

    **Follow-ups the interviewer may ask.**
    - What happens to a million open connections during a deploy?
    - How does the registry survive a cache node failure?

    **Watch out for.** Scaling connection servers on CPU. Open connections, not CPU, are what fills these servers.
  </InterviewQuestion>
