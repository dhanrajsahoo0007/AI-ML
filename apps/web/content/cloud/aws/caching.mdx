A cache in a system design diagram is usually **ElastiCache** on AWS. The choices that matter are the engine (Valkey for new clusters), node-based versus Serverless, and whether the data may be lost. Data you cannot lose belongs in **MemoryDB** or a real database. For DynamoDB-heavy designs, **DAX** caches without any cache code.

## The idea

A managed cache keeps answers you will need again in fast memory, and the cloud runs the servers, the copies and the failover. You still decide what goes in, under which key, for how long, and what happens on a miss.

## TL;DR

- **ElastiCache for Valkey** for cache-aside, sessions, counters, leaderboards, rate limits and ephemeral state such as presence.
- **ElastiCache Serverless** when traffic is unpredictable or you don't want to size shards; **node-based clusters** for steady, large caches at the lowest cost.
- **MemoryDB** when Redis data structures are the system of record and must survive failover without data loss.
- **DAX** for read-heavy DynamoDB tables. **CloudFront** is also a cache, for HTTP responses at the edge.

## How it fits together on AWS

In step 2 the app servers read the hero poster's key from an ElastiCache node and fill it from RDS on a miss. Steps 3 and 4 are code in the app. ElastiCache has no built-in guard against a stampede, so the rebuild lock is a `SET … NX EX 5` on the same cache. In step 5 the node becomes a **replication group**: a primary plus a replica in a second Availability Zone, with Multi-AZ automatic failover. In step 6, **cluster mode enabled** spreads the slots over shards. Step 7 is CloudWatch.

| The concept says | On AWS | What to know |
|---|---|---|
| The cache's one address | Primary endpoint (one shard) or configuration endpoint (cluster mode enabled) | The endpoint name stays the same after a failover; clients must reconnect |
| Replica in zone B | A replica in the same replication group, Multi-AZ on | A reader endpoint spreads reads over replicas |
| Shards | Cluster mode enabled | Needs a cluster-aware client; resharding is online |
| What to watch | CloudWatch: `CacheHitRate`, `Evictions`, `DatabaseMemoryUsagePercentage`, `EngineCPUUtilization`, `ReplicationLag` | Alarm on engine CPU, not the node's average CPU |

## Services

### Amazon ElastiCache

<CloudServiceProfile id="aws-elasticache" />

Pick it when the data can be rebuilt from a database or other source: page caches, sessions, counters, presence.

| Use | Data structure | Example |
|---|---|---|
| Cache-aside | String with TTL | `user:42 → JSON`, 5-minute TTL |
| Sessions | Hash with TTL | `session:abc → {user, roles}` |
| Rate limiting | Counter with expiry, or sorted set | `rl:42:2026-11-05T10:01 → 17` |
| Leaderboards | Sorted set | `ZADD board 1500 user42` |
| Presence and routing | String with TTL, refreshed by heartbeat | `conn:42 → chat-server-7` |
| Nearby search | GEO set | `GEOSEARCH couriers FROMLONLAT … BYRADIUS 3 km` |
| Fan-out between servers | Pub/sub | `PUBLISH convo:9 …` |

### Amazon MemoryDB

<CloudServiceProfile id="aws-memorydb" />

Pick it when the Redis-style data is the only copy and an acknowledged write must survive a failover.

### Amazon DynamoDB Accelerator (DAX)

<CloudServiceProfile id="aws-dax" />

Pick it when a DynamoDB table is read far more than it is written and eventually consistent reads are fine.

## Where this shows up in system design

- **[Messenger](/system-design/case-studies/facebook-messenger):** the session registry (user → chat server) and presence with heartbeat TTLs in ElastiCache.
- **[Uber Eats](/system-design/case-studies/uber-eats):** live courier locations in a GEO set, refreshed every few seconds.
- **[Rate limiter](/system-design/case-studies/rate-limiter):** token or sliding-window counters with atomic Lua scripts (see [Rate Limiting](/system-design/patterns/rate-limiting)).
- **[URL shortener](/system-design/case-studies/url-shortener) and [typeahead](/system-design/case-studies/typeahead):** hot keys and top prefixes cached in front of the database.

## Common mistakes

- **Using the cache as the database.** A failover or eviction can lose recent writes. Rebuild from the source, or use MemoryDB.
- **No TTLs.** Stale data never leaves and memory fills. Give every key a TTL unless there is a clear reason not to.
- **Cache stampede on a hot key.** When it expires, thousands of requests hit the database at once. Use a rebuild lock, early refresh and jittered TTLs (see [Managed Caches](/cloud/data/managed-caches)).
- **Multi-key operations across shards.** In cluster mode, keys in one transaction must share a hash slot. Use hash tags such as `{user42}:cart`.
- **Picking Redis OSS by habit.** Valkey is protocol-compatible and priced lower on ElastiCache.

  <InterviewQuestion question="ElastiCache or MemoryDB?" category="Cloud" level="Mid">
    **Short answer.** ElastiCache when the data can be rebuilt from a source of truth: page caches, sessions you can recreate, counters that may reset. MemoryDB when the in-memory store is the source of truth and must not lose an acknowledged write.

    **Why.** ElastiCache copies writes to its replica a moment later, so a failover can drop the last few. For Brightpost's product pages that is only a miss. MemoryDB writes each change to a log across several zones before it answers. That makes writes take a few milliseconds instead of well under one, and it costs more.

    <AnimatedDiagram spec="animated/cloud/cache-patterns" step={5} cloud="aws" highlight={["cache", "replica"]} minWidth={620} caption="ElastiCache copies to the replica after it answers, so the newest writes can be lost in a failover." />

    **Follow-ups the interviewer may ask.**
    - Would snapshots on ElastiCache make it safe for orders?
    - Where would Brightpost's baskets go, and why?

    **Watch out for.** Calling ElastiCache with Multi-AZ "durable". It survives a node, not every recent write.
  </InterviewQuestion>

  <InterviewQuestion question="How would you keep a presence system in ElastiCache?" category="Cloud" level="Mid">
    **Short answer.** Each chat server sets a key per connected user with a short TTL, say 30 seconds, and refreshes it on every heartbeat. A missing key means offline.

    **Why.** The TTL does the clean-up: a crashed server stops refreshing, and its users go offline within 30 seconds with no extra code. The value can hold the user's chat server, so the same key routes messages. Last-seen times are written to the database when a user disconnects. Status changes reach friends through pub/sub or the messaging pipeline.

    **Follow-ups the interviewer may ask.**
    - What happens to presence during an ElastiCache failover?
    - How do you avoid sending every status change to every friend?

    **Watch out for.** Storing presence in the database. Millions of heartbeats a minute are writes nobody needs to keep.
  </InterviewQuestion>

  <InterviewQuestion question="Brightpost outgrows one ElastiCache shard. What changes when you turn on cluster mode, and what still breaks?" category="Cloud" level="Senior">
    **Short answer.** The keys spread over several shards, each with its own replica, and the app connects through the configuration endpoint with a cluster-aware client. Multi-key commands now need related keys in one slot, and a hot key still lives on one shard.

    **Why.** Brightpost's 260 MB fits one node today, so this is the growth plan. With cluster mode on, the client learns which shard owns each slot and sends each command straight there. Resharding moves slots online. A transaction on `basket:42` and `basket:42:items` fails unless both use a hash tag such as `{basket:42}`. The hero poster's 600 reads a second still land on one shard's main thread.

    <AnimatedDiagram spec="animated/cloud/cache-patterns" step={6} cloud="aws" highlight={["cache", "shards", "key"]} minWidth={620} caption="Cluster mode hands slots to new shards; the hero poster's key stays on the shard that owns its slot." />

    **Follow-ups the interviewer may ask.**
    - When is a bigger node a better answer than more shards?
    - Would ElastiCache Serverless remove this decision?

    **Watch out for.** Pointing the old single-shard client at the configuration endpoint. A client that is not cluster-aware gets redirect errors on most keys.
  </InterviewQuestion>
