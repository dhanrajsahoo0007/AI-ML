A design isn't finished until you can say how you'd know it's broken. On AWS that means **CloudWatch** for metrics, alarms and logs, **X-Ray** (fed by **OpenTelemetry**) for traces across services, and **CloudTrail** for who changed what in the account. Teams that already live in Prometheus and Grafana use the managed versions of those instead.

## The idea

A running system sends out three signals: metrics say whether something is wrong, logs say what happened, and traces say where the time went. An agent on each workload ships them to managed stores, and an alert watches the number users feel.

## TL;DR

- **Alarm on symptoms users feel**: error rate, latency percentiles, queue age, consumer lag. Don't alarm on CPU alone.
- **Instrument once with OpenTelemetry** (the AWS Distro for OpenTelemetry, ADOT), and send traces to X-Ray and metrics to CloudWatch or Managed Prometheus. The X-Ray SDKs reach end of support in February 2027.
- **Structured JSON logs** with a trace id, searched with Logs Insights, and a retention period on every log group.
- **A CloudTrail organisation trail** into a locked log-archive account for audit and security.

## How it fits together on AWS

In steps 1 and 2, Brightpost's three services run on six EC2 instances, and each writes its own log file. In step 3 the **CloudWatch agent** goes on every instance. EC2 already reports processor, network and disk traffic; memory and disk space need the agent, because they live inside the operating system. A CloudWatch dashboard charts them.

In step 4 the same agent tails the log files into **CloudWatch Logs**, one log group per service, each with 30 days of retention set in code. In step 5 the ADOT libraries in each service create spans and pass the W3C `traceparent` header on every call; the agent or an ADOT collector forwards them to **X-Ray**. In step 6 a **CloudWatch alarm** watches p99 Pay time and publishes to an SNS topic, which reaches Asha's paging tool.

| The concept says | On AWS | What to know |
|---|---|---|
| Collector | CloudWatch agent, or the ADOT collector | Memory and disk space on EC2 appear only with the agent |
| Log store | A CloudWatch Logs log group per service | A new group keeps logs forever until you set retention |
| Trace store | X-Ray; CloudWatch Application Signals on top | An Application Load Balancer adds its own `X-Amzn-Trace-Id` header; your code must still pass the context on |
| Alert rule and route | CloudWatch alarm → SNS topic | A composite alarm joins two alarms, such as a short and a long window |
| Audit trail | CloudTrail organisation trail | Lands in the audit account, not the shop account |

## What to watch in a typical design

| Component | Key signals | Alarm when |
|---|---|---|
| Load balancer / API Gateway | 5xx rate, p99 latency, request count | 5xx > 1% for 5 min; p99 above SLO |
| ECS service / Lambda | Errors, throttles, duration, concurrency | Throttles > 0; errors spike |
| SQS queue | Age of oldest message, DLQ depth | Oldest message older than the processing SLA; DLQ > 0 |
| Kinesis / MSK | Iterator age / consumer lag | Lag growing for 10 min |
| DynamoDB | Throttled requests, latency | Any sustained throttling |
| Aurora | CPU, replica lag, connections | Replica lag > a few seconds; connections near max |
| ElastiCache | Evictions, memory, hit ratio | Evictions rising; hit ratio dropping |

## Services

### Amazon CloudWatch

<CloudServiceProfile id="aws-cloudwatch" />

Pick it when the workload runs on AWS: it is where AWS services already send their metrics and logs, and where alarms live. **Logs Insights** queries log groups with a pipe-style query language; **Application Signals** adds service maps and SLOs on top of the same data.

### AWS X-Ray

<CloudServiceProfile id="aws-xray" />

Pick it when one request crosses several services and you need the slow hop. Instrument new code with ADOT, not the X-Ray SDKs.

### AWS CloudTrail

<CloudServiceProfile id="aws-cloudtrail" />

Pick it for every account, always: it answers "who changed this, and when?" after an incident or a leak.

### Amazon Managed Service for Prometheus and Amazon Managed Grafana

Pick them when the team already writes PromQL queries and Grafana dashboards, often for EKS. AWS runs the storage and the Grafana servers; the dashboards keep working, and Grafana can read CloudWatch and X-Ray as extra data sources.

## Where this shows up in system design

- **Every case study's "how would you monitor this?" follow-up:** name the SLOs (for example, 99.9% of messages delivered within 1 second) and the signals above that measure them.
- **[Metrics and logging](/system-design/case-studies/metrics-and-logging):** the case study designs what CloudWatch and Prometheus do internally.
- **Debugging fan-out:** a trace shows a message going from the chat server through the bus and fan-out workers to the recipient's server, with the time spent at each hop.

## Common mistakes

- **Alerting on causes, not symptoms.** In July Brightpost's print servers sat at about 20% processor use while Pay took 9 seconds. Alarm on p99 Pay time.
- **No retention on log groups.** A new group keeps every line until told otherwise. Set retention when the group is created, in code.
- **Averages instead of percentiles.** p99 latency shows the slow requests an average hides.
- **New code on the X-Ray SDKs.** They are near end of support. Use ADOT, which also lets you change backends later.
- **No trace id in the logs.** Without one id across logs and traces you can't follow a request.

  <InterviewQuestion question="Brightpost's alarm fires: p99 Pay time is above 2 seconds. How do you find the cause on AWS?" category="Cloud" level="Mid">
    **Short answer.** Metrics first, then a trace, then logs. The CloudWatch chart shows when it started and which service changed. An X-Ray trace of a slow Pay shows which span held the time. A Logs Insights query on that trace id shows why.

    **Why.** Each signal answers one question, and each is one click from the next. In July the p99 was 8.7 seconds while the average was 1.1, so only some baskets were slow. The trace showed 9.0 seconds inside the print service. Its log lines, found by trace id, said an A1 print file was being built before Pay answered. Starting from the logs meant six files and no shared id: 2 days instead of 5 minutes.

    - What if the trace for that Pay was not kept by sampling?
    - How would Application Signals change this walk?

    **Watch out for.** Saying "check the logs" first. Without a trace id, the logs are 6 files to read by the clock.

  <InterviewQuestion question="Which alarms would you set for an SQS-based worker pipeline?" category="Cloud" level="Mid">
    **Short answer.** The age of the oldest message, dead-letter queue depth above zero, the worker's error rate and throttles, and the latency of whatever the worker calls.

    **Why.** Suppose Brightpost builds print files from an SQS queue after Pay answers. The oldest message's age says the workers are falling behind, in the time a shopper's order waits. A message in the dead-letter queue has failed again and again, so one is enough to look at. Queue length alone misleads: a long queue that drains in a minute is fine.

    **Follow-ups the interviewer may ask.**
    - Which of these alarms should page someone, and which should open a ticket?
    - How would you scale the workers from the same metric?

    **Watch out for.** Alarming on `ApproximateNumberOfMessagesVisible` alone. It rises on every busy morning and teaches people to ignore it.
  </InterviewQuestion>

  <InterviewQuestion question="How do you set up CloudTrail so that someone who breaks into the shop account cannot erase the evidence?" category="Cloud" level="Senior">
    **Short answer.** One organisation trail, created from the management account, writing to an S3 bucket in the separate audit account. Member accounts cannot change or stop an organisation trail, and nobody in the shop account can delete objects in that bucket.

    **Why.** Brightpost keeps its log archive in the audit account for this reason. A trail inside the shop account can be stopped by anyone who takes over an admin role there. The archive bucket gets a policy that refuses deletes, Object Lock for a retention period, and log file validation, so a changed file is detectable. Operational logs stay in CloudWatch in each account, with 30 days of retention.

    **Follow-ups the interviewer may ask.**
    - Would you record data events, such as every S3 read, and what would that cost?
    - How would you alert when someone makes a bucket public?

    **Watch out for.** Relying on the 90 days of event history in each account. It is not a trail, and it lives in the account being attacked.
  </InterviewQuestion>
