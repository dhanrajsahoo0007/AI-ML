Brightpost's product pages and baskets must load in well under a millisecond on sale day, without every view becoming a query on the orders database. On Google Cloud that job belongs to one product, **Memorystore**, which runs Valkey, Redis or Memcached for you. Two facts shape the design. A Memorystore cache has no public address, so it is reached only from inside your VPC network. And durability is a setting on the same cache, not a separate product.

## The idea

A managed cache keeps answers you will need again in fast memory, and the cloud runs the servers, the copies and the failover. You still decide what goes in, under which key, for how long, and what happens on a miss.

## TL;DR

- **Memorystore for Valkey** is the default for new caches: sessions, page caches, counters, leaderboards and presence.
- **Memorystore for Redis Cluster** for existing Redis code that needs shards; a single **Memorystore for Redis** instance grows only in size.
- There is no serverless tier: you choose node type, shard count and replicas, and change them online.
- No cache is built into Firestore or Bigtable. Put Memorystore in front of them in your own code.

## How it fits together on Google Cloud

Step 1: the app servers on Compute Engine read baskets from Memorystore and every product page from Cloud SQL. Step 2: product pages move to cache-aside on one Memorystore key with a 5-minute TTL. Steps 3 and 4 are the stampede and its fix. The rebuild lock is code in the app, a key set only if it does not exist, on the same cache.

Step 5: each shard gets a **replica** in another zone of the region, and Memorystore promotes it if the primary fails. Step 6: Valkey and Redis Cluster spread the 16,384 slots over shards and add shards while serving. Step 7: Memorystore sends hit rate, evictions, memory and processor metrics to **Cloud Monitoring**, where Brightpost's alarms live.

| The concept says | On Google Cloud | What to know |
|---|---|---|
| The cache's address | A private endpoint inside your VPC network | No public address; Valkey and Redis Cluster connect through Private Service Connect |
| Replica in zone B | Replica count per shard (Valkey, Redis Cluster); Standard tier (single Redis instance) | The Basic tier of a single instance has no replica |
| Shards | Shard count on Valkey or Redis Cluster | A single Redis instance cannot shard |
| Persistence | Off, snapshots, or an append-only log | Speeds a restart; does not make the cache a database |

## Services

### Memorystore

<CloudServiceProfile id="gcp-memorystore" />

Pick **Memorystore for Valkey** for anything new. Pick **Redis Cluster** when existing code or tooling expects Redis by name. Pick a **single Redis instance** for a small cache that will not outgrow one node. Pick **Memcached** for a pure string cache where a lost node costs only misses.

Brightpost's 260 MB of product pages and baskets fits one small Valkey shard with one replica in a second zone.

## Common mistakes

- **Creating the cache before the network.** Memorystore lives behind a private connection in one VPC network and region. Plan the network, and where the app servers run, first.
- **Choosing the Basic tier of a single Redis instance for sessions.** It has no replica, so a node failure logs every shopper out.
- **Treating persistence as durability.** Snapshots and the append-only log help a restart; a failover can still lose the last writes. Orders stay in Cloud SQL.

## Where this shows up in system design

- **Read-heavy pages:** cache-aside in front of Cloud SQL or Spanner, with jittered TTLs and a rebuild lock for hot keys.
- **Sessions and rate limits:** small keys with TTLs, read on every request, kept in Valkey with a replica.
- **NoSQL read paths:** a hot Firestore document or Bigtable row cached in Memorystore, because neither database has a cache built in.

  <InterviewQuestion question="Which Memorystore engine would you pick for Brightpost's baskets and product pages?" category="Cloud" level="Junior">
    **Short answer.** Memorystore for Valkey, with one replica in a second zone. It stores hashes and counters, takes over from a replica if a node fails, and can add shards later.

    **Why.** Baskets are small, read on every page, and annoying to lose, so they need a copy that survives one node. Memcached keeps no copies. A single Redis instance can have a replica but cannot shard, so growth means a bigger node. Valkey speaks the same commands as Redis, so existing client code works.

    **Follow-ups the interviewer may ask.**
    - When would Memcached be the better pick?
    - What would make you choose Redis Cluster over Valkey?

    **Watch out for.** Picking the cheapest option without a replica. Losing the node logs out every shopper with a basket.
  </InterviewQuestion>

  <InterviewQuestion question="The app servers cannot connect to a new Memorystore for Valkey cache. What do you check?" category="Cloud" level="Mid">
    **Short answer.** That the app runs in the same VPC network the cache was attached to, and that the private connection for that network and region exists. Memorystore has no public address to fall back on.

    **Why.** Valkey and Redis Cluster are reached through Private Service Connect endpoints created in your network for that region. An app server in another network, or a laptop on the internet, has no route. Then check the client: authentication, encryption in transit if it is on, and a cluster-aware client when there is more than one shard.

    **Follow-ups the interviewer may ask.**
    - How would a second project's app reach the same cache?
    - Why might connecting work but most commands fail?

    **Watch out for.** Opening firewall rules to the internet. The cache cannot be reached that way; the fix is in the network design.
  </InterviewQuestion>

  <InterviewQuestion question="Someone proposes keeping orders in Memorystore with the append-only log turned on. Is that safe?" category="Cloud" level="Mid">
    **Short answer.** No. Persistence helps a restarted node reload its data; it does not stop a failover from losing the last writes. Orders stay in Cloud SQL, and Memorystore keeps baskets and page copies.

    **Why.** The primary answers a write, then copies it to its replica a moment later. If the primary's zone fails in between, the promoted replica never saw that write, whatever the log on the old primary says. For a basket that is an annoyance; for a paid order it is lost money. Google Cloud has no separate durable in-memory database, so the durable copy belongs in a database.

    **Follow-ups the interviewer may ask.**
    - What does a cold restart cost without persistence?
    - Where would you put a write that must be fast and must not be lost?

    **Watch out for.** Saying "snapshots make it durable". A snapshot is minutes old by design.
