Google Cloud permissions follow the **resource hierarchy**: roles granted on the organisation or a folder are inherited by every project and resource below. Workloads act as **service accounts**, and **Workload Identity** lets GKE pods and external CI use them without key files. **Cloud Armor** protects the edge, and **Security Command Center** watches the whole organisation.

## TL;DR

- Grant **roles to groups and service accounts** at the right level of the hierarchy; avoid Owner and Editor.
- **No service account keys**: use Workload Identity and attached service accounts.
- **Identity Platform** for customer sign-in; **Secret Manager** and **Cloud KMS** for secrets and keys.
- **Cloud Armor** on the load balancer; **Security Command Center** for posture and threats.

## Coming from AWS

| On AWS | On Google Cloud | What actually changes |
|---|---|---|
| Accounts in an Organization | Projects in folders | Policies inherit down the folder tree |
| IAM role for a task or function | Service account | Attached to the workload; Workload Identity for GKE |
| SCPs | Organization policies | Constraints on what can be created or configured |
| WAF + Shield | Cloud Armor | One service on the load balancer |
| Security Hub + GuardDuty | Security Command Center | Tiers from free to Enterprise |
