Brightpost's shop runs as containers: three copies of shop-web, one per zone, beside checkout and search. On Google Cloud, Google Kubernetes Engine (GKE) runs them on a cluster, and Cloud Run runs an image with no cluster at all. One GKE choice changes a design: in Autopilot mode Google runs the nodes, and the bill follows what each pod asks for.

## The idea

A <Term id="kubernetes">Kubernetes</Term> cluster keeps a written list of what should run in its control plane, and its nodes keep changing until they match it. On GKE, Google always runs the control plane; Autopilot hands it the nodes as well.

## TL;DR

- **Cloud Run first** for stateless HTTP services, event handlers and jobs. It scales on requests, down to zero.
- **GKE when Kubernetes is the requirement:** many services on one platform, Helm charts or operators.
- **Start GKE in Autopilot.** Google runs, patches and sizes the nodes, and you pay mostly for what pods request.
- **Pick GKE Standard** for node-level control: your own machine types, node pools and node settings.

## How it fits together on Google Cloud

A deploy pipeline sends the desired state, "3 copies of shop-web", to the GKE control plane, which Google runs. A regional cluster copies it across zones, so one zone's outage does not stop changes. The nodes are Compute Engine virtual machines. In Standard mode you group them into <Term id="node-pool">node pools</Term>; in Autopilot Google picks them. On each node the kubelet pulls the image from Artifact Registry and starts the <Term id="pod">pods</Term>.

| The idea | On Google Cloud | What to know |
|---|---|---|
| Control plane | GKE, zonal or regional | A zonal cluster has one control plane in one zone. Use regional for production. |
| Nodes | Node pools of Compute Engine VMs | One pool spread over three zones gives one shop-web node per zone. |
| Hands-off nodes | Autopilot | The bill follows pod requests. Some node-level access, such as privileged pods, is refused. |
| Upgrades | Release channels | GKE upgrades on its own schedule; set a maintenance window so it never lands in a sale. |

## Services

### Google Kubernetes Engine

<CloudServiceProfile id="gcp-gke" />

**Pick it when** several teams share one platform, or you need Kubernetes tools. Start in Autopilot. In Standard you pay for whole nodes, empty room included. In Autopilot a pod that asks for 2 vCPU and uses 0.3 still pays for 2.

### Cloud Run

<CloudServiceProfile id="gcp-cloud-run" />

**Pick it when** a stateless service needs no cluster; [Serverless on Google Cloud](/cloud/gcp/serverless) covers it.

### Artifact Registry

<CloudServiceProfile id="gcp-artifact-registry" />

**Pick it when** you store images for GKE or Cloud Run. Deploy by digest, the fingerprint of an image's exact bytes, not by a moving `latest` tag.

## Common mistakes

- **Standard mode by habit.** Without a need for node control, you take on node sizing and patching for nothing.
- **Requests copied from a template.** In Autopilot every pod pays for what it asks. Size requests from real use.
- **No maintenance window.** Release channels upgrade the cluster on Google's schedule. Choose the hours yourself.

## Where this shows up in system design

- **Stateless web tier:** shop-web on GKE with a readiness check, behind a Google Cloud load balancer. See [load balancing patterns](/system-design/patterns/load-balancing).
- **Queue workers:** Pub/Sub consumers as a GKE Deployment that scales on the backlog, not on CPU. See [back pressure](/system-design/patterns/back-pressure).

  <InterviewQuestion question="What is the difference between GKE Standard and Autopilot?" category="Cloud" level="Junior">
    **Short answer.** Google runs the control plane in both. In Standard you manage the nodes and pay for them whole. In Autopilot Google manages them, and you pay mostly for what pods request.

    **Why.** In Standard, Brightpost picks 3 nodes with 4 vCPU and 16 GB each, upgrades them, and pays for them even when half empty. In Autopilot it writes only pod specs, and Google adds or removes machines to fit them.

    <AnimatedDiagram spec="animated/cloud/k8s-cluster-anatomy" cloud="gcp" highlight={["kubelet1", "kubelet2", "kubelet3"]} minWidth={620} caption="The node band: yours to size and patch in Standard, Google's in Autopilot." />

    **Follow-ups the interviewer may ask.**
    - What would make you pick Standard anyway?
    - What kinds of pods does Autopilot refuse?

    **Watch out for.** Saying Autopilot has no nodes. The nodes exist; you do not manage them.
  </InterviewQuestion>

  <InterviewQuestion question="Cloud Run or GKE for a new microservice on Google Cloud?" category="Cloud" level="Mid">
    **Short answer.** Cloud Run, unless the service needs what only Kubernetes gives: operators, node-level agents, or a shared cluster other teams already use.

    **Why.** Cloud Run removes the cluster: no version to upgrade, no nodes, and it scales to zero. GKE pays off when many services share one platform with namespaces and policies. If Brightpost already runs GKE for its shop, one more Deployment there may be less new work than a second platform.

    **Follow-ups the interviewer may ask.**
    - How would a Cloud Run service and a GKE service call each other privately?
    - What would make you move a service onto GKE later?

    **Watch out for.** Treating Cloud Run as "functions only". It runs any container image that answers HTTP.
  </InterviewQuestion>

  <InterviewQuestion question="A GKE Autopilot bill doubled after a release, but traffic did not change. What do you check?" category="Cloud" level="Mid">
    **Short answer.** Pod requests. Autopilot bills mostly by what pods request, so a release that raised requests raises the bill, whatever the real use.

    **Why.** Suppose the release raised shop-web's request from 1 vCPU to 2. Real use stayed near 0.3 vCPU a pod, but 3 copies now reserve 6 vCPU instead of 3. Compare requested with used, then set requests to real use plus headroom.

    <AnimatedDiagram spec="animated/cloud/k8s-cluster-anatomy" cloud="gcp" highlight={["scheduler", "web1", "web2", "web3"]} minWidth={620} caption="The scheduler places pods by their requests, and Autopilot bills those same requests." />

    **Follow-ups the interviewer may ask.**
    - Why not set requests very low to save money?
    - How would you catch this before the release ships?

    **Watch out for.** Counting nodes. In Autopilot the nodes are Google's; the bill follows requests.
