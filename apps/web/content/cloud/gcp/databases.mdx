Brightpost keeps two kinds of data. Orders and payments live in PostgreSQL, where a payment and its order must change together. The printing partner's parcel updates live in a NoSQL table, read by order id. On Google Cloud the relational side has an unusual next step: when one primary is no longer enough, **Spanner** keeps SQL and strong consistency while it spreads rows over many machines and regions.

## The idea

A managed database runs the engine, the backups and a standby in a second zone, and you still decide which copy each request reads. Read replicas take reads that may be a few seconds old, a pooler shares connections, and a failover drill proves the standby works.

## TL;DR

- **Cloud SQL** is the default for PostgreSQL, MySQL and SQL Server. Switch on high availability for a standby in a second zone of the region.
- **AlloyDB** is PostgreSQL-compatible, with storage kept apart from compute, for heavy reads and analytical queries next to transactions.
- **Spanner** is relational and strongly consistent, and grows by adding compute, in one region or several. Pick keys that spread writes.
- **Firestore** holds app documents with live updates; **Bigtable** holds huge, write-heavy tables read by row key. **Database Migration Service** moves databases into Cloud SQL and AlloyDB.

## How it fits together on Google Cloud

Step 1 is a Cloud SQL for PostgreSQL instance with high availability switched on. Google keeps a standby in a second zone of the same region and writes to both before a commit returns. The standby serves no queries. Automated backups run at 03:00, and the saved change log allows a point-in-time restore.

In step 2 a Cloud SQL read replica, built for the finance lead's monthly report, also takes the order page. It copies changes asynchronously, which means the primary does not wait for it, and it has its own address. Step 3 is the failure: on sale day the replica falls 40 seconds behind and about 130 shoppers pay twice. High availability does not help, because the standby never served that page. Step 4 sends a shopper's reads to the primary for 60 seconds after a write, and a Cloud Monitoring alert watches replica lag.

Step 5 differs most here. The Cloud SQL Auth Proxy and the language connectors encrypt and authorise connections, but they do not pool them. So the pooler is one you run, such as PgBouncer, or a pool inside the app. In step 6 a failover drill promotes the standby. The instance keeps its IP address, so the app reconnects to the same place after about 2 minutes.

| The idea | On Google Cloud | What to know |
|---|---|---|
| Standby in a second zone | Cloud SQL high availability | Synchronous and serves no reads; it covers a zone, not a region |
| Read copy | Cloud SQL read replica; AlloyDB read pool | Asynchronous; a read pool puts several read nodes behind one address |
| Connection pooler | PgBouncer or an app-side pool you run | The Auth Proxy secures connections; it does not share them |
| Copy in another region | Cross-region read replica | Asynchronous, so a region loss can cost the last seconds of writes |
| Writes beyond one primary | Spanner, regional or multi-region | Sized in nodes, or smaller processing units; strongly consistent |

## Services

### Cloud SQL

<CloudServiceProfile id="gcp-cloud-sql" />

**Pick it when** your data is relational and fits on one primary. It is the default home for business records such as Brightpost's orders.

### AlloyDB for PostgreSQL

<CloudServiceProfile id="gcp-alloydb" />

**Pick it when** a PostgreSQL database needs more read capacity, less replica lag or fast analytical queries, and the team accepts a migration.

AlloyDB keeps compute apart from a regional storage layer. Its primary has a standby node in a second zone, and read pool nodes share the same storage, so adding one copies no data.

### Spanner

<CloudServiceProfile id="gcp-spanner" />

**Pick it when** relational data outgrows one primary, or must keep taking writes through a zone or region failure without losing any.

Spanner splits each table into ranges of its primary key and moves ranges between servers as load shifts. Transactions across ranges stay strongly consistent, helped by clocks kept in step across Google's data centres. The design rule that matters most is the key. A timestamp or counting order number sends every new write to the last range, so use a random id or a bit-reversed sequence. [NewSQL Databases](/system-design/databases/newsql-databases) explains the theory.

### Firestore

<CloudServiceProfile id="gcp-firestore" />

**Pick it when** a mobile or web app reads and writes documents, wants live updates, and should have no servers to size.

Each Firestore database runs in one of two modes, chosen when you create it: Native mode, with live listeners and mobile sync, or Datastore mode for server apps. Firestore picks partitions itself, so hot spots move to single documents. Brightpost's sale counter would hit the same wall here as on any NoSQL table, because one document accepts only a low, steady write rate. Split it into ten documents and add them up on read.

<AnimatedDiagram spec="animated/cloud/nosql-partitions" step={2} cloud="gcp" minWidth={620} caption="One hot key: every page view writes the same counter, so one partition takes every write and refuses the excess." />

### Bigtable

<CloudServiceProfile id="gcp-bigtable" />

**Pick it when** a table takes a huge, steady stream of writes, such as metrics or events, and every read names a row key or a range of keys.

Bigtable sorts rows by one row key and indexes nothing else. Put a spread-out field first, such as a device or order id, then the time.

### Database Migration Service

<CloudServiceProfile id="gcp-database-migration-service" />

**Pick it when** you move MySQL, PostgreSQL or SQL Server into Cloud SQL or AlloyDB with only minutes of downtime. The cutover is a promotion of the target, and it is one-way. [Database Migration](/cloud/data/database-migration) walks through the whole move.

## Common mistakes

- **Counting the high-availability standby as read capacity.** It serves no queries. Reads that may be stale go to a replica; reads that must be fresh go to the primary.
- **One connection per function copy.** The Auth Proxy does not pool, so a burst of functions can use every connection. Put a pooler in front, or let one Cloud Run instance serve many requests at once.
- **Counting keys in Spanner or Bigtable.** Every new row lands in the same range, and one server does all the work while the rest sit idle.

## Where this shows up in system design

- **Orders and payments:** Cloud SQL with high availability, a replica for reports, and reads after a write sent to the primary, as in [Single-Leader Replication](/system-design/databases/single-leader-replication).
- **Global inventory and ledgers:** Spanner in a multi-region configuration, when writes must continue through a region failure.
- **Events and time series:** Bigtable with a row key that spreads writes, as in [Wide-Column Stores](/system-design/databases/wide-column-stores).

  <InterviewQuestion question="What does a Cloud SQL high-availability instance protect against, and what does it not?" category="Cloud" level="Mid">
    **Short answer.** It protects against losing the primary's machine or zone. A standby in a second zone, written synchronously, takes over in about 2 minutes with no committed write lost. It does not protect against a region outage, a bad delete, or stale reads from a read replica.

    **Why.** Every write waits for the standby, so it holds every committed order. It copies mistakes just as faithfully: a bad delete is gone on both, and only a point-in-time restore undoes it. The standby serves no reads, so it cannot help a replica that falls 40 seconds behind. That is how about 130 Brightpost shoppers paid twice. A region outage needs a cross-region replica and a written recovery plan.

    <AnimatedDiagram spec="animated/cloud/managed-relational-ha" step={3} cloud="gcp" highlight={["primary", "standby", "replica", "paid"]} caption="On sale day the replica falls behind. The standby holds every write but serves no reads, so it cannot help." />

    **Follow-ups the interviewer may ask.**
    - How long is the app cut off during a failover, and what should it do meanwhile?
    - A deploy deletes rows at 09:41 and the standby copies it at once. How do you recover?

    **Watch out for.** Saying high availability means no downtime. Open connections break, and new ones fail for about 2 minutes until the standby is promoted.
  </InterviewQuestion>

  <InterviewQuestion question="When would you move Brightpost's orders from Cloud SQL to Spanner?" category="Cloud" level="Mid">
    **Short answer.** When writes outgrow the largest single primary, or when orders must keep being written through a region failure with nothing lost. At about 400 orders a day, and 4,000 on the biggest sale day, Brightpost needs neither, so Cloud SQL stays.

    **Why.** A Cloud SQL instance has one primary. Replicas add reads, not writes, and a cross-region replica is asynchronous, so losing the region can lose the last seconds of orders. Spanner splits tables by key range across servers and keeps transactions strongly consistent across them, in one region or several. The costs are a bigger bill at Brightpost's size, key design to avoid hot ranges, behaviour that differs from PostgreSQL even through Spanner's PostgreSQL interface, and a migration.

    <AnimatedDiagram spec="animated/cloud/managed-relational-ha" step={6} cloud="gcp" path="proxy>standby" caption="Cloud SQL's failover stays inside one region, with one primary at a time. Spanner is for when that is not enough." />

    **Follow-ups the interviewer may ask.**
    - What would you measure to know Cloud SQL is running out of room?
    - What would you try first: AlloyDB, a cache, or moving the busiest table elsewhere?

    **Watch out for.** Choosing Spanner for scale the shop does not have. A missing index or a storm of unpooled connections is the usual problem, and both follow you to Spanner.
  </InterviewQuestion>

  <InterviewQuestion question="Why do sequential primary keys hurt in Spanner and Bigtable?" category="Cloud" level="Senior">
    **Short answer.** Both store rows sorted by key and split the key space into ranges served by different servers. A key that always grows, such as a timestamp or a counting order number, sends every new write to the last range. One server does all the writing while the rest sit idle. Use a random id, a bit-reversed sequence, or a spread-out field first in the key.

    **Why.** Splitting a hot range helps only the keys already written; the next new key still lands at the end. Adding nodes does not help either, because the work cannot be shared. In Bigtable, put the spreading field first, such as a device or order id, then the time, so a range read still returns one device's events in order. In Spanner, a bit-reversed sequence keeps keys unique numbers while spreading them.

    <AnimatedDiagram spec="animated/cloud/nosql-partitions" step={2} cloud="gcp" highlight={["app", "router", "p3"]} caption="The same shape as a counting key: every new write reaches one partition while the others sit idle." />

    **Follow-ups the interviewer may ask.**
    - What does a bit-reversed sequence give up compared with a counting key?
    - Customers want order numbers that count up. How do you show them without a hotspot?

    **Watch out for.** Hashing the whole row key in Bigtable. Writes spread, but a read of one device's last hour now touches every server.
