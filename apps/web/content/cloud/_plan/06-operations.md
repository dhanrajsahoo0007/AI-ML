This hub is for someone who can draw an architecture but has never had to run one: a developer, a junior architect, or a candidate who gets asked "how would you know it's broken, how do you ship it, and what does it cost?" Read it in order: first learn to see the system (observability, then SLOs and alerting), then to change it safely (CI/CD and deployment strategies, then config/patching/fleets), then to pay for it (cost models, then FinOps tools), and finally the two large-scale change projects every exam and every real company faces (migration and modernization, AI/ML platforms). Brightpost, the running shop, goes from "we found out from a customer tweet" to a team with an error budget, a canary pipeline, a monthly cost review and a RAG-based product-support assistant.

#### 3. ci-cd-and-deployment-strategies — CI/CD and Deployment Strategies (Intermediate, ~2,800 words)
- Scope: From a commit to production without downtime: build once, promote the same artifact, and choose between rolling, blue/green and canary based on how fast you must roll back and how much capacity you can afford. Feature flags are shown as the way to separate "deploy" from "release".
- Sections: The Friday deploy that took the shop down; Pipeline stages: build, test, package, promote; Immutable artifacts and registries; Environments and approvals; Rolling, blue/green, canary; Rollback: what each strategy gives you; Feature flags; Deploying the database too (expand/contract, link only); Keyless CI (OIDC / Workload Identity Federation); What breaks; Try it; On AWS / Google Cloud / Azure; Common mistakes; Related; Interview questions.
- Diagrams:
  1. animated stepper `animated/cloud/deployment-strategies` — load balancer in front of Brightpost's app fleet, registry on the side, alarm node. Steps: "All at once" (every instance replaced, traffic drops); "Rolling" (one slice at a time, old and new serve together); "Blue/green" (second full fleet, LB flips, old fleet kept for rollback); "Canary" (one new instance takes 5% of traffic, alarm watches it); "A deploy fails" (canary error rate rises, alarm fires, traffic shifts back to blue, bad version never reached 95% of users); "Feature flag" (flag service node; same build, behaviour switched without a deploy).
  2. mermaid asset `mermaid/cloud/ci-cd-pipeline` — commit → CI build/test → registry → deploy to staging → integration tests → approval → prod deploy → alarm-triggered rollback.
  3. mermaid inline — cost and rollback-speed comparison as a small matrix rendered from a table (not a diagram): rolling vs blue/green vs canary.
  4. widget `<CloudDecisionTree topic="deploy-strategy">` — questions: can you double capacity briefly, do you need instant rollback, do you have alarms worth trusting, is the change schema-coupled.
- Reuses: CloudGroupTable group="devops"; CloudServiceProfile aws-codepipeline, gcp-cloud-build, gcp-cloud-deploy, azure-pipelines; capability rows ci, cd, git-hosting, app-config (feature flags: AWS AppConfig, azure-app-configuration); existing mermaid in /cloud/aws/devops is replaced by a `<Mermaid ref>` to the asset above.
