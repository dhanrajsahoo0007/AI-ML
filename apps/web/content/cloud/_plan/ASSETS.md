# Reserved diagram ids for the Cloud section

Every concept diagram is a spec at `apps/web/assets/diagrams/animated/cloud/<id>.ts` with a `<id>.meta.yaml` sidecar
(`source: original`, `alt` required, `tags: [cloud, <hub>, <topic>]`). The registry is generated by
`npm run assets -w web`. Embed with `<AnimatedDiagram name="cloud/<id>" />` (add `step={n}` or `stepper`).

This list lives here and not in the assets folder because the asset builder rejects any file under
`assets/diagrams/animated/` that is not a `.ts` spec or a `.meta.yaml` sidecar.

Rules:

- **One owner page per id.** The owner page creates the spec. Every other page embeds it by id and never redraws it.
- **The id names the concept, never a provider.**
- **Kinds** (see `content/system-design/COMPONENTS.md` §3): `architecture` (nodes, zones and edges; a stepper when it
  has `steps`), `sequence` (lanes and messages), `layout` (a static drawing). The drawings the briefs call
  "mermaid asset" or "svg" are `sequence` or `layout` specs here (RECONCILIATION §1). Mermaid is kept only for tiny
  decision flows.
- Every spec must pass `lintSpec` (`npm test` lints every spec file).
- Where a brief still uses an old id or an old page slug, this file and `RECONCILIATION.md` win.

Format of each line: id — owner page — kind — what it shows.
