Brightpost keeps orders and payments in PostgreSQL, and the printing partner's parcel updates in a NoSQL table read by order id. On Azure one fact shapes the choice: **the engine picks the product**. PostgreSQL means Azure Database for PostgreSQL flexible server, and the SQL Server engine means Azure SQL Database. Features such as pausing or a built-in pooler belong to one product, not both. For NoSQL, Cosmos DB makes consistency a setting you choose.

## The idea

A managed database runs the engine, the backups and a standby in a second zone, and you still decide which copy each request reads. Read replicas take reads that may be a few seconds old, a pooler shares connections, and a failover drill proves the standby works.

## TL;DR

- **Azure Database for PostgreSQL flexible server** is the open-source default. Zone-redundant high availability adds a standby in another zone, and PgBouncer is built in.
- **Azure SQL Database** runs the SQL Server engine as a service. Its tiers differ in storage and copies, and every tier has high availability built in.
- **Cosmos DB** holds key-value and document data. You choose the partition key, a consistency level and how you pay for request units.
- **Azure DocumentDB** serves MongoDB apps, **Azure AI Search** handles search and retrieval, and **Database Migration Service** moves databases in.

## How it fits together on Azure

Step 1 is a flexible server with zone-redundant high availability. Azure keeps a standby in another zone and writes to it before a commit returns; the standby serves no reads. Backups run at 03:00 and keep the change log, so you can restore to any second. A restore builds a new server, so write down how the app moves to it.

In step 2 a read replica, built for the finance lead's monthly report, also takes the order page. It copies changes asynchronously, which means the primary does not wait for it, and it has its own server name. Step 3 is the failure: on sale day the replica falls 40 seconds behind and about 130 shoppers pay twice. Step 4 sends a shopper's reads to the primary for 60 seconds after a write, and an Azure Monitor alert watches replica lag.

Step 5 is shortest on Azure. PgBouncer, a connection pooler, is built into flexible server: you switch it on and connect to its port instead of the database's. The resize function on Azure Functions then borrows connections instead of opening its own. In step 6 a failover drill promotes the standby, and the server name points at the new primary after about 2 minutes.

| The idea | On Azure | What to know |
|---|---|---|
| Standby in a second zone | Zone-redundant high availability | Synchronous and serves no reads; a same-zone option exists where a region has no zones |
| Read copy | Read replica | Asynchronous, with its own server name, in the same or another region |
| Connection pooler | Built-in PgBouncer | Switched on per server; the app connects to its port |
| Cloud-native engine | Azure SQL Database Hyperscale | SQL Server engine only; compute apart from shared storage |
| Pausing when idle | Azure SQL Database serverless | Flexible server does not pause by itself; you can stop it by hand |

## Services

### Azure Database for PostgreSQL

<CloudServiceProfile id="azure-postgresql" />

**Pick it when** your engine is PostgreSQL and the data fits on one primary. It is the default home for Brightpost's orders on Azure.

Flexible server comes in three compute tiers. **Burstable** suits small or test servers that idle most of the day. **General Purpose** suits most production work, and **Memory Optimized** suits databases whose busy data needs more memory.

### Azure SQL Database

<CloudServiceProfile id="azure-sql" />

**Pick it when** the app uses the SQL Server engine, such as a .NET app, or a SaaS product that gives each customer its own database.

Azure SQL Database is sold by vCore, a unit of processor, in three service tiers. **General Purpose** keeps data on remote storage and starts fresh compute when a machine fails; it is the budget choice for most apps. **Business Critical** keeps several copies on fast local disks in different machines, so failover is quicker, and one copy can answer read-only queries. **Hyperscale** keeps compute apart from shared storage, so a very large database grows and adds read copies without copying data. The **serverless** option scales between a minimum and a maximum and can pause when idle. **Elastic pools** share one budget among many small databases. An older DTU model bundles processor, memory and disk into one number.

### Azure Cosmos DB

<CloudServiceProfile id="azure-cosmos-db" />

**Pick it when** key-value or document data needs fast reads by key at any scale, or copies in several regions.

Cosmos DB makes consistency a setting. **Strong** means every read sees the latest write. **Bounded staleness** lets reads trail by at most a set time or number of changes. **Session**, the default, shows each client its own writes in order, while others may see them a moment later. **Consistent prefix** never shows writes out of order but may be behind, and **eventual** promises only that reads catch up. You set one level for the account and can relax it per request. Weaker levels cost fewer request units per read. Strong needs a single write region, so an account that writes in several regions is never strongly consistent.

The partition key is fixed when a container is created. Provisioned throughput is divided across the physical partitions, so one hot key throttles at a fraction of what you pay for.

### Azure DocumentDB

<CloudServiceProfile id="azure-documentdb" />

**Pick it when** a MongoDB app moves to Azure and the team wants MongoDB tools with clusters sized by vCore.

### Azure AI Search

<CloudServiceProfile id="azure-ai-search" />

**Pick it when** you need product search, document search or the retrieval step of a chatbot that answers from your own documents. Feed it from the main database; never treat it as the source of truth.

### Azure Database Migration Service

<CloudServiceProfile id="azure-dms" />

**Pick it when** you move SQL Server into Azure SQL, or MySQL into Azure Database for MySQL, with a short cutover. PostgreSQL sources use flexible server's own migration service. [Database Migration](/cloud/data/database-migration) walks through the whole move.

## Common mistakes

- **Picking the product before the engine.** Pausing and Hyperscale exist only in Azure SQL Database. A PostgreSQL team gets neither, so plan with flexible server's features.
- **A Cosmos DB partition key chosen in a hurry.** It cannot be changed later; changing it means copying the data to a new container. Choose it from the reads you will make.
- **Strong consistency everywhere.** Each read costs more request units, and it rules out writes in several regions. Session is enough for most reads a user makes.

## Where this shows up in system design

- **Orders and payments:** flexible server with zone-redundant high availability, a replica for reports, and reads after a write sent to the primary, as in [Single-Leader Replication](/system-design/databases/single-leader-replication).
- **Multi-tenant SaaS:** Azure SQL Database elastic pools, one small database per customer sharing one budget.
- **Global user data:** Cosmos DB with session consistency and a home region per user, as in [Consistency Models](/system-design/patterns/consistency-models).

  <InterviewQuestion question="An Azure Functions app opens too many connections to a PostgreSQL flexible server. What do you change?" category="Cloud" level="Mid">
    **Short answer.** Switch on the built-in PgBouncer and point the function at its port, and cap how many function instances run at once. PgBouncer keeps a small set of database connections and lends one to each transaction, so a burst shares them.

    **Why.** Brightpost's server allows 200 connections, and the app servers need most of them on sale day. The resize function scales out on a burst of photo uploads, and each instance opens its own connection. Through the pooler, the function borrows at most 20 and everything shares 150. In transaction pooling, settings a session changes do not carry over between transactions, so test the app against it.

    <AnimatedDiagram spec="animated/cloud/managed-relational-ha" step={5} cloud="azure" highlight={["fn", "proxy", "primary", "app"]} caption="The resize function and the app servers share PgBouncer's connections instead of opening their own." />

    **Follow-ups the interviewer may ask.**
    - How do you cap how far a Functions app scales out?
    - What happens to pooled connections during a failover?

    **Watch out for.** Raising the server's connection limit instead. Each connection costs memory, and the next burst is bigger.
  </InterviewQuestion>

  <InterviewQuestion question="Which Cosmos DB consistency level would you choose for a chat app?" category="Cloud" level="Mid">
    **Short answer.** Session. Each user always sees their own messages, in order, right after sending them. Other users may see a new message a moment later, which a chat can live with, and reads stay fast and cheap.

    **Why.** Strong consistency costs more request units per read, adds latency, and rules out writes in several regions. Eventual could hide a message from its own sender just after sending, which looks like a lost message. Consistent prefix keeps order but still may not show the sender's own write. Session gives exactly the promise users notice, at about the cost of the weaker levels.

    **Follow-ups the interviewer may ask.**
    - What must the client keep so that session consistency works across app servers?
    - Which messages, if any, would need a stronger read?

    **Watch out for.** Choosing strong "to be safe". It is slower and costlier for every read, and it blocks the move to several write regions later.
  </InterviewQuestion>

  <InterviewQuestion question="Brightpost adds a Cosmos DB write region in Australia. What happens when both regions change the same item?" category="Cloud" level="Senior">
    **Short answer.** By default the write with the later timestamp wins, and the other is lost without an error. You can supply your own conflict logic instead. The account can no longer use strong consistency, so give each item a home region that does all its writes, or store each change as a new item.

    **Why.** Each region accepts writes locally and copies them to the other, usually within a second or two. Brightpost's 30 Australian orders a day would get faster writes. But a parcel status written in London and a correction written in Sydney a moment apart cannot both survive. If each order is written only in the region that took it, two regions never fight over one item.

    <AnimatedDiagram spec="animated/cloud/nosql-partitions" step={6} cloud="azure" highlight={["router", "replica"]} caption="A second write region: each region accepts writes and copies its changes to the other." />

    **Follow-ups the interviewer may ask.**
    - Which of Brightpost's data is safe to write in both regions?
    - How does session consistency behave when a user's requests move to the other region?

    **Watch out for.** Assuming several write regions give one global truth. They give fast local writes, and you design away the conflicts.
