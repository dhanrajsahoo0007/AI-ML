Brightpost's shop runs as containers: three copies of shop-web, one per zone, beside checkout and search. On Azure, Azure Kubernetes Service (AKS) runs them on a cluster, Container Apps runs services with no cluster to see, and Azure Container Registry (ACR) stores the images. One AKS rule changes a design: every cluster needs a system node pool for its own add-ons.

## The idea

A <Term id="kubernetes">Kubernetes</Term> cluster keeps a written list of what should run in its control plane, and its nodes keep changing until they match it. On AKS, Azure always runs the control plane; AKS Automatic hands it the nodes as well.

## TL;DR

- **Container Apps first** for APIs, microservices and queue workers. It scales on traffic or queue length, down to zero.
- **AKS when Kubernetes is the requirement.** Start with **AKS Automatic**, where Azure picks, scales and upgrades the nodes.
- **Container Instances for one-off containers:** a build, a nightly task, burst room. Not for long-running services.
- **ACR for every image.** Choose the Premium tier from day one if you need copies in other regions.

## How it fits together on Azure

A deploy pipeline sends the desired state, "3 copies of shop-web", to the AKS control plane, which Azure runs out of sight. People sign in with Microsoft Entra ID, Azure's identity service. The nodes sit in <Term id="node-pool">node pools</Term>, each a Virtual Machine Scale Set: identical virtual machines that Azure grows and shrinks. A system pool runs the cluster's add-ons, such as its DNS; user pools run Brightpost's apps. The kubelet on each node pulls images from ACR with the cluster's managed identity, so no registry password exists.

| The idea | On Azure | What to know |
|---|---|---|
| Control plane | AKS, Free or Standard tier | The Free tier has no uptime SLA; production uses Standard. |
| Nodes | Node pools on Scale Sets | One system pool for add-ons, user pools for apps, each across three zones. |
| Hands-off nodes | AKS Automatic | Azure picks, scales and upgrades nodes, with preset security defaults. |
| Who may change the cluster | Entra ID with RBAC | Grant access to groups, never to people one by one. |

## Services

### Azure Kubernetes Service

<CloudServiceProfile id="azure-aks" />

**Pick it when** several teams share one platform, or you need Kubernetes tools such as Helm charts. Start with AKS Automatic.

### Azure Container Apps

<CloudServiceProfile id="azure-container-apps" />

**Pick it when** services and workers should scale on traffic or a queue, with no cluster. Each change makes a revision, and traffic can split between revisions.

### Azure Container Instances

<CloudServiceProfile id="azure-container-instances" />

**Pick it when** one container must start in seconds, run a task and stop, or AKS needs burst room.

### Azure Container Registry

<CloudServiceProfile id="azure-acr" />

**Pick it when** you run containers on Azure at all. Deploy by digest, the fingerprint of an image's exact bytes, not by a moving `latest` tag.

## Common mistakes

- **Apps on the system node pool.** A pod with no memory limit can starve the cluster's DNS. Keep apps on user pools.
- **The Free tier in production.** It has no uptime SLA. Use Standard for anything customers reach.
- **Container Instances as a service platform.** It has no rollouts or scaling. Use Container Apps.

## Where this shows up in system design

- **Queue workers:** Container Apps scaling on Service Bus queue length, down to zero overnight. See [back pressure](/system-design/patterns/back-pressure).
- **Stateless web tier:** shop-web on AKS with a readiness check, behind Application Gateway for Containers. See [load balancing patterns](/system-design/patterns/load-balancing).

  <InterviewQuestion question="What does AKS run for you, and what is still your job?" category="Cloud" level="Junior">
    **Short answer.** Azure runs the control plane: API server, state store, scheduler and controllers. The nodes are yours unless you use AKS Automatic, and so is everything you deploy.

    **Why.** In Standard AKS, Brightpost sizes and upgrades the nodes; AKS Automatic takes them over. In both, requests, limits and readiness checks stay Brightpost's, so its 90-second warm-up gap would break any AKS cluster.

    **Follow-ups the interviewer may ask.**
    - What does the Standard tier add over Free?
    - Who decides when the Kubernetes version is upgraded?

    **Watch out for.** "The cluster is Azure's problem." Node upgrades in Standard AKS, and every workload, stay yours.
  </InterviewQuestion>

  <InterviewQuestion question="Container Apps or AKS for a new set of microservices on Azure?" category="Cloud" level="Mid">
    **Short answer.** Container Apps, unless you need the Kubernetes API itself: operators, node-level agents, or a shared cluster other teams already use.

    **Why.** Container Apps gives event-based scaling and traffic splits with no cluster to upgrade. For Brightpost's 3 engineers, node pools and version upgrades leave their week. AKS pays off when many teams share one platform, or the tools you need ship only as Helm charts.

    **Follow-ups the interviewer may ask.**
    - What would make you move a container app onto AKS later?
    - How does a container app reach a private database?

    **Watch out for.** "Container Apps cannot scale like Kubernetes." It runs on Kubernetes and KEDA underneath; you cannot reach that layer.
  </InterviewQuestion>

  <InterviewQuestion question="How would you scale queue workers on Azure?" category="Cloud" level="Mid">
    **Short answer.** Run them in Container Apps with a KEDA scale rule on the Service Bus queue length. KEDA is an open-source autoscaler that reads the backlog; workers grow with it and return to zero.

    **Why.** CPU is a late signal: by the time it is high, the queue is already long. A rule such as "one copy per 20 messages, at most 10" reacts to the backlog itself. On Brightpost's sale day, 4,000 orders fill the queue by noon; overnight the workers fall to zero.

    **Follow-ups the interviewer may ask.**
    - What happens to a message in progress when a copy is removed?
    - How would you run the same workers on AKS?

    **Watch out for.** Forgetting that a message can arrive twice. Make each handler safe to repeat.
  </InterviewQuestion>
