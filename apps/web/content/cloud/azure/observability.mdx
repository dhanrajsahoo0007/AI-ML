When Pay gets slow, Brightpost needs to know within minutes, find the service holding the time, and read the line that says why. On Azure that job belongs to **Azure Monitor**: metrics and alerts, logs in a **Log Analytics workspace** queried with KQL, the Kusto Query Language, and **Application Insights** for traces. One fact shapes the design. The workspace is the unit: one KQL query can read across every resource that sends to it. But a resource sends its own logs there only once you add a diagnostic setting.

## The idea

A running system sends out three signals: metrics say whether something is wrong, logs say what happened, and traces say where the time went. An agent on each workload ships them to managed stores, and an alert watches the number users feel.

## TL;DR

- **One Log Analytics workspace** per environment, with retention and table plans chosen on purpose.
- **Diagnostic settings** on every resource whose logs you need; without one, those logs are not kept.
- **Application Insights** with the Azure Monitor OpenTelemetry Distro for requests, dependencies and traces.
- **Alert rules on symptoms**, sharing a few **action groups** that decide who is told.

## How it fits together on Azure

In steps 1 and 2, Brightpost's three services run on six Azure VMs, and each writes its own log file. In step 3 the **Azure Monitor Agent** goes on every VM, told what to collect by a **data collection rule**. Azure already reports processor and network metrics; memory needs the agent, because it lives inside the operating system. A Monitor workbook charts it all.

In step 4 the agent sends the log files to the Log Analytics workspace, where each kind of data gets its own table and Brightpost keeps 30 days. In step 5 the OpenTelemetry Distro inside each service passes the `traceparent` header on every call. It sends spans straight to **Application Insights**, not through the agent. In step 6 an **alert rule** watches p99 Pay time and calls an **action group**, which reaches Asha's paging tool.

| The concept says | On Azure | What to know |
|---|---|---|
| Collector | Azure Monitor Agent plus a data collection rule | The rule says what to collect and which workspace receives it |
| Log store | Log Analytics workspace, one table per kind of data | Retention is set per workspace and per table |
| Platform logs | A diagnostic setting on each resource | No setting, no resource logs |
| Trace store | Application Insights, backed by the workspace | Traces and logs share a workspace, so one KQL query can join them |
| Alert route | Alert rule → action group | Change who is called in one action group, not in every rule |

## Services

### Azure Monitor

<CloudServiceProfile id="azure-monitor" />

Pick it for all monitoring on Azure: platform metrics, the Activity Log of control-plane changes, workspaces, alert rules and workbooks. **Managed Prometheus** stores its metrics in an **Azure Monitor workspace**, a different thing from a Log Analytics workspace, and **Azure Managed Grafana** draws dashboards over both.

### Application Insights

<CloudServiceProfile id="azure-app-insights" />

Pick it when a request crosses several services and you need the slow hop. The application map shows which service calls which, and each request's transaction view lines up its spans with its log lines.

## Common mistakes

- **No diagnostic settings.** A database or load balancer keeps its logs out of the workspace until one is added. Add them in the same template that creates the resource.
- **Every log on the full-price table plan.** Verbose lines you rarely query fit the Basic or Auxiliary plans, which cost less and query with limits.
- **Alerting on processor use.** In July the print servers sat at about 20% while Pay took 9 seconds. Alert on p99 Pay time.

The fix belongs in the template that creates the database, so the next one is covered too.

  <InterviewQuestion question="The p99 Pay alert fires. How do you get from the alert to the failing line on Azure?" category="Cloud" level="Mid">
    **Short answer.** Open the requests chart in Application Insights, pick a slow Pay, and open its end-to-end transaction view. The longest span names the service; its log lines carry the same operation id, the trace id under another name, so one KQL query finds them.

    **Why.** Application Insights stores requests, dependencies and traces in the same workspace as the logs. In July this walk shows Pay at 9.3 seconds and the print service at 9.0. The print service's lines show three A1 print files built before Pay answered, about 3 seconds each. Without the shared id, it was 6 files and 2 days.

    **Follow-ups the interviewer may ask.**
    - What if sampling dropped that request's trace?
    - How would you write the p99 alert as a log search alert rule?

    **Watch out for.** Searching all logs for the time window first. Hundreds of lines share that minute; only the operation id narrows it to one Pay.
  </InterviewQuestion>

  <InterviewQuestion question="One Log Analytics workspace for Brightpost, or several?" category="Cloud" level="Senior">
    **Short answer.** One workspace per environment: one for test and one for the shop. The Activity Log and security logs also go to a workspace in the audit subscription, which shop admins cannot change.

    **Why.** A KQL query is simplest inside one workspace, so services that are debugged together should share one. Test and shop stay apart, so test noise stays out of shop queries and costs, and access is simpler. Audit data is kept apart for a different reason: someone who takes over the shop subscription must not be able to delete it. Within the shop workspace, resource-level access lets a team read only its own resources' logs.

    **Follow-ups the interviewer may ask.**
    - Where would the Prometheus metrics from a Kubernetes cluster go?
    - How would you set different retention for audit tables and debug tables?

    **Watch out for.** One workspace per resource. Every incident then starts with a query across ten workspaces.
  </InterviewQuestion>
