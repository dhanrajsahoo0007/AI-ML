## In one sentence

<KeyIdea>
  When another system calls you to say "this happened", answer at once, do the work later, and make sure that doing it twice changes nothing.
</KeyIdea>

## The story

Brightpost's customers pay through a payment provider. When a payment succeeds, the provider sends the shop a request: "order 58213 is paid". The shop's code marks the order paid and sends a print job to the printing partner, then replies. That takes about 2 seconds. The provider waits 10 seconds; with no reply, it sends the same event again a minute later. On a sale morning the busy database made the code take about 14 seconds. Between 9:05 and 9:40, 40 payment events got no reply in time. Each first copy finished anyway, and each resent copy ran again. So 40 orders were marked paid twice. The printing partner's staff spotted 38 repeated jobs, but two customers got two parcels.

Every step below repairs one part of that morning, then turns the idea round for the webhooks Brightpost sends.

## How it works

Three words first. A **webhook** is a request that one system sends to a web address of another when something happens. The sender is the **provider**; the system that owns the address is the **receiver**. The thing that happened is an **event**: a small record with its own id, such as `evt_7731`, a type, such as "payment succeeded", and the data.

### Step 1: Two directions, one rule

<AnimatedDiagram spec="animated/cloud/webhook-receiver" step={1} minWidth={620} caption="Brightpost's first setup: the provider posts the event and waits while the handler marks the order paid and sends the print job." />

Brightpost uses webhooks both ways. It **receives** them from the payment provider. Its wholesale shop **sends** them: when a bulk order ships, the gift shop that ordered it gets a "shipped" request. There are about 300 gift shops.

The theory, a signed request with retries and duplicates, is on [Webhooks and callbacks](/system-design/fundamentals/webhooks). This page builds both sides on a cloud, with one rule. The receiver checks the request, stores the event and replies within a second. A worker does the slow part later, safely even when an event comes twice. In the picture the handler breaks that rule: the provider waits while it does all the work.

### Step 2: The slow reply that pays twice

<AnimatedDiagram spec="animated/cloud/webhook-receiver" step={2} minWidth={620} caption="The failure: no reply within 10 seconds, so the provider sends the event again, and the handler runs the whole job a second time." />

A provider cannot see inside your code. It sees one thing: did a success reply arrive in time? If not, it tries again, because losing a payment is worse than sending it twice. Providers deliver **at least once**: every event arrives, and some arrive twice.

<Callout tone="red" title="What breaks">
  At 9:12 the handler starts on order 58213. At 10 seconds the provider stops waiting; at 14 seconds the handler marks the order paid. At 9:13 the same event arrives again, and nothing tells the handler it has seen it. It records a second payment and sends a second print job. This happened 40 times before 9:40.
</Callout>

The morning had two causes. The reply waited for slow work, and the work had no memory of the events it had done. Steps 4 and 5 remove one each. Fixing only the first is not enough.

### Step 3: A public door that checks the signature

<AnimatedDiagram spec="animated/cloud/webhook-receiver" step={3} minWidth={620} caption="A public webhook endpoint checks each request's signature with the secret it reads from the secret store." />

The receiver needs a public address, so anyone can send it a fake "order paid". The defence is a **signature**. Both sides share a <Term id="secret">secret</Term>, a random string nobody else knows. The provider mixes it with the request's exact bytes and a timestamp, and sends the result in a header. The endpoint does the same sum and compares. A stranger cannot produce a match, and an old timestamp means a replayed copy.

The endpoint is a small piece of code behind a public URL: an <Term id="api-gateway">API gateway</Term> route, or a function with its own address ([Hosting REST and GraphQL APIs](/cloud/networking/hosting-apis) compares them). The secret lives in the cloud's **secret store**, which hands secrets only to identities allowed to read them. The endpoint reads it with its service identity and caches it for a few minutes. [Secrets management](/cloud/resilience/secrets-management) covers rotation: for a day, accept the old and the new secret.

### Step 4: Reply in milliseconds, work from a queue

<AnimatedDiagram spec="animated/cloud/webhook-receiver" step={4} minWidth={620} caption="The endpoint adds the event to a queue and replies at once. The handler takes events from the queue at its own pace." />

The endpoint now does three things, in order: check the signature, add the event to a **queue**, reply with success. That takes about 50 milliseconds. A queue is a managed list of messages that workers take one at a time ([Queues vs Streams](/cloud/start-here/queues-vs-streams)). The payment handler becomes the worker. On a sale morning it may fall 10 minutes behind, and the provider never notices.

The order matters. Reply before queueing, and a crash loses the event for good. Reply after, and a crash in between brings a resend, which Step 5 makes safe. So when the queue refuses an event, the endpoint replies with an error, and the provider tries later.

### Step 5: The queue alone still lets a double through

<AnimatedDiagram spec="animated/cloud/webhook-receiver" step={5} minWidth={620} caption="Event evt_7731 arrives twice. The handler finds its id in the processed-events table and skips the second copy." />

Brightpost expected the queue to stop the doubles. In the first month the provider still sent 9 events twice. Twice, a release restarted the endpoint after it queued an event but before it replied. Seven times, the reply was lost on the network.

The queue cannot help. Each copy is a separate request, so it becomes a separate message with its own message id. To the queue they are two jobs. Only the event id inside, `evt_7731` both times, says they are one.

So the handler is made <Term id="idempotent">idempotent</Term>: running it twice on one event has the same effect as running it once. It works in one database transaction, a group of changes saved together or not at all:

1. Add the event id to a **processed-events** table, where each id may appear once.
2. If that id is already there, stop and treat the message as done.
3. Otherwise mark the order paid and create the print job.
4. Save all of it in one commit.

A crash before the commit saves nothing, and the queue hands the event out again. A crash after leaves the id in place, and the retry stops at item 2. The 9 doubles became 9 skipped messages. [Idempotency](/system-design/patterns/idempotency) covers the pattern in depth.

### Step 6: Park failures, replay after the fix

<AnimatedDiagram spec="animated/cloud/webhook-receiver" step={6} minWidth={620} caption="An event that fails 5 times moves to the dead-letter queue. After the fix it is sent back to the main queue." />

Some events fail every time. In June, orders paid partly by gift voucher crashed the handler on every try. A **dead-letter queue** stops that loop: after 5 failed tries, the queue moves the event aside, and the rest carry on.

An alarm fires when the dead-letter queue holds one event. Asha fixed the voucher bug that afternoon and **replayed** the 3 parked events: she moved them back to the main queue. Each went through once, because of Step 5.

One cheap safety net remains. Payment providers let you list recent events, so once an hour a small job compares them with the orders table. An event the provider gave up on still gets processed.

### Step 7: Sending: an outbox and a delivery worker

<AnimatedDiagram spec="animated/cloud/webhook-receiver" step={7} minWidth={620} caption="The other direction: the shipped change and an outbox row are saved together, and a delivery worker sends each row to the gift shop's URL." />

Now Brightpost is the provider. Sending the request right after saving "shipped" looks easy, but a crash between "saved" and "sent" loses the notice unseen.

An **outbox** fixes that. It is a table in the same database. The "shipped" change and an outbox row, "tell shop 112 that order W-2207 shipped", are saved in one transaction. Both exist, or neither does. A **delivery worker** reads unsent rows and sends each one. It signs the body with that shop's own secret, so one shop cannot fake events for another. Every notice carries an event id, so shops can drop doubles the way Brightpost does.

### Step 8: Retries, backoff and jitter for 300 endpoints

<AnimatedDiagram spec="animated/cloud/webhook-retry" stepper caption="One success, one retry that works, one shop that stays down, and the row parked after 24 hours." />

On any day a few gift shops' servers are down. A success reply means done; an error, or no reply within 5 seconds, means "try later".

- **Backoff.** The first retry waits about 1 minute; each wait doubles, up to 2 hours. A shop down all day gets about 20 tries.
- **Jitter.** Each wait gets a random part. When a host that many shops share comes back, their retries arrive spread over minutes, not in one burst.
- **Isolation.** At most 2 requests per shop are open at once, so a hanging shop ties up 2 workers, not all.
- **Give up, visibly.** After 24 hours the row is parked as failed. The shop gets an email and can press "resend" on its account page.

[Quotas, Throttling, Retries and Backoff](/cloud/resilience/quotas-and-retries) applies the same rules to every cloud call.

## On AWS, Google Cloud and Azure

The idea is the same on all three clouds: a signature-checking endpoint, a queue, an idempotent worker, a dead-letter queue, and an outbox for sending.

<Tabs title="On each cloud">
  <Tab label="AWS">
    - **Public endpoint:** a route on Amazon API Gateway, or a Lambda function URL for a single function.
    - **Signing secret:** AWS Secrets Manager, read by the function's IAM role and cached in memory.
    - **Queue and worker:** an Amazon SQS queue; Lambda polls it and hands the worker batches of messages.
    - **Failed events:** a second SQS queue as the dead-letter queue, after a maximum receive count. SQS can move parked messages back.
    - **Sending webhooks:** Amazon EventBridge API destinations call an outside URL, with a stored auth header, a rate limit per destination, retries and a dead-letter queue.

    **The difference that changes a design.** API Gateway can write a request straight into SQS, with no function in front. That is the fastest acknowledgement. But nothing checks the signature before the queue, so the worker must, and the raw body and signature header must reach the message unchanged.
  </Tab>
  <Tab label="Google Cloud">
    - **Public endpoint:** a Cloud Run service or function whose URL allows unauthenticated calls. The signature is its only gate.
    - **Signing secret:** Secret Manager, read by the service's service account, or mounted into the container.
    - **Queue and worker:** a Pub/Sub topic. A push subscription posts each message to a Cloud Run worker; a success reply acknowledges it.
    - **Failed events:** a dead-letter topic on the subscription, after a maximum number of attempts. Replay by publishing to the main topic again.
    - **Sending webhooks:** Cloud Tasks with HTTP targets, each queue with its own rate limit and retry settings. No service is made for sending to many outside customers.

    **The difference that changes a design.** Pub/Sub pushes to the worker over HTTPS, so there are two doors with two gates. The public endpoint accepts anyone with a valid signature. The worker's URL accepts only Pub/Sub, which attaches a token for a service account you choose. Never make the worker's URL public too.
  </Tab>
  <Tab label="Azure">
    - **Public endpoint:** an Azure Functions HTTP trigger. Azure API Management can stand in front when many webhooks share one door.
    - **Signing secret:** Azure Key Vault, read by the function's managed identity.
    - **Queue and worker:** an Azure Service Bus queue, read by a function with a Service Bus trigger.
    - **Failed events:** every Service Bus queue has a built-in dead-letter subqueue, used after a maximum delivery count. Replay by resending to the main queue.
    - **Sending webhooks:** Azure Event Grid delivers events from a custom topic to webhook subscribers, with retries and dead-lettering to a storage container.

    **The difference that changes a design.** Service Bus can drop a second message with the same message id within a time window you set. Use the provider's event id as the message id, and many doubles never reach the worker. Keep the processed-events check anyway, because the window ends. For sending, Event Grid asks each new subscriber URL to prove it wants the events, and every gift shop's software would have to answer.
  </Tab>
</Tabs>

The queue costs one service and about a day of work, and turns a slow morning into a backlog, not 40 double payments.

## Common pitfalls

- **Doing the work before replying.** The provider's time limit becomes your code's, and a slow day turns into resends. Check, queue, reply; work in a worker.
- **Trusting the queue to remove doubles.** A resent event is a new message. Store the event id, with a unique rule, in the same commit as the work.
- **Checking the signature on a changed body.** Some gateways and frameworks rebuild the body, with different spaces or key order, so the sums never match. Check the raw bytes as they arrived.
- **No alarm on the dead-letter queue.** Parked events are silent, and a payment parked for a week is an order that never ships. Alarm on one message.
- **One slow customer blocks every delivery.** A gift shop that hangs on each request can tie up every worker. Cap open requests per shop and keep time limits short.

## How to say it in an interview

"I treat an incoming webhook as a message to store, not a job to run. A public endpoint checks the signature with a secret from the secret store, queues the event and replies in milliseconds. Providers deliver at least once, so the worker records the event id in the same transaction as the change and skips ids it has seen. Repeated failures go to an alarmed dead-letter queue for replay. To send webhooks, I write an outbox row with the business change. A delivery worker signs each request and retries with backoff, jitter and a per-customer limit. A managed delivery service can replace that worker, but not the outbox."

## Interview questions

<InterviewQuestions>
  <InterviewQuestion question="Should a shop learn about payments through webhooks or by asking the provider?" level="Junior" category="Cloud">
    **Short answer.** Webhooks, so the shop hears about a payment within a second, plus an hourly job that asks the provider for recent events to catch anything missed.

    **Why.** Asking every few seconds about every waiting order costs thousands of requests a day, most answered "not yet". A webhook is one request per event. But the endpoint can be down, and the provider gives up after its retries. The hourly comparison with the orders table catches those. The webhook is fast; the job makes it complete.

    <AnimatedDiagram spec="animated/cloud/webhook-receiver" step={4} path="provider>endpoint>queue>handler" caption="The webhook path: the provider posts, the endpoint queues and replies, the worker processes." />

    **Follow-ups the interviewer may ask.**
    - What does the hourly job do with a payment that has no event?
    - When would polling alone be the better choice?

    **Watch out for.** Calling webhooks reliable on their own. The provider stops retrying at some point.
  </InterviewQuestion>

  <InterviewQuestion question="Your webhook receiver already puts every event on a queue. Why must the worker still be idempotent?" level="Mid" category="Cloud">
    **Short answer.** The provider can send one event twice, and each copy becomes a separate queue message. Only the event id inside shows they are one, so the worker must check it.

    **Why.** A provider resends whenever it misses your success reply, for example when the reply is lost on the network. Brightpost saw 9 doubles in the month after adding its queue. The worker adds the event id to a processed-events table, with a unique rule, in the same commit as marking the order paid. A second copy finds the id and stops.

    <AnimatedDiagram spec="animated/cloud/webhook-receiver" step={5} highlight={["queue", "handler", "seen", "db"]} caption="Two queue messages, one event id: the processed-events table stops the second." />

    **Follow-ups the interviewer may ask.**
    - Why must the id and the order change be in one commit?
    - The queue has its own duplicate check. Why is that not enough?

    **Watch out for.** Using the queue's message id as the key. Two copies of one event get different message ids.
  </InterviewQuestion>

  <InterviewQuestion question="The provider waits 10 seconds for a reply, and your handler takes 14 seconds on busy days. What do you change?" level="Mid" category="Cloud">
    **Short answer.** Split replying from working. The endpoint checks the signature, queues the event and replies in milliseconds. A worker takes as long as it needs.

    **Why.** After 10 seconds the provider assumes failure and resends, which cost Brightpost 40 double payments in one morning. With a queue, the reply takes about 50 milliseconds whatever the database is doing, and a busy morning becomes a backlog. Reply only after the queue accepts the event, so a crash cannot lose it. Keep the event-id check for the resends that still happen.

    <AnimatedDiagram spec="animated/cloud/webhook-receiver" step={2} caption="Before the change: the provider gives up at 10 seconds, resends, and the work runs twice." />

    **Follow-ups the interviewer may ask.**
    - What should the endpoint reply if the queue is unavailable?
    - How do you know the worker is falling behind?

    **Watch out for.** Making the handler faster and stopping there. The next slow day brings the resends back.
  </InterviewQuestion>

  <InterviewQuestion question="How does your endpoint know a webhook really came from the payment provider?" level="Mid" category="Cloud">
    **Short answer.** It checks a signature that the provider computes from a shared secret, the raw body and a timestamp. The endpoint repeats the sum and refuses a mismatch or an old timestamp.

    **Why.** The URL is public, so anyone can post to it. Only the secret's holder can make a matching signature, and the timestamp stops replays of a captured request. The secret sits in the secret store, read by the endpoint's own identity, so no copy lives in code. During a rotation the endpoint accepts the old and the new secret for a day.

    <AnimatedDiagram spec="animated/cloud/webhook-receiver" step={3} highlight={["provider", "endpoint", "secret"]} caption="The endpoint reads the signing secret from the secret store and checks every request before anything else." />

    **Follow-ups the interviewer may ask.**
    - Why must the check use the raw bytes and not the parsed body?
    - Does an IP allow-list replace the signature?

    **Watch out for.** Relying on a hard-to-guess URL. URLs leak through logs and screenshots.
  </InterviewQuestion>

  <InterviewQuestion question="Design webhook delivery for a platform that notifies 10,000 customers, with dead-letter handling." level="Senior" category="Cloud">
    **Short answer.** Write an outbox row in the same transaction as each business change. Delivery workers sign each request with the customer's own secret and retry with backoff, jitter and a per-customer limit. After about a day a delivery is parked, and the customer is told and can replay it.

    **Why.** The outbox means no event is lost between "saved" and "sent". At 10,000 endpoints, some are always down. Backoff keeps a dead endpoint to a few tries an hour, and jitter spreads retries when a shared host comes back. A per-customer limit stops one slow endpoint from holding every worker. Each event carries a stable id, so customers can drop doubles. A managed delivery service can take over retries and dead-lettering.

    <AnimatedDiagram spec="animated/cloud/webhook-retry" step={3} caption="A customer that stays down: each try stops at 5 seconds, and the waits between tries double." />

    **Follow-ups the interviewer may ask.**
    - A customer is down for a week. When do you stop, and what do you keep?
    - Do you promise the order of events, and if not, what do customers do?

    **Watch out for.** Sending from the code that saves the change, with no outbox. A crash between the two loses the event unseen.
  </InterviewQuestion>
</InterviewQuestions>
