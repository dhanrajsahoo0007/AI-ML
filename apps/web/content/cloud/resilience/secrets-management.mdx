## In one sentence

<KeyIdea>
  Keep every password and key a program needs in one locked place that hands each one only to the program allowed to have it, and change them on a schedule so a stolen copy soon stops working.
</KeyIdea>

## The story

Brightpost's customers pay through a payment provider, and the shop proves who it is to that provider with an API key: a long secret string, like a password for programs. Since the storage-key leak, the key lives in a locked store, and each app server reads it once when it starts. On the biggest sale day a calendar reminder says "rotate the payment key". At 10:00 Asha makes a new key, saves it, and restarts the 6 servers on her list so they load it. Then she revokes the old key at once. Autoscaling had started 3 more servers that morning, and they still hold the old key in memory. For 20 minutes the provider refuses every charge those 3 servers send: about 60 checkouts fail before an alert fires.

Every step below makes the next rotation one that nobody notices.

## How it works

Three words first. A <Term id="secret">secret</Term> is a value a program needs that must stay private: a database password, an API key, a signing secret. **Rotation** means replacing a secret with a new value and retiring the old one. A **secret store** is a managed service that keeps secrets encrypted and hands each one only to callers allowed to read it.

### Step 1: A secret store, and who may read it

<AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={1} minWidth={620} caption="Brightpost's setup: the app servers show their attached identity, read the payment key from the store, and charge cards with it." />

The servers hold no secret on disk and none in the code. Each one has a service identity attached, as on the [identity page](/cloud/fundamentals/identity-and-access). When a server asks the store for the payment key, it sends that identity's short-lived token. The store asks two questions. Is the token real? Does a <Term id="policy">policy</Term> let this identity read this one secret?

Only then does the store decrypt the value and send it. The store encrypts every secret with a key from the cloud's <Term id="kms">key management service</Term>, so a copy of its disks reveals nothing. The access rule follows <Term id="least-privilege">least privilege</Term>: the app servers may read the payment key and the database password, and the image-resize worker may read neither. The theory of hashing and encryption lives in [Encryption, hashing and secrets](/system-design/fundamentals/encryption-and-hashing).

### Step 2: Rotated by hand, revoked at once

<AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={2} minWidth={620} caption="The failure: v1 is revoked at once, and the 3 servers that missed the restart have every charge refused." />

Each saved value of a secret is a **version**. The old key is v1 and the new one is v2. Asha did three things in the right order: make v2, store it, restart servers. The mistake was the fourth step. She revoked v1 while some servers still used it, and she trusted a list to know where it was used.

<Callout tone="red" title="What breaks">
  At 10:00 there are 9 servers, not 6. The restarted 6 charge with v2 and work. The other 3 read v1 at start-up and will never read the store again until they restart. The provider refuses v1, so every checkout the load balancer sends to them fails. That is one in three for 20 minutes, about 60 orders.
</Callout>

The store did its job. The outage came from two habits: reading a secret only at start-up, and switching off the old value with no overlap. The next steps remove both.

### Step 3: The secrets that remain

The [identity page](/cloud/fundamentals/identity-and-access) showed the best secret: none at all. A workload inside the cloud uses its attached identity and short-lived tokens, so there is nothing to store. Some secrets cannot go away that easily, because the other side is not your cloud.

[Receiving and sending webhooks](/cloud/networking/webhooks-on-the-cloud) covers the signing secret. This page covers how all four are read and rotated.

### Step 4: When to read: at start-up, on every use, or cached

A program can read a secret at three moments.

1. **At start-up.** One read, then the value sits in memory. A new version reaches the program only on its next restart. Brightpost's 3 servers show the cost.
2. **On every use.** Each checkout reads the store first. A new version takes effect at once. But every charge waits for one more network call, and a store outage stops checkout.
3. **Cached, with a lifetime.** Read once, keep the value for a set time, then read again. The lifetime is a <Term id="ttl">TTL</Term>, short for time to live. Brightpost now uses 1 hour.

A cache of 1 hour means 9 servers make about 216 reads a day, not 4,000. A store outage changes nothing for up to an hour. The price is that a new version can take up to an hour to arrive. Step 5 makes that harmless.

### Step 5: Two valid keys during a rotation

<AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={3} minWidth={620} caption="A rotation job makes v2 and saves it beside v1. The 3 stragglers keep working, because v1 stays valid for a day." />

Most payment providers let an account hold two live API keys at once. That makes a safe rotation possible. A small **rotation job**, a function that runs on a schedule, replaces Asha's hands:

<AnimatedDiagram spec="animated/cloud/secrets-management-1" stepper caption="Make v2, let every server move over on its own, revoke v1 a day later, and let a straggler recover by itself." />

1. Ask the provider for v2. v1 still works.
2. Save v2 in the store as the **current** version. Keep v1 as the **previous** one.
3. Wait one day. Every server re-reads within an hour, so it gets 24 chances to move.
4. Check the store's record: has anyone read v1 in the last few hours? If not, revoke it.

Asha now sets the schedule and nothing else. A rotation happens on a quiet Monday morning, not on the sale day.

### Step 6: Refused? Re-read and retry once

<AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={4} minWidth={620} caption="A server whose key is refused re-reads the store at once and retries the charge with the current version." />

Overlap covers the planned case. An unplanned one remains: the provider revokes a key early, perhaps because it leaked. So the code treats "key refused" as a signal. It throws away its cached copy, reads the store, and retries the same request one time.

With this rule in place on the sale day, each of the 3 servers would have failed one charge, re-read, and recovered within a second. Retry exactly once: a second refusal with a fresh value means a real problem, and it must raise an alert. Make the retried request safe to repeat, so a charge that went through is not taken twice. [Quotas, throttling and retries](/cloud/resilience/quotas-and-retries) covers retries in general.

### Step 7: Versions and rollback

A secret store keeps old versions, and that gives three tools.

1. **Labels.** "Current" and "previous" are pointers to versions. Code asks for "current" and never names a number.
2. **Rollback.** If v2 is bad, perhaps pasted with a missing letter, point "current" back at v1. Servers pick it up within an hour, or at once on a refusal.
3. **Disable before destroy.** A disabled version cannot be read, but it can be switched back on. Brightpost disables an old version first and destroys it 30 days later.

Version history is also a record of change: who wrote each version and when.

### Step 8: Database passwords on a schedule

<AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={5} minWidth={620} caption="The same job changes the orders database password every 30 days and saves each new value in the store." />

Brightpost's database is managed, and here the cloud helps most. The rotation job can change the password inside the database, test that the new one logs in, and only then mark it current. Some managed databases do all of this for you with a built-in setting.

One trap: changing the password of a single database user ends every open connection that used the old one. The fix is two database users with the same rights. Each rotation changes the user that is *not* in use and makes it current. Servers still holding the other user's password keep working until the next rotation. Better still, where the engine supports it, servers sign in with their cloud identity and there is no password at all.

### Step 9: A record of every read

<AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={6} minWidth={620} caption="Every read of the store is written down: which identity, which secret, which version, and when." />

The store can write down every read. Brightpost keeps that record in the audit account with its other logs. It answers three questions. Who still reads v1, so may it be revoked? Did any identity other than the app servers and the rotation job read the payment key? Did the resize worker ever ask for a secret? It should not, so one such read raises an alert.

On some clouds, reads of secret values are recorded only after you switch that on. Check, because a leak with no record of reads is the identity page's weekend again.

### Step 10: Build pipelines and images

A build pipeline, the automated system that tests and deploys the shop, is a workload too. It signs in with federation, as the identity page shows, and stores no cloud key. It needs few secrets of its own, because the app reads its secrets at run time, not at build time.

A **container image** is a frozen copy of the app and everything it needs to run. Never put a secret into one. Every layer of an image is kept, so a key added in one layer and deleted in the next is still inside. Anyone who can pull the image can read it.

## On AWS, Google Cloud and Azure

The idea is the same on all three clouds: one store, read by the workload's own identity, with versions, rotation and a record of reads.

<Tabs title="On each cloud">
  <Tab label="AWS">
    - **Secret store:** AWS Secrets Manager. Parameter Store, part of Systems Manager, also holds encrypted values, but has no built-in rotation; it suits settings and secrets you rotate yourself.
    - **Who may read:** an IAM policy on the workload's role allows reading one named secret. A resource policy on the secret can add a second check, and it is needed for access from another account.
    - **How the app gets it:** an SDK call at run time, with AWS's caching libraries. Container services can also place a secret in an environment variable when a task starts, which is a read at start-up.
    - **Rotation:** a schedule runs a Lambda function in four stages: create, set, test, finish. Amazon RDS can manage the master password in Secrets Manager and rotate it for you.
    - **Versions and audit:** staging labels such as AWSCURRENT and AWSPREVIOUS point at versions; moving AWSCURRENT back is the rollback. CloudTrail records each read of a secret value.

    **The difference that changes a design.** Rotation is built into the store. It runs your function's four stages, and it moves the "current" label only after the test stage passes. A failed test leaves the old value current. For database passwords, the alternating-users strategy rotates two database users in turn, as in Step 8.
  </Tab>
  <Tab label="Google Cloud">
    - **Secret store:** Secret Manager. Each secret holds numbered versions, and each version is enabled, disabled or destroyed.
    - **Who may read:** the Secret Manager Secret Accessor role, granted to the workload's service account on one secret rather than on the whole project.
    - **How the app gets it:** the client library at run time. Cloud Run can also expose a secret as an environment variable, read when an instance starts, or as a mounted file.
    - **Rotation:** a rotation schedule on a secret sends a message to a Pub/Sub topic. Your own code, for example a Cloud Run function, makes the new value. Cloud SQL supports IAM database sign-in, which removes the password.
    - **Versions and audit:** code reads the "latest" alias or a pinned version number. Disabling a version is a fast rollback you can undo. Reads appear in Cloud Audit Logs as Data Access logs, which must be turned on for Secret Manager.

    **The difference that changes a design.** The store reminds you; it does not rotate. The schedule only publishes a message, so the rotation job and its overlap rules are yours to write. Teams that pin version numbers in their deploy config get rollouts and rollbacks that are explicit, reviewed changes.
  </Tab>
  <Tab label="Azure">
    - **Secret store:** Azure Key Vault, which also holds encryption keys and certificates. Soft delete keeps a deleted secret recoverable for a set period, and purge protection stops anyone from erasing it early.
    - **Who may read:** the Key Vault Secrets User role, assigned to the app's managed identity at the vault or on one secret. Older vaults may still use access policies instead of roles.
    - **How the app gets it:** the SDK at run time. App Service and Functions also accept a Key Vault reference in their settings, which the platform resolves and re-reads from time to time.
    - **Rotation:** a secret can carry an expiry date. Key Vault publishes a "near expiry" event through Event Grid, and a function you write rotates the value. Azure SQL and Azure Database for PostgreSQL accept Microsoft Entra sign-in with a managed identity, which removes the password.
    - **Versions and audit:** every update makes a new version with its own id, and a reference without an id gets the newest. Reads are logged once a diagnostic setting sends the vault's logs to Azure Monitor.

    **The difference that changes a design.** One vault holds keys, secrets and certificates, and access and limits apply per vault. So the usual layout is one vault per application and environment. Brightpost would run a shop vault and a test vault, never one shared vault for everything.
  </Tab>
</Tabs>

The cache with a refresh on refusal costs a few lines of code. It is the only option that survives both a store outage and an early revoke.

## Common pitfalls

- **An env file in the repository.** A file of settings committed "only to the private repository" lives in its history forever, even after you delete it. Keep secrets in the store, and scan every commit for key patterns.
- **A secret in a container image.** Every layer is kept, and anyone who can pull the image can read it. Read secrets at run time with the workload's identity.
- **A secret in a log line.** A debug line that prints request headers, or a crash dump of environment variables, copies the key into logs that many people can read. Mask known secret fields before anything is written.
- **Revoking the old value at once.** Something you forgot still uses it, as Brightpost's 3 servers did. Keep two valid values for a day, and revoke only when the record shows no reads of the old one.
- **One secret shared by every workload.** If the shop and the resize worker read the same database password, a break-in at the worker gets everything. Give each workload its own secret, or better, its own identity.

## How to say it in an interview

"First I try to remove the secret: workloads use attached identities, and databases accept identity sign-in where the engine supports it. What remains, such as a payment provider's API key, goes into the cloud's secret store, encrypted, and each workload reads only its own secrets by its identity. The app caches a value for about an hour, and if a key is refused it re-reads the store and retries once. Rotation is a scheduled job: it makes the new value, keeps the old one valid for a day, and revokes it when no one reads it any more. Every read is logged, and nothing secret goes into repositories, images or logs."

## Interview questions

<InterviewQuestions>
  <InterviewQuestion question="Why should an app read its secrets from a secret store instead of an environment file kept in the repository?" level="Junior" category="Cloud">
    **Short answer.** A file in a repository is copied to every laptop, every build and the repository's history, and none of those copies can be revoked or audited. A secret store keeps one encrypted copy, hands it only to identities allowed to read it, and records each read.

    **Why.** At Brightpost, the app servers read the payment key with their attached identity, and the policy names exactly which identities may read which secret. A rotation changes the one stored value, and every server picks it up. With a file, rotation means a commit, a build and a deploy, and the old value is still in the history.

    <AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={1} highlight={["svcid", "server", "store"]} caption="The server proves who it is with its attached identity, and the store hands it only what its policy allows." />

    **Follow-ups the interviewer may ask.**
    - The repository is private. Why is that still not enough?
    - How does the app prove who it is to the store without a password?

    **Watch out for.** Saying "we encrypt the env file". The key to decrypt it then becomes the secret, and it needs a home too.
  </InterviewQuestion>

  <InterviewQuestion question="How do you rotate a third-party API key without breaking anything?" level="Mid" category="Cloud">
    **Short answer.** Keep two valid keys during the change. Make the new key, save it as the current version, let every caller move over within its cache lifetime, and revoke the old key only when nothing reads it any more.

    **Why.** Brightpost revoked its old payment key at once on a sale day. 3 of its 9 servers still held it, and about 60 checkouts failed in 20 minutes. Now a job makes v2 and keeps v1 valid for a day. Servers re-read the store every hour, so each one gets 24 chances to move. Before revoking, the job checks the audit record for recent reads of v1. A refusal also triggers a re-read, so a straggler recovers by itself.

    <AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={3} highlight={["rotator", "store", "provider", "stale"]} caption="The job saves v2 beside v1, so servers with the old copy keep working until they move." />

    **Follow-ups the interviewer may ask.**
    - What if the provider allows only one live key at a time?
    - How do you know when it is safe to revoke the old key?

    **Watch out for.** Restarting "all the servers" from a list. Autoscaling changes the list, which is exactly how Brightpost missed 3.
  </InterviewQuestion>

  <InterviewQuestion question="Should an app fetch a secret at start-up or on every use?" level="Mid" category="Cloud">
    **Short answer.** Neither. Cache the value with a lifetime, about an hour, and re-read at once when the other side refuses it. You get almost no extra reads, no wait per request, and fast recovery from a revoke.

    **Why.** Reading only at start-up is why Brightpost's 3 servers kept a dead key until someone restarted them. Reading on every use adds a network call to each of about 4,000 sale-day checkouts, and a store outage then stops checkout. A 1-hour cache makes about 216 reads a day for 9 servers and rides out a store outage for up to an hour. The refresh on refusal covers the gap the lifetime leaves.

    <AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={4} highlight={["stale", "store", "provider"]} caption="A refused key makes the server re-read the store and retry once." />

    **Follow-ups the interviewer may ask.**
    - What lifetime would you pick, and what does a shorter one cost?
    - Why retry only once?

    **Watch out for.** Retrying in a loop on refusal. A key that is refused twice with a fresh value is a real fault that needs an alert, not more calls.
  </InterviewQuestion>

  <InterviewQuestion question="How do you rotate a managed database's password without an outage?" level="Mid" category="Cloud">
    **Short answer.** Use two database users with the same rights. Each rotation changes the password of the user not in use, tests it, and makes it current, so servers holding the other password keep working. Better, where the engine supports it, sign in with the cloud identity and have no password.

    **Why.** Changing a single user's password ends every connection that used the old one, so all 9 of Brightpost's servers would fail until they re-read the store. With two users, the old password stays valid until the next rotation, 30 days later. The job tests that the new password logs in before marking it current, so a bad value never reaches the servers.

    <AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={5} highlight={["rotator", "db", "store"]} caption="The job changes the password inside the database and saves the new value in the store." />

    **Follow-ups the interviewer may ask.**
    - What happens to connections already open when the password changes?
    - What does identity sign-in to the database cost you?

    **Watch out for.** Rotating the administrator password the app uses. The app should have its own user with only the rights it needs.
  </InterviewQuestion>

  <InterviewQuestion question="A payment API key was printed into application logs six months ago. What do you do today, and what should have made it harmless?" level="Senior" category="Cloud">
    **Short answer.** Treat it as stolen. Rotate the key now with an overlap of minutes, not a day, then search the provider's records for use you did not make. Find and remove the log copies and fix the code that printed the key. Regular rotation would have limited the leak to one rotation period.

    **Why.** A key in logs is readable by everyone with log access, and logs are often copied to other systems. The secret store's record shows who read the key, but not who read the logs, so you check the provider's side for strange charges or refunds. Brightpost rotates the payment key on a schedule, so a six-month-old copy would have been dead for months. Logs mask known secret fields before anything is written.

    <AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={6} highlight={["store", "trail", "rotator"]} caption="Rotation makes an old copy useless; the record of reads shows who held the current one." />

    **Follow-ups the interviewer may ask.**
    - How short can the overlap be when the key is known to be stolen?
    - How would you stop the next key from reaching logs at all?

    **Watch out for.** Deleting the log lines and stopping there. The key has already been copied, so only rotation ends the risk.
  </InterviewQuestion>
