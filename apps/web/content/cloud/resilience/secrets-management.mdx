## In one sentence

<KeyIdea>
  Keep each password and key a program needs in one locked store, hand it only to programs allowed to read it, and change it often.
</KeyIdea>

## The story

Brightpost's customers pay through a payment provider. The shop proves who it is with an API key: a long secret string, like a password for programs. The key lives in a locked store, and each app server reads it once when it starts. On the biggest sale day a calendar reminder says "rotate the payment key". At 10:00 Asha makes a new key, saves it, and restarts the 6 servers on her list so they load it. Then she revokes the old key at once. Autoscaling had started 3 more servers that morning, and they still hold the old key in memory. For 20 minutes the provider refuses every charge those 3 servers send: about 60 checkouts fail before an alert fires.

Every step below makes the next rotation one that nobody notices.

## How it works

Three words first. A <Term id="secret">secret</Term> is a value a program needs that must stay private: a database password, an API key, a signing secret. **Rotation** means replacing a secret with a new value and retiring the old one. A **secret store** is a managed service that keeps secrets encrypted and hands each one only to callers allowed to read it.

### Step 1: A secret store, and who may read it

<AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={1} minWidth={620} caption="Brightpost's setup: the app servers show their attached identity, read the payment key from the store, and charge cards with it." />

The servers hold no secret on disk or in code. Each has a service identity attached, as on the [identity page](/cloud/fundamentals/identity-and-access). To ask for the payment key, a server sends that identity's short-lived token. The store asks two questions. Is the token real? Does a <Term id="policy">policy</Term> let this identity read this one secret?

Only then does it decrypt the value and send it. Every secret is encrypted with a key from the cloud's <Term id="kms">key management service</Term>; [Encryption, hashing and secrets](/system-design/fundamentals/encryption-and-hashing) explains the theory. Access follows <Term id="least-privilege">least privilege</Term>: the app servers may read the payment key and the database password, and the image-resize worker may read neither.

### Step 2: Rotated by hand, revoked at once

<AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={2} minWidth={620} caption="The failure: v1 is revoked at once, and the 3 servers that missed the restart have every charge refused." />

Each saved value of a secret is a **version**: the old key is v1, the new one v2. Asha made v2, stored it and restarted servers, in the right order. Then she revoked v1 while some servers still used it, trusting a list to say where it was used.

<Callout tone="red" title="What breaks">
  At 10:00 there are 9 servers, not 6. The restarted 6 charge with v2 and work. The other 3 read v1 at start-up and will never read the store again until they restart. The provider refuses v1, so every checkout the load balancer sends to them fails. That is one in three for 20 minutes, about 60 orders.
</Callout>

The store did its job. Two habits caused the outage: reading a secret only at start-up, and revoking the old value with no overlap.

### Step 3: The secrets that remain

The identity page showed the best secret: none at all, because a workload inside the cloud uses its attached identity. Some secrets remain, because the other side is not your cloud.

### Step 4: When to read: at start-up, on every use, or cached

A program can read a secret at three moments.

1. **At start-up.** One read; a new version arrives only at the next restart, as Brightpost's 3 servers show.
2. **On every use.** A new version works at once, but each charge waits for one more call, and a store outage stops checkout.
3. **Cached, with a lifetime.** Read, keep the value for a set time, read again. The lifetime is a <Term id="ttl">TTL</Term>, time to live. Brightpost now uses 1 hour.

With a 1-hour cache, 9 servers make about 216 reads a day, and a store outage changes nothing for an hour. The price: a new version takes up to an hour to arrive. Step 5 makes that harmless.

### Step 5: Two valid keys during a rotation

<AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={3} minWidth={620} caption="A rotation job makes v2 and saves it beside v1. The 3 stragglers keep working, because v1 stays valid for a day." />

Many payment providers let an account hold two live API keys at once. A small **rotation job**, a function that runs on a schedule, uses that in place of Asha's hands:

<AnimatedDiagram spec="animated/cloud/secrets-management-1" stepper caption="Make v2, let every server move over on its own, revoke v1 a day later, and let a straggler recover by itself." />

1. Ask the provider for v2. v1 still works.
2. Save v2 in the store as the **current** version. Keep v1 as the **previous** one.
3. Wait one day. Every server re-reads within an hour, so it gets 24 chances to move.
4. Check the store's record: has anyone read v1 in the last few hours? If not, revoke it.

Asha now sets the schedule, and rotations happen on a quiet Monday morning.

### Step 6: Refused? Re-read and retry once

<AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={4} minWidth={620} caption="A server whose key is refused re-reads the store at once and retries the charge with the current version." />

Overlap covers the planned case. In an unplanned one, the provider revokes a key early, perhaps because it leaked. So the code treats "key refused" as a signal: drop the cached copy, read the store, retry the request once.

With this rule on the sale day, each of the 3 servers would have lost one attempt and recovered within a second. A second refusal with a fresh value is a real fault, so it raises an alert. The retried charge must be safe to repeat; [Quotas, throttling and retries](/cloud/resilience/quotas-and-retries) covers that.

### Step 7: Versions and rollback

A secret store keeps old versions, which gives three tools.

1. **Labels.** "Current" and "previous" point at versions. Code asks for "current", never a number.
2. **Rollback.** If v2 is bad, point "current" back at v1. Servers pick it up within an hour, or at once on a refusal.
3. **Disable before destroy.** A disabled version cannot be read but can be switched back on. Brightpost destroys an old version 30 days after disabling it.

### Step 8: Database passwords on a schedule

<AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={5} minWidth={620} caption="The same job changes the orders database password every 30 days and saves each new value in the store." />

Here the cloud helps most. The rotation job changes the password inside the managed database, tests that it logs in, and only then marks it current. Some managed databases do all of this through a built-in setting.

One trap: with a single database user, servers holding the old password fail at their next login. The fix is two users with the same rights. Each rotation changes the user *not* in use and makes it current, so the other password works until the next rotation. Better still, servers sign in with their cloud identity where the engine supports it.

### Step 9: A record of every read

<AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={6} minWidth={620} caption="Every read of the store is written down: which identity, which secret, which version, and when." />

The store can write down every read, and Brightpost keeps that record in the audit account. It answers three questions. Who still reads v1, so may it be revoked? Did anyone besides the app servers and the job read the payment key? Did the resize worker ask for any secret? It never should, so one such read raises an alert.

On some clouds, reads of secret values are recorded only after you switch that on. Check it on day one.

### Step 10: Build pipelines and images

A build pipeline, the system that tests and deploys the shop, is a workload too. It signs in with <Term id="federation">federation</Term> and stores no cloud key. The app reads its own secrets at run time, so nothing secret is baked into the **container image**, the frozen copy of the app that the pipeline builds.

## On AWS, Google Cloud and Azure

The idea is the same on all three clouds: one store, read by the workload's own identity, with versions, rotation and a record of reads.

<Tabs title="On each cloud">
  <Tab label="AWS">
    - **Secret store:** AWS Secrets Manager. Parameter Store, in Systems Manager, also holds encrypted values but has no built-in rotation.
    - **Who may read:** an IAM policy on the workload's role allows reading one named secret. A resource policy on the secret adds a second check, and allows other accounts.
    - **How the app gets it:** an SDK call at run time, with AWS's caching libraries. Container services can also inject it as an environment variable at start-up.
    - **Rotation:** a schedule runs a Lambda function in four stages: create, set, test, finish. Amazon RDS can manage the master password in Secrets Manager and rotate it for you.
    - **Versions and audit:** staging labels such as AWSCURRENT and AWSPREVIOUS point at versions; moving AWSCURRENT back is the rollback. CloudTrail records each read of a secret value.

    **The difference that changes a design.** Rotation is built into the store. It moves the "current" label only after the test stage passes, so a failed test leaves the old value current. For databases, the alternating-users strategy rotates two users in turn, as in Step 8.
  </Tab>
  <Tab label="Google Cloud">
    - **Secret store:** Secret Manager. Each secret holds numbered versions, and each version is enabled, disabled or destroyed.
    - **Who may read:** the Secret Manager Secret Accessor role, granted to the workload's service account on one secret rather than on the whole project.
    - **How the app gets it:** the client library at run time. Cloud Run can also expose a secret as an environment variable, read at start-up, or as a mounted file.
    - **Rotation:** a rotation schedule sends a message to a Pub/Sub topic, and your own code, such as a Cloud Run function, makes the new value. Cloud SQL supports IAM database sign-in, with no password.
    - **Versions and audit:** code reads the "latest" alias or a pinned version number. Disabling a version is a rollback you can undo. Reads appear as Data Access audit logs, which you must turn on.

    **The difference that changes a design.** The store reminds you; it does not rotate. The rotation job and its overlap rules are yours to write. Pinning version numbers in deploy config turns each rollout and rollback into a reviewed change.
  </Tab>
  <Tab label="Azure">
    - **Secret store:** Azure Key Vault, which also holds keys and certificates. Soft delete keeps a deleted secret recoverable for a set period; purge protection stops early erasure.
    - **Who may read:** the Key Vault Secrets User role, assigned to the app's managed identity at the vault or on one secret. Older vaults may still use access policies instead of roles.
    - **How the app gets it:** the SDK at run time. App Service and Functions also accept a Key Vault reference in their settings, which the platform resolves and re-reads periodically.
    - **Rotation:** a secret can carry an expiry date. Key Vault publishes a "near expiry" event through Event Grid, and a function you write rotates the value. Azure SQL and Azure Database for PostgreSQL accept Microsoft Entra sign-in, with no password.
    - **Versions and audit:** every update makes a new version with its own id, and a reference without an id gets the newest. Reads are logged once a diagnostic setting sends the vault's logs to Azure Monitor.

    **The difference that changes a design.** One vault holds keys, secrets and certificates, and access and limits apply per vault. So the usual layout is one vault per application and environment: a shop vault and a test vault, never one shared vault.
  </Tab>
</Tabs>

Only the cache with a refresh on refusal survives both a store outage and an early revoke.

## Common pitfalls

- **An env file in the repository.** A settings file committed "only to the private repository" stays in its history after you delete it. Keep secrets in the store, and scan every commit for keys.
- **A secret in a container image.** Every layer is kept, and anyone who can pull the image can read it. Read secrets at run time with the workload's identity.
- **A secret in a log line.** A debug line that prints request headers, or a crash dump, copies the key into logs many people read. Mask secret fields before anything is written.
- **Revoking the old value at once.** Something you forgot still uses it, as Brightpost's 3 servers did. Keep two valid values for a day, and revoke only when the record shows no reads of the old one.
- **One secret shared by every workload.** If the shop and the resize worker read the same database password, a break-in at the worker gets everything. Give each workload its own secret, or better, its own identity.

## How to say it in an interview

"First I try to remove the secret: workloads use attached identities, and databases use identity sign-in where they can. What remains, such as a payment API key, goes into the secret store, and each workload reads only its own secrets by its identity. The app caches a value for about an hour, and if a key is refused it re-reads the store and retries once. Rotation is a scheduled job: it makes the new value, keeps the old one valid for a day, then revokes it. Every read is logged, and nothing secret goes into repositories, images or logs."

## Interview questions

<InterviewQuestions>
  <InterviewQuestion question="Why should an app read its secrets from a secret store instead of an environment file kept in the repository?" level="Junior" category="Cloud">
    **Short answer.** A file in a repository is copied to every laptop, every build and the repository's history, and none of those copies can be revoked or audited. A secret store keeps one encrypted copy, hands it only to identities allowed to read it, and records each read.

    **Why.** Brightpost's app servers read the payment key with their attached identity, and a policy names which identities may read it. A rotation changes one stored value. With a file, rotation means a commit, a build and a deploy, and the old value stays in the history.

    <AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={1} highlight={["svcid", "server", "store"]} caption="The server proves who it is with its attached identity, and the store hands it only what its policy allows." />

    **Follow-ups the interviewer may ask.**
    - The repository is private. Why is that still not enough?
    - How does the app prove who it is to the store without a password?

    **Watch out for.** Saying "we encrypt the env file". The key to decrypt it then becomes the secret, and it needs a home too.
  </InterviewQuestion>

  <InterviewQuestion question="How do you rotate a third-party API key without breaking anything?" level="Mid" category="Cloud">
    **Short answer.** Keep two valid keys during the change. Save the new key as the current version, let every caller move over within its cache lifetime, then revoke the old key once nothing reads it.

    **Why.** Brightpost once revoked its old payment key at once, and 3 of 9 servers still held it: about 60 checkouts failed in 20 minutes. Now a job keeps v1 valid for a day while servers re-read hourly. It revokes v1 only when the audit record shows no recent reads. A refusal also triggers a re-read.

    <AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={3} highlight={["rotator", "store", "provider", "stale"]} caption="The job saves v2 beside v1, so servers with the old copy keep working until they move." />

    **Follow-ups the interviewer may ask.**
    - What if the provider allows only one live key at a time?
    - How do you know when it is safe to revoke the old key?

    **Watch out for.** Restarting "all the servers" from a list. Autoscaling changes the list, which is exactly how Brightpost missed 3.
  </InterviewQuestion>

  <InterviewQuestion question="Should an app fetch a secret at start-up or on every use?" level="Mid" category="Cloud">
    **Short answer.** Neither. Cache the value with a lifetime, about an hour, and re-read at once when the other side refuses it. You get almost no extra reads, no wait per request, and fast recovery from a revoke.

    **Why.** Reading only at start-up kept a dead key in Brightpost's 3 servers until a restart. Reading on every use adds a call to each of about 4,000 sale-day checkouts, and a store outage stops checkout. A 1-hour cache means about 216 reads a day and rides out an hour-long outage.

    <AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={4} highlight={["stale", "store", "provider"]} caption="A refused key makes the server re-read the store and retry once." />

    **Follow-ups the interviewer may ask.**
    - What lifetime would you pick, and what does a shorter one cost?
    - Why retry only once?

    **Watch out for.** Retrying in a loop on refusal. A key that is refused twice with a fresh value is a real fault that needs an alert, not more calls.
  </InterviewQuestion>

  <InterviewQuestion question="How do you rotate a managed database's password without an outage?" level="Mid" category="Cloud">
    **Short answer.** Use two database users with the same rights. Each rotation changes the password of the user not in use, tests it, and makes it current, so servers holding the other password keep working. Better, where the engine supports it, sign in with the cloud identity and have no password.

    **Why.** With one user, all 9 of Brightpost's servers would fail their next login until they re-read the store. With two, the old password stays valid until the next rotation, 30 days later. The job tests the new password before marking it current, so a bad value never reaches the servers.

    <AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={5} highlight={["rotator", "db", "store"]} caption="The job changes the password inside the database and saves the new value in the store." />

    **Follow-ups the interviewer may ask.**
    - What happens to connections already open when the password changes?
    - What does identity sign-in to the database cost you?

    **Watch out for.** Rotating the administrator password the app uses. The app should have its own user with only the rights it needs.
  </InterviewQuestion>

  <InterviewQuestion question="A payment API key was printed into application logs six months ago. What do you do today, and what should have made it harmless?" level="Senior" category="Cloud">
    **Short answer.** Treat it as stolen. Rotate the key now with an overlap of minutes, not a day, then search the provider's records for use you did not make. Find and remove the log copies and fix the code that printed the key. Regular rotation would have limited the leak to one rotation period.

    **Why.** Everyone with log access could read the key, and logs are often copied elsewhere. The store's record shows who read the key, not who read the logs, so check the provider's side for odd charges or refunds. With scheduled rotation, a six-month-old copy would have been dead for months.

    <AnimatedDiagram spec="animated/cloud/secret-fetch-rotate" step={6} highlight={["store", "trail", "rotator"]} caption="Rotation makes an old copy useless; the record of reads shows who held the current one." />

    **Follow-ups the interviewer may ask.**
    - How short can the overlap be when the key is known to be stolen?
    - How would you stop the next key from reaching logs at all?

    **Watch out for.** Deleting the log lines and stopping there. The key has already been copied, so only rotation ends the risk.
  </InterviewQuestion>
</InterviewQuestions>
