## In one sentence

<KeyIdea>
  Every kind of data needs a home that matches how it is used and what happens if that home disappears.
</KeyIdea>

## The story

In March, Asha adds a "download my data" button to Brightpost's shop. The shop builds a ZIP file of the customer's orders and home address, saves it on the server's own disk, and emails a link that works for 7 days. Tests pass on the one-server test account. In the first week 120 customers ask for a file. The load balancer sends each click to either of 2 servers, so 58 first clicks find no file. On Saturday's sale the fleet grows to 10 servers, and at 11 p.m. the scaling rule removes 8. Their disks go with them, and 38 files nobody had downloaded are gone. By Monday the support agent has 74 emails to answer.

The file lived in the one place on the cloud that is thrown away on purpose. This page maps where each kind of Brightpost's data lives instead, and points to the page that covers each store.

## How it works

Four words first. A **store** is any service that keeps data: a disk, a bucket, a database, a cache. **Durability** is the chance that saved data is still there later; clouds buy it with copies. <Term id="availability">Availability</Term> is whether you can reach the data right now. <Term id="consistency">Consistency</Term> is whether every reader sees the latest write.

So far the orders database has left the server and has a standby, and the photos sit in a bucket.

<AnimatedDiagram spec="animated/cloud/brightpost-grows" step={5} highlight={["db", "standby", "photos"]} minWidth={620} caption="Brightpost so far: a managed database with a standby in a second zone, and a bucket for photos." />

### Step 1: Every kind of data has a home

<AnimatedDiagram spec="animated/cloud/data-map" step={1} minWidth={620} caption="Today: each server has its own disk, orders go to the database, and a nightly export file goes to a bucket." />

Orders live in the managed database, export files and photos in buckets, and each server's operating system and code on its own disk.

The disk and the buckets are two of the three storage shapes. <Term id="block-storage">Block storage</Term> is a disk attached to one server. <Term id="object-storage">Object storage</Term> keeps whole files, called objects, fetched by name over the network. <Term id="file-storage">File storage</Term> is a shared folder that several servers open at once. [Object, Block and File](/cloud/data/storage-types) compares them. To place data, ask what happens to it if its holder disappears.

<PremiumBreak />

### Step 2: A server's disk is scratch space

<AnimatedDiagram spec="animated/cloud/data-map" step={2} minWidth={620} caption="The failure: export files sit on whichever server built them, and removing a server deletes its disk." />

A server's disk keeps copies of every block inside one zone, so a failed drive loses nothing. But other servers cannot read it, and Brightpost's disks are deleted with their server, the usual setting for a boot disk.

<Callout tone="red" title="What breaks">
  Each export file exists on one of 2 servers, so about half the first clicks reach the wrong one: 58 of 120. On Saturday the scaling rule removes 8 of 10 servers, and 38 files go with their disks. Each held a home address, on a disk nobody had listed as holding customer data.
</Callout>

### Step 3: Files go to object storage

<AnimatedDiagram spec="animated/cloud/data-map" step={3} minWidth={620} caption="Export files go to their own bucket, which every server can reach; the disk keeps only what a new server rebuilds." />

Export files now go to an exports bucket that every server reaches, with copies across several zones. A <Term id="lifecycle-rule">lifecycle rule</Term> deletes each file after 7 days, so no address outlives the link. The email link points at the shop, which checks the sign-in and hands out a 15-minute link to the file. [Object Storage](/cloud/data/object-storage) covers classes, versions and signed links.

### Step 4: Copies for speed: a cache and a search index

<AnimatedDiagram spec="animated/cloud/data-map" step={4} minWidth={620} caption="Baskets move to an in-memory cache, and product changes feed a search index." />

Two stores hold copies shaped for speed, and both can be rebuilt. The <Term id="cache">cache</Term> keeps baskets in memory for 7 days and answers in under a millisecond. The search index holds a copy of the 2,000 products, so a search never touches the orders database. [Managed Caches](/cloud/data/managed-caches) covers the cache.

### Step 5: Events, items by key, and folders

<AnimatedDiagram spec="animated/cloud/data-map" step={5} minWidth={620} caption="Click events go to a stream, the printing partner's updates go to a key-value table, and the file share stays empty." />

1. **Click events.** About 25,000 a day. An **event stream** keeps them in order for 7 days, and several readers each read at their own pace. See [Queues, Topics, Streams and Workflows](/cloud/data/streaming-and-messaging-services).
2. **Delivery status.** The printing partner sends three updates per order, about 1,200 a day, always read by order id. A key-value table in a [managed NoSQL](/cloud/data/managed-nosql) service fits.
3. **Folders.** Nothing needs a shared folder yet. A file share is for software that opens files by path; see [File Shares, Hybrid Storage and Moving Bulk Data](/cloud/data/file-hybrid-and-transfer).

### Step 6: A warehouse for questions across years

<AnimatedDiagram spec="animated/cloud/data-map" step={6} minWidth={620} caption="The warehouse takes the click events and a nightly copy of the orders, for questions across two years." />

The finance lead asks which posters sell best each December: millions of rows, few columns. A **data warehouse** keeps each column together, so a question reads only what it needs. It loads the orders and click events every night and is never the source of truth. [Warehouses, Lakes and Query Engines](/cloud/data/warehouses-lakes-and-query-engines) covers the choices.

### Step 7: Backups live somewhere else

<AnimatedDiagram spec="animated/cloud/data-map" step={7} minWidth={620} caption="The 03:00 backup of the orders database is kept in a vault in the audit account." />

The database's standby protects against a failed zone, not a bad delete, which it copies within a second. A backup does. Brightpost's 03:00 backup goes to a locked **backup vault** in the audit account, out of reach of a mistake in the shop account. [Backups, Snapshots, Vaults and Immutability](/cloud/resilience/backups-and-vaults) covers retention and restore tests.

### Step 8: Five questions for every store

1. **How durable is it?** How many copies exist, and what can each survive?
2. **Where do the copies live?** One zone, several zones, another region or another account?
3. **Who can read it?** A copy does not inherit the original's access rules.
4. **How is it backed up?** By a backup, by a rebuild from the source, or not at all?
5. **What does it cost to keep and to move?** Storage bills per gigabyte kept; data leaving the cloud bills per gigabyte sent.

## On AWS, Google Cloud and Azure

Every store on the map has a managed service on all three clouds. What differs is where each one keeps its copies by default.

<Tabs title="On each cloud">
  <Tab label="AWS">
    - **Object:** Amazon S3 buckets.
    - **Block and file:** Amazon EBS for server disks; Amazon EFS and Amazon FSx for shared folders.
    - **Databases:** Amazon RDS and Aurora for relational. Amazon DynamoDB for key-value and documents.
    - **Cache, search and streams:** Amazon ElastiCache, Amazon OpenSearch Service and Amazon Kinesis Data Streams.
    - **Warehouse and backups:** Amazon Redshift; AWS Backup, whose vaults can live in another account.

    **The difference that changes a design.** An EBS volume lives in one zone, while most S3 storage classes keep copies across several zones. So a bucket survives a zone outage and a volume does not. To bring a volume back in another zone, restore it from a snapshot kept at region level.
  </Tab>
  <Tab label="Google Cloud">
    - **Object:** Cloud Storage buckets.
    - **Block and file:** Persistent Disk and Hyperdisk for server disks; Filestore for shared folders.
    - **Databases:** Cloud SQL and AlloyDB for relational. Firestore for documents, and Bigtable for very large tables.
    - **Cache, search and streams:** Memorystore, Vertex AI Search and Pub/Sub.
    - **Warehouse and backups:** BigQuery; the Backup and DR Service, with backup vaults.

    **The difference that changes a design.** Two choices here are about place. A persistent disk can be regional, with a synchronous copy in a second zone, so a disk can survive a zone outage. A bucket's location is a region, a dual-region or a multi-region, fixed when you create it; moving files later means copying them to a new bucket.
  </Tab>
  <Tab label="Azure">
    - **Object:** Azure Blob Storage, inside a storage account.
    - **Block and file:** Azure Managed Disks for server disks; Azure Files for shared folders.
    - **Databases:** Azure SQL Database and Azure Database for PostgreSQL for relational. Azure Cosmos DB for key-value and documents.
    - **Cache, search and streams:** Azure Managed Redis, Azure AI Search and Azure Event Hubs.
    - **Warehouse and backups:** Microsoft Fabric, which includes a warehouse (older setups use Azure Synapse Analytics); Azure Backup, with its own vaults.

    **The difference that changes a design.** Redundancy is a setting of the storage account, and every blob and file share in it follows it. Locally redundant storage keeps its copies in one datacenter; zone-redundant storage spreads them across zones, and geo-redundant storage adds a second region. Files that must survive a zone outage need zone-redundant or wider.
  </Tab>
</Tabs>

The disk wins only on the time to start a read. For a file a customer fetches once, tens of milliseconds cost nothing; losing 38 files cost a week.

## Common pitfalls

- **Files on a server's own disk.** The next scaling event deletes them, and other servers never see them. Use a bucket or a database.
- **Copies nobody listed.** Each copy of customer data is one more place to protect and delete from. List every store that holds it.
- **Backups in the same account as the data.** One mistake or one stolen login can delete both. Keep a locked copy in a separate account.
- **Treating a copy as the source of truth.** A cache, an index and a warehouse trail the real data. Read a price or an order from the source.

## How to say it in an interview

"I place each kind of data by how it is used and what happens if its home disappears. A server's disk is scratch space, because a scaling rule can delete it. Files go to object storage, which every server reaches. Records that change together go to a relational database, the source of truth; caches, indexes and warehouses hold copies. For every store I ask how durable it is, where its copies live, who can read it, how it is backed up, and what it costs."

## Interview questions

<InterviewQuestions>
  <InterviewQuestion question="Which of Brightpost's data belongs in object storage, and why?" level="Junior" category="Cloud">
    **Short answer.** Whole files written once and read by name: product photos, the nightly order exports, customer export files and backups. A bucket keeps them across zones, every server reaches them, and a lifecycle rule deletes them on schedule.

    **Why.** None of these files is edited in place or queried inside. A server disk would tie each file to one server, and a database is not built for large files. Orders stay in the database, because an order and its lines change together.

    <AnimatedDiagram spec="animated/cloud/data-map" step={3} highlight={["app", "buckets", "exports"]} caption="Order files, photos and exports live in buckets that every server reaches." />

    **Follow-ups the interviewer may ask.**
    - How do you let a customer download a file without making the bucket public?
    - Which of these files would you move to a cheaper storage class, and when?

    **Watch out for.** Putting the orders themselves in a bucket "because it is cheap". You lose transactions, and every question becomes a read of whole files.
  </InterviewQuestion>

  <InterviewQuestion question="A cloud disk keeps copies of every block. Why did Brightpost still lose 38 export files?" level="Mid" category="Cloud">
    **Short answer.** Durability says a saved block survives a failed drive, not how long the disk itself lives. Brightpost's disks were deleted with their servers when the scaling rule removed 8 of them.

    **Why.** An autoscaled fleet removes servers on purpose, and a boot disk goes with its server. The disk was also visible to one server only, so 58 of 120 first clicks failed before anything was deleted. The fix is placement: a bucket every server reaches, with a 7-day lifecycle rule.

    <AnimatedDiagram spec="animated/cloud/data-map" step={2} caption="Export files on one server's disk: the wrong server answers, then the disk is deleted with its server." />

    **Follow-ups the interviewer may ask.**
    - What is the difference between durability and availability?
    - When is a server's own disk the right place for data?

    **Watch out for.** Answering "take snapshots of every disk". Snapshots save the files but not the design: the other servers still cannot read them.
  </InterviewQuestion>

  <InterviewQuestion question="Where would you put click events so both the app and the analysts can read them?" level="Mid" category="Cloud">
    **Short answer.** In an event stream. The app writes each event once, and several readers each read at their own pace. One reader loads them into a warehouse every night for the analysts.

    **Why.** About 25,000 events a day in the orders database would load the store checkout depends on. The stream keeps events for 7 days, so a slow reader can catch up; the warehouse keeps them for years. If the load stops for more than 7 days, events are lost.

    <AnimatedDiagram spec="animated/cloud/data-map" step={6} path="app>stream>warehouse" caption="The app writes events once; the warehouse is one of the stream's readers." />

    **Follow-ups the interviewer may ask.**
    - How would you get the events into the warehouse within minutes instead of overnight?
    - What do you watch so a stopped reader is noticed within a day?

    **Watch out for.** Using a queue. A queue hands each message to one reader and then deletes it, so the analysts' reader and the app's reader would steal events from each other.
  </InterviewQuestion>

  <InterviewQuestion question="A customer asks Brightpost to delete their data. How do you make sure every copy goes?" level="Senior" category="Cloud">
    **Short answer.** Keep a list of every store that holds personal data. Delete at the source, then in each copy, and let copies that cannot be edited, such as backups, expire on a known schedule.

    **Why.** On Brightpost's map the address lives in five stores: the orders database, the nightly export files, the exports bucket, the warehouse and the backup vault. The database and the warehouse delete rows. The 730 export files must be rewritten or expire; exports go after 7 days. Backups are rarely edited, so keep a list of deleted customers and apply it after any restore.

    <AnimatedDiagram spec="animated/cloud/data-map" step={7} highlight={["db", "buckets", "exports", "warehouse", "vault"]} caption="Five stores on the map hold a customer's address; each needs its own delete." />

    **Follow-ups the interviewer may ask.**
    - How do you find copies a team added without telling anyone?
    - What retention would you set on backups, and who agrees to it?

    **Watch out for.** Deleting the database row and calling it done. Every copy on the map still holds the address.
  </InterviewQuestion>
</InterviewQuestions>
