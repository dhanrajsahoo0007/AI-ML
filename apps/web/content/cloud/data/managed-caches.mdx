## In one sentence

<KeyIdea>
  A cache keeps answers you will be asked for again in fast memory, and a managed cache is one the cloud runs, copies and repairs for you, while you still decide what goes in it and for how long.
</KeyIdea>

## The story

Brightpost already keeps shoppers' baskets in a cache, since [baskets moved out of the database](/cloud/start-here/databases-per-cloud). Product pages still come from the orders database: one query gathers the price, the stock and the star rating, about 40 ms each. Before the spring sale, Asha caches product pages too. At 8:55 she loads the 40 sale products into the cache, each with a 5-minute expiry. At 9:00 all 40 expire together, just as the sale email lands. In the next 2 seconds, 1,200 requests ask for the hero poster's page. Every one misses the cache, and every one runs the same query. The database's 4 processors hit 100%, and each query now takes over 6 seconds. The app gives up after 3, so no request ever puts the page back. Checkout waits up to 8 seconds. At 9:12 Asha loads the key by hand. About 70 orders were lost in those 12 minutes.

The steps below rebuild Brightpost's cache so that 9:00 cannot happen again, then add what a managed cache gives you on top.

## How it works

Three words first. A <Term id="cache">cache</Term> is a store that keeps copies of data in memory, so a read takes well under a millisecond. A **key** is the name you store a value under, such as `page:hero-poster`. A **hit** means the key was there; a **miss** means it was not, and the app must fetch the data from the real store, here the orders database.

### Step 1: A managed cache, and what the cloud runs for you

<AnimatedDiagram spec="animated/cloud/cache-patterns" step={1} minWidth={620} caption="Before the change: baskets come from the cache, but every product view runs a query on the orders database." />

A managed cache is a cache server that the cloud installs, patches, watches and replaces. You ask for an amount of memory, an engine and a number of copies. You get back one address that your app connects to. The service keeps a copy in a second zone, swaps out a broken machine, and takes backups if you ask.

What stays yours: which data goes in, under which key, for how long, and what happens when it is missing. In the picture, baskets already come from the cache. Product pages do not, so every one of Brightpost's product views costs the database a 40 ms query. The theory of caching, from strategies to invalidation, lives in [Caching](/system-design/patterns/caching). This page is about running one on a cloud.

### Step 2: Cache-aside, with a TTL on every key

<AnimatedDiagram spec="animated/cloud/cache-patterns" step={2} minWidth={620} caption="Cache-aside: the app reads the key first and reaches the database only on a miss, then stores the answer for 5 minutes." />

Most apps on a managed cache use **cache-aside**: the app, not the cache, does the work.

1. Read the key from the cache. On a hit, return it.
2. On a miss, run the query on the database.
3. Store the answer in the cache with a <Term id="ttl">TTL</Term>, a time to live, then return it.

The TTL is the longest a copy can be out of date. Brightpost picks 5 minutes for product pages, so a new price shows within 5 minutes. When staff change a price, the admin tool also deletes that key, so the next read fetches the new one. The cache never talks to the database itself. If the cache is down, the app can still read the database, only slower.

Every key gets a TTL. A key without one stays until memory runs out, and nobody remembers why it is there.

### Step 3: The key expires, and everyone misses at once

<AnimatedDiagram spec="animated/cloud/cache-patterns" step={3} minWidth={620} caption="The failure: the hero poster's key expires at 9:00, 1,200 requests miss together and all of them query the database." />

Cache-aside has a weak moment: the second after a popular key expires. Every request that arrives before someone refills it is a miss. If each miss runs the query, a **cache stampede** follows: many requests rebuild the same value at the same time.

<Callout tone="red" title="What breaks">
  At 9:00:00 the hero poster's key expires. In 2 seconds, 1,200 requests miss and send 1,200 copies of the same 40 ms query. On 4 processors that is 12 seconds of work arriving at once, and checkout waits behind it. Each query now takes over 6 seconds, but the app gives up after 3, so none of them refills the key. Shoppers press refresh, which adds more misses.
</Callout>

Two choices made it worse. All 40 keys were loaded at 8:55 with the same TTL, so they expired in the same second. And the app had no rule for "someone else is already rebuilding this".

### Step 4: One rebuild per key, refreshed before it expires

<AnimatedDiagram spec="animated/cloud/cache-patterns" step={4} minWidth={620} caption="One request takes the rebuild lock and runs the query; the others get the old copy, and the key is refreshed before it expires." />

Brightpost adds three guards, each one small.

- **Request coalescing.** Many requests for one missing key are merged into one rebuild. Brightpost does it with a **lock**: a short-lived key that only one request can create. The winner runs the query; the others wait 50 ms and read the cache again.
- **Early refresh.** The app stores the build time inside the value. When less than 30 seconds of the 5 minutes remain, the next reader takes the lock and rebuilds in the background. Everyone else still gets the current copy, so a busy key never misses at all.
- **Jittered TTLs.** Each key's TTL is 5 minutes plus or minus a random 30 seconds. Keys loaded together now expire over a minute, not in one second.

```python
page = cache.get(key)
if page and page.age < 270:            # more than 30 s left: serve it
    return page
if cache.set("lock:" + key, me, nx=True, ex=5):   # only one caller wins
    page = build_from_database()
    cache.set(key, page, ex=300 + random.randint(-30, 30))
    cache.delete("lock:" + key)
    return page
return page or wait_and_read_again()   # someone else is rebuilding
```

The lock expires after 5 seconds by itself, so a crashed rebuild cannot block the key forever. At 9:00 next time, 1,200 requests cause 1 query.

### Step 5: Pick the engine: Redis, Valkey or Memcached

The **engine** is the cache software the service runs. Managed caches offer three.

Valkey started in 2024 as an open-source copy of Redis, after Redis changed its licence. The two accept the same commands, so the same client code works with both. Memcached is simpler and spreads work over many cores. It fits a pure cache of strings that the app can rebuild in seconds. It does not fit anything you want back after a node dies, such as baskets.

### Step 6: Memory, eviction and sizing

<CacheSim policy="lru" capacity={4} sequence="H A H B H C D H E A H B" title="Which key leaves when memory is full?" />

A cache node has a fixed amount of memory. When it is full and a new key arrives, the **eviction policy** decides what happens. In the widget, H is the hero poster: it is read so often that least-recently-used eviction never drops it.

- **Least recently used** drops the key read longest ago. Least frequently used drops the one read least often.
- **Only keys with a TTL** limits eviction to keys that would expire anyway.
- **No eviction** refuses new writes with an error. That suits a store you cannot lose data from, never a cache.

Brightpost's data is small: 2,000 product pages of about 30 KB is 60 MB. Up to 40,000 baskets of 5 KB, each kept 7 days, is 200 MB. Its node has 1 GB, so it runs at about 30%. Keep used memory under about 75%. Copying to a replica, taking a snapshot and fragmented memory all need room. Services keep some memory back for this, and the amount differs. If evictions appear on a node holding baskets, the node is too small, whatever the policy.

### Step 7: A replica in a second zone, and automatic failover

<AnimatedDiagram spec="animated/cloud/cache-patterns" step={5} minWidth={620} caption="The primary copies every write to a replica in zone B, which takes over if zone A fails." />

The cache keeps a copy in a second zone, as on the databases page. That copy is a <Term id="read-replica">replica</Term>: the primary sends it every write a moment after it happens. This <Term id="replication">replication</Term> is asynchronous, so the replica can trail by a few milliseconds.

If the primary or its <Term id="availability-zone">zone</Term> fails, the service promotes the replica. This is <Term id="failover">failover</Term>. The cache's address stays the same and now points at the new primary. In Brightpost's drill, the app saw about 30 seconds of errors. Detection and promotion took part of it. The rest came from app servers holding broken connections, and from client timeouts set too long. A client with a 1-second timeout and quick retries brings it down to a few seconds.

Writes from the last moment before the failure can be lost. For a cache that is fine: a missing key is a miss.

### Step 8: Cluster mode, shards and the hot key

<AnimatedDiagram spec="animated/cloud/cache-patterns" step={6} minWidth={620} caption="Cluster mode hands part of the key slots to new shards, so memory and writes spread over more nodes." />

One node has a ceiling: its memory, and the work its main thread can do. **Cluster mode** splits the keys over several <Term id="sharding">shards</Term>. Each shard is a primary with its own replicas. In Redis and Valkey, every key is hashed into one of 16,384 **slots**, and each shard owns a range of slots. The client asks which shard owns which slot and sends each command straight there. To grow, the service moves slots to a new shard while the cache keeps serving.

Two rules come with it. Commands that touch several keys work only when the keys share a slot, so related keys need a common part in braces, such as `{basket:42}:items`. And sharding spreads keys, not load on one key. The hero poster's key lives in one slot on one shard, however many shards there are. That is a <Term id="hot-key">hot key</Term>. At Brightpost's 600 reads a second, one node does not notice. A shop 100 times bigger would: read that key from replicas, or keep a 2-second copy inside each app server. Brightpost's 260 MB fits one node, so it runs without cluster mode for now.

### Step 9: Persistence, durable stores and serverless caches

A cache that restarts empty is **cold**: every read misses until it fills, which is a stampede waiting to happen. Some engines can avoid that.

- **No persistence.** The node keeps data only in memory. A restart starts cold. Fine for pages you can rebuild.
- **Snapshots.** The node writes all its data to disk every so often. A restart reloads the last snapshot, so it starts warm but misses the writes since then.
- **An append-only log.** Every write is also added to a log on disk. Less is lost, and each write costs a little more.
- **A durable in-memory database.** Some clouds sell a separate service with the same commands. It writes every change to a log in several zones before it answers. It can be the source of truth, at a higher price per write.

The rule from the databases page holds: a basket may live in the cache, an order never does.

A **serverless cache** asks for no node size or shard count. You pay for the data stored and the requests made, and it grows with the load. It fits spiky or unknown traffic. It takes away some settings, and at a steady high load, nodes you size yourself usually cost less. Not every cloud offers one; the tabs below say which do.

## On AWS, Google Cloud and Azure

The idea is the same on all three clouds: an engine in memory, a replica in another zone with automatic failover, shards when one node is not enough, and TTLs and eviction that you choose.

<Tabs title="On each cloud">
  <Tab label="AWS">
    - **Engines:** Amazon ElastiCache runs Valkey, Redis OSS or Memcached.
    - **High availability:** replicas in other zones with automatic failover. The endpoint name stays the same and moves to the new primary.
    - **Scaling out:** cluster mode for Valkey and Redis OSS spreads slots over shards and reshards online. Memcached grows by adding nodes.
    - **Persistence:** snapshots, called backups, for Valkey and Redis OSS. Memcached keeps nothing.
    - **Serverless or durable option:** ElastiCache Serverless picks nodes and shards for you. Amazon MemoryDB is the durable in-memory database.

    **The difference that changes a design.** AWS splits the cache from the durable store. ElastiCache is a cache: plan for losing recent writes. When Redis-style data must survive any failure, the design moves to MemoryDB, which commits each write to a log across zones. Snapshots on ElastiCache do not make it a database.
  </Tab>
  <Tab label="Google Cloud">
    - **Engines:** Memorystore runs Valkey, Redis (single instance or Cluster) or Memcached. Valkey is the default for new caches.
    - **High availability:** replicas in other zones with automatic failover.
    - **Scaling out:** Valkey and Redis Cluster spread slots over shards and change the shard count online. A single Redis instance grows only in size.
    - **Persistence:** an option on Valkey and Redis: snapshots, or on some an append-only log.
    - **Serverless or durable option:** no separate durable product and no serverless tier. You choose the node type and the shard count.

    **The difference that changes a design.** One product covers caching and persistence. Durability is a setting on the same cache, not a move to another service. The cache is reached over a private connection into your network, so the network plan comes before the cache.
  </Tab>
  <Tab label="Azure">
    - **Engines:** Azure Managed Redis. The older Azure Cache for Redis is being retired. There is no managed Memcached.
    - **High availability:** a replica of each shard with automatic failover, spread across zones where the region has them.
    - **Scaling out:** clustered from the start. A clustering policy decides whether clients see every shard or one endpoint.
    - **Persistence:** optional: snapshots or a log of writes.
    - **Serverless or durable option:** no serverless tier. You choose a tier and a memory size, and the service sets the shards.

    **The difference that changes a design.** You size a whole cache, not nodes and shards. The clustering policy then decides the client: a cluster-aware client for the policy that shows every shard, any client for the single endpoint. Pick the policy before writing client code, because changing it later means a new cache.
  </Tab>
</Tabs>

## Common pitfalls

- **The same TTL on keys loaded together.** They all expire in the same second, as at 9:00. Add random jitter to every TTL.
- **No rule for a missing popular key.** Every miss runs the query, and the database takes the stampede. Use a rebuild lock and refresh hot keys before they expire.
- **The cache as the only copy.** A failover or a restart can lose the last writes. Write anything that matters to the database first.
- **No eviction, no headroom.** A full cache with no eviction refuses writes, and one at 95% evicts during a snapshot. Keep memory under 75% and alarm on evictions.
- **Long client timeouts.** During a failover the app waits on dead connections. Set timeouts of about a second, retry with a short pause, and run a failover drill every quarter.

## How to say it in an interview

"I use a managed cache so the cloud handles patching, replicas and failover, and I own the keys, the TTLs and the miss path. The default is cache-aside: read the cache, query the database on a miss, store the answer with a TTL. Every TTL gets random jitter, and hot keys get a rebuild lock and an early refresh, so one expiry cannot turn into a stampede. I pick Valkey or Redis when I need data structures or a replica in another zone, and Memcached only for a pure cache. I keep memory under about 75%, run a replica in a second zone, and add shards only when one node runs out. I alarm on hit rate, evictions, memory and the main thread, and nothing that must survive lives only in the cache."

Memcached's many-core speed matters only above a load a small shop never reaches.
